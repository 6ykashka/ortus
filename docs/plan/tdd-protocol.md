# Протокол TDD для модулей Ортус

Этот документ обязателен для каждого агента, который реализует рабочий поток (WS) из `docs/plan/ws/`. Он описывает, как именно «сначала тест, потом код» применяется на каждом слое, какие тесты пишутся до реализации, и что считается красным, зелёным и рефакторингом.

## 1. Цикл

Один цикл = одна проверяемая единица поведения (правило домена, обработчик API, компонент, экран).

1. **Red.** Написать тест, который формулирует требование словами источника (`docs/plan/analysis/*.md`, `design/docs/**`). Запустить, убедиться, что он падает по ожидаемой причине (не из-за опечатки или отсутствующего импорта). Зафиксировать коммитом `test(<scope>): …`.
2. **Green.** Написать минимальный код, который делает тест зелёным. Не добавлять поведение, которого нет в тесте. Коммит `feat(<scope>): …` или `fix(<scope>): …`.
3. **Refactor.** Убрать дублирование, привести к стилю скилов (`golang-code-style`, `golang-naming`, `vercel-react-best-practices`), прогнать линтеры. Тесты остаются зелёными. Коммит `refactor(<scope>): …`.
4. Повторить для следующей единицы. Один коммит не должен смешивать red и green разных единиц.

Запрещено: писать реализацию до теста; «подгонять» тест под случайно получившееся поведение; помечать тесты `skip` без ссылки на открытый вопрос в `docs/plan/decisions.md`.

## 2. Порядок написания тестов внутри WS

Для каждого WS тесты пишутся сверху вниз по пирамиде из `design/docs/15-quality-security.md`, но **первым всегда пишется e2e-скелет страницы** в состоянии `test.fixme`, чтобы критерий приёмки был зафиксирован до любой реализации:

| Шаг | Слой | Инструмент | Что фиксируется |
|---|---|---|---|
| 1 | E2E-скелет | Playwright, `frontend/apps/web/e2e/<page>.spec.ts` | Чек-лист приёмки из `docs/plan/analysis/*.md` → один `test()` на пункт, все в `test.fixme()` |
| 2 | Домен | Vitest (`packages/domain`), `go test` (`backend/internal/...`) | Правила: `compat`, `legs`, `inspMissing`, `odoError`, `validateExpense`, `bookingConflicts`, `TASK_FLOW`, `permit()`, `scopeQuery()` — на примерах из `07-domain-and-adapter.md` |
| 3 | Контракт | `oapi-codegen` strict server + Spectral; Vitest на `openapi-fetch` клиенте с MSW | Каждая операция OpenAPI, которую трогает WS: тело запроса, коды ответов, `Problem.code` |
| 4 | Интеграция | testcontainers-go (PostgreSQL 17, MinIO) | Репозитории, транзакции, ограничения, outbox |
| 5 | Изоляция и конкурентность | Go-тесты на фикстурах `backend/test/isolation`, `backend/test/concurrency` | Чужой тенант/фирма → 404, функция driver → нет начислений, 100 параллельных броней → 1×201 + 99×409 |
| 6 | Компоненты | Vitest + Testing Library + axe (`packages/ui`) | Состояния, клавиатура, aria, контраст |
| 7 | Экран | Vitest + Testing Library + MSW (`apps/web/src/routes/**`) | Состояния экрана: обычное, пусто, загрузка, ошибка, нет права, конфликт, офлайн, только чтение |
| 8 | E2E | Playwright, снятие `fixme` по одному | Пункты чек-листа приёмки проходят на телефоне 390 и десктопе 1440 |
| 9 | Визуальная сверка | Playwright `toHaveScreenshot` против локального эталона | См. `docs/plan/verification-protocol.md` §3 |

Шаги 2–7 выполняются по циклу Red → Green → Refactor; шаг 8 закрывает каждый `fixme` отдельным циклом.

## 3. Соглашения по тестам

### Go

- Файлы `*_test.go` рядом с кодом; табличные тесты с полем `name`; `t.Parallel()` там, где нет общего состояния.
- Доменные ошибки сравниваются через `errors.Is`; HTTP-ошибки — по `Problem.code` из `design/docs/12-errors-and-events.md`.
- Интеграционные тесты под build tag `integration`, изоляция и конкурентность — тег `isolation`, `concurrency`; они блокируют merge (CI).
- Фикстуры изоляции — единый сид из `design/docs/15-quality-security.md` «Фикстуры изоляции» (тенант A «Холдинг», тенант B «Чужой клиент», менеджеры Москва-1/2, водители, пользователь с двумя ролями).
- Правила скилов `golang-testing`, `golang-error-handling`, `golang-context` обязательны; расхождения с ними фиксируются в PR.

### TypeScript

- Vitest, `describe` по единице поведения, имена тестов — на русском, формулировка из источника: `it('пробег при сдаче не меньше пробега при выезде', …)`.
- Компоненты тестируются через Testing Library по ролям и подписям, не по классам. Каждый компонент имеет axe-тест.
- Сетевые вызовы мокаются MSW по OpenAPI; хендлеры генерируются из примеров контракта (`frontend/apps/web/mocks`). Прямой мок `fetch` запрещён.
- Экраны тестируются через роутер в памяти с `QueryClient` без retry.

### Playwright (E2E)

- Один spec на страницу: `e2e/<page-key>.spec.ts` (ключ из инвентаря экранов: `home`, `modules`, `users`, `review`, `driver-today`, …).
- Селекторы: `getByRole`, `getByLabel`, `getByText` с дословными подписями из прототипа. `data-testid` — только когда у элемента нет доступного имени; это сигнал проверить a11y.
- Проекты: `mobile-390` (Pixel-подобный, 390×844, touch), `tablet-768`, `desktop-1440`. Каждый пункт чек-листа гоняется минимум на `mobile-390` и `desktop-1440`.
- Данные: приложение в режиме e2e запускается против mock-адаптера (демо-сид прототипа) — те же идентификаторы (`Р-208`, `m-kotova`, `t-alta`, `t-lotos`), что и в `design/ortus/mock-data.js`. Для backend-e2e (фаза 2) — против стенда compose с сидом `make seed`.
- Запрещены `waitForTimeout` и условные ожидания; используются авто-ожидания и `expect.poll`.

## 4. Definition of Done единицы

- Все тесты шагов 2–8 зелёные локально и в CI; визуальная сверка в допуске.
- Линтеры: `golangci-lint`, `eslint`, `prettier`, `spectral` — без ошибок.
- Покрытие домена ≥ 90 % строк (`packages/domain`, `backend/internal/platform/authz`, `backend/internal/modules/*/service*`), остальное — без порога, но каждый `Problem.code` покрыт хотя бы одним тестом.
- Чек-лист приёмки страницы (из `analysis`) полностью снят с `fixme`; если пункт не может быть закрыт — он остаётся `fixme` с ссылкой на вопрос в `decisions.md`, и это явно указано в отчёте агента.

## 5. Как агент отчитывается

В конце WS агент возвращает отчёт по шаблону `docs/plan/orchestration.md` §5: список тестов (red → green), что осталось `fixme`, вывод прогонов (`npm run test`, `go test ./...`, `npm run e2e`), ссылки на коммиты. Отчёт без вывода прогонов не принимается интегратором.
