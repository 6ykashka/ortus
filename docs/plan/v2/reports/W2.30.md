Строки изоляции. Объекты создаются сменами через API:

- принятая смена с начислением 4 500 ₽: машина, потреблённая бронь, осмотры, подтверждённый расход, начисление;
- сданная смена с расходом на проверке;
- бронь в hold с осмотром выезда;
- осмотр с блокирующим дефектом на проверке.

Места строк:

- чужая фирма `a.manager-msk2`;
- наблюдатель другой фирмы `ab.member`;
- другой водитель `a.driver-msk1`;
- водитель с начислениями через группу `a.driver-earnings`;
- `b.owner` по пути тенанта A;
- `b.owner` по своему пути с id из A;
- фирма-тёзка `b.manager-msk1` по своему пути.

Операции: 16 чтений и списков, 12 команд (`releaseReservation`, `reserveVehicle`, `startTrip`, `submitInspection`, `assignTripVehicle`, `decideInspectionDefect`, `createTripExpense`, `finishTripRoute`, `returnTrip`, `reviewTripExpense`, `reviewTrip`, `setTripEarnings`). Команды идут с настоящим If-Match.

Что проверяет каждая строка:

1. Ответ совпадает с ответом на тот же запрос, где id объектов заменены несуществующими (`type`, `title`, `status`, `code`, `detail`).
2. Статус соответствует модели шлюза по каталогу фикстур:
   - нет членства — 404;
   - начисления у функции «Водитель» — 403 `function_blocked`;
   - действия нет ни в одном гранте вида области, который допускает x-scope, — 403 `forbidden_action`;
   - иначе 404, а у списка — 200.
3. id объектов нет ни в теле, ни в заголовках, у списков — ни на одной странице.

После всех строк ETag объектов не изменились. Затем законный актор выполняет каждую команду — это контроль, что строка попала в живой объект. Водитель смены видит свой рейс, карточку и списки без единого поля начисления, а начисления, в том числе свои, получает как 403 `function_blocked`.

### Открытые вопросы возврата 1

- **Q-W2.30-4 (изоляция, владельцы W2.02 и W2.04).** Водитель с ролью «Водитель» на подразделении (временное назначение, группа «Водители Север» стенда) читает брони, осмотры (выезда и сдачи) и дефекты **другого** водителя этого подразделения: `getReservation`, `getInspection`, `getInspectionDefect` отвечают 200, а `listReservations` и `listInspections` отдают объекты другого водителя. Причина: `reservations.go:66`, `inspections/read.go:19` и `inspections/defects.go:22` фильтруют по `v.unit_id` без ограничения функции «Водитель». `driverOnly` (рейсы видит только их водитель) есть в `trips`, `review`, `expenses`, `finance`. Рейсы, расходы и начисления того же водителя закрыты, а брони, осмотры и дефекты — нет. Это расходится с AUTH-05 («водитель видит свои брони/рейсы/осмотры») и с AC-06 («временный водитель видит только согласованный рейс»). **По умолчанию:** считаю это дефектом, строки остаются red с `t.Skip`. Исправление: `driverOnly` в чтениях `reservations` и `inspections` (свой рейс, своя бронь, свой осмотр). Если продукт решит иначе (водитель на подразделении видит все брони и осмотры машин), строки надо перевести в ожидание 200 через `override`.
- **Q-W2.30-5 (изоляция, владелец W2.04).** `submitInspection` водителя на бронь другого водителя видимой машины отвечает 403 `forbidden_action` «Осмотр отправляет водитель рейса.», а на несуществующую бронь — 404. Ответ раскрывает, что чужая бронь существует (AC-01). **По умолчанию:** дефект. Для водителя-не-владельца рейса на подразделении ответ должен быть 404, как в `trips.authorize` (`own && !same → 404`).
- **Q-W2.30-6 (minor, владелец W2.02).** В `listVehicles` водителя у машины, которую держит рейс другого водителя, есть `heldByTripId` — id рейса, который `getTrip` этому водителю не отдаёт. **По умолчанию:** дефект малой тяжести. Для `driverOnly` убрать `heldByTripId` чужого рейса или заменить его на признак «занята».
