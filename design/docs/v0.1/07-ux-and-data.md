# UX, формы и единое представление данных — версия 0.1

Исследование источников: 30.09.2026. Сводная редакция: 01.10.2026. Документ задаёт требования к проектируемому интерфейсу, формам, рабочим местам и данным; не описывает проверенную реализацию. Сравнение Google Forms и Яндекс Форм находится в обзоре продуктов. Здесь изложены решения для нашей CRM.

## 1. Общий принцип

Одно адаптивное приложение предоставляет рабочие места по обязанностям. Общие формы и таблицы используют те же области и ограничения, что исходные модули. Активная профессиональная функция `driver` блокирует чтение начислений через любую роль, группу, отчёт и экран, включая собственные начисления. Квалификация водителя без действующего профессионального назначения не равна функции `driver`.

## 2. Минимальный контракт модуля «Формы и отчёты»

### Сущности и состояния

1. **Форма** — постоянный объект с именем, областью, владельцем, черновиком и опубликованными версиями.
2. **Версия формы** — неизменяемая схема. Вопросы и варианты имеют стабильные ID. Смена подписи не меняет ID; смена смысла или несовместимого типа создаёт новое поле. Старые ответы остаются связаны со своей версией.
3. **Публикация** — конкретная версия, аудитория, сроки, правила отправки. Адрес может оставаться общим, но начатая сессия фиксирует версию. Закрытая публикация не принимает новые ответы даже из старой открытой вкладки.
4. **Ответ** — исходная ревизия, область работы, автор/внешний участник, время события, время приёма сервером и ссылки на вложения. Исправление создаёт новую ревизию; тихо переписывать исходный ответ нельзя.
5. **Задание на заполнение** — кто, по какому объекту, за какой период и к какому сроку должен ответить. Требуется для регулярной отчётности, но не для открытого опроса.
6. **Сводка** — конфигурация показателей и фильтров; не отдельная вручную редактируемая копия ответов.

Редактор: «Черновик → Проверка → Опубликовано → Приём остановлен → Архив». Публикация изменений создаёт следующую версию. Новый обязательный вопрос нельзя требовать от завершённого ответа прошлой версии. Открытые сессии либо завершаются по старой версии в ограниченный срок, либо предлагают обновление с сохранением совместимых полей; политика задана явно.

Ответ: «Черновик → На проверке → Принят», с веткой «На исправлении → Отправлен повторно» и завершением «Отклонён». Если проверка не нужна, отправленный ответ сразу учтён. Для показателей выбирается одна ревизия: обычно последняя принятая. Отклонённые/тестовые записи исключены по умолчанию.

### Конструктор и повторяемые строки

На широком экране: каталог полей слева, форма в центре, свойства выбранного поля справа. На телефоне — последовательный экран с отдельной панелью свойств. Обязательные поля сначала: название, тип, варианты, обязательность, пояснение. «Условия», «Проверки» и «Показатели» раскрываются по запросу.

P0: текст, число, деньги с валютой, один/несколько вариантов, да/нет, дата/время, оценка, фото/файл, ссылка на объект CRM; разделы и многостраничность; ограниченные условия равенства, набора, диапазона, заполненности. Ссылки условий только назад по форме, без циклов. Условная видимость не является разграничением доступа.

Повторяемая группа имеет ID группы, ID экземпляра и ID каждого поля. Ограничиваются число строк и общий объём. В полном универсальном редакторе это раннее расширение; в первом логистическом и строительном пилоте повторяемые расходы/дефекты/материалы нужны сразу как заранее подготовленные блоки. Не требуется выпустить все возможности универсального редактора, чтобы обеспечить эти сценарии.

После изменения раннего ответа сервер заново вычисляет применимость полей. Значения скрытой ветки исключаются из отправляемого результата; обязательность действует только для применимых вопросов. В аналитике различаются «не показывался», «не ответил», «не собирался в этой версии» и ноль.

Предзаполнение служебного контекста приходит от сервера: сотрудник, смена, автомобиль, визит, проект и область. Подмена скрытого поля или параметра URL не меняет принадлежность записи. Публичной форме не выдаётся произвольный поиск по сотрудникам, клиентам или автомобилям бизнеса.

### Публичный вход и вложения

Открытая ссылка даёт право заполнить конкретную опубликованную форму; персональная ссылка остаётся предъявительским разрешением и сама по себе не доказывает личность человека. Для строгой идентификации нужен вход либо отдельная проверка личности по выбранному каналу.

Сервер выдаёт сессии заполнения ограниченные полномочия: прочитать разрешённую схему, загрузить файл только в эту сессию/ответ, отправить ответ. Нет полномочий владельца бизнеса, чтения ответов других людей, внутренних заметок и сводных результатов. Публичный маршрут не является обычным маршрутом CRM с выключенной авторизацией.

Токены криптографически случайны, имеют срок и отзыв; в журналах и аналитике не сохраняются в открытом виде. Хранится проверяемое защищённое представление. Публикация определяет бизнес на сервере; переданный клиентом tenant ID не считается доверенным.

Гостевая загрузка: заранее резервируется квота бизнеса; допустимы только установленные типы/размеры/число файлов; выдаётся краткосрочное разрешение на конкретный объект. После загрузки — проверка фактического размера/типа, карантин и проверка содержимого, привязка к ответу. Временные файлы незавершённых сессий удаляются по сроку. Уровень защиты от злоупотреблений усиливается при превышении порогов; бесконечное бесплатное публичное хранилище не создаётся.

При отправке обязательное фото должно быть надёжно загружено и проверено. «Фото выбрано» не означает «фото сохранено». Мобильная форма показывает прогресс каждого файла и конкретную причину отказа. Открытие файла — проверка доступа к родительскому ответу, затем короткоживущая ссылка; права публичного заполнения не дают общего права скачивания.

### Связь с операциями бизнеса

Ответ формы — заявление человека. Он не является автоматически складским движением, начислением или кассовой операцией. Осмотр прикрепляется к передаче автомобиля; менеджер принимает его и разрешённая команда модуля завершает передачу. Услуга мастера вызывает расход по утверждённой технологической карте; произвольное число в анкете не переписывает остаток склада.

Автоматизация хранит версию правила и выполняется с отдельными ограниченными полномочиями в выбранной области. Доставка событий повторяема, обработчики идемпотентны. В журнале видно «ответ принят → задача создана» либо «нужно исправить настройку». Повторная обработка не создаёт вторую задачу, расход или начисление. Произвольные SQL и исполняемый код бизнесу не выдаются.

### Права и приёмка

Раздельные действия: читать форму; создавать/изменять черновик; публиковать; управлять внешними ссылками; заполнять; читать свои ответы; читать ответы области; проверять; исправлять с историей; строить сводки; выгружать; управлять заданиями на заполнение. Конструктор формы не обязательно читает чувствительные ответы.

Минимальные критерии: новая версия не меняет исторические значения; отозванная ссылка не принимает отправку; второй повтор одного запроса не создаёт дубль; менеджер чужой фирмы не видит её строки/фото/счётчики; скрытая ветка не попадает в статистику; файл нельзя прикрепить к чужому ответу; опубликованный ответ создаёт максимум одну доменную операцию; UI сообщает об отсутствии связи без ложного статуса «Отправлено».

## 3. «Данные» и «Файлы» — две понятные области

**«Данные»** — единый каталог таблиц и показателей, которые предоставляют модули. **«Файлы»** — фотографии, вложения и документы с папками/привязками, квотами и сроками хранения. Не следует называть оба понятия «Хранилище данных» в пользовательском меню: это создаёт путаницу между отчётами, файлами и технической БД.

Модуль остаётся владельцем своих данных. Реестр публикует доступные наборы: «Автомобили», «Поездки», «Расходы», «Визиты», «Движения материалов», «Ответы на осмотр», «Задачи». Таблица и график читают разрешённое представление этого источника. Копии для поиска/аналитики допустимы только как восстановимые проекции с явной актуальностью; их нельзя независимо редактировать.

### Контракт набора данных

| Элемент | Требование |
|---|---|
| Источник | Стабильный ID модуля и набора, версия схемы, название для пользователя, ответственная команда |
| Единица строки | Явно: поездка, расход, строка расхода материала, ответ, строка повторяемой группы |
| Ключи и связи | Стабильный ID записи; разрешённые связи с описанной кратностью, без произвольного соединения таблиц |
| Поля | Стабильные ID, подпись, тип, допустимость пустого значения, точность, единица/валюта, часовой пояс |
| Смысл | Определение показателя, допустимые агрегаты, какие статусы входят, правила отсутствующих данных |
| Доступ | Политики строк/области, ограничения полей, отдельные права экспорта, чтение исходного объекта |
| Актуальность | Время последнего обновления и состояние источника; для проекции — задержка и контрольная позиция обработки |
| Происхождение | Модуль, объект/версия формы, ревизия ответа/документа, правило вычисления, ссылка на первоисточник |
| Совместимость | Предупреждение об устаревшем поле, миграция сохранённых видов, запрет тихой смены типа/смысла |

Поля «Цена», «Количество», «Сумма» в разных модулях не объединяются только по названию. Например, заявленная водителем сумма чека, принятый менеджером расход и выплата — разные факты, связанные происхождением.

### Работа пользователя

Маршрут: «Данные → Поездки → Таблица → Выбрать столбцы → Фильтр → Сохранить вид». Для сводки: «Показатель → Как считать → По чему разделить → Период → Вид графика». Начальный набор: число, таблица с итогом, столбцы, временная линия. Графики по умолчанию показывают период, единицу измерения, статусы и время актуальности.

Открытие строки ведёт к исходной карточке модуля. Если требуется редактирование непосредственно в таблице, редактор вызывает разрешённую команду владельца данных со всеми проверками; нельзя писать в аналитическую копию или чужие таблицы. P0 разумно ограничить раздел «Данные» чтением, сохранёнными видами и экспортом.

Сервер принимает только ограниченную спецификацию запроса по реестру полей/операций. Права применяются до фильтрации, группировки, подсчёта и экспорта. Запрещённое финансовое поле не участвует также в сортировке, фильтре, подсказках поиска или группировке, позволяющих вывести его косвенно. Кэш учитывает бизнес, актуальную политику и область пользователя, версию схемы и фильтры; один пользователь не получает ранее рассчитанный чужой результат.

Для первого выпуска сводки доступны только тому, кто может читать исходные строки и поля. Отдельные агрегаты без доступа к строкам требуют позднее самостоятельной модели защиты от восстановления отдельных значений и малых групп. Даже количество ответов или сумма расходов — данные с областью доступа.

Выгрузка фиксирует схему, период, часовой пояс, фильтры и момент снимка; повторно проверяет права при запуске задания и при получении результата. Изменение прав отзывает доступ к готовому серверному файлу. Уже скачанную пользователем копию технически нельзя отозвать — это не обещать. Срок доступности экспорта ограничен, его создание журналируется, а лимиты не позволяют загрузить систему огромным запросом.

### Корректность показателей

- Доход родительской поездки не умножается при соединении с несколькими расходами или фото. Метрики объявляют свою единицу наблюдения; дочерние строки агрегируются до соединения.
- Разные валюты и единицы не суммируются молча. Деньги — точное десятичное представление; количество материалов имеет единицу.
- Ноль отличается от отсутствия данных. Средние считаются по действительным наблюдениям, а не как невзвешенное среднее групп.
- «Заполнили 80%» допустимо только при наличии снимка ожидаемых заданий. Для публичного опроса — число ответов без выдуманного знаменателя.
- Область исторической операции фиксируется на момент работы. Перевод водителя в соседнюю фирму не переносит туда старые расходы.
- После отключения модуля данные не становятся общедоступными и не исчезают мгновенно. Просмотр/экспорт регулируется политикой жизненного цикла подписки; реестр сообщает состояние источника. Сохранённый отчёт объясняет, почему показатель недоступен.

## 4. Единое приложение с рабочими местами по обязанностям

Рекомендация: один адаптивный веб-продукт и установочный режим PWA, общие аккаунты и дизайн-система. Внутри — рабочие места под задачи: водитель, мастер, прораб, менеджер, владелец. Это представления разрешённых действий, а не разные базы пользователей и не независимые системы прав. Сотрудник с несколькими обязанностями переключает вид, не получает новые права этим переключателем.

Платформенное управление организациями — отдельная административная поверхность с отдельной авторизацией и навигацией. Администратор платформы видит тариф, состояние, квоты и техническое здоровье; обычного доступа к клиентским фото, складам, зарплате и клиентам не получает.

### Контекст всегда виден

Верхняя строка бизнеса: «Название бизнеса · Москва · Север». Выбор бизнеса меняет tenant; выбор региона/фирмы сужает уже разрешённые данные. Показ «Все доступные подразделения» никогда не обозначается просто «Все», если пользователь не имеет полного доступа.

При одном бизнесе и одной группе пользователь сразу попадает в «Мой день». При нескольких — восстанавливается последняя разрешённая организация и область; при утрате доступа предлагаются доступные варианты. Чётко различить «аккаунт», «участник бизнеса» и «сотрудник/рабочий без входа». Рабочих бригады можно учитывать без приглашения и без лицензии для пользователя; условия тарифа по таким записям определяются отдельно.

На телефоне нижняя навигация ограничена четырьмя-пятью пунктами по роли. Водитель: «Сегодня», «Автомобили», «Задания», «Ещё». Мастер: «Сегодня», «Расписание», «Клиенты» при разрешении, «Ещё». Прораб: «Сегодня», «Объекты», «Отчёты», «Ещё». Менеджер сохраняет расширенную боковую панель на настольном экране.

### Десять основных экранов

| № | Экран | Содержание и главное действие |
|---|---|---|
| 1 | **Мой день** | Текущая область, ближайшая работа, требующие решения вопросы, несданные отчёты. Главная кнопка зависит от задачи: «Начать осмотр», «Открыть визит», «Отметить работы» |
| 2 | **Календарь** | День/неделя/список, люди и ресурсы, длительность работ, подготовка/уборка, бронь. Конфликты времени/ёмкости объясняются; перенос мышью — предложение, подтверждаемое сервером |
| 3 | **Ресурсы и планирование** | Доступные машины/кабинеты/оборудование, занятость, ограничения, фильтры. Для логиста — заказы и маршрут; для владельца — регионы и фирмы. «Запросить сотрудника» открывает разрешённый пул, не весь штат чужой фирмы |
| 4 | **Выполнение работы** | Карточка поездки/визита/работы на объекте, последовательность шагов, чек-лист, фото, материалы, расходы и отправка на проверку. Реальное доменное состояние видно отдельно от синхронизации |
| 5 | **Задачи** | Проект, список/доска, статусы, ответственный, срок, подзадачи, комментарии, файлы, связанные объекты. Тяжёлые Jira-подобные настройки открываются администратору по мере надобности |
| 6 | **Знания и файлы** | Инструкции, поиск, версии, папки/пространства; фотоотчёты открываются с привязкой к первоисточнику. Права на статью/файл не следуют из самого присутствия в поиске |
| 7 | **Формы и отчёты** | «Нужно заполнить», «Ответы», «Сводки», «Шаблоны». У формы: «Обзор», «Ответы», «Сводка», «Конструктор», «Доступ и публикация» по правам |
| 8 | **Данные** | Каталог наборов модулей, таблица, сохранённые виды, графики, экспорт, происхождение и актуальность. У недоступного поля нет значений в ответе API |
| 9 | **Компания и доступ** | Люди, группы, регионы/фирмы, приглашения и статусы, шаблоны/пустые роли, модули, проверка доступа, журнал. У владельца дополнительно подписка и место с разбивкой |
| 10 | **Управление платформой** | Список tenant-организаций, владельцы, сроки/пробный период, статус, подключённые возможности, измеренные квоты, продление/ограничение, история действий; отдельный вход от интерфейса бизнеса |

### Конкретные мобильные сценарии

**Водитель.** «Автомобили» показывает только разрешённый пул и состояние «Свободна», «Забронирована», «На маршруте», «Проверяется», «Недоступна». Карточка объясняет пригодность: тип кузова, длина, грузоподъёмность, температура для рефрижератора. «Забронировать» атомарно проверяется сервером; локальная старая зелёная карточка не доказывает доступность.

После брони: «Принять автомобиль → Осмотр → Маршрут → Сдать автомобиль». Осмотр: передняя/задняя/левая/правая стороны, салон/грузовой отсек по шаблону, одометр и топливо, дефекты. Для пробега требуется одометр, не текущее значение скорости. Фото в слоте не заменяет проверку человеком. Серьёзная неисправность переводит машину в состояние ожидания решения; не позволять автоматически считать её исправной после заполнения формы. В маршруте — последовательность точек и «Добавить расход» с категорией «Топливо»/«Мойка», суммой, количеством при необходимости, фото чека. При сдаче повторный осмотр, пробег/топливо, сравнение и отправка менеджеру. Зарплатного блока нет.

**Мастер SPA.** Открывает свои визиты, видит длительность и подготовку кабинета. При начале процедуры отображаются разрешённые сведения клиента и состав услуги; после — фактически использованные материалы и завершение. Списание выполняет команда склада по технологической карте/подтверждённому отклонению. Чужие доходы и зарплата не показываются; касса только по отдельному праву. Не просить мастера выбирать произвольный «модуль учёта» в процессе процедуры.

**Прораб.** Выбирает объект, участок/этап, отмечает сделанный объём, работников, трудозатраты, материалы и фото. Работник может быть записью исполнителя без аккаунта. Посещаемость, выполненные работы и начисления — отдельные записи, даже если заполняются на одном экране. Текущий отчёт и принятый заказчиком/менеджером объём не смешиваются.

**Владелец.** Сводки бизнеса и очередь решений; переход к региону и фирме без потери фильтров. Квоты видны в «Подписка и место»: использовано/доступно, разбивка по фото/документам/другим учитываемым данным, ожидаемые удаления/незавершённые загрузки по принятой модели тарификации. Понижение пакета показывает, когда изменится лимит и какие действия будут ограничены; не удаляет материалы немедленно.

## 5. Настройка ролей и подключаемых модулей

Три самостоятельных действия в интерфейсе: **«Подключить модуль бизнесу»**, **«Разрешить работу с модулем роли»**, **«Выбрать область действия»**. Подключение не выдаёт всем права. Право роли не подключает оплачиваемый модуль. Выбор региона/фирмы на экране не выдаёт доступ.

«Создать роль» предлагает: «Из шаблона», «Скопировать существующую», **«Пустая роль»**. Пустая роль содержит ноль бизнес-разрешений. Внутри карточки роли модули отображаются знакомыми переключателями. Включение раскрывает понятные действия: «Просматривать», «Создавать», «Изменять», «Проверять», «Выгружать», «Настраивать». Для каждого модуля набор берётся из его манифеста, а не из универсальной фиктивной кнопки «Полный доступ».

Финансовые разрешения показаны отдельным блоком: «Видеть начисления» (`fleet.earnings.read`), «Управлять начислениями» (`fleet.earnings.manage`). Подтверждение и выплата — самостоятельные доменные операции; детальные новые разрешения вводятся только через версионирование реестра и API, без автоматического расширения существующих ролей. По текущему требованию шаблон водителя не содержит финансовых прав, а действующее назначение `driver` дополнительно запрещает начисления независимо от иных ролей и групп. Противоречивое назначение, включая сочетание владельца и `driver`, в MVP отклоняется. Менеджер имеет их только в назначенной фирме; владелец — в пределах своего бизнеса.

Назначение роли человеку/группе включает область и при необходимости даты. В карточке видно происхождение: «Менеджер · Москва / Север · через группу Диспетчеры». При нескольких основаниях снятие одного не должно обещать полную блокировку. Показывать вычисленный итог и оставшиеся основания.

«Проверить доступ» предлагает выбрать сотрудника, объект и действие. Ответ: «Может просматривать автомобили Север · разрешено ролью Менеджер» или «Не может видеть начисление · нет финансового разрешения». Кнопка «Посмотреть рабочее место» — просмотр вычисленной навигации/возможностей, а не вход под пользователем и не обход авторизации. Опасные значения в предварительном просмотре сами требуют права их читать.

Каталог соседних свободных водителей — отдельное разрешённое представление с минимальными сведениями: имя/рабочий идентификатор, квалификация, доступный интервал, принимаемые условия. Не раскрывать зарплату, личные контакты и полную историю чужой фирмы. Запрос согласует уполномоченный руководитель, затем создаётся временное назначение с ограниченной областью и сроком. История прежней работы остаётся в исходной области.

После установки нового модуля действующие пользовательские роли не получают его разрешения автоматически. Владельцу предлагается сопоставить шаблоны; системное право владельца на настройку бизнеса отдельно защищает от самоблокировки. Отключение модуля показывает связанные формы, отчёты, задачи и автоматизации до применения изменения.

## 6. PWA и отсутствие связи

Первый выпуск может сохранять разрешённый рабочий пакет, черновик осмотра, фото и очередь отправки на устройстве. Полноценная автономная работа всей CRM в P0 не обещается. Фоновая работа браузера ограничена: service worker может останавливаться, длительная передача не гарантирована; локальное хранилище по умолчанию может быть очищено браузером [W1,W2].

В интерфейсе различаются состояния: «Сохранено на устройстве», «Ожидает отправки», «Передаётся», «Принято сервером», «Требует исправления». Повтор имеет стабильный ID операции. Вернувшаяся связь запускает проверку действующих прав, версии объекта и конфликта. Нельзя ставить «Автомобиль сдан» лишь потому, что локально заполнены поля.

Без связи допустимы чтение ранее загруженной ограниченной информации, черновики фото/форм/расходов. Бронь автомобиля, подтверждение свободного интервала, изменение ролей, кассовая операция и окончательное складское движение требуют подтверждения сервера. Если бизнесу нужен старт/завершение поездки вне покрытия, это отдельный регламент: предварительно выданный ограниченный допуск, регистрация офлайн-события и последующее согласование. Такой регламент нельзя незаметно заменить оптимистичной кнопкой «Поехать».

Рабочие пакеты разделяются по бизнесу/участнику, имеют короткий срок; при выходе/смене аккаунта очищаются по принятой политике. Сервер не может мгновенно удалить уже сохранённые данные с полностью отключённого устройства — это учитывается минимизацией кэша. Перед завершением сессии UI показывает неотправленные данные и предлагает допустимый способ закончить отправку. Запрос persistent storage снижает риск потери, но не даёт гарантии от пользовательской очистки/потери устройства.

Нужна реальная матрица поддерживаемых Android/iOS/настольных браузеров, проверка камеры/файлов, повторной загрузки, нехватки места и разрыва связи. Не обещать надёжный постоянный GPS в фоне как обычную возможность PWA; при требовании непрерывной телематики выбор нативного клиента/устройства проверяется отдельно.

## 7. Визуальный язык и проверяемый прототип

Современный UI: нейтральные поверхности, один акцент бизнеса, плотные рабочие таблицы на компьютере и карточки действий на телефоне, единая шкала отступов/типографики, подписи у критичных иконок, понятные статусы и пустые состояния. Цвет не единственный носитель статуса. Декоративные панели KPI не занимают место ежедневного действия.

Таблицы: закреплённые важные колонки, сортировка/фильтры, выбор колонок, сохранённые представления; строка открывает карточку, массовые действия показывают число выбранных и частичные отказы. Редактирование суммы не должно происходить от случайного клика. На телефоне первичные действия имеют удобные крупные цели; проектный ориентир 44–48 CSS px. Это наш ориентир удобства; минимальный критерий WCAG 2.2 для цели указателя — 24×24 CSS px с описанными исключениями [W3].

Перетаскивание карточки/броней/вопросов дополняется кнопками «Переместить»/выбором даты и клавиатурой. Одной клавиатурной альтернативы недостаточно для пользователей сенсорного указателя — нужна и операция нажатием без перетаскивания [W4]. Проверять видимый фокус, подписи полей, тексты ошибок, порядок чтения и увеличение масштаба.

Интерактивный прототип следует проверять по трём сквозным историям, с синтетическими данными и явно подписанным демонстрационным режимом:

1. Владелец создаёт пустую роль «Менеджер Север», включает логистику/склад/проверку форм, задаёт область, отдельно включает начисления; проверка глазами водителя показывает отсутствие зарплаты.
2. Водитель бронирует доступную машину, делает осмотр с 5 обязательными фото и дополнительным ракурсом по настройке, имитирует потерю сети и видит очередь, отправляет расход и сдаёт автомобиль; менеджер принимает или возвращает конкретный шаг.
3. Пользователь создаёт форму отчёта из шаблона, публикует новую версию, получает ответы; в «Данных» строит сумму принятых расходов по фирме, открывает источник, переводит дату и видит корректные права/единицы.

Отдельная короткая проверка: мастер видит тот же каркас «Мой день» с визитами, прораб — со своими объектами. Это подтверждает переиспользование рабочих компонентов; отраслевые правила при этом не растворяются в универсальной таблице.

Этот документ является текстовым критерием оценки интерфейса. Демонстрационный прототип из общего пакета иллюстрирует решения; серверная авторизация, физическая загрузка фото и финансовые операции требуют отдельной реализации и проверки.
