## 1. Цель

После W0.08 контракт `api/` и tenant-миграции покрывают поверхности этапа 1, которых нет в OpenAPI 0.1 (03 «Что требуется допроектировать», строки Auth и «Группы и владельцы»; C п.2, 14, 17; G-01, G-02, G-19):

- **вход** (S1-05): начало входа OIDC Code + PKCE, callback, получение CSRF-токена, выход;
- **приглашение** (S1-06): просмотр приглашения по токену и принятие с проверкой почты;
- **переключатель бизнеса** (S1-07): выбор бизнеса запоминается (`MeContext.lastTenantId`);
- **группы** (S1-16, 03 «Группы и владельцы»): CRUD и состав с проверкой делегирования и SoD;
- **передача владения** (S1-16, AUTH-08): список владельцев, передача с подтверждением, снятие совладельца, последний владелец не снимается;
- **«Почему доступно»** (S1-14, AUTH-04): `explainAccess` — разбор проверок `x-authorization-order` и назначений;
- **входящие уведомления** (S1-26): `/me/notifications`, сводка, отметка прочитанного; миграция inbox;
- **импорт CSV людей** (S1-10): предпросмотр с ошибками строк и применение;
- **сессии загрузки** (S1-20): статус и отмена сессии; миграция `files.upload_sessions`;
- **ADR-0014** «Расширяемые области оценщика» (F8, PD-53, C п.3–5) — вход W1.04.

Контракт **только аддитивный**: операции, пути и схемы 0.1 и W0.07 не меняются, кроме объявленных в `source-delta.yaml` добавлений (`info.version`, новый тег, новое необязательное поле `MeContext.lastTenantId`).

Не здесь: генерация кода (`make gen`, W0.09 — в подволне 0c параллельно), канал реального времени (ADR PD-58 — W1.00), импорт машин (S1-10, вторая половина — контракт fleet W2.00), список файлов и «Хранилище» по модулям (W1.00, шаг 1.8), dev-вход `?persona=` (BFF-only, только e2e-сборка, PD-54).

Решения по умолчанию в контракте:

- Токен приглашения — только в теле запроса (не в URL, не в логах); ссылка письма несёт его во фрагменте `#`.
- Ключей каталога не добавляется: группы — `members.read`/`members.manage` (состав группы с ролями сервер проверяет как назначение: `roles.assign`, делегирование, SoD); владение — `members.manage` + `x-scope: tenant-owner` (OwnerBinding, AUTH-08); импорт — `members.manage`, приглашения из файла — `members.invite` через `x-field-permissions`.
- Передача владения: `confirmation` = почта получателя, `reason` 5–500 символов, свежий вход (`auth_time` не старше 10 минут, иначе 401 `session_expired` — «Перелогин с возвратом на экран»). Получатель — активный участник с подтверждённым аккаунтом.
- Входящие хранятся в tenant DB; `listMyNotifications` требует `tenantId` (без межтенантного обхода); сводка — счётчики по членствам. Адресат и право (`required_permission`, `sensitivity`) перепроверяются при выдаче (02 «Уведомления/realtime»): уведомление о начислении водителю не выдаётся никогда.
- `Scope` 0.1 не меняется; расширение видов областей — по ADR-0014.

### 4.3 ADR-0014 «Расширяемые области оценщика»

Статус «предложено». Варианты: (1) закрытый enum `scope_kind`, расширяемый миграцией; (2) реестр видов областей (модуль регистрирует вид, резолвер «объект → область» и предков) + `scope_kind text` с проверкой по реестру; (3) ACL на объектах без областей. Рекомендация: (2) + ACL-хук на объекте (`share`, `access.list`, `chat_source`) + параметры гранта (`limit: amount`), правила «не автор», `owner_only`, `blocked_by_function`; PD-53 — объектная область засчитывается только для объекта того же вида и id; `project` разводится на `project` (Задачи), `repair_object`, `service_direction` (вид = таблица `scope_ref`). Контракт: `Scope.kind` расширяется аддитивно, клиент показывает неизвестный вид как «Особая область».
