## 1. Цель

Команда модели доступа держит строку `access.policy_state` (`kit.LockPolicy`) и для проверок оценщика (`Evaluator.Permit`, `ScopeQuery`, `Capabilities`) берёт **второе** соединение пула tenant: `authz.PGSource` читает гранты, функции, модули и предков подразделения через `pgxpool.Pool`. Пул tenant — 4 соединения (`tenantctx.DefaultMaxConns`). Четыре команды держат все четыре соединения: одна — строку политики и ждёт пятое соединение, три — ждут строку политики. Ожидание `Acquire` без срока — зависание навсегда (в control держатель `tenants FOR UPDATE` при этом ждёт `pool.Begin` tenant, и встают приглашения и принятия).

Исправление — **вариант (а): оценщик команды читает в её транзакции** (тот же `pgx.Tx`):

1. `authz.TxSource{Q}` — тот же `Source` и `UnitTree`, что `PGSource`, поверх одного `Querier` (`pgx.Tx`, соединение, пул); `PGSource` делегирует ему, SQL грантов один.
2. `kit.Within(ctx, ev, tc, tx)` — копия оценщика на один запрос (`kit.Request`: часы заморожены, субъект читается один раз), читающая через `tx`; субъект участника читается сразу, до первой записи команды: проверки видят модель доступа такой, какой её застали блокировки, а не незакоммиченные записи самой команды (как прежде отдельное соединение).
3. Все проверки оценщика внутри транзакций команд (`createAssignment`, `revokeAssignment`, `inviteMember`, `updateRole`, команды групп) идут через `kit.Within`; команда держит не больше одного соединения tenant. Порядок блокировок не меняется: `tenants` (control) → люди → политика (Q-W1.03-12, Q-W1.06-14).

Почему не (б) и не (в) — §10.

## 4. Контракты

Контракт API не меняется (коды и тела ответов те же). Внутренние интерфейсы:

- `authz.Querier` — `Query(ctx, sql, args...) (pgx.Rows, error)` (`*pgxpool.Pool`, `*pgxpool.Conn`, `pgx.Tx`).
- `authz.TxSource{Q Querier}` — `Subject`, `InstalledModules`, `Ancestors` (tenantID не используется: `Q` уже база тенанта).
- `kit.Within(ctx, ev, tc, q authz.Querier) (*authz.Evaluator, error)`; `kit.Request` остаётся для чтений вне транзакции (`explainAccess`, `createRole` до транзакции).

## 10. Риски и решения по умолчанию

1. **Почему (а).** После (а) каждая команда держит не больше одного соединения tenant и ждёт соединение, ничего не держа в tenant DB (разве что строку `tenants` в control, которую держатели соединений tenant не ждут): цикла ожиданий нет при любом размере пула. (б) — резерв соединений оценщику (семафор `MaxConns − 1` на команды) — хрупок: команды W1.05 (`createWorkProfile`), `org/move`, импорт тоже ждут строку политики, держа соединение, и съедают резерв. (в) — срок `Acquire` → 503 — не убирает взаимоблокировку, а превращает её в отказы под обычной нагрузкой трёх вьюпортов W1.30.
2. **`authz` правится.** Без SQL грантов команда не может прочитать субъекта в своей транзакции; копия `grantsSQL` в `kit` — второе определение «действующего гранта», которое разойдётся с W1.04. Правка аддитивная: `PGSource` делегирует `TxSource`, его тесты не меняются.
3. **Свои записи.** Чтение в транзакции видит незакоммиченные записи команды; `Within` читает субъект участника сразу (до записей), поэтому проверки видят то же, что видело отдельное соединение. Предки подразделений читаются лениво — команды модели доступа `org.unit_closure` не пишут.
4. **Ошибка запроса оценщика** теперь прерывает транзакцию команды — команда и так отвечает 503.
5. **Остаточный риск:** другие модули, держащие соединение в ожидании строки политики, но проверяющие оценщиком вне транзакции (W1.05 `people`, `org`), — взаимоблокировки не создают (оценщик у них до транзакции).
