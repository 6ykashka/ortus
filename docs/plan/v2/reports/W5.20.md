Пакет `backend/internal/modules/spa` — 11 операций тега `Spa` контракта `0.12.0-stage5` над tenant `0044_spa` и `sched`:

| Операция | Что делает |
| --- | --- |
| `listSpaServices`, `getSpaService` | услуги подразделений, видимых по `spa.services.read`, с техкартой; чужое подразделение — 404 |
| `createSpaService`, `updateSpaService` | длительность 1…1440 мин, буферы до и после 0…240 (граница `sched.bookings`), цена в копейках, оборудование подразделения (`sched.resources` вида `equipment`), техкарта до 50 материалов; единицы техкарты `ml`/`g`/`piece` против базовой единицы материала — совпадение либо явный пересчёт мл→л и г→кг без потери шестого знака (мл ↔ г не пересчитываются, SPA-02); правка — `If-Match` (нет — 428, чужой — 412), ревизия растёт, состояние каждой ревизии хранится в `spa.service_revisions`; имя уникально в подразделении |
| `createAppointment` | один запрос — одна бронь `sched.bookings` (`appointment`, `spa/appointment`, подготовка и уборка из услуги) и по подтверждённой резервации на практика, кабинет и оборудование с `occupied = окно ± буферы`; ресурсы блокируются в порядке id (как `sched.Hold` и календарь), гонка за кабинет — ровно один успех, остальные 409 `resources_unavailable` с полями запроса (`roomId`, `practitionerMemberId`, `equipmentIds[i]`) и `retryable`, без чужих деталей; рабочий день каждого ресурса (CAL-05); оборудование услуги обязательно в записи; снимок услуги (ревизия, длительность, буферы, цена, оборудование, техкарта) хранится в визите |
| `listAppointments`, `getAppointment` | визиты по `spa.appointments.read` над подразделением либо «свои» (`self`: практик визита); фильтры `status`, период (визиты, пересекающие его), практик; сортировка по началу; курсор — смещение |
| `rescheduleAppointment` | только `confirmed`; ресурсы обоих наборов блокируются вместе, занятость проверяется заново с буферами **снимка**; конфликт ничего не меняет; освобождается прежняя занятость, брони и резервации переносятся, ревизия растёт |
| `cancelAppointment` | только `confirmed` (иначе 409 `invalid_transition`, причина `not_in_status`); `noShow` → `no_show`; бронь отменяется, ресурсы свободны сразу; нужна причина |
| `recordAppointmentPerformance` | факт выполнения отдельно от учёта: `confirmed` → `performed_pending_posting` («незавершённый учёт»), время не раньше начала визита и не позже «сейчас» + 5 мин; склад и деньги не трогаются; повтор — тот же ответ, второго факта нет |
| `completeAppointment` | `performed_pending_posting` → `completed`: в **одной** транзакции расход материалов техкарты снимка со склада (`inventory.Consume`, FEFO, один движение-`issue` с источником `spa/appointment`), строка `spa.completions` (первичный ключ по визиту — списание один раз, AC-07), цена по факту (`finalPrice`, иначе цена снимка), предложение кассе «визит»; нехватка/просрочка — 409 `invalid_transition` с причиной `insufficient_stock`/`lot_expired`, транзакция откатывается целиком (в том числе первые строки расхода), факт и статус остаются; повтор после поправки остатка списывает один раз; повтор после завершения — тот же ответ без второго списания (10 параллельных — одно движение) |

Права: запись/перенос/отмена — `spa.appointments.create`, факт — `spa.appointments.perform`, завершение — `spa.appointments.complete` (над подразделением визита или «свои»); расход со склада — целевое право `inventory.consume` на склад списания (практик получает его областью `warehouse`, не общим `inventory.movements.post`); поправка расхода (`overrides`, фактическое количество в единице строки техкарты, причина обязательна, ноль снимает строку) — дополнительно `inventory.consumption.override`. ## Решения по умолчанию и вопросы

- **Q-W5.20-1.** `createCalendarBooking` остаётся 501 (`sched/calendar`, владелец W4.40): брони создаёт сам модуль (`createAppointment`). Поэтому `calendar_w490.yaml` сохраняет `pending: W5.20`, хотя комментарий W4.90 ждёт от SPA его снятия: положительная строка требует хендлера календаря. Решение владельца/стюарда: оставить 501 навсегда (тогда убрать операцию или `pending`) или дать календарю создание ручных броней.
- **Q-W5.20-2.** Связь со складом — прямой импорт `inventory` с `//nolint:depguard` (прецедент `fleet` → `sched`), порт `spa.Stock` уже отделён интерфейсом; реестр портов модулей в проекте ещё не заведён. Новый файл `inventory/consume.go` — в чужом каталоге W5.10 (аддитивно); интегратору принять или перенести.
- **Q-W5.20-3.** Модуль сам пишет `sched.bookings`/`sched.reservations` (как делает календарь): `sched.Hold` не знает буферов и броней. Блокировки ресурсов — в порядке id, как `sched.Hold`.
- **Q-W5.20-4.** Правила ресурсов: практик — любая действующая запись `people.person_profiles` (подразделение не проверяется), кабинет и оборудование — активные `sched.resources` **ровно** подразделения визита (не потомков); в записи должно быть всё оборудование услуги, лишнее допускается; «практик» — `practitionerMemberId` = id профиля человека (`MemberId` контракта).
- **Q-W5.20-5.** Буферы одинаковы для всех ресурсов (простой шаблон `08-domain-scenarios.md` §5.2); пример «мастер 09:55–11:00, кабинет 09:50–11:15» (разные буферы по ресурсам, расширенный шаблон) не моделируется — в контракте одно поле на услугу.
- **Q-W5.20-6.** Календарь и SPA владеют одной бронью. Окно визита всегда читается из `sched.bookings` (перенос в календаре виден в SPA), но отмена брони, смена ресурсов и перенос практика/кабинета в календаре (`updateCalendarBooking`) статус и ресурсы `spa.appointments` не обновляют. По умолчанию — расхождение допустимо; предложение: календарь отказывает (`invalid_transition`) на отмену и смену ресурсов брони с источником `spa/appointment` или вызывает порт SPA (владелец W4.40 / стюард).
- **Q-W5.20-7.** Запись «в прошлое» разрешена (внесение задним числом); факт — не раньше начала визита и не позже «сейчас» + 5 мин (часы устройства); `performedAt` не двигает окно.
- **Q-W5.20-8.** `overrides`: фактическое количество в **единице строки техкарты** (не материала), ноль снимает строку, материал вне техкарты визита — 422 `overrides[i].itemId`; причины и количества хранятся в `spa.completions.overrides`. Расход после архивации материала всё равно выполняется (единица известна).
- **Q-W5.20-9.** Завершение предлагает кассе приход «визит» на цену по факту (иначе цена снимка), ключ `visit:<id>` (идемпотентно), счёт по умолчанию не выбирается, сумма 0 — предложения нет. Оплату клиента визит не подтверждает (CASH-03). Связь с подразделением «салон» кассы — Q-W5.00-1.
- **Q-W5.20-10.** `clientId` — идентификатор без справочника клиентов (его в продукте нет): проверяется только форма; чувствительные поля клиента (SPA-04) не выдаются вовсе.
- **Q-W5.20-11.** Сида салона для стенда нет: сид календаря пишет брони с источником `spa/appointment`, но строк `spa.appointments`/`spa.services` нет, а режим stand страницы W5.21 (`test.fixme`) ждёт их. Нужен файл сида SPA (владелец сида / W5.21): услуги «Лотоса» с техкартой, склад салона, визиты, привязанные к броням календаря.
- **Q-W5.20-12.** Положительные строки изоляции для SPA невозможны в матрице W1.04 (модуль `spa` у фикстур не подключён, а добавить его — править фикстуры вне границ); покрыто integration-тестами пакета и стеком `cmd/api`.
- **Q-W5.20-13.** SPA-03 «план визита может резервировать материалы» и предупреждение о нехватке до начала процедуры в контракте не представлены — резервов склада при записи нет; отмена до выполнения освобождает только ресурсы. Если нужно — поле/операция в контракте (стюард).
- **Q-W5.20-14.** Отмена и перенос защищены `spa.appointments.create` (как в контракте), `no_show` — тем же правом; отдельного права «неявка» нет.
