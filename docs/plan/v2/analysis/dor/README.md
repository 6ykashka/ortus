# DoR модулей этапов 4–7 (W4.00, часть 1)

Разборы составили аналитики DoR W4.00 19.10.2026 по полному экспорту эталона 19.10. Этот экспорт внесён в `design/` снимком W4.00 (тег `design-2026-10-19`, блокер B-1 закрыт, `design/MANIFEST.md`). Разборы перенесены в репозиторий как есть.

Устройство каждого разбора:

- §0–1 — подключение модуля к «Ортус CRM.dc.html» и инвентарь экранов: ширины, персонажи, состояния, подписи дословно;
- §2 — данные и операции: сущности, действия на экранах → операции API, события, ошибки;
- §3 — права (каталог `api/permissions.yaml`) и области (для W4.01);
- §4 — варианты: что выбрано и чем макеты «… - варианты» отличаются от основного файла;
- §5 — расхождения: эталон ↔ документ комплекта ↔ логика `ortus/*.js` ↔ контракт `0.6.2-stage2`;
- §6 — разбивка на WS этапа, кандидаты в новые WS;
- §7 — вопросы владельцу продукта со значением по умолчанию. Они перенесены в `docs/plan/decisions.md`, раздел «Вопросы DoR этапов 4–7 (W4.00)», строки `Q-W4.00-<модуль>-<n>`.

**Оговорки.**

- Номера строк в разборах взяты по файлам экспорта. После снимка 19.10 все 70 файлов экспорта побайтно совпадают с `design/`, поэтому ссылки действуют и на `design/`.
- Фразы вида «файла нет в `design/` (B-1)» и «в `design/` старая версия» описывают состояние до снимка. Теперь эти файлы в `design/` есть.
- Проходку Playwright по эталону аналитики не выполняли: MCP `playwright` не подключился, разборы сделаны по чтению шаблона и логики. Отрисовку модулей в Chromium проверил снимок W4.00 (отчёт `reports/W4.00.md`). Единственная ошибка консоли — TypeError в «Чатах» (дефект эталона `Чаты.dc.html:449`, PD-60).
- Разборы заменяют устаревшие разделы старых анализов:
  - `repair.md` — карту 06b (версия 03.10);
  - `forms.md` — анализ 05 §6, а вопросы Q-60, Q-67 и Q-69 закрываются как «заменено модулем»;
  - `knowledge.md` — анализ 06 §6 (плоская страница `kbVM`).

## Общие выводы для W4.01 (области)

Области, которые нужны модулям (§3 разборов):

| Вид области | Модули | Вывод |
|---|---|---|
| `tenant`, `org_unit` | все | Уже есть. «Обращениям» нужно поле `direction.unitId`, иначе назначения на подразделение не работают |
| `project` | Задачи, Обращения | Только проект задач (RS-08: Q-W4.00-tasks-1, Q-W4.00-repair-2). Направление обращений — сервисный проект задач, поэтому `project` у него тот же. `self` в наследование проекта не входит. БЗ, Формы и Документы `project` не используют, у `knowledge.*` вид оставлен ради совместимости |
| `repair_project` (новый) | Ремонт | Объект ремонта — отдельный вид, а не `project` (Q-W4.00-repair-1, -2) |
| `space`, `page` | БЗ | Папка БЗ — это узел, отдельный `folder` для БЗ не нужен. Роль пространства вне пространства прав не даёт (PD-53) |
| `folder`, `doc` | Документы | Назначения ролей папок и документа |
| `account` | Касса; Ремонт и Обращения — косвенно (выплаты, возвраты) | Новый вид, эквайринг входит в область кассы |
| `chat` | Чаты | Объектная область, роли чата устроены как роли проекта |
| `relation` | БЗ, Документы, Чаты, Формы, Ремонт | Вычисляемая связь с записью. Разновидности: «прораб объекта» (БЗ, Документы, Чаты), «водитель рейса» (Чаты), связь ответа с рейсом (Формы: логист рейса видит ответ), «исполнитель задачи» (Чаты, Документы), «исполнитель задачи-заявки» и «автор замера» (Ремонт). Сравнение по имени (`obj.foreman`) заменяется на id участника |
| `self` | Формы, Касса, Документы | Уже есть: свои ответы, подотчёт, свой документ |
| `warehouse` | Ремонт (кладовщик, `inventory.*`) | Есть в `scope_kind`, но в список W4.01 не входит — этапы 5–6 |

Общие механизмы:

1. **ACL на узлах** — одна модель для БЗ и Документов. Это `mode` (`inherit` / `listed`) и список записей `role` (+ `unit`), `group`, `member`, `relation`. Режим «Только выбранные» обрывает наследование, подузел наследует и чтение, и правку. Проверка идёт по цепочке организация → пространство или папка → родители → узел → функция.
2. **PD-53 и Q-W0.11-1.** Роль на объекте (проект, пространство, касса, чат) не даёт права без объекта. Меню и гейты считаются через `canAny`, команды — через `can` с объектом. Иначе пропадают пункты меню, которые эталон показывает через `M.can` без объекта (у массажиста Морозовой — «Касса»).
3. **`explainAccess` с объектом** нужен четырём модулям: Задачи («Проверить доступ»), БЗ («Проверить сотрудника»), Документы («Откуда доступ»), Чаты (права в панели «Сведения»).
4. **Временные назначения со сроком `until`** — общий механизм с пулом водителей W2.57. Его используют запрос чтения в БЗ и подрядчик объекта в Ремонте.
5. **Правила модуля поверх оценщика**:
   - «касается меня» (`about`) в Обращениях — это запрет, а не выдача права;
   - разделение обязанностей в Кассе;
   - функции `driver` / `foreman` закрывают права (`function_blocked`).

   Оценщик W4.01 их не решает, нужны тесты изоляции модуля.
6. **Роли пространств в `listRoles`.** Access API их не отдаёт (Q-W4.30-16, Q-W4.00-knowledge-21): они видны только в «Участниках и доступе» БЗ.

## Порядок контрактных PR этапа 4 (часть 2 W4.00)

Часть 2 начинается после выхода этапа 2 на дельте `0.6.2-stage2` (W2.57 уже в main). Номер версии контракта и номера миграций выдаёт стюард при открытии PR. Резерв tenant для этапа 4 — 0020–0039. В трёх разборах этапа 4 миграции записаны как «0020+», поэтому номера распределяются по порядку вливания.

1. **Общий PR для W4.01:**
   - перечисление `Scope.kind` и миграция `scope_kind`: `space`, `page`, `folder`, `doc`, `account`, `chat`, `relation`, `repair_project` (по Q-W4.00-repair-2);
   - `explainAccess` с объектом;
   - `files.purpose: task_attachment`;
   - ключи `screens.yaml` этапа 4 из §6 разборов;
   - общие коды и поля ошибок, например `reason` у `invalid_transition`.

   Это блокирует W4.01, а через него — все Б-дорожки этапа.
2. **tasks** — 19 новых операций и расширение 7, таблицы проектов, процесса с версиями, согласований, автоматизации и вложений (`tasks.md` §2.2, §2.5). Первым из модулей, потому что `TaskPort` нужен формам (W4.26, W4.24), маршрутам документов (W7.22, W7.24) и обращениям (W7.31).
3. **knowledge** — 30 операций по `knowledge.md` §2.2, решение Q-W4.30-16. Идёт до форм: действие формы «в БЗ» ссылается на операции и схемы БЗ.
4. **forms** — `FormDefinition` v2, черновик, настройки формы, группы, правила, `FormResponse` v2, сводка, CSV. `FormPatch` переделывается, а не дополняется (C п. 13). Схемы ссылаются на задачи и БЗ.
5. **Календарь, сохранённые виды и выгрузка** (W4.40, W4.41, W4.50). В части 1 их не разбирали: эти страницы живут в главном файле, опора — анализы A и 01–04.
6. **billing и branding** (W4.60, W4.61) — control, миграции 0007+.

PR 2–4 можно готовить параллельно, а вливать по порядку из-за ссылок между схемами. PR 5 и 6 от них не зависят.
