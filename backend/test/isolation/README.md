# Набор изоляции

Негативные тесты доступа Ортус (`design/docs/15-quality-security.md`, «Isolation suite»; история S0-07). Правило 3 плана 27: каждый эндпоинт добавляет строки в матрицу, набор блокирует merge (CI job `isolation`), строки пишутся до хендлера.

```text
backend/test/
├─ harness.go                 пакет test: Now() (01.10.2026 10:30 MSK), StartPostgres, ParseProblem
└─ isolation/
   ├─ <module>.yaml           строки матрицы модуля (пишет WS модуля); authz_gate.yaml — отказы шлюза без pending
   ├─ <module>_test.go        генерируется isogen из YAML — руками не править
   ├─ main_test.go            TestMain: PostgreSQL (testcontainers) → фикстуры → цель
   ├─ target_test.go          цель набора: cmd/api целиком (W0.09), часы набора — APP_FIXED_NOW (W1.04)
   ├─ fixtures/               данные фикстур и загрузка в БД (владелец — W1.04)
   ├─ matrix/                 формат строк, проверки, раннер, NotImplemented
   └─ cmd/isogen/             генератор Go-тестов
```

## Команды

| Команда                                                                                | Что делает                                                                                                |
| -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `corepack pnpm run test:isolation`                                                     | весь набор: `go -C backend test -tags isolation -count=1 ./test/isolation/...` (как job `isolation` в CI) |
| `go -C backend generate ./test/isolation`                                              | перегенерировать `<module>_test.go` после правки YAML (удаляет файлы, чей YAML удалён)                    |
| `go -C backend test -tags "isolation isolation_pending" -count=1 ./test/isolation/...` | строки с `pending` проверяют настоящие ожидания — красные, пока нет хендлера                              |
| `go -C backend test ./test/...`                                                        | юнит-тесты формата, генератора, раннера и проверка дрейфа генерации (без Docker)                          |

Нужен Docker: PostgreSQL 17.11 поднимается через testcontainers (`PG_TEST_IMAGES` меняет образ, берётся первый). Внешнего сервера нет. Без Docker набор падает, а не пропускается.

## Как WS добавляет строки

1. Контрактный PR шага влит: операция есть в OpenAPI.
2. Добавить эндпоинт в `isolation/<module>.yaml` (файл на модуль), `pending: <ID своего WS>`.
3. `go -C backend generate ./test/isolation`, закоммитить YAML и `<module>_test.go` вместе (red-коммит). Строка с `pending` проходит в двух случаях: цель ответила 501 (операции нет обработчика) или ответ уже совпал с ожиданиями строки. Второй случай — ответ шлюза операции W0.09 до хендлера: сессия 401 → CSRF/Origin 403 → членство 404/403 → право 403. Если положительная строка (2xx) получила 2xx, строка падает с подсказкой снять `pending`: хендлер уже есть. Любой другой ответ — нарушения строки с пометкой `pending <WS>`.
4. Хендлер готов: убрать `pending`, перегенерировать, строки проверяют ожидания (green-коммит).

`pending` принимает 501 у любой строки, поэтому отрицательная `pending`-строка не замечает шлюз, ошибочно пропустивший запрос: хендлера нет, придёт 501. Отказ, который шлюз выдаёт до хендлера (нет гранта с действием x-permissions нужного вида области, x-scope `tenant-owner`, функция закрывает действие), пишется без `pending` и с `code` — в отдельный эндпоинт (`op` в файле уникален, поэтому в отдельный файл, как `authz_gate.yaml` у `authz.yaml`). Такая строка проверяет свои ожидания сразу и остаётся верной, когда хендлер появится.

Так CI остаётся зелёным, пока хендлера нет. Красные строки до хендлера видны в строгом режиме (`-tags isolation_pending`). Это отступление от `tdd-protocol.md` §2 записано в `docs/plan/decisions.md` (Q-W0.15-1).

## Формат `<module>.yaml`

```yaml
module: me # = имя файла; [a-z][a-z0-9]*(_[a-z0-9]+)*; не main/target/fixtures/suite/doc
endpoints:
  - op: getMyContext # operationId; уникален в файле
    method: GET # GET | POST | PUT | PATCH | DELETE
    path: /api/v1/me/context # /api/v1/…; {param} — из rows[].params
    channel: http # по умолчанию http; другие каналы — ниже
    pending: W0.09 # необязательно: хендлера ещё нет → 501 или ответ шлюза, совпавший со строкой
    rows:
      - actor: b.owner # актор фикстур или anonymous
        params: {} # параметр пути → ссылка на фикстуру
        status: 200 # 200 201 204 401 403 404 409
        code: function_blocked # необязательно, только при статусе ошибки: Problem.code ответа (errors.yaml)
        present: [tenant:b] # id, которые обязаны быть в теле
        absent: [tenant:a] # id, которых не должно быть ни в теле, ни в заголовках
        body: '{"unitId": "{{unit:a.msk1}}"}' # необязательно: JSON запроса, {{ссылка}} → id
        note: … # необязательно
```

Генератор отклоняет файл, если:

- есть неизвестные поля;
- модуль не совпадает с именем файла;
- `op` повторяется;
- метод, канал, статус или `pending` недопустимы;
- у параметра пути нет значения или есть лишний параметр;
- актор или ссылка неизвестны;
- строка повторяется (тот же актор и те же параметры);
- `present` указан при статусе ошибки;
- `code` указан при статусе успеха или не похож на код Problem (`snake_case`);
- у эндпоинта нет негативной строки (401/403/404 или непустой `absent`).

Что проверяет раннер (`matrix.Check`):

- статус;
- тело ошибки — `application/problem+json` с `type`, `title`, `status`, `code`, `requestId`; если у строки есть `code` — он совпадает с `Problem.code` (403 `function_blocked` не равен 403 `forbidden_action`);
- `present` и `absent` (id ищутся без учёта регистра, `absent` — ещё и в заголовках);
- строка 404 с параметрами повторяется с несуществующим id: статус и `code` должны совпасть (AC-01, «чужой = несуществующий»);
- строка с `pending`: 501 или все проверки выше; 2xx на положительную строку — подсказка снять `pending` (шаг 3 выше).

Каналы `data`, `export`, `search`, `files`, `notifications`, `realtime`, `audit` уже есть в формате, но раннер пока поддерживает только `http`. Канал добавляет его владелец: Data Hub, экспорт, поиск и файлы — W1.04 и модули; уведомления — W1.10; realtime — W1.07; аудит — W1.01. Перепроверку адресата уведомления при выдаче выражают http-строки `listMyNotifications` на уведомлениях фикстур (W1.44). Канал `notifications` нужен для проверки адресата при постановке в очередь: для неё в цели набора должны работать worker и outbox (W1.42).

Цель набора получает фиктивное хранилище (`S3_ENDPOINT=http://127.0.0.1:9`): `getFileDownload` только подписывает ссылку локально, в сеть не ходит. Загрузки в строках останавливает шлюз (`files_gate.yaml`).

Аккаунты: issuer `urn:ortus:dev`, subject `iso-<актор>`. Модуль `logistics` включён в обоих тенантах. Периоды назначений отсчитываются от `harness.Now()`. Цель получает это время в `Env.Clock` и передаёт `cmd/api` в `APP_FIXED_NOW` (W1.04): оценщик сверяет периоды с часами набора, а не с `now()` базы.

## Цель набора

`matrix.Factory` в `target_test.go` строит `matrix.Target{Handler, Authenticate}` из `matrix.Env`:

- `World` — фикстуры и URL баз;
- `Clock` — фиксированное «сейчас»;
- `Getenv` — `CONTROL_DB_URL` и `TENANT_DB_URL` под `ortus_api`, `MIGRATOR_DB_URL`, `APP_ENV=test`, `AUTH_PROVIDER=dev`.

Изменяющий запрос актора получает свой `Idempotency-Key` (W1.03, W1.06): без ключа строгий сервер отвечает 400 до хендлера, а формат строк заголовков не передаёт. `If-Match` строки по-прежнему не передают — у операций с ним здесь только отказы до хендлера.

Запросы идут в `Handler` через `httptest`, порт не нужен. До W0.09 цель — `matrix.NotImplemented()`: любой запрос получает 501 `not_implemented`. Строгий сервер W0.09 отвечает 501 только после шлюза операции, поэтому негативные `pending`-строки (401/403/404) с ним уже проходят по своим ожиданиям.
