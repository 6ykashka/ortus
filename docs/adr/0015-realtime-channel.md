# 0015. Канал реального времени

Статус: принято (решение плана PD-58 по умолчанию; пересмотр — через `docs/plan/decisions.md`)
Дата: 2026-10-15 · W1.00 (стюард контракта этапа 1) · Участники: W1.07 (канал), W1.10 и W1.22 (входящие), W1.20 (оболочка), W7.12 (чаты), tech lead, backend lead
Принято: 2026-10-16 · W1.42 (подключение канала в `cmd/api` и `cmd/worker` закрепляет вариант 1) · по умолчанию до ответа решающих: Q-W1.00-7, Q-W1.07-1 (вариант 1), Q-W1.07-2 (библиотека `github.com/coder/websocket v1.8.15` в `backend/go.mod`)
Кто решает: tech lead, backend lead (решение плана, а не комплекта)

Решение плана: PD-58 (план v2 §7: «Один канал реального времени для отзыва прав, входящих и чатов. ADR в W1.00, по умолчанию WebSocket-шлюз»). Вход шагов 1.6 (S1-15), 1.9 (S1-26) и 7.1 (CHAT-01).

## Контекст

Канал нужен трём потребителям, которые в документах спроектированы независимо (C п.18, F7):

| Потребитель | Требование | Источник |
|---|---|---|
| Отзыв прав (S1-15, W1.07) | «Новые запросы после применения ревокации блокируются; кеш и realtime отражают изменение ≤ 5 с» | `design/docs/v0.1/02-architecture.md` «Revocation»; `docs/12-errors-and-events.md`: `access.assignment.revoked.v1`, `access.policy.bumped.v1` — «закрытие подписок realtime» |
| Входящие (S1-26, W1.10, W1.22) | Счётчик и лента обновляются без перезагрузки; адресат проверяется при постановке в очередь и при доставке | `02-architecture.md` «Уведомления/realtime»; контракт `0.3.0-stage1` (`listMyNotifications`, `getMyNotificationSummary`) |
| Чаты (CHAT-01, W7.11, W7.12) | Новые сообщения, набор текста, прочтение, голосования; канал `chat:{id}` | `docs/25-chats.md` (вариант А — свой сервис, доставка WebSocket, например Centrifugo) |

Ограничения среды и плана:

- Браузер ходит в API через BFF с cookie-сессией `HttpOnly`, без токенов в JavaScript (`03-api-guide.md` «Вход»). Изменяющие запросы с cookie требуют `Origin` и `X-CSRF-Token`.
- У каждой организации своя БД. Событие рождается в tenant DB (outbox), а соединение браузера привязано к аккаунту, у которого может быть несколько организаций.
- OpenAPI 3.1 и `oapi-codegen` strict server не описывают апгрейд протокола (ответ 101). Контракт должен оставаться проверяемым (`contract --check`, Spectral, `make gen`).
- Пилот — одна компания, десятки одновременных пользователей (`docs/plan/v2/load-profile.md`). Горизонтальное масштабирование API — не раньше этапа 3.
- Отзыв прав не может зависеть от доставки сообщения: если канал потерян, права всё равно проверяются на сервере на каждом запросе.

## Варианты

1. **Свой WebSocket-шлюз в процессе `cmd/api` (рекомендуется).** Путь `GET /api/v1/realtime`, подпротокол `ortus.realtime.v1`, аутентификация одноразовым билетом из `POST /api/v1/auth/realtime-tickets` (cookie-сессия + CSRF), билет передаётся первым кадром. Сообщения — подсказки без данных (`context.changed`, `notifications.changed`, `session.ended`, `ping`); клиент перечитывает данные обычными операциями. Разветвление между экземплярами API — `LISTEN/NOTIFY` на control DB (полезная нагрузка — только id). Плюсы: один процесс и одна модель прав, не нужен новый сервис в compose, контракт проверяем (билет — обычная операция, кадры — схемы в `components`). Минусы: свой код соединений (heartbeat, backpressure, закрытие при отзыве), зависимость Go для WebSocket (`github.com/coder/websocket`) через интегратора.
2. **Centrifugo рядом с API.** API публикует в Centrifugo по HTTP API, браузер подключается к Centrifugo с JWT-подписью канала от BFF. Плюсы: готовые каналы, история, presence — пригодится чатам (25 рекомендует). Минусы: новый сервис в compose и на проде (D-05), второй контур прав (подпись каналов), токен в JavaScript (противоречит модели BFF), для этапа 1 избыточно.
3. **Server-Sent Events.** `GET /api/v1/me/events` с `text/event-stream`, cookie-сессия. Плюсы: проще WebSocket, работает через прокси, описывается OpenAPI как поток. Минусы: только сервер → клиент — чатам (набор текста, подтверждения) нужен двусторонний канал, значит в этапе 7 появится второй канал вопреки PD-58; лимит соединений HTTP/1.1 на источник.
4. **Опрос (polling).** `getMyNotificationSummary` и `getMyContext` раз в N секунд. Плюсы: ничего нового. Минусы: отзыв ≤ 5 с требует опроса каждые 2–3 с у каждого клиента — нагрузка на API и tenant DB без пользы; чатам не подходит.

## Решение

Рекомендация по умолчанию — **вариант 1**, WebSocket-шлюз в `cmd/api`. Принят по умолчанию (PD-58): пакет `platform/notify/realtime` (W1.07) подключён в процессы (W1.42), зависимость `github.com/coder/websocket v1.8.15` — в `backend/go.mod` (без транзитивных зависимостей). Пересмотр — новым ADR со статусом «заменено 0015» у этого:

- **Контракт (W1.00, `0.4.0-stage1`).** Операция `createRealtimeTicket` (тег `Auth`, только `sessionCookie`, CSRF, `Origin`; без `Idempotency-Key` — см. ниже) возвращает `RealtimeTicket`: `ticket` (одноразовый, 60 секунд, привязан к сессии и аккаунту), `path` = `/api/v1/realtime`, `protocol` = `ortus.realtime.v1`, `heartbeatSeconds`. Кадры — схемы `RealtimeClientMessage` (`auth`, `pong`) и `RealtimeServerMessage` (`context.changed`, `notifications.changed`, `session.ended`, `ping`), на них ссылается расширение `x-realtime` операции билета. Сам путь WebSocket в `paths` не входит.
- **Подключение.** Шлюз проверяет `Origin` при апгрейде (защита от CSWSH), ждёт кадр `auth` с билетом не дольше 10 секунд, иначе закрывает с кодом 4401. Билет не попадает в URL и журналы.
- **Билет без `Idempotency-Key` (ревью W1.00, возврат 1).** Ответ идемпотентной команды хранится не меньше 7 дней (`idempotency_keys.response_body`, control 0005) и отдаётся повтору с тем же ключом. Для билета это означало бы секрет открытым текстом в базе и выдачу уже израсходованного билета на повтор. Поэтому операция ключ не принимает (правило Spectral `ortus-idempotency-key`, список `singleUse`), ответ не хранится и не повторяется: каждый вызов выдаёт новый билет, потерянный ответ клиент восполняет новым запросом. По умолчанию W1.03 хранит в хранилище сессий только хэш билета; ограничение частоты — общий `429`.
- **Подсказки, а не данные.** Ни заголовков, ни текстов, ни сумм, ни персональных данных по сокету не идёт. На `context.changed` клиент перечитывает `getMyContext` (новые права, модули, состояние организации, `permissionVersion`), на `notifications.changed` — `getMyNotificationSummary` и открытую ленту. Поэтому проверка адресата и прав при доставке — та же, что у обычных операций, а пропуск подсказки не раскрывает и не теряет данных: разрыв в `seq` или переподключение — повод перечитать всё.
- **Отзыв прав ≤ 5 с (S1-15).** Сервер не полагается на канал: каждая проверка прав сверяет `access.policy_state.policy_version` tenant DB (кеш оценщика — не дольше 1 секунды, W1.04/W1.07), поэтому новые запросы блокируются сразу после транзакции. Канал отвечает за интерфейс: транзакция изменения прав увеличивает `policy_version` и пишет событие outbox `access.policy.bumped.v1`; worker (W1.01, опрос не реже раза в секунду) публикует `pg_notify` в control DB с id организации и затронутых аккаунтов; шлюз шлёт `context.changed` их соединениям. Бюджет: ≤ 1 с outbox + ≤ 1 с доставка + перечитывание `/me/context` — в пределах 5 с. Отзыв членства или окончание сессии — `session.ended` и закрытие сокета.
- **Входящие (S1-26).** Постановка уведомления в `notify.notifications` (W1.10) — тот же путь outbox → `pg_notify` → `notifications.changed` адресату.
- **Масштабирование.** Внутри процесса — карта «аккаунт → соединения»; между экземплярами — `LISTEN ortus_realtime` в control DB. Отдельный процесс `cmd/realtime` или Centrifugo — только если нагрузка этапа 3 (W3.01) покажет необходимость; контракт кадров при этом не меняется.
- **Чаты (W7.12).** Тот же шлюз и тот же протокол: добавляются типы кадров (подписка на `chat:{id}` по правам чата, `message.new` как подсказка с id). Решение «свой шлюз или Centrifugo для чатов» пересматривается в DoR этапа 7 новым ADR, если появятся требования истории и presence.
- **Уточнение для чатов (W7.00, 0.12.0-stage7, ADR-0016, Q-W4.00-chats-7).** Принято по умолчанию: только подсказка `chat.changed` (`chatId`, `lastSeq`) — кадр сервера `RealtimeServerMessage`; клиент перечитывает `listChatMessages?afterSeq=`; кадров подписки, набора текста и присутствия нет, адресаты — участники чата (проверка при постановке и при доставке). Тест шлюза, отвергающий `chat.*`, обновляет W7.12. Centrifugo — отдельным ADR, если понадобятся история и присутствие.
- **Режим mock.** MSW выдаёт билет по контракту, но WebSocket не поднимает: клиент режима mock заменяет подсказки перечитыванием по таймеру (W1.20, W1.22).

## Последствия

- Проще: один канал на три потребителя (PD-58), одна модель прав, никаких данных в канале — изоляцию не нужно проверять отдельно для сокета, достаточно строк изоляции обычных операций. Контракт остаётся генерируемым.
- Сложнее: свой код шлюза (heartbeat, ограничение очереди на соединение, закрытие при отзыве, корректное завершение при остановке `cmd/api`); WebSocket-маршрут монтируется в `cmd/api/main.go` вручную, рядом с генерируемым `router.go`.
- Нужно сделать:
  - W1.07 — шлюз `platform/notify/realtime/`, `LISTEN/NOTIFY`, кеш оценщика по `policy_version`, тест «отзыв роли → `context.changed` ≤ 5 с» и строка изоляции «чужой аккаунт не получает подсказку» (сделано);
  - W1.01 — публикация outbox → `pg_notify` (миграция tenant 0007 — аренда и dead-letter) (сделано: `realtime.Relay` — потребитель outbox);
  - W1.03 — `createRealtimeTicket` в BFF (билет в хранилище сессий, одноразовость) (сделано: `authhttp.Server.Realtime`; билеты — `realtime.MemTickets` одного процесса, общее хранилище — при нескольких экземплярах API, Q-W1.07-9);
  - W1.42 — подключение: в `cmd/api` кеш прав, хаб, шлюз `GET /api/v1/realtime`, билеты, `LISTEN` и подсказки команд оператора; в `cmd/worker` — `realtime.Relay` и `inbox.Consumer` в реестре outbox; `realtime.BumpPolicy` при смене модулей;
  - W1.20, W1.22 — клиент: билет, переподключение с экспоненциальной паузой, перечитывание по подсказкам;
  - интегратор — зависимость `github.com/coder/websocket` с точной версией в `backend/go.mod` (сделано: v1.8.15).
- Как проверим: integration `cmd/api` «билет → сокет → отзыв роли → `context.changed` ≤ 5 с» (W1.42); e2e режима stand «владелец снимает роль — у сотрудника пункт меню исчезает ≤ 5 с без перезагрузки» (W1.30, рядом с AC-10 «отзыв роли во время экспорта → 403»); unit-тесты шлюза на `Origin`, просроченный и повторно использованный билет, разрыв `seq`; нагрузочный сценарий соединений в W3.01.
