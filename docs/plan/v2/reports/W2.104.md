# Отчёт W2.104 — флейк изоляции TestIsolationFormsPublicW490/W483 (Windows)

Ветка `ws/W2.104`. Изменён один файл: `backend/test/isolation/target_test.go` (+ бриф `docs/plan/v2/ws/W2.104.md`).

## Причина

`getPublicUploadStatus` собственной загрузки гостя держит транзакцию ссылки и берёт вторую связь пула арендатора
(Session/File модуля files). Пул арендатора — 4 связи (`tenantctx.DefaultMaxConns`). Параллельные тесты всех модулей
забивают пул такими держателями; запрос ждёт 20-30 с (замер в логе API: `duration_ms` 19915-28061), выходит за
`WriteTimeout` API (30 с), соединение рвётся и прокси набора отвечает 502 «proxy error: EOF». Одиночный `-run` — без
конкуренции, поэтому зелёный. Гипотеза «медленный отказ закрытого порта S3 на Windows» проверена (локальный стаб 404
вместо 127.0.0.1:9) и отвергнута: Stat к хранилищу в этом пути не вызывается.

## Исправление

Прокси цели изоляции пропускает не более двух запросов в API одновременно (`limitInFlight`, `maxInFlight = 2`): два
запроса требуют не более четырёх связей. Набор стал быстрее (пакет 73-85 с вместо 105-290 с).

## Проверки

- До исправления: пакет `test/isolation` падал (W490 502 через 33 с, W483 502 через 31 с) в 4 из 4 прогонов.
- `GOFLAGS=-p=2 go -C backend test -tags isolation -count=1 ./test/isolation/...` три раза подряд, все ok (75.6 с, 85.2 с, 79.6 с).
- `node tools/ci/pipeline.mjs --job isolation`: exit 0, «isolation: ок» (go-isolation и go-concurrency).
- `corepack pnpm run lint`: exit 0, «0 issues.»
- `corepack pnpm run typecheck`: exit 0.
- `corepack pnpm run test`: exit 0 (хвост: `ok  github.com/ortus/ortus-crm/backend/test/isolation/matrix 1.526s`).

## Замечание интегратору / владельцу W4.82

Корень — продуктовый: запрос гостя держит транзакцию и берёт вторую связь того же пула (hold-and-wait). Пока пул 4,
реальная нагрузка из четырёх параллельных гостей (загрузки) может так же ждать. Переменная `TENANT_DB_POOL_MAX`,
упомянутая в комментарии `pools.go`, нигде не читается.
