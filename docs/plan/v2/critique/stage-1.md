## 2. Пропуски

### П-1. CI на GitHub красный с влития W1.05 (блокирует выход)

`e2e-stand` падает на трёх прогонах main подряд: 38750452537, 38752259304 и 38765228603. `frontend/apps/web/e2e/me-context.spec.ts:53–56` ждёт в режиме stand `listMembers` владельца → 501 `not_implemented`. С W1.05 стенд отвечает 200. Ни исполнитель, ни интегратор W1.05/W1.06/W1.09 не прогоняли `e2e-stand` перед вливанием. В строке статуса W1.05: «web не затронут — e2e не требуется». Предложение:

- исправить ожидание: на стенде 200 и 10 участников «Альты» по сиду;
- добавить в DoD backend-WS прогон `ci:job e2e-stand`, если WS снимает 501 с операции, которую проверяет `@stand`-spec.

Владелец: W1.40 (follow-up). Ветка `ws/W1.20` тоже правит `me-context.spec.ts`, поэтому при влитии W1.20 нужно сверить ожидание.

### П-2. Приглашение не доставляется (блокирует выход)

`inviteMember` (`backend/internal/modules/access/assignments/invite.go:207`) отбрасывает токен из `invitations.Issue`. В backend нет отправителя почты: нет SMTP-клиента и нет обработчика outbox. На стенде есть Mailpit и `SMTP_HOST`/`SMTP_PORT` в `.env`, но в проверке ящик пуст. Приглашённый сотрудник не может получить ссылку `/auth/invitation#token=…` и принять приглашение. Часть критерия «…приглашает сотрудников» не выполняется ни в UI, ни через API. Владельца в реестре нет:

- W1.03 владеет `invitations` и `Issue`;
- W1.06 владеет `inviteMember`;
- платформенного сервиса почты нет ни в одной карточке.

Предложение — W1.41.

### П-3. W1.11 (оператор) не влит

Ветка `ws/W1.11` построена до W1.00 и реализует операторские команды через `updatePlatformTenant`. Это противоречит контракту 0.4.0-stage1 по пяти пунктам: отдельные операции, правила продления, возобновление по подписке, имена действий аудита, ключ идемпотентности (причина отката в итогах интеграции). Без W1.11 нет S1-04 и журнала оператора (S1-23), а значит нет и W1.25. По плану W1.30 ждёт всех W1.*. W1.11 — WS реестра, а не новая работа. Его нужно вернуть исполнителю с постановкой интегратора: перебазировать на main, реализовать три операции и `listPlatformAuditEvents`, заменить `stage1b_stubs.go` целиком, добавить 428 `revision_required` вместо 400 без If-Match (Q-W1.11-9).

### П-4. Готовые серверные части не подключены к процессам

Каждый WS отложил подключение к `cmd/api` и `cmd/worker` как «чужой файл». Ни интегратор, ни следующий WS подключение не сделали.

- W1.07: `realtime` не смонтирован в `cmd/api` (`/api/v1/realtime` 404, `createRealtimeTicket` 501). `realtime.Relay` не зарегистрирован в `cmd/worker`. Рецепт есть в отчёте W1.07 (Q-W1.07-11).
- W1.10: `inbox.Consumer` не зарегистрирован в `cmd/worker/tenants.go` (newRegistry). Событие без обработчика «доставляется никому и считается успешным» (`events.go:126`).
- W1.05: `importer.Purge` не вызывается по расписанию. Строки истёкшего импорта с ПДн остаются в базе дольше 24 ч. Это расходится с Q-W1.05-17.
- W1.08: `realtime.BumpPolicy` не вызывается при подключении и отключении модуля, поэтому `context.changed` не приходит (Q-W1.08-12).

Предложение — W1.42.

### П-5. Операции этапа 1, всё ещё 501

- `updateMember`: приостановка и восстановление участника, последний владелец, места, сессии. Владелец — W1.06 (Q-W1.05-11), операция не в `accessImplemented`. Предложение — W1.43.
- `commitPeopleImport` с `sendInvitations=true` (адаптер `importer.Inviter`, Q-W1.05-10) — после W1.41, в той же W1.43.
- Billing: операции мест — 501 (`subshttp/server.go:193`); `requestSubscriptionChange` — 501 до W4.60 (Q-W1.08-6, решение по умолчанию).
- Platform: `suspend`, `resume`, `extendPlatformTrial`, `listPlatformAuditEvents` — W1.11 (П-3).

### П-6. Клиентская часть этапа не влита

На main 0 из 22 экранов этапа 1. W1.20 не принят после трёх возвратов. W1.22…W1.25 не начаты, потому что ждут W1.20. Под угрозой критический путь: этап 2 (W2.20+) тоже строится на оболочке W1.20. Это WS реестра. Решение за интегратором и оркестратором: дать W1.20 новый раунд с другим исполнителем или разбить на части (навигация `domain/nav` и `run`, отдельно экраны оболочки). В ветке 46 коммитов и 13 тыс. строк, и после двух возвратов она отстаёт от main на 16 коммитов.

### П-7. W1.30 (приёмка) не начат, брифов этапа 1 нет

В `docs/plan/v2/ws/` нет брифов W1.11, W1.20, W1.22…W1.25 и W1.30. Брифы W1.11 и W1.20 есть только в своих ветках. Для W1.30 нужен бриф с точным сценарием:

- оператор создаёт организацию (или используется сид);
- владелец создаёт регион и фирму, роль, назначение, приглашает;
- приглашённый принимает приглашение из Mailpit через dev-провайдер;
- AC-01, AC-02 и AC-11 проверяются в браузере на стенде;
- AC-07 и AC-10 — сквозь API.

Ещё нужен каталог `e2e/journeys/stage1/` и `e2e/_stand/` (фикстура Mailpit). До W1.20…W1.25 часть сценария можно выразить API-шагами `@stand`, но критерий требует, чтобы владелец действовал «сам», то есть через UI.

### П-8. Покрытие AC неполное до сквозного уровня

- AC-10 «отзыв роли во время экспорта → выдача 403»: оценщик (`TestAC10RevokedRoleDuringExport`) и выдача файла (`TestAC10DownloadAfterRevoke`) покрыты. Самого экспорта нет до модуля «Данные» (этап 4). Принять на этапе 1 как закрытый на уровне integration. Сквозной тест экспорта — в DoD владельца экспорта (W4.x).
- AC-11 (категория E2E): серверная часть закрыта, а «экспорт работает в read_only» проверить нечем (этап 4). Браузерную часть «создание → 403 `tenant_read_only`, баннер» должен проверить W1.30 после W1.20.
- AC-01 при id в теле (не в пути) раннер матрицы не выражает (README изоляции, «Открыт»). Строки с позитивными ответами ждут фикстур: импорт (Q-W1.05-19), файлы с реальным `fileId` (Q-W1.09-11), уведомления (Q-W1.10-8). Предложение — W1.44.

### П-9. Шум аннотаций в job `unit` на GitHub

Шесть аннотаций `X` на проходящих подтестах `tools/gen` («Servers с полем на тег…», «код → статус и title», «строка операции с правами») появляются при каждом прогоне. Строки `ok N - …` приходят в лог с префиксом `##[error]`. Красные аннотации на зелёной job приучают их не читать. Предложение — W1.45.

### П-10. Среда Windows-слотов

- Антивирус блокирует `fleetrules.test.exe`, а иногда и `events.test.exe`.
- Провайдер testcontainers сбоит при параллельном старте («rootless Docker is not supported on Windows»).

Из-за этого локальный `ci:local` на Windows не проходит целиком, а проверяющие тратят время на повторы. Нужно исключение каталога go-build в антивирусе — это сделает человек, см. `remaining`. Ещё можно ограничить параллелизм integration на Windows: `-p` в `pipeline.mjs`. Предложение — W1.46, не блокирует выход.
