## 2. Сводка

- Один DC-компонент с собственным `state` (`:537–573`), **не** ходит в `ortus/api.js`, не читает `db`, не проверяет права. Все изменения — локальные `setState`; «сервер» отсутствует. В CRM права на вкладки обеспечивает только `TABS` в `repairVM` (`CRM:4291`).
- Два режима (`:873–876`): **standalone** (открыт файл напрямую) — шапка «Альта Групп · Ремонт и стройка», вертикальная навигация с группами «Продажи» / «Объект · кв. 42», карточка объекта с «Готовность по закрытым актам»; **embedded** (`props.embedded && props.tab`) — без шапки, навигации и карточки, `padding:0`, `border-radius:12px`, рисуется одна секция `t[tab]`.
- Встраивание (`CRM:2126`): контейнер `div[style=display:{block|none}]` держит компонент **смонтированным всегда** (и на «Обзор», и на «Работы»), поэтому состояние вкладок переживает переключения, а `onStatus` срабатывает сразу после монтирования (`componentDidMount → report`, `:577, 589`) — обзор «дорисовывается» вторым рендером.
- Сводка `onStatus` (`:871`): `{ sched: {due, forecast, slip, slipText, why, noWho[]}, req[], draft[], sms[], est, fin: {total, paid, spent, margin} }` — отправляется только при изменении JSON (`:589`). Из неё CRM строит чип срока в шапке, бейджи «Документы»/«Снабжение», пункты очереди решений и карточку «Деньги» (`CRM:4291, 4301–4306, 4315, 4319, 4336`).
- Переходы между вкладками внутри макета (`go`, `:576`): в embedded → `props.onTab(id)` → `rpTab` (`CRM:4324`); в standalone → `state.tab`. Кнопки-переходы: «Открыть смету» (`estimate`), «График по этапам сметы» (`schedule`), «Открыть объект» в воронке (`measure`).
- Самый дорогой фрагмент — «График»: ~232 строки шаблона + ~220 строк логики; это полноценный CPM-планировщик (прямой и обратный проход, резерв, критический путь, рабочий календарь с праздником 04.11, паузы в календарных днях), с перетаскиванием мышью, черновиком изменений, причинами переноса и журналом.
- Календарь макета: `D0 = 05.10.2026` (день 0, понедельник), `TODAY = 15` → 20.10 (вт), `HOL = [30]` → 04.11 (`:473`). Это **не** совпадает с «сегодня» приложения (01.10, 06 §14 #8). Новые записи журнала датируются «20.10» жёстко (`:616, 789`).
- Деньги считаются от замера: площади помещений → объёмы сметы с чипом «из замера» → `total` 413 379 ₽ → аванс 30 % = 124 014 ₽, маржа 27 % = 111 612 ₽ (`:843–857, 865, 885–892`). Изменение любой длины/ширины в «Замере» меняет смету, «Финансы», «Кабинет заказчика» и сводку `fin` в обзоре — даже при согласованной смете (см. §18 #4).
- Цепочка состояний между вкладками: «Смета» `draft → sent → approved`; «Документы» акт № 1 `draft → sms → signed`; подпись акта открывает «Начислить по акту № 1» (`payCanAccrue`, `:894`), меняет цвет этапа «Демонтаж» на «Закрыто актом» (`:651, 764`), поднимает готовность для заказчика с 6 % до 13 % (`:857`), добавляет расход «Начисление бригаде по акту № 1» (`:890`).
- Вкладка «Заявки» (`t.leads`) видна только standalone; в CRM пункт навигации «Заявки · в «Задачах»» существует в данных (`:870, 875`), но навигация при заданном `tab` скрыта (`showNav = !props.tab`, `:873`), поэтому `on-leads` из дочернего макета в CRM **недостижим**.
- Адаптивность — своя, по ширине `main` через ResizeObserver (`:579–588`): `narrow = W < 640` (список вместо диаграммы по умолчанию, колонка этапа 128 px, без перетаскивания, без мета-строки), `side = W ≥ 980` (боковая панель 320 px справа, иначе под диаграммой) (`:622–626, 825–826`). Пока `gw = 0` (первый рендер, скрытый контейнер) используется `W = 1000`.

### 4.6 Встраивание в «Ортус CRM.dc.html»

1. `CRM:2126`: `<div style="display:{{ rp.childDisplay }}"><dc-import name="Ремонт и стройка" embedded="{{ true }}" tab="{{ rp.childTab }}" on-tab="{{ rp.onChildTab }}" on-status="{{ rp.onChildStatus }}" on-leads="{{ goLeads }}" hint-size="100%,560px"></dc-import></div>`. `support.js:661–688` (`walkComponent`) собирает атрибуты в props (`on-tab` → `onTab` и т. д.), `hint-size` — только подсказка редактора (`support.js:424`).
2. `CRM:4323–4324`: `isChild = tab ∉ {overview, works}`; `childDisplay = isChild ? 'block' : 'none'`; `childTab = isChild ? tab : 'measure'`; `onChildTab = (id) => setState({rpTab: id})`; `onChildStatus = (st) => setState({rpChild: st})`.
3. `CRM:4285`: `cs = s.rpChild || { req: [], draft: [], sms: [], est: 'draft', fin: null }` — до первого `onStatus` деньги «—», чип срока «сдача 27.11» из `o.due` (`CRM:4319, 4336`).
4. `CRM:4292`: если `rpTab` не входит в `TABS` персонажа → `overview`. Следствие: у прораба (без `canFin`) кнопка «Открыть смету» на «Замере» вызывает `onTab('estimate')` → `rpTab='estimate'` ∉ `TABS` → показывается «Обзор», а `childTab` становится `measure`.

### 8.9 Модель расписания (`gsched :512–530`, `gnorm :531–534`)

- Рабочие дни: `isW(d) = d % 7 < 5 && !HOL.includes(d)`; `fw/pw` — ближайший рабочий вперёд/назад; `addW(s, n)` — конец отрезка из `n` рабочих дней; `shW(d, n)` — сдвиг на `n` рабочих дней; `wdIn(a, b)` — число рабочих дней в `(a, b]`.
- Прямой проход: `es = fw(max по предшественникам fw(end_pred + 1 + lag))`, `bind` — предшественник, задавший `es`; `dur` = переопределение из `o.dur` или `GST.dur` (веха — 1); `start` = фактический `as` (если задан) или `shW(es, off)`; `end = addW(start, dur)` (веха: `start`). Паузы `lag` — в календарных днях (сохнет и в выходные), отрицательный `lag` — старт внахлёст.
- Обратный проход от `fin = R.s10.end`: `lf = min(pw(ls_succ − 1 − lag))`, `ls = subW(lf, dur)`, резерв `fl = wdIn(end, lf)`; критический путь — `fl === 0` у невыполненных.
- Три расписания: `B = gsched(null)` (договор, базовый план), `P = gsched(plan)`, `R = draft ? gsched(draft) : P` (`:621`); отклонение `vr = ±wdIn(B.end, R.end)` (`:633`).
- `gnorm` убирает `off ≤ 0`, `dur` равную `GST.dur`, `lag` равный `GLK[2]`, сортирует ключи — черновик сравнивается с планом по JSON.
- Этапы `GST` (`:493–504`): s1 Демонтаж (5 дн, факт с дня 0, выполнен), s2 Электрика · черновая (8 дн, факт с дня 7, принято 20/38, на приёмке 3/38, заявка З-13), s3 Штукатурка стен (10, З-12), s4 Стяжка пола (2), s5 Шпаклёвка и покраска стен (12), s6 Плитка в санузле (5, без исполнителя, З-15), s7 Укладка ламината (3, З-14), s8 Электрика · чистовая (2), s9 Уборка и подготовка к сдаче (1), s10 Сдача объекта (веха, Алексей Соколов). ## 17. Инварианты и правила

1. Дочерний макет не вызывает API и не хранит состояние в `db`; в CRM права только фильтруют вкладки (`CRM:4291`), поэтому в реализации вкладки «Смета», «Финансы», «Оплата бригады», «Подрядчики», «Кабинет заказчика» и `fin` в сводке должны закрываться на сервере (`docs/19-construction.md:94, 130`).
2. Готовность по закрытым актам (`:857`) и готовность по объёмам (`CRM:4320`) — разные числа; в кабинете заказчика и карточке standalone — только первая.
3. Начисление бригаде возможно только после `docs.find(d => d.act).st === 'signed'` (`:856, 894`); выплата — только после начисления.
4. Согласованная смета (`approved`) в макете всё ещё пересчитывается от замера — в реализации версия должна фиксироваться (RS: «правки — новая версия», `19-construction.md:127`).
5. Расписание: фактическое начало (`as`) не сдвигается; начатый этап нельзя закончить раньше `fw(TODAY + 1)`; `off ≥ 0`; `−5 ≤ lag ≤ 30`; веха = 1 день без длительности и исполнителя; паузы в календарных днях, работы — в рабочих (`:512–530, 673, 759, 785`).
6. Любое изменение плана сохраняется только с причиной из `GREASONS` и попадает в «История изменений» вместе с уведомлениями исполнителям затронутых этапов и заказчику при изменении даты сдачи (`:612–617, 746`).
7. Базовый план `B` неизменяем («меняется только допсоглашением», `:299, 784`): его показывают серой линией/ромбом и считают от него отклонения.
8. Статус = иконка + текст + тон (`ch`), критический путь — отдельный чёрный чип; выполненные этапы в режиме «Критический путь» приглушаются до `opacity:.3`.
9. Перетаскивание — только мышью, только на ширине ≥ 640; клавиатура/касание — кнопки ±; все иконки проблем имеют `role="img"` + `aria-label`.
10. `onStatus` вызывается после каждого рендера при изменении JSON сводки (`:589`); потребитель не должен полагаться на порядок/частоту вызовов.
11. `data-screen-label` у секций — ключ для скриншотов визуальной сверки (`verification-protocol`); значение «Оплата бригад» у `t.pay` отличается от заголовка.
12. Числа и даты: `rub` с неразрывными пробелами и ` ₽`; `num` с запятой; даты `dd.mm` и `dd.mm, дн` (weekday сокращённо, строчными).

1. **`on-leads` недостижим в CRM**: навигация макета скрыта при заданном `tab` (`:873`), пункт «Заявки · в «Задачах»» (`:870`) не рендерится; нужен ли в карточке объекта переход к заявкам (`docs/19-construction.md:29` говорит «пункта «Заявки» нет») — тогда prop лишний.
2. **Две даты «сегодня»**: приложение — 01.10.2026, график — 20.10 (`:134, 473`); записи журнала и начисления датируются «20.10» жёстко (`:616, 789, 890`). При переносе в репозиторий нужна одна инъекция «сегодня» и один сид.
3. **Смета «Версия 2»** — константа; история версий, «новая версия при правке» и блокировка правок замера после `approved` не реализованы (`19-construction.md:127`). Решить: запрет редактирования замера при `approved` или автосоздание версии 3.
4. **Готовность для заказчика** `round(Σ«Демонтаж»/total·100) + 8` (`:857`) — «+8» ничем не объяснён; RS-07 (стоимость vs трудоёмкость) открыт.
5. **Факт на графике** (`acc`, `pen` у s2) — константы, не связаны с отметками `WL-*` CRM и с «Объёмы работ» (`w1–w3` в м², этапы сметы — в точках/м²); нужна модель соответствия «работа CRM ↔ этап графика ↔ раздел сметы».
6. **«Операции появились в кассе»** (`:895`) — ложно в контексте CRM (06 §14 #10); при реализации — проводка через `cash` или смена текста.
7. **Снабжение**: «Закупить» не запрашивает сумму/чек (QR не сканируется), материалы снабжения (`З-*`) не связаны с «Материал» формы отметки (`mt1/mt2`, 06 §11.1).
8. **Подрядчик**: нет персонажа-подрядчика, «цены не видны» не проверяемо; дата «31.10» и «Оплачено 20 000» жёстко; закрытие доступа не отражается в «Люди на объекте» (`CRM:4334`).
9. **Кабинет заказчика** — превью, не отдельная публичная страница (`GET /public/client/{token}`, `19-construction.md:164`); «Подписать по SMS» — `span`; ссылка без токена и срока.
10. **Перетаскивание** только `pointerType === 'mouse'` (`:670`); для касания и клавиатуры — только ±кнопки. Достаточно ли (a11y) или нужны стрелки на выбранной полосе?
11. **Исполнитель** меняется мгновенно без причины и уведомления (`:789`), в отличие от сроков; конфликт исполнителя только предупреждает (`:341`), не блокирует.
12. **Этап «Отказ»** в воронке (`19-construction.md:21`) не нарисован; воронка в CRM живёт в «Задачах» — проверять по отчёту 05.
13. **`data-screen-label="Оплата бригад"`** (`:411`) против заголовка «Оплата бригады» — опечатка макета; для скриншотов зафиксировать одно имя.
14. **Акт № 2 · электрика** никогда не меняет состояние; связь «этап закрыт прорабом → акт готов к отправке» не моделируется.
15. **Ширина `W`** измеряется ResizeObserver'ом `main`; при скрытом контейнере (`display:none`) `clientWidth = 0` и `gw` не обновляется — первый показ вкладки «График» после «Обзора» рендерится с `W = 1000`, затем перерисовывается. В React-реализации лучше брать ширину от общего breakpoint CRM.
16. **Пауза ≥ 0 в календарных днях, отрицательный лаг — нахлёст в календарных днях** (`:516`): `fw(end + 1 + lag)` при `lag = −3` на пятницу даёт старт в среду той же недели — поведение задумано, но проверять в unit-тестах.
17. ⚠ не найдено в источниках: куда ведёт «Фото и план помещения прикладываются к замеру через «Файлы»» (связи с `pg.files` нет); что происходит с бейджем «Снабжение» standalone после «Списать на объект» (считаются только `request` — остаётся); текст уведомления заказчику при переносе.
