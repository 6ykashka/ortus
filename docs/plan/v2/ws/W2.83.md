# W2.83 · Integration на GitHub зелёный: таймаут ryuk на Linux и нестабильный `TestExportJobChecks`

Этап 2 · вид backend · слот 3 (API `127.0.0.1:8103`, compose `ortus-s3` — не нужен: только testcontainers). WS вне реестра §4 — постановка интегратора 24.10 (найдено предпроверкой выхода этапа; та же работа у W4.75 — отдельно её не будет). Исходная точка — `main` `29ab2328`.

## 1. Цель

На GitHub `main` проходят job `integration` и следующий за ним `isolation` + `concurrency` (AC-03…AC-06). Сейчас `integration` красный в прогонах 39821553611, 40118104842, 40120489895 — `isolation`, `build`, шарды e2e и `e2e-stand` пропускаются.

| № | Причина | Исправление |
|---|---|---|
| А | `dockerEnv()` (`tools/ci/pipeline.mjs`, W1.46) ставит `RYUK_RECONNECTION_TIMEOUT=5m` только на win32. На ubuntu пакеты одного `go test -tags integration ./...` делят один ryuk; он завершается через 10 с без соединений, следующий пакет падает «create container: reaper: … wait for reaper …: context deadline exceeded» (`access/groups`, `access/roles`, `data/fleet`, `files`) | таймаут ryuk 5m (если не задан ни `RYUK_RECONNECTION_TIMEOUT`, ни `TESTCONTAINERS_RYUK_RECONNECTION_TIMEOUT`) — на любой платформе; `DOCKER_HOST` — по-прежнему только win32 |
| Б | `TestExportJobChecks` (`data/fleet/jobs_integration_test.go`, W4.50) ставит три выгрузки `a.manager-msk1` и ждёт 429 на четвёртой, а параллельные тесты пакета ставят выгрузки того же участника в той же базе — третья выгрузка уже получает `rate_limited` | проверка предела — своим участником, которого не используют другие тесты пакета (`a.two-roles`: менеджер Москвы-1, как `a.manager-msk1`), и проверка, что активных выгрузок у него до проверки нет; продуктовый код не меняется |
