### 1. Флейк pre-push (Vitest `@ortus/web`)

Причина воспроизведена. Под нагрузкой (`go -C backend build -a ./...` в цикле) исходный конфиг даёт 6 падений из 697. Это `people.test.tsx` «Назначить роль» (Test timed out in 5000ms), `photos.test.ts`, `app.test.tsx`, `InboxPanel.test.tsx`, `tenants.page.test.tsx` («Unable to find role…»). При двойной переподписке CPU (22 потока нагрузки) падений 66. Причины:

- первый тест файла на холодную импортирует ленивую страницу, оболочку, MSW и сид. На свободной машине это 1–1,5 с (замер в изоляции: 0,9 с до первого h1), при занятых ядрах — 5–12 с. Срок теста 5 с при этом был меньше ожиданий самих тестов: `SLOW` у findBy — 5–8 с;
- в файлах без `configure` ожидания Testing Library держались 1 с, а `InboxPanel` задавал свои 3 с;
- вложенные `waitFor(async () => (await findBy…))` в `people.test.tsx` при каждом опросе обходили всё дерево ролей;
- `photos.test.ts` ставил итог проверки через фиксированные 60 мс. Под нагрузкой `completeUpload` к этому времени не успевал, файл оставался на проверке, и загрузка падала «scan timeout» или по сроку теста. Это настоящая гонка, не только срок.

Что исправлено:

- `frontend/apps/web/vitest.config.ts`: `testTimeout` и `hookTimeout` — 20 000 мс, причина записана в комментарии;
- новый `frontend/apps/web/vitest.setup.ts`: `asyncUtilTimeout` 10 000 мс — половина срока теста;
- `people`, `users`, `modules.page`, `plan`, `InboxPanel`: сняты свои короткие сроки; вложенные ожидания в people заменены синхронной проверкой строки;
- `photos.test.ts`: тест ждёт сессию `completed` и меняет статус только её файла.

Прогоны после правки:

- под той же нагрузкой `go build -a` — 697/697;
- под двойной переподпиской — 1 падение из 697 (InboxPanel со своими 3 с; после правки этот срок снят);
- три полных `corepack pnpm run test` подряд под нагрузкой — раздел «Прогоны».

Новый помощник `frontend/apps/web/e2e/logistics.stand.ts` готовит сид и возвращает его. Стенд `e2e-stand` общий для трёх проектов (`workers 1`), поэтому каждая строка сама возвращает то, что поменяла:

- **«Логистика» и роль логиста.** На базовом сиде «Логистики» в «Альте» нет. Строка подключает её (`setModuleInstallation`) и даёт Котовой «Менеджер логистики» в «Север Логистик» с поддеревом, как seed demo. Уборка идёт в обратном порядке:
  1. читаются входящие владельца;
  2. снимаются назначения;
  3. модуль отключается с `owner_export`. Состояние `disabled` в `/me/context` гейт показывает так же, как «не подключена организацией». `access-gate @stand` после строк этапа 2 проходит во всех проектах.

  На сиде показа модуль и роль уже есть, и уборки нет.
- **Свой рейс строки.** `createTripPlan` с меткой проекта. Окно ставится после последнего окна, в котором машина занята. Если водитель занят (409 `resources_unavailable`), окно сдвигается.

  Экран водителя показывает первый незавершённый рейс (`pickTrip`), поэтому `driverTrip` берёт Р-208, пока он не пройден, иначе новый рейс Ильи Васильева. Смену, которую оставила упавшая строка, закрывает `closeTrip` по состоянию рейса:
  - бронь снимается;
  - дефект разрешается;
  - начатая смена завершается, сдаётся и принимается.

  Без этого модуль при отключении уходил в `draining`, и падали все следующие строки.
- **Второй водитель для API-смен.** Строки дефекта, приёмки и начисления ведут смену командами API Тимура Ахмедова (`acc-9`). Строка даёт ему роль «Водитель», уборка роль снимает.
- **Назначение логиста.** `logistics-fleet` назначает машину из Mercedes Sprinter, Ford Transit или Hyundai Porter — их не берут другие строки, рейс лёгкий. Назначение API снять не даёт (см. вопросы).
- **Фото.** Настоящий JPEG из canvas идёт через presigned PUT в MinIO, затем проверка cmd/worker. Если хранилище стенда браузеру недоступно, строка пропускается с причиной `NO_STORAGE`. Так происходит в `e2e-stand`: он поднимает compose без MinIO и не добавляет хост MinIO в `E2E_ALLOW_HOSTS`. Признак — хост `uploadUrl` настоящего билета, билет сразу отменяется.

Строки, которым MinIO не нужен, идут в `e2e-stand` целиком:

- рабочее место и назначение;
- планирование формой;
- «Автомобили» и бронь;
- «Моя смена» до осмотра;
- очереди дефектов и приёмки, начисления по API стенда.

Строки с фото:

- водитель — пять фото через MinIO, выезд, сдача, «Смена принята»;
- «Завершить рейс» диалогом;
- дефект «разрешить выезд» → «Решённые»;
- «Принять смену» экраном;

Все они проверены на стенде слота 1 с MinIO (`.claude/tmp/W2.53/devstand.mjs`: базовый сид как в e2e-stand + `minio` + `bucket` + хост MinIO в `E2E_ALLOW_HOSTS`).

### 3. Фото в ручном mock

Новый `frontend/packages/adapter/src/msw/files/storage.ts` — хранилище режима mock, как MinIO стенда:

- PUT по `uploadUrl` билета: ключ — сессия, тип содержимого — из билета, объект не больше заявленного;
- коды: 200 с `ETag`, сессия переходит в `uploaded`; 404 — неизвестная сессия; 403 — истёкший билет, закрытая сессия или чужой тип; 400 — объект больше заявленного.

`ScenarioServer.storage` — обработчик MSW, `put()` — тот же ответ без MSW. Опция `scanAfterMs` завершает проверку только загруженного файла после `completeUpload`. `scanFiles(s, ids?)` в `core/dev.ts` теперь умеет и один файл.

Где хранилище включено:

- `node.ts` — хранилище вместе с API;
- `browser.ts` — вне Playwright хранилище включено, проверка завершается через 1,5 с, путь водителя проходит руками. Под Playwright (`navigator.webdriver`) PUT по-прежнему уходит в сеть, его и проверку ведёт сам e2e. Сценарий «сбой загрузки» по маршруту контекста не сломан;
- явный выбор — опция `startMockWorker({ storage })` или sessionStorage `ortus:msw:storage` = `on` | `off`. Так проверяющий через MCP получает ручной режим.

e2e: `driver-today.spec.ts` «ручной режим mock: пять фото без маршрута хранилища и scanFiles — «Фото · 5 из 5»» на 390 и 1440. Маршрут контекста отклоняет любой запрос к хранилищу, и тест проверяет, что сеть не видела ни одного PUT.
