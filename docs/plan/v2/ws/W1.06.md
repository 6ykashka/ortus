## 1. Цель

Backend 19 операций тега `Access` контракта 0.4.0-stage1 (18 по карточке и `inviteMember` — по Q-W1.03-5, где W1.03 передал выпуск приглашения W1.06):

1. **Редактор ролей (S1-12, AUTH-03):** `listRoles`, `getRole`, `createRole` (в том числе пустая роль), `updateRole` (`If-Match` = ревизия), `deleteRole`. Ключи прав — только из каталога `api/permissions.yaml`; права уровней `sensitive` и `restricted` хранятся и проверяются отдельно (таблица чувствительности с тестом дрейфа против каталога, аудит с чувствительностью роли); ничего не включается неявно. Делегирование: участник (не владелец) выдаёт в роль только те права, которые есть у него самого (409 `delegation_exceeds_grant`). Системная роль не редактируется и не удаляется (409 `invalid_transition`); назначенная роль не удаляется (409 `invalid_transition`). Роль с функцией «Водитель» (шаблон `driver`) не может содержать начисления; роль, назначенная водителю (прямо или через группу), не получает начисления (409 `separation_of_duties_conflict`). Правка роли переводит её действующие назначения на новую версию и поднимает `policy_version`.
2. **Назначение с областью и сроком (S1-13, AUTH-04/05/08, D-10):** `listAssignments`, `createAssignment`, `revokeAssignment`. Область — `tenant`, `org_unit` (с поддеревом или без), `self`, объектные `project`, `resource_pool` (PD-53); срок — `validFrom`/`validUntil`. Delegation check: назначающий имеет `roles.assign` над областью назначения и каждое действие роли в этой области (для поддерева — над каждым подразделением поддерева). Конфликт функции driver → 409 `separation_of_duties_conflict` в обе стороны: роль с начислениями — водителю (или группе, где есть водитель), роль «Водитель» — сотруднику с финансовыми правами. Список — только назначения, видимые актору по `roles.read` (через `scopeddb`). Снятие роли последнего владельца — 409 `last_owner_required`.
3. **«Почему доступно» (S1-14, AUTH-04):** `explainAccess` — проверки `x-authorization-order` по порядку до первой неудачной (членство, состояние организации, модуль, тариф, SoD, право, область ресурса), решение оценщика W1.04 (`Evaluator.Explain`) для участника, каждый грант с правом и причиной несовпадения (`out_of_scope`, `other_object`, `object_scope_without_object`, `expired`, `dormant_module`, `function_blocked`), гранты вне области актора — только `hiddenGrants=true`. Участник и подразделение вне области актора — 404.
4. **Последний владелец и передача владения (S1-16, AUTH-08):** `listOwners`, `transferOwnership`, `revokeOwnership` по `owner_bindings` control DB под `FOR UPDATE` строки `tenants`; свежий вход (≤ 10 минут, иначе 401 `session_expired`), подтверждение почтой получателя (422), получатель — активный участник с действующим аккаунтом, ещё не владелец (409 `invalid_transition`), последний владелец не снимается (409 `last_owner_required`), аудит с причиной, событие для «Входящих» (W1.10).
5. **Группы (CRUD):** `listGroups`, `getGroup`, `createGroup`, `updateGroup`, `deleteGroup` (архив; 409, пока есть действующие назначения группы), `setGroupMembers` (полная замена состава с `If-Match`; скрытые участники сохраняются; новый участник группы с ролями проверяется как прямое назначение — делегирование и SoD; изменение состава группы с ролями поднимает `policy_version`).
6. **Приглашение (S1-06, формат W1.03):** `inviteMember` — карточка в tenant DB, назначения приглашения в `dormant`, приглашение в control через `invitations.Issue` с их id; адрес участника или ожидающего приглашения — 422; мест нет (участники + ожидающие приглашения) — 409 `seats_exhausted`; каждая роль — как прямое назначение: делегирование и D-10 между ролями приглашения в любом их порядке (возврат 2).
7. **Изоляция:** строки `backend/test/isolation/access_model.yaml` (чужой тенант, чужая фирма, скрытые гранты, AC-01) — красными до хендлера; отказы шлюза — `access_model_gate.yaml` без `pending`; id чужого тенанта в теле — `access_model_refs.yaml`. Файлы `access*.yaml` модуля `access` принадлежат W1.05 (возврат 2: свои строки W1.06 разведены по отдельным файлам).

## 10. Риски и решения по умолчанию

| # | Вопрос | По умолчанию |
|---|---|---|
| 1 | `memberId` контракта | id карточки `people.person_profiles` (как `principalId`, примеры и сид W1.04); членство control DB — по `memberships.person_profile_id` |
| 2 | Описание роли (`Role.description`) | Колонки нет (tenant 0001): описание не хранится, ответ — `""`. Колонка `access.roles.description` — миграция стюарда (decisionsNeeded) |
| 3 | `builtIn` | `kind = 'system'`; шаблонные роли (`template`) редактируются и удаляются, как свои |
| 4 | Правка роли и действующие назначения | Новая версия роли; неснятые назначения переводятся на неё в той же транзакции (в прототипе правка роли сразу меняет права держателей); `policy_version + 1` |
| 5 | Делегирование при `createRole`/`updateRole` | Участник добавляет только права, которые есть в его действующих грантах; в роль с действующими назначениями — только если право есть у него над каждой целью этих назначений (`RoleReach`, возврат 1, AUTH-08 по областям); владелец — любые ключи каталога; `owner_only` — только владелец |
| 6 | Делегирование при назначении | `roles.assign` и каждое действие роли разрешены актору над областью назначения (`Permit`); поддерево — над каждым подразделением поддерева; `self` — над домашним подразделением принципала и каждого человека, которого достигает назначение (участники группы, `Reach`, возврат 1); объектная область — над объектом (на этапе 1 — только грантом организации); владелец не проверяется |
| 7 | SoD (D-10) | Роль с действиями `blocked_by_function: [driver]` не назначается принципалу, у которого функция driver пересекается со сроком назначения (через группу — у любого участника); роль шаблона `driver` не назначается тому, у кого есть такие гранты (в том числе спящие); ни то, ни другое не добавляется в состав группы и в роль; в одном приглашении роль «Водитель» и роль с начислениями — 409 в любом порядке. Функцию driver при начислениях отклоняет W1.05 своей `org/kit.DriverConflict` |
| 8 | Объектные области (`project`, `resource_pool`) | Таблиц объектов на этапе 1 нет: существование объекта не проверяется, назначение и объяснение по объекту — только при гранте актора на организацию (`roles.assign`/`roles.read`); область `account` (касса) и прочие будущие виды — 422 до своего этапа |
| 9 | Видимость назначения и гранта | По «якорю»: `org_unit` — подразделение области; `tenant` — организация (нужен грант на организацию); `self` и объектные — домашнее подразделение принципала (группа без подразделения — организация) |
| 10 | Состояние назначения | `revoked` не показывается; `dormant` — как есть; закончившееся — `expired`; остальное (в том числе ещё не начавшееся) — `active` |
| 11 | `revokeAssignment` последнего владельца | Назначение системной роли владельца (`template_key='owner'`) у последнего активного владельца — 409 `last_owner_required` (как прототип); владение (OwnerBinding) не меняется |
| 12 | Свежий вход | `Session.IssuedAt` (dev-вход: время входа). После слияния W1.03 — `Session.AuthTime` (одна строка в `cmd/api/access.go`) |
| 13 | Уведомления и письма владельцам | Событие `access.owner.changed.v1` в outbox; «Входящие» пишет worker W1.10, письма — вне этапа 1 |
| 14 | Архив группы и гранты (Q-W1.04-19) | Группа с действующими или спящими назначениями не архивируется (409), поэтому у архивной группы нет действующих грантов; фильтр в `authz/pg.go` — на усмотрение W1.04 |
| 15 | Заголовки `If-Match`/`Idempotency-Key` без значения | Строгий сервер отвечает 400 `malformed_request` до хендлера (W0.09); контракт обещает 428 — вопрос владельцу `cmd/api` |
| 16 | `GroupPatch.homeUnitId: null` | Генератор не отличает `null` от отсутствия: перенос группы на всю организацию через `updateGroup` невозможен до правки контракта/генератора |
| 17 | Нарушения полей (`violations`) | `problem.Body` W0.09 не несёт `violations`: 422 отдаёт `detail` с текстом прототипа |
| 18 | `policyVersion` объяснения | Десятичная строка `access.policy_state.policy_version` |
| 19 | Доставка токена приглашения | Токен не возвращается (схема `Invitation`) и не хранится; письма на этапе 1 нет — способ доставки (почтовый worker с перевыпуском токена) — decisionsNeeded |
| 20 | Имя приглашённого | Обязательно («Укажите имя», как сервер прототипа), хотя в `InvitationCreate` поле необязательно |
| 21 | Порядок блокировок и конкуренция | Команды модели доступа — `InPolicyTx` (строка `access.policy_state` до проверок; люди, которым команда даёт права, — до неё, п. 24); команды control + tenant DB — `InControlTx` (`FOR UPDATE tenants` первой, затем `LockPolicy`); актор владения перепроверяется под блокировкой (403) |
| 22 | Фиксация в двух БД | Control DB фиксируется первым; при сбое `COMMIT` tenant DB — компенсация в control DB (`Undo`: привязки владения, отзыв приглашения), несделанная компенсация — в журнал ошибок (Q-W1.06-11) |
| 23 | Причина отказа «Почему доступно» | Только по видимым актору грантам; если подходящие гранты все скрыты — «Среди видимых вам назначений сотрудника нет подходящих: остальные вне вашей области.» и `hiddenGrants` |
| 24 | D-10 под конкуренцией с W1.05 (возврат 2) | W1.05 блокирует человека (`createWorkProfile`) или функцию (`updateWorkProfile`), проверяет начисления и только затем поднимает `policy_version`. Команды, которые могут дать права людям (`createAssignment`, `setGroupMembers`, `updateRole` с правами), — `InPeopleTx`: карточки людей и их функции driver (`LockPeople`, по id) до строки политики, тот же порядок, что у W1.05; `Separation` и `RoleHeldByDriver` блокируют проверяемых людей ещё раз (для уже заблокированных — без ожидания). Итог: одна из команд ждёт фиксации другой и видит её запись — без write skew и без дедлока |
| 25 | Назначение пустой группе и его снятие (возврат 2) | Ничьи права не меняются: `policy_version` не растёт, события `access.policy.bumped.v1` нет (пустой `personIds` relay W1.07 читает как «каждый участник»), как у правки роли без держателей |
| 26 | Снятие назначения группе с областью `self` (возврат 2) | Право на снятие проверяется по целям якоря (`Targets`: домашнее подразделение группы), а не по подразделениям участников (`Reach`, как при создании). Снятие только сужает права, поэтому управляющий домашним подразделением группы может снять её назначение целиком — несимметрично с AUTH-08 при создании, но не расширяет ничьих прав |
| 27 | Сбой `COMMIT` control DB (возврат 2) | Исход неизвестен (обрыв после фиксации на сервере): tenant DB откатывается без компенсации, ответ 503, запись `slog.Error` с тенантом для ручного разбора (`Deps.Log`, как неудачная компенсация) |
| 28 | D-10 и владелец | W1.05 (`org/kit.DriverConflict`) считает владельца держателем начислений и не даёт ему функцию «Водитель»; W1.06 при `transferOwnership` функцию получателя не проверяет, `EarningsConflict` смотрит только назначения. Права не утекают (оценщик закрывает начисления функцией и для владельца); единое правило — decisionsNeeded |
| 29 | Адрес уже занят (`inviteMember`) | По примеру контракта `api/openapi/examples/inviteMember/validation_failed.json`: 422 `validation_failed`, `detail` «Участник с таким адресом уже есть.» (в прототипе — `conflict` без точки, `api.js:296`); decisionsNeeded |
