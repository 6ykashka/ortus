## Сводка

1. **Протоколы переиспользуются почти целиком.** Цикл TDD (e2e-скелет первым, red → green → refactor по 9 слоям), четыре проверки страницы (e2e 390/1440, пиксельная + структурная сверка с эталоном, проходка Playwright MCP с evidence, ревью), роли агентов, формат отчёта, worktree-на-WS, границы автономии и изоляция портов верны и для плана 27. Меняется «рамка времени»: волны 0–4 «весь UI на mock → backend» заменяются этапами 0–8 с порядком внутри шага «контрактный PR → моки из примеров → backend ‖ frontend». Отсюда правки: новая роль «стюард контракта» (владелец `api/`, `permissions.yaml`, нумерации миграций на этап), фаза «Контракт» в `workflow.template.js`, `phase 1/2` → `stage 0–8 × mode mock|stand`, барьеры волн → критерии выхода этапов, формула портов не от номера WS.
2. **Дерево репозитория и владельцы каталогов (МП §3.3) годятся как основа разметки**: каталоги уже нарезаны по модулям; меняется только «кто и на каком шаге» (§3 ниже даёт привязку к шагам П27). Новые каталоги: `chats`, `documents`, `requests`, `inventory` (склад отдельно от SPA), `cash` отдельно от `spa`.
3. **Реестр WS: 58 строк, а не 55** (README и `status.md` расходятся с МП §5.1). Итог сверки: 5 WS — оставить как есть (compose, backend логистики: ядро, приёмка, пул, наборы данных), 21 — оставить с правкой (3 из них переписать), 11 — перенести в другой этап (страницы S3+ → этапы 4–6; Keycloak, provisioning, PWA, CSV-импорт → раньше, в этапы 1–2), 19 — разделить по шагам, 2 — удалить или отложить (WS-15 contract-delta растворяется в контрактных PR шагов; WS-11 docs-site вне плана 27). Отдельных WS нет у 14 шагов П27 (0.1, 0.11, S2-17…S2-19, 3.3–3.7, 4.6 «места», 5.1 склад, 7.1–7.3) — их надо завести.
4. **«Точно как нарисовано» не противоречит переносу страниц в этапы 4–7**: четыре проверки применяются к странице в том этапе, где её строят, против замороженного на этап снимка эталона. Противоречия возникают только на стыках: оболочка и «Главная» пилота показывают в эталоне пункты и сигналы модулей, которых ещё нет; осмотр в эталоне пишет ответ формы и задачу (в пилоте — S2-17); «Путь проверки» заходит в кассу. Нужен вид allowlist «вне этапа» с решением и сроком снятия.
5. **Решения: конфликт нумерации.** Кит v0.2 уже занял D-13…D-28 (смета, меню, формы, задачи, чаты), план 27 предлагает D-29…D-34, а старый план держит свои D-13…D-52 (D-25…D-52 ещё даже не внесены в `decisions.md`, только в МП §10.3). Решения старого плана нужно перенумеровать с префиксом. По содержанию противоречат П27: D-15 (UI-first), D-18 и D-41 (Keycloak позже), D-33 (core/delta), D-40 (два интегратора волны 2), D-44 (демо-панель переносится; П27 0.9 и R-08 — не переносится), частично D-47, D-48, D-51, D-52; Q-04, Q-21, Q-31, Q-44, Q-48, Q-49, Q-95, Q-109 и блок форм и задач Q-60…Q-71 устарели.
6. **Горячие точки в новой последовательности смещаются**: вместо «одного владельца контракта на волну» каждый шаг открывает контрактный PR, а backend и frontend одного шага идут параллельно. Значит, нужна очередь контрактных PR с одним стюардом на этап, выдача номеров миграций в этом PR, файл на модуль для прав, сидов, текстов, изоляции и меню, а также генерируемые баррели `index.ts`. Появляется новый конфликт портов: backend-агенты (API `8080`, compose, Keycloak с redirect на `:5173`), чего старый §7.4 не покрывает.

## 6. Горячие точки и сериализация

В П27 backend и frontend одного шага идут параллельно, а шаги разных модулей одного этапа (4.1…4.6, 5.x, 6.x) — тоже. Поэтому общие файлы трогают чаще, чем в старом плане.

| Горячая точка | Почему горячая в П27 | Как сериализовать |
|---|---|---|
| `api/openapi/ortus.yaml` (корень, `components/`, общие схемы `Problem`, пагинация) | каждый шаг открывает контрактный PR | **Стюард контракта на этап** — единственный писатель `api/`. Очередь PR в порядке шагов; PR шага X.Y мержится до старта его backend и frontend. Пути и схемы — `paths/<tag>.yaml`, `components/<tag>/*` (файл на модуль); корень и общие схемы — только стюард. Контракт аддитивный (D-47); `make gen` и drift — в том же PR |
| `api/permissions.yaml` | каждый модуль добавляет ключи; CODEOWNERS, 2 ревьюера | разделы по модулю, только добавление; входит в контрактный PR шага; константы `PERM.*` генерируются там же |
| `api/errors.yaml` / enum `Problem.code` | новые коды у модулей | только добавление в конец; в контрактном PR; тест «каждый код покрыт» в шаге |
