## 1. Цель

1. **Осмотр → ответ формы (D-30 комплекта, ответ владельца 17.10).** Потребитель outbox в `cmd/worker` на `fleet.inspection.submitted.v1` пишет осмотр ответом формы «Осмотр машины» — как `recordInspection` эталона (`design/ortus/api.js:64–77`, снимок `design-2026-10-19`):
   - форма — опубликованная форма организации с именем «Осмотр машины» (имя уникально в организации), принимающая ответы (`closedReason`: статус, «Принимать до», лимит, модуль формы включён); нет такой формы — ничего не пишется, как `if (!f || !f.published) return`;
   - ответ: канал `inspection`, действующая версия, автор — водитель (`submitted_by` осмотра), объект — рейс («Рейс Р-208 · выезд» / «· сдача»), статус «Принят», время — время осмотра;
   - ответы по вопросам действующей версии: `q-photos` «N фото», `q-odo` пробег, `q-fuel`/`q-fuel-t` уровень топлива (¼, ½, ¾, Полный), `q-checks` пункты чек-листа, `q-defect` «Есть дефекты?», `q-defect-text` «зона: описание» и `q-critical` первого дефекта; вопрос с ключом пункта чек-листа версии (форма из `FormDefinition` чек-листа W2.45) — результат пункта; вопросы, скрытые условием, не заполняются;
   - **дедупликация `trip:kind:rev` (Q-59, «как в прототипе»):** ключ `<рейс>:dep:rev1` у выезда (повторный выезд после «Подтвердить неисправность» второго ответа не пишет), `<рейс>:ret:rev1` у первой сдачи и `<рейс>:ret:rev2` у сдачи после доработки (третья сдача — тот же `rev2`); повторная доставка события ничего не дублирует (`events.Once` + уникальный `forms.responses (form_id, dedup_key)`);
   - правила формы выполняются в транзакции ответа (W4.21): «в БЗ» (au-2 — строка «Осмотры»), «задача» (au-1). Задача ответа осмотра — как в эталоне: «Проверить осмотр Р-208 (выезд)» / «(сдача)», срочная при блокирующем дефекте, чек-лист «Сверить фото с прошлым осмотром», «Проверить пробег», связи — ответ и рейс. «Повторить» в журнале ответа строит ту же задачу.
2. **Дефект → задача вместо очереди S2-17 (D-29 комплекта).** Проверка блокирующего дефекта — одна задача менеджеру:
   - при осмотре с блокирующим дефектом задача ответа (au-1) и есть задача дефекта: становится срочной, получает метку «дефект», связи «машина» и «дефект», исполнителя, назначенного дефекту, и строку истории «Связана с дефектом осмотра: {зона} — {описание}»;
   - нет формы, правила «задача» или правило отказало (журнал ответа) — задача дефекта W4.11 «Проверить дефект: {машина} — {зона}» в проекте области машины;
   - задача ответа уже завершена или связана с другим дефектом (повторный выезд с тем же ключом) — тоже своя задача дефекта;
   - `fleet.defect.assigned.v1` и `fleet.defect.decided.v1` (W4.11) находят задачу дефекта и по связи «дефект»: назначение переносится, решение завершает задачу строкой «Решение по дефекту: …»;
   - `fleet.defect.blocking_reported.v1` больше не создаёт задачу сам: задачу ставит потребитель осмотра (одна задача, без гонки двух потребителей одного осмотра).
3. **Очередь S2-17 и строки этапа 2 не меняются:** `listInspectionDefects`, `getInspectionDefect`, `decideInspectionDefect`, `assignInspectionDefect`, уведомление менеджерам, AC-04, строки изоляции `fleet.yaml` остаются зелёными — модуль `fleet/inspections` не правится.

## 10. Риски и решения по умолчанию

- Q-W4.24-1: форма осмотра — по имени «Осмотр машины» (уникально в организации), а не по id эталона `fm-insp`; настройки «форма осмотра» в контракте нет.
- Q-W4.24-2: `q-photos` — текст «N фото» (как сид и эталон), фото осмотра остаются файлами рейса; `q-checks` — все варианты, кроме тех, чья подпись входит в подпись неисправного пункта; ответы — от сервера без `pvCheck` (как сид).
- Q-W4.24-3: задача ответа осмотра — заголовок правила + « Р-208 (выезд)», срочная при блокирующем дефекте, чек-лист эталона; срок «01.10» эталона не переносится.
- Q-W4.24-4: блокирующий дефект — задача ответа становится задачей дефекта (одна задача, как в эталоне); `blocking_reported` задачу больше не создаёт; связь дефекта с задачей — `relatedObjects` `fleet/defect` (колонки `fleet.defects.task_id` нет, миграция — стюарду при необходимости).
- Q-W4.24-5: ответ пишется асинхронно (worker), а не в транзакции осмотра: сбой форм или задач не мешает водителю.
- Риск: e2e стенда с подсчётом ответов «Осмотра машины» или задач LOG после спеков водителя — проверяется полным `e2e:stand`.
