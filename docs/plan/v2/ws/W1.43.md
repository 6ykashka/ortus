## 1. Цель

1. **`updateMember`** (`PATCH /tenants/{tenantId}/members/{memberId}`, `members.manage`, If-Match) — последняя операция тега Access этапа 1 с ответом 501 (Q-W1.05-11). Приостановка и восстановление участника, перенос в другое подразделение, набор рабочих функций; инвариант «≥ 1 активный владелец» (02-architecture §4 «Последний владелец»), места тарифа при восстановлении, завершение сессий приостановленного. Операция попадает в `accessImplemented`.
2. **`commitPeopleImport` с `sendInvitations=true`** (Q-W1.05-10): адаптер `importer.Inviter` над приглашениями модуля доступа. Новые карточки импорта с почтой получают приглашение W1.03 (без ролей), места проверяются для всех сразу, письма уходят **только после COMMIT** обеих БД, как у `inviteMember` (Q-W1.41-1).
3. **Q-W1.41-10 (П-14)**: при выключенной почте (`mail.Off`, нет `SMTP_HOST`) исход `inviteMember` сохраняется в транзакции эффекта (`kit.Complete`), поэтому повтор с тем же `Idempotency-Key` после падения между COMMIT и записью исхода даёт replay 201, а не 422.
4. **Q-W1.41-8**: харнесс изоляции (`startAPI`) обнуляет `SMTP_HOST` для `cmd/api` — строка `inviteMember 201` не зависит от env стенда (санкция дана).
5. Попутно **Q-W1.47-4**: `TestAccessCommandsUnderSmallPool` покрывает `revokeAssignment`, `createGroup` и новую `updateMember`.

## 4. Контракты

Контракт API не меняется (тела, коды, тексты — по контракту и моку). Внутренние интерфейсы:

- `assignments.(*Handler).UpdateMember` — strict-метод тега Access.
- `assignments.Invitee{Person, Email, Unit, Line}`, `(*Handler).InviteCards(ctx, tc, fn func(tx pgx.Tx) ([]Invitee, error), complete func(tx pgx.Tx) error) (int, error)`: транзакция tenant под блокировкой `tenants` (control), приглашения в control, письма после COMMIT; `complete` вызывается в транзакции, когда писем по сети нет.

- `assignments.(*Handler).WithInvitationMail(m)`: отправитель `mail.Off` (доставка выключена) — как без почты (`mail == nil`, исход в транзакции).

## 10. Риски и решения по умолчанию

1. **Сессии.** `auth_sessions` — на аккаунт, не на организацию. Приостановка закрывает доступ к организации сразу (`Resolve`: неактивное членство → 404 на каждом запросе), `policy_version` +1 → `context.changed` (кэши возможностей). Сессии аккаунта отзываются, только если у него не остаётся других активных членств и он не оператор платформы: иначе приостановка в одной организации выкидывала бы человека из остальных. → decisionsNeeded.
2. **Кто приостанавливает владельца.** Только владелец (02-architecture: «Администратор не может снять владельца»); иначе 403. Последний активный владелец — 409 `last_owner_required` «Нельзя приостановить последнего владельца» (мок).
3. **Себя** приостановить нельзя: 409 `invalid_transition` «Нельзя приостановить себя.» (в прототипе нет; аналог control 0001 «нельзя отключать себя» у операторов). → decisionsNeeded.
4. **Карточка без аккаунта** (нет membership) — приостанавливать нечего: 409 `invalid_transition`. **Завершённое** участие — 409. → decisionsNeeded.
5. **Места.** Восстановление занимает место: `seats_used` (active + invited) + ожидающие приглашения ≥ лимит → 409 `seats_exhausted` с текстом мока. Приостановка место освобождает (`tenant_seat_usage` считает только active и invited).
6. **orgUnitIds** — одно подразделение (как `createMember`: у сотрудника одно домашнее); неизвестное и невидимое — один 422; видимое без `members.manage` — 403; архивное — 422. Перенос не меняет права человека — `policy_version` не растёт.
7. **workProfiles** — набор действующих функций: добавленные начинаются сейчас (бессрочно), снятые заканчиваются сейчас; «Водитель» человеку с начислениями или владельцу — 409 SoD (как W1.05). Рост `policy_version`.
8. **Импорт: кого приглашать.** Только создаваемые строки с почтой (мок приглашает создаваемых); строки без почты — карточки без приглашения; совпавшие (update/skip) не приглашаются. Места — на всех приглашаемых сразу (409 на весь импорт, ничего не записано); адрес участника или ожидающего приглашения — 422 «Строка N: …». → decisionsNeeded.
9. **Импорт: письма.** После COMMIT обеих БД, вне блокировок; письмо не ушло — приглашение отозвано (карточка остаётся — это результат импорта), `totals.invited` — число ушедших писем; ответ 200 (импорт применён). С почтой по сети исход сохраняет guard после писем (как `inviteMember`), без почты — `complete` в транзакции. Письма идут по одному: на большом файле с медленным SMTP ответ может выйти за `WriteTimeout` 30 с — outbox (Q-W1.41-1) снимет это вместе с реальным SMTP этапа 3. → decisionsNeeded.
10. **mail.Off.** Решение Q-W1.41-10 — вариант «`h.mail = nil`»: `WithInvitationMail` с отправителем `mail.Off` оставляет хендлер без почты (исход в транзакции эффекта). Строку журнала `mail: delivery is off` для каждого письма больше не пишет — при старте `cmd/api` уже пишет `api: mail enabled=false`.
11. **Изоляция.** `updateMember` требует If-Match, а формат строк его не передаёт (README изоляции): строки — только отказы шлюза; область на объекте (невидимый участник 404, AC-01) — integration T-4.
