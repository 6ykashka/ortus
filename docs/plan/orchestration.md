# Оркестрация: параллельные агенты, сборка, проверка

Документ описывает, как несколько агентов одновременно выполняют план `docs/plan/v2/00-parallel-plan.md` (дальше — «план v2»), не ломая друг другу код, и как результаты собираются и проверяются. Редакция v2 от 14.10.2026 (W0.00, план v2 §6). Прежняя рамка «волны 0–4» заменена этапами 0–8 плана реализации 27.

## 1. Единица работы — WS

Рабочий поток (WS) — самодостаточный бриф `docs/plan/v2/ws/W<этап>.<nn>.md`. Источники брифа:

- карточка из плана v2 §4;
- старый бриф из колонки «Было» (`docs/plan/ws/WS-NN-*.md`) с правками из `v2/analysis/D-plan-reconciliation.md` §4;
- анализы `docs/plan/analysis/*` и `docs/plan/v2/analysis/A…D`.

Бриф состоит из 11 разделов:

1. цель;
2. границы файлов (колонка «Владеет»);
3. входы (анализ новой итерации и истории этапа);
4. контракты — ссылка на контрактный PR шага, интерфейсы, типы, компоненты;
5. экраны, диалоги и состояния;
6. тесты, которые пишутся первыми;
7. шаги TDD;
8. проверка;
9. критерии готовности (DoD);
10. риски и решения по умолчанию;
11. промпт запуска.

Правила, которые делают WS параллельными:

- **Непересекающиеся каталоги.** Владелец каталога назначается на шаг. Два активных WS не пишут в один каталог. Горячие точки — корень OpenAPI, `permissions.yaml`, `errors.yaml`, миграции, баррели, сид, меню, матрица изоляции, lock-файлы, CI — сериализуются по плану v2 §3.5: пишет стюард или интегратор, либо файлы разложены по модулям.
- **Каждый шаг начинается с контрактного PR.** В него входят:
  - OpenAPI (`paths/<tag>.yaml`);
  - `permissions.yaml`, `errors.yaml`;
  - миграция с номером из блока этапа;
  - примеры;
  - `make gen` с проверкой дрейфа.

  Стюард контракта этапа — единственный, кто пишет в `api/**` и выдаёт номера миграций (PD-56, PD-59). После слияния контрактного PR MSW-хендлеры, backend, frontend и строки изоляции шага идут одновременно, не дожидаясь друг друга (план v2 §3.2).
- **Собственная ветка и worktree.** Каждый агент работает в `git worktree` на ветке `ws/<ID>` (например `ws/W1.04`) от актуального `main`. Коммиты оформляются по Conventional Commits (скил `git-commit`), сообщение передаётся через `git commit -F` в UTF-8 без BOM. В конце работы агент выполняет `git switch --detach`, чтобы освободить ветку для интегратора и продолжателя.
- **Ничего «на потом».** WS закрывается только с полным DoD (`tdd-protocol.md` §4, `verification-protocol.md`), иначе интегратор возвращает его. Если работу не позволяет сделать среда или решение, агент записывает блокер с точной причиной и выполняет остальное.

## 2. Этапы и подволны

Последовательность задаёт план 27: этап 0 → платформа → логистика (вертикальный пилот) → пилот → общие модули → склад, SPA, касса → ремонт → чаты, документы, обращения. Принцип старого плана «сначала весь UI на моках» (PD-15) отменён.

| Этап | Содержание | Реестр |
|---|---|---|
| 0 | Подготовка: решения, репозиторий, CI, стенд, контракт 0.1–0.3, `/me/context` сквозь стек, токены и 6 компонентов, ядро домена, MSW, скелет изоляции | план v2 §4 «Этап 0», подволны 0a–0d |
| 1 | Платформа: аудит и outbox, provisioning, OIDC, оценщик прав, структура и роли, канал реального времени, модули, файлы, входящие, оболочка | §4 «Этап 1», 1a–1d |
| 2 | Логистика — вертикальный пилот | §4 «Этап 2», 2a–2d |
| 3 | Запуск пилота | §4 «Этап 3» |
| 4–7 | Модули по шаблону: домен → контракт → backend ‖ frontend → изоляция и сквозной сценарий | §4 «Этапы 4–7» |
| 8 | Расширение (только после подтверждения спроса) | §4 «Этап 8» |

Внутри этапа WS собраны в подволны по зависимостям шагов. В подволне не больше 10 исполнителей. Подволна стартует, когда её входы влиты в `main`. Барьера между WS нет: зависящий WS стартует сразу после слияния своего входа (принцип «pipeline, не parallel»).

Каждый шаг идёт конвейером:

```text
contract(x.y) → mocks(x.y) → be(x.y) ‖ fe(x.y) ‖ isolation(x.y) → verify + integrate
```

**Опережающая дорожка (PD-55).** Во время этапа N два-три агента готовят этап N+1:

- DoR-сверщик (`W<N+1>.00`);
- перенос домена модулей;
- черновики контрактных PR в `api/drafts/`.

## 3. Роли агентов

- **Исполнитель WS** — реализует по `tdd-protocol.md`, проверяет по `verification-protocol.md`, возвращает отчёт (§5).
- **Стюард контракта** — один на этап:
  - ведёт очередь контрактных PR в порядке шагов;
  - единственный пишет в `api/**`, `screens.yaml`, `screen-labels.ts` и `errors.ts` словаря;
  - выдаёт номера миграций из блока этапа (план v2 §3.5);
  - делает `make gen` в том же PR.

  В скрипте Workflow это WS вида `contract`, его выполняет фаза «Контракт».
- **DoR-сверщик** — `W<N>.00` до старта этапа:
  - замораживает снимок эталона (тег `design-stage-N`, PD-57);
  - сверяет экраны прототипа с историями этапа;
  - обновляет анализ экранов;
  - собирает открытые вопросы в `decisions.md` и список экранов для дорисовки (вид allowlist `no-reference`).

  Только он обновляет `design/`, и только на границе этапа.
- **Проверяющий страницы** — отдельный агент на каждую закрытую страницу и режим (`mock` и, с этапа 1, `stand`). Заново запускает e2e, делает проходку через Playwright MCP, сверяет со снимком эталона этапа и пишет вердикт. Это не тот агент, что исполнитель. Одновременно работают не больше 6 проверяющих.
- **Ревьюер** — по скилу `requesting-code-review`. На WS один ревьюер, на authz, миграции, финансы и контрактные PR — два (CODEOWNERS).
- **Интегратор** — один на этап:
  - ребейзит ветки на `main` в порядке DAG этапа и разрешает только механические конфликты (смысловые возвращает исполнителю);
  - прогоняет полный CI и сливает;
  - отвечает за горячие точки плана v2 §3.5 (CI, `CLAUDE.md`, lock-файлы, `make examples`, общий стенд compose, Keycloak-smoke);
  - ведёт `docs/plan/v2/status.md`.

  Допустимо делить работу интегратора на UI и backend внутри этапа, но интегратор этапа один.
- **Критик полноты** — после подволны сверяет сделанное с историями и инвентарём экранов **этапа**, а не со всем прототипом. Найденные пропуски становятся WS.

## 4. Скрипт Workflow (шаблон)

Инструмент Workflow (Claude Code) запускает агентов по подволнам. Шаблон — `docs/plan/workflow.template.js`, аргументы — по образцу плана v2 §8. Тесты шаблона: `node --test "docs/plan/scripts/*.test.mjs"`. Схема:

```text
каждый WS подволны стартует, как только приняты его зависимости (dependsOn, needsContract: true);
по умолчанию зависимостей нет. WS вида contract идут по одному, последовательно (стюард, фаза «Контракт»).
Для каждого WS:
  agent(executePrompt(ws), {isolation: 'worktree', label: `ws:${id}` | `contract:${id}`}) // исполнитель
     → chunked(страницы × режимы, по полосам)  → agent(verifyPrompt(…, полоса))         // ≤ 6 проверяющих на всю подволну
     → parallel(ревьюеры: 1 или 2)
     → пока есть return или request-changes и итераций < 3:
          agent(fixPrompt(…), {isolation: 'worktree', label: `fix:${id}#n`})             // продолжатель той же ветки
          → повторная проверка всех страниц WS → повторное ревью
     → иначе escalated: true
→ agent(integratePrompt(…), {label: 'integrate'})                                         // интегратор подволны
→ agent(criticPrompt(…), {label: 'critic'})                                               // критик этапа
```

- Проверяющие и ревьюер получают **только** отчёт исполнителя и бриф, а не его рассуждения: так проверка остаётся независимой.
- Если проверяющий находит расхождение или ревьюер просит изменений, WS возвращается. В API скрипта Workflow нет SendMessage, поэтому возврат выполняет агент-продолжатель. Он получает бриф, прошлый отчёт, расхождения и блокирующие замечания, переключается на ту же ветку `ws/<ID>`, исправляет по TDD и дописывает в отчёт раздел «Возврат N». Итераций не больше 3, затем WS уходит интегратору с отметкой `escalated`.
- Зависимости внутри подволны задаются явно: `ws.dependsOn` — ID WS этой же подволны из колонки «Зависит от» плана v2 §4, `ws.needsContract: true` — зависимость от всех контрактных WS подволны. По умолчанию WS не ждёт никого, и фаза «Контракт» не становится барьером. Зависимости из прошлых подволн закрыты стартом подволны и в `dependsOn` не пишутся. Если зависимость не принята (эскалация или пропуск), зависящий WS не запускается и попадает в `skipped`, в том числе по цепочке.
- После любого возврата проверяющие заново проверяют все страницы WS, а не только вернувшиеся: продолжатель менял код.
- Порты: исполнитель занимает `5200/7200/8100 + slot` и `COMPOSE_PROJECT_NAME=ortus-s<slot>`. Проверяющий работает на полосе проверки 1…6 и порту `6100 + полоса`. Полоса вычисляется из слота WS и номера проверки, на полосе одновременно один проверяющий. Поэтому одновременные проверяющие не делят порт, а промпты не зависят от порядка завершения агентов и при resume берутся из кэша (план v2 §3.6).

## 5. Отчёт исполнителя (обязательный формат)

Файл `docs/plan/v2/reports/<ID>.md`. Тот же набор полей возвращается структурой `REPORT_SCHEMA` шаблона.

```markdown
# Отчёт <ID> <название>
- stage: <N> · step: <шаг плана 27> · stories: <S1-xx, …> · mode: mock | stand | none
- contractPr: <ветка или коммит контрактного PR шага; «—», если контракт не нужен>
- isolationRows: <файл и имена тестов строк матрицы изоляции; «—», если эндпоинтов нет>
## Сделано
- файлы и каталоги, коммиты (hash — subject)
## Тесты (red → green)
| Тест | Слой | Коммит red | Коммит green |
## Прогоны
<вывод pnpm test / go test ./... / pnpm e2e — дословно, последние 40 строк>
## Проверка MCP
- страницы и режимы: … ; снимки: docs/plan/evidence/<page-key>/
- расхождения с эталоном и что сделано
## Осталось fixme / открытые вопросы
- … (ссылка на PD- или D- в decisions.md)
## Контракты, которые я изменил
- … (только через контрактный PR стюарда)
## Блокеры
- … (точная причина: среда или решение)
```

## 6. Сборка и проверка подволны (интегратор)

1. `git fetch`. Для каждого WS подволны в порядке DAG этапа (план v2 §5 и колонка «Зависит от»; контрактные PR — первыми):
   - `git rebase main`, разрешить механические конфликты;
   - прогнать `pnpm lint`, `pnpm typecheck`, `pnpm test`, `go -C backend test ./...`, `node --test "docs/plan/scripts/*.test.mjs"`, `node docs/plan/scripts/renumber-decisions.mjs --check`.
2. Слить (squash) в `main`, поставить тег `stage-N-<ID>` (например `stage-0-W0.07`).
3. После всех WS подволны:
   - полный CI;
   - `pnpm e2e` на всех проектах;
   - визуальная сверка страниц подволны со снимком `design-stage-N`;
   - с этапа 1 — `pnpm e2e:full` на стенде (режим `stand`).
4. Обновить `docs/plan/v2/status.md`: строки WS (готово / возвращён / блокирован), ссылки на отчёты и evidence.
5. Вместо барьера волны — **критерий выхода этапа** (план v2 §4, «Выход из этапа N»). Следующий этап стартует, когда критерий выполнен в CI.
6. Запустить критика полноты. Его пропуски становятся WS этого или следующего этапа.

## 7. Границы автономии агентов

- Можно:
  - создавать файлы в границах WS;
  - добавлять тесты и моки;
  - добавлять зависимости с пином версии и отметкой для интегратора;
  - править свою строку в `docs/plan/v2/status.md`.
- Нельзя без стюарда или интегратора:
  - менять контракт (OpenAPI, `permissions.yaml`, `errors.yaml`, токены, пропсы общих компонентов);
  - менять CI и `CLAUDE.md`;
  - добавлять внешние сервисы в compose;
  - менять `design/` (эталон обновляет только DoR-сверщик на границе этапа);
  - менять чужие каталоги и lock-файлы.
- Любой вопрос, который меняет поведение относительно эталона, записывается в `docs/plan/decisions.md` (PD-) или передаётся владельцу продукта (D- комплекта). До решения действует значение по умолчанию (план v2 §2, §7).
