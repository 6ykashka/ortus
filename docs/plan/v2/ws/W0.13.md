## 1. Цель

После W0.13 приложение и тесты в режиме `mock` работают против MSW-сценарного сервера, который отвечает на **все 62 операции контракта этапа 1** (теги `Context`, `Auth`, `Platform`, `Billing`, `Access`, `Modules`, `Files`; бандл `0.3.0-stage1`) так же, как будет отвечать стенд:

- **Состояние** строится из сида домена W0.12 (`createSeed()`): организации, аккаунты, членства, подразделения, участники, группы, роли, назначения, модули; идентификаторы — UUID v5 по PD-30 (`seedUuid`), членства — `membership:<организация>:<аккаунт>` в области `platform`, как в Go-сиде W0.06. Атрибутов, которых нет в домене (канонические права ролей, манифесты модулей, подписка, место, файлы, входящие), сервер берёт из примеров `api/openapi/examples` (PD-43: примеры — снимки сценарного сервера).
- **Шлюз** повторяет `cmd/api` W0.09: сессия (401) → CSRF изменяющих (403) → оператор платформы (404) → членство и состояние организации (404/403) → `x-permissions` (403 `forbidden_action`) → хендлер; `If-Match` (428/412), `Idempotency-Key` (повтор с `Idempotency-Replayed`), `X-Request-Id`, `Cache-Control: private, no-store`, `ETag`. Операции без хендлера отвечают `501 not_implemented`, неизвестный путь под `/api/v1/` — `404`, как стенд.
- **Команды** с состоянием: приглашение и места, участник, роли, назначения (правило «Водитель» ↔ начисления — `separation_of_duties_conflict`, последний владелец), подразделения, группы, владельцы, «Почему доступно», импорт CSV, модули и настройки, подписка и место, загрузки файлов, входящие, переключатель организации, вход и приглашение.
- **Сценарии** (PD-31): заголовок `X-Test-Scenario: [<operationId>=]<сценарий>[, …]` — `<Problem.code>`, `empty`, `offline`, `delay=<мс>`, `loading`; пресеты состояния (`logistics-ready`, `seats-full`, `trial-ended`, `storage-full`); управление из e2e — `POST /api/v1/dev/scenario` (вне контракта, только `mock`).
- **Срез логистики** этапа 1: модуль `fleet` (домен `logistics`) подключается и отключается через `setModuleInstallation`, доступ логиста и водителя в `/me/context` следует назначениям; операции `Fleet` — `501` до W2.00 (`adapter/src/msw/fleet/`).
- **Conformance**: раннер `test/conformance/` (Vitest + `msw/node`), файл кейсов на модуль, каждый ответ проверяется ajv 2020-12 по схеме бандла; покрытие — каждая операция этапа 1 имеет кейс успеха и ошибки, каждый пример этих операций воспроизводится сервером (или записан как известное расхождение с причиной).
- **Подключение к `apps/web`** (точка подключения, отчёт W0.09): `VITE_ADAPTER=mock` → `startMockWorker()` до dev-входа; dev-вход `?persona=` (PD-54, контракт H11 из брифа W0.05 §4.4) обслуживает MSW. Снимается `fixme` с H11, smoke `me-context` включается в режиме `mock`.
- **Расхождение `membershipId`** (W0.09 п. 5): примеры `getMyContext/*`, `selectTenant/ok`, `acceptInvitation/ok` приводятся к сиду — `seedUuid('platform', 'membership:<t>:<acc>')`; ключи добавляются в `examples/seed-ids.yaml`. Контракт (`api/openapi/**` кроме `examples/`, `api/*.yaml`) не меняется.

## 4. Контракты (публикуются из `@ortus/adapter`; меняются аддитивно)

```ts
// @ortus/adapter/msw (и корень @ortus/adapter)
createScenarioServer(o?: { state?; now?: () => string; operations?: Registry; cookies?: CookieJar;
  origins?: string[]; onChange?: (s) => void }): ScenarioServer
interface ScenarioServer {
  handlers: HttpHandler[];                 // MSW 2: один диспетчер /api/v1/* (поиск операции — как opIndex cmd/api)
  handle(request: Request): Promise<Response>;  // тот же ответ без MSW (тесты шлюза)
  state(): ScenarioState;                  // текущее состояние (JSON-сериализуемо)
  reset(state?: ScenarioState): void;      // свежий сид или переданный снимок
  applyPreset(name: PresetName): void;     // 'logistics-ready' | 'seats-full' | 'trial-ended' | 'storage-full'
  setScenario(spec: string | null, once?: boolean): void;  // постоянный X-Test-Scenario (e2e без заголовков)
  setNow(at: string): void;                // часы сервера (по умолчанию — «сейчас» сида 2026-10-01T07:30:00Z)
}
createScenarioState(): ScenarioState       // проекция сида W0.12 + атрибуты из примеров
PERSONAS: Record<string, string>           // e2e-kit → acc-N / op-1, как session/dev W0.09
// @ortus/adapter/msw/browser
startMockWorker(o?: { persist?: boolean; url?: string }): Promise<ScenarioServer>  // состояние в sessionStorage
// @ortus/adapter/msw/node
createNodeServer(o?): { server: SetupServer; scenario: ScenarioServer }
// @ortus/adapter/vite (JS, для vite.config.ts)
mswWorker(): Plugin                        // отдаёт /mockServiceWorker.js из пакета msw
```

Реестр хендлеров (P3): `src/msw/<модуль>/` экспортирует `Registry` (`operationId → хендлер`), `src/msw/handlers.ts` собирает их одной строкой на модуль. Хендлер получает контекст шлюза (`ctx.org()`, `ctx.user()`, `ctx.revision(n)`, `ctx.newId()`) и возвращает тело или бросает `ProblemError`.

- Вне контракта (только `mock`, как dev-провайдер BFF): `POST /api/v1/dev/login {persona}` → `{userId, csrfToken}` + cookie; `POST /api/v1/dev/logout`; `POST /api/v1/dev/scenario {reset?, preset?, scenario?, once?, now?, scanFiles?}` и `GET /api/v1/dev/scenario` → сводка (часы, сценарий, пресеты, токены приглашений).
- `X-Test-Scenario` (PD-31): `forbidden_action`, `listMembers=empty`, `getMyContext=offline`, `delay=300`, `loading`. Код ошибки применяется, только если операция объявляет его статус; тело — пример операции `<код>.json`, иначе Problem по реестру.
- Conformance (`test/conformance/`): `ConformanceCase { id; title; module; operationId; example?; ignore?; run(ctx) }`; `ctx.as(persona)` — клиент с cookie-сессией, CSRF, `Idempotency-Key`; каждый ответ — ajv по схеме операции и статусу из `responses`. Режим `mock` — `msw/node`; интерфейс цели оставляет место раннеру `stand` (W1.x).
