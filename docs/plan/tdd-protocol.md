# Протокол TDD для модулей Ортус

Этот документ обязателен для каждого агента, который реализует рабочий поток (WS) плана `docs/plan/v2/00-parallel-plan.md` (брифы `docs/plan/v2/ws/`). Редакция v2 от 14.10.2026 (W0.00): строки изоляции пишутся до хендлера, e2e проходят в режимах `mock` и `stand`. Документ описывает, как именно «сначала тест, потом код» применяется на каждом слое, какие тесты пишутся до реализации, и что считается красным, зелёным и рефакторингом.

## 1. Цикл

Один цикл = одна проверяемая единица поведения (правило домена, обработчик API, компонент, экран).

1. **Red.** Написать тест, который формулирует требование словами источника (`docs/plan/analysis/*.md`, `design/docs/**`). Запустить, убедиться, что он падает по ожидаемой причине (не из-за опечатки или отсутствующего импорта). Зафиксировать коммитом `test(<scope>): …`.
2. **Green.** Написать минимальный код, который делает тест зелёным. Не добавлять поведение, которого нет в тесте. Коммит `feat(<scope>): …` или `fix(<scope>): …`.
3. **Refactor.** Убрать дублирование, привести к стилю скилов (`golang-code-style`, `golang-naming`, `vercel-react-best-practices`), прогнать линтеры. Тесты остаются зелёными. Коммит `refactor(<scope>): …`.
4. Повторить для следующей единицы. Один коммит не должен смешивать red и green разных единиц.

Запрещено: писать реализацию до теста; «подгонять» тест под случайно получившееся поведение; помечать тесты `skip` без ссылки на открытый вопрос в `docs/plan/decisions.md`.

## 2. Порядок написания тестов внутри WS

Для каждого WS тесты пишутся сверху вниз по пирамиде из `design/docs/15-quality-security.md`, но **первым всегда пишется e2e-скелет страницы** в состоянии `test.fixme`, чтобы критерий приёмки был зафиксирован до любой реализации:

| Шаг | Слой | Инструмент | Что фиксируется |
|---|---|---|---|
| 1 | E2E-скелет | Playwright, `frontend/apps/web/e2e/<page>.spec.ts` | Чек-лист приёмки из анализа экрана (`docs/plan/analysis/*.md`, дельта `v2/analysis/A`) и истории этапа → один `test()` на пункт, все в `test.fixme()` |
| 2 | Домен | Vitest (`packages/domain`), `go test` (`backend/internal/...`) | Правила: `compat`, `legs`, `inspMissing`, `odoError`, `validateExpense`, `bookingConflicts`, `permit()`, `scopeQuery()` и правила модулей — на примерах из `07-domain-and-adapter.md` и `v2/analysis/B`; тесты паритета с `ortus/*.js` итерации этапа |
| 3 | Контракт | `oapi-codegen` strict server + Spectral; Vitest на `openapi-fetch` клиенте с MSW | Каждая операция из контрактного PR шага, которую трогает WS: тело запроса, коды ответов, `Problem.code`. Контракт приходит контрактным PR стюарда (`orchestration.md` §1), WS его не меняет |
| 4 | Изоляция (строки матрицы) | Go-тесты на фикстурах `backend/test/isolation/<m>_test.go` + `isolation/<m>.yaml` | **Красные до хендлера** (правило 3 плана 27): для каждого нового эндпоинта — чужой тенант, чужая фирма или область → 404, функция driver → нет начислений. Набор изоляции блокирует merge с первого эндпоинта |
| 5 | Интеграция | testcontainers-go (PostgreSQL 17, MinIO) | Репозитории, транзакции, ограничения, outbox |
| 6 | Конкурентность | Go-тесты `backend/test/concurrency` | 100 параллельных броней → 1×201 + 99×409; старт рейса, приёмка |
| 7 | Компоненты | Vitest + Testing Library + axe (`packages/ui`) | Состояния, клавиатура, aria, контраст |
| 8 | Экран | Vitest + Testing Library + MSW (`apps/web/src/routes/**`) | Состояния экрана: обычное, пусто, загрузка, ошибка, нет права, конфликт, офлайн, только чтение |
| 9 | E2E | Playwright, снятие `fixme` по одному | Пункты чек-листа приёмки проходят на телефоне 390 и десктопе 1440 в режиме `mock`, а для страниц пилота с этапа 1 — ещё и в режиме `stand` |
| 10 | Визуальная сверка | Playwright `toHaveScreenshot` против снимка эталона этапа | См. `docs/plan/verification-protocol.md` §3 |

Шаги 2–8 выполняются по циклу Red → Green → Refactor; шаг 9 закрывает каждый `fixme` отдельным циклом. Строки изоляции шага 4 остаются красными, пока хендлер не написан: их red-коммит идёт раньше коммита хендлера, а green — вместе с ним или после. Frontend-WS шаги 4–6 не выполняет. Backend-WS без страниц пропускает шаги 1, 7–10.

## 3. Соглашения по тестам

### Go

- Файлы `*_test.go` рядом с кодом; табличные тесты с полем `name`; `t.Parallel()` там, где нет общего состояния.
- Доменные ошибки сравниваются через `errors.Is`; HTTP-ошибки — по `Problem.code` из `design/docs/12-errors-and-events.md`.
- Интеграционные тесты под build tag `integration`, изоляция и конкурентность — тег `isolation`, `concurrency`; они блокируют merge (CI).
- Фикстуры изоляции — единый сид из `design/docs/15-quality-security.md` «Фикстуры изоляции» (тенант A «Холдинг», тенант B «Чужой клиент», менеджеры Москва-1/2, водители, пользователь с двумя ролями).
- Правила скилов `golang-testing`, `golang-error-handling`, `golang-context` обязательны; расхождения с ними фиксируются в PR.

### TypeScript

- Vitest, `describe` по единице поведения, имена тестов — на русском, формулировка из источника: `it('пробег при сдаче не меньше пробега при выезде', …)`.
- Компоненты тестируются через Testing Library по ролям и подписям, не по классам. Каждый компонент имеет axe-тест.
- Сетевые вызовы мокаются MSW по OpenAPI: сценарный сервер на сиде прототипа, хендлеры собраны из примеров контракта (`frontend/packages/adapter/src/msw/<m>/`). Сценарии ошибок задаются через `X-Test-Scenario`. Прямой мок `fetch` запрещён.
- Экраны тестируются через роутер в памяти с `QueryClient` без retry.

### Playwright (E2E)

- Один spec на страницу: `e2e/<page-key>.spec.ts` (ключ из инвентаря экранов: `home`, `modules`, `users`, `review`, `driver-today`, …).
- Селекторы: `getByRole`, `getByLabel`, `getByText` с дословными подписями из прототипа. `data-testid` — только когда у элемента нет доступного имени; это сигнал проверить a11y.
- Проекты: `mobile-390` (Pixel-подобный, 390×844, touch), `tablet-768`, `desktop-1440`. Каждый пункт чек-листа гоняется минимум на `mobile-390` и `desktop-1440`.
- Данные, режим `mock`: приложение в e2e-сборке работает против MSW-сценарного сервера на сиде прототипа. Идентификаторы те же (`Р-208`, `m-kotova`, `t-alta`, `t-lotos`), что в `design/ortus/mock-data.js` и `extra-data.js` снимка этапа. Персонаж выбирается dev-входом `?persona=` только в e2e-сборке: демо-панели в реализации нет (PD-54).
- Данные, режим `stand` (с этапа 1): тот же spec идёт против стенда compose — миграции, Go-сид (`make seed`), dev-провайдер входа. Для страниц пилота оба режима обязательны в одном шаге. Расхождения стенда — дефект backend или запись allowlist с решением.
- Запрещены `waitForTimeout` и условные ожидания; используются авто-ожидания и `expect.poll`.

## 4. Definition of Done единицы

- Все тесты шагов 2–9 зелёные локально и в CI (режимы `mock` и, где положено, `stand`); визуальная сверка в допуске; строки матрицы изоляции нового эндпоинта зелёные.
- Линтеры: `golangci-lint`, `eslint`, `prettier`, `spectral` — без ошибок.
- Покрытие домена ≥ 90 % строк (`packages/domain`, `backend/internal/platform/authz`, `backend/internal/modules/*/service*`), остальное — без порога, но каждый `Problem.code` покрыт хотя бы одним тестом.
- Чек-лист приёмки страницы (из `analysis`) полностью снят с `fixme`; если пункт не может быть закрыт — он остаётся `fixme` с ссылкой на вопрос в `decisions.md`, и это явно указано в отчёте агента.

## 5. Как агент отчитывается

В конце WS агент возвращает отчёт по шаблону `docs/plan/orchestration.md` §5 (`docs/plan/v2/reports/<ID>.md`). В отчёте:

- `stage`, `step`, `stories`, `mode`, `contractPr`, `isolationRows`;
- список тестов (red → green) и что осталось `fixme`;
- вывод прогонов (`pnpm test`, `go test ./...`, `pnpm e2e`);
- ссылки на коммиты.

Отчёт без вывода прогонов интегратор не принимает.
