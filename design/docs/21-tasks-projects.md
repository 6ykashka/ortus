# 21. Задачи и проекты: разбор Jira и предложение для Ортуса

Версия 0.2 · 8 октября 2026 года. Статус: реализовано в прототипе (D-27). Экран — `Задачи и проекты.dc.html`, встроен в раздел «Задачи» CRM. Макеты: `Задачи - варианты.dc.html` (корень), 1a–1e.

## Реализация в прототипе

- **Проекты:** список доступных проектов и форма создания — название, ключ (автоматически по названию), область, уровень доступа, процесс «Простой / С согласованием / Копия проекта». Создатель становится руководителем проекта. «Заявки · Ремонт» открывает прежнюю воронку.
- **Доска:** колонки по статусам процесса, фильтры «Мои» и «Ждут моего согласия», быстрое создание. Карточка: доступные переходы и причина недоступных, согласование (кто согласовал, кто ждёт, «Вернуть на доработку» с обязательным комментарием), исполнитель, приоритет, чек-лист, история.
- **Участники:** уровень доступа; добавление с ролью проекта (назначение с областью `project` в `assignments`); «Откуда доступ»; проверка «может ли и почему нет»; состав ролей. Открытый проект передаёт все права ролей области, ограниченный — только чтение, закрытый — ничего.
- **Процесс:** статусы по категориям, переходы. У перехода настраиваются «Кто может», согласование («достаточно одного» или «нужны все», куда вернуть при отказе), «не автор», комментарий, чек-лист, «назначить на автора». Правки идут в черновик; публикация не двигает задачи и не проходит, если задачи стоят в удалённом статусе.
- **Автоматизация:** «задача создана» или «перешла в статус»; условие по приоритету; действия: назначить, приоритет, комментарий. Правило работает от имени автора с проверкой права; изменения правил другие правила не запускают. В журнале видны успехи, остановки по условию и ошибки.
- **Роли проекта** (шаблоны в «Пользователях и ролях»): Руководитель проекта, Согласующий, Исполнитель, Наблюдатель. Вербы прототипа: view, create, edit (менять статус), review (согласовывать), settings.
- **Демо:** проект LOG — ограниченный, процесс с согласованием; задача T-65 «Заменить шины» ждёт согласования, автор Илья Васильев сам согласовать не может; два правила автоматизации.
- **API прототипа:** `createProject`, `updateProject`, `setProjectRole`, `initProjectWorkflow`, `saveWorkflowDraft`, `publishWorkflow`, `createProjectTask`, `runTransition`, `rejectApproval`, `setTaskField`, `saveAutomation`, `toggleAutomation`, `deleteAutomation`. Проверки прав — `projAccess`, `projCan`, `trCheck`, `approversOf` в `ortus/models.js`.
- **Пока нет:** общие схемы процесса, срок и эскалация согласования, «все по очереди», события других модулей как триггеры, повтор ошибок автоматизации.

## Создание задачи и вложения

**Как в Jira.** Кнопка «Создать» открывает диалог: пространство, тип работы, начальный статус, тема (обязательная), описание в редакторе с форматированием, исполнитель со ссылкой «Назначить меня», приоритет, метки, срок, родительская задача, связи и поле вложений. Файлы перетаскивают в диалог или в открытую задачу, скриншот вставляют из буфера прямо в описание. Галочка «Создать ещё» оставляет диалог открытым для следующей задачи, после создания показывается ссылка на новую задачу. Набор полей и их обязательность задаёт конфигурация полей пространства и типа работы. На вложения есть отдельные права пространства: «Создавать вложения», «Удалять свои», «Удалять все». Размер файла ограничивает администратор.

**Как у нас.** Кнопка «Задача» при пустом быстром поле открывает диалог «Новая задача»; с текстом в поле — создаёт задачу сразу.

| Что | Решение | Почему |
|---|---|---|
| Поля диалога | Проект (только те, где есть «Создавать»), начальный статус (только чтение), тема*, описание до 5000 символов, вложения, исполнитель и «Назначить меня», приоритет, срок, метки | Те же поля, что у Jira, без типа работы и конфигурации полей (TP-05) |
| Исполнитель | Только те, кто видит проект | Нельзя назначить задачу тому, кто её не увидит |
| Вложения | Перетаскивание, выбор с устройства, вставка скриншота в описание. Фото, PDF, документы Office, текст, ZIP; до 20 МБ каждый, до 30 на задачу. Неподходящий файл помечается с причиной до отправки | Ошибка видна сразу, а не после сохранения |
| Права на файлы | Прикрепить при создании — право «Создавать»; к существующей задаче — «Менять статус». Свой файл удаляет автор, чужие — руководитель проекта. Файл виден тем, кто видит задачу | Отдельных прав на вложения, как в Jira, не заводим: действуют роли проекта |
| История | Добавление и удаление файла пишутся в историю задачи | Видно, кто и когда приложил счёт |
| «Создать ещё одну» | Диалог остаётся открытым; проект, исполнитель, приоритет и срок сохраняются, тема, описание, метки и файлы очищаются | Как в Jira |

В карточке задачи есть блок «Описание» с метками и «Вложения»: кнопка «Прикрепить», перетаскивание на карточку, миниатюры фото. API: `createProjectTask({ …, description, labels, files })`, `addTaskFiles`, `removeTaskFile`, `setTaskField({ description })`. В прототипе файлы живут до перезагрузки страницы; в продукте они идут в общее хранилище `core.files` и считаются в квоту организации.

Пока нет: форматирование и упоминания в описании, редактирование описания в карточке, подзадачи и связи при создании, черновик незавершённой задачи.

## Связи задач: «входит в» и «состоит из»

**Как в Jira.** Два механизма. Иерархия через поле «Родитель»: эпик → задача → подзадача, у родителя видны дочерние с прогрессом, переход можно запретить, пока подзадачи не завершены. И связи между задачами с типами «блокирует / заблокирована», «связана с», «дублирует»; связи не влияют на иерархию.

**Как у нас (иерархия).**

- У задачи один родитель (`task.parent`), до трёх уровней, без циклов. Родитель — видимая вам незавершённая задача любого проекта с процессом.
- Карточка задачи, блок «Связи»: «Входит в» со ссылкой и «Убрать связь»; «Состоит из» с прогрессом «N из M готово», статусами и кнопкой «Исключить из состава»; «＋ Подзадача» открывает диалог с заполненным «Входит в задачу»; «Добавить существующую…» добавляет задачу без родителя. Переход по ссылке открывает задачу в её проекте.
- Диалог создания: поле «Входит в задачу». На доске: «↳ LOG-…» у подзадачи, «☰ 1/2» у родителя.
- Процесс: флажок перехода «Подзадачи должны быть завершены» (по умолчанию включён у «Принять» и «Согласовать»). Недоступный переход объясняет: «Сначала завершите подзадачи: …». Завершённой считается задача в статусе категории «Готово» (в том числе «Отменена»).
- Права: менять связь может тот, кто может менять дочернюю задачу и видит родителя. Если родитель или часть подзадач в недоступном проекте, названия не показываются, только факт связи и количество. Изменения связей пишутся в историю обеих задач.
- API: `setTaskParent(taskId, parentId | null)`, `createProjectTask({ …, parent })`; `childrenOf`, `isDone` и проверка `tr.children` в `trCheck` (`ortus/models.js`).
- Демо: T-66 «Подготовить парк к зиме» состоит из T-65 (шины) и T-58 (ТО).

**Следующий шаг (TP-07).** Связи без иерархии: «блокирует / заблокирована» с правилом перехода «нельзя начать, пока блокирующая не готова», и «связана с». Нужно ли автоматически закрывать родителя, когда готовы все подзадачи, — решает правило автоматизации (новый триггер «все подзадачи готовы»).

## Что есть сейчас

- Задачи привязаны к проекту (LOG, ЗАЯ, SPA). Статусы — фиксированный список на проект, есть чек-лист, источник задачи (ответ формы и правило).
- Права `core.tasks` в `11-permissions.yaml`: `tasks.projects.read/manage`, `tasks.read/create/update/transition`, области `tenant`, `unit`, `project`, `self`. Права согласовывать нет, процесс и автоматизация не настраиваются.

## Как это устроено в Jira

**Пространства (бывшие проекты).** Задачи (в Jira теперь «рабочие элементы») живут в пространстве с ключом: ключ даёт номера LOG-1, LOG-2. Пространства бывают двух видов: командные, где настройки свои, и общие, где процесс, поля и права задаются схемами, общими для нескольких пространств. Уровень доступа: открытое, ограниченное или закрытое.

**Люди и роли.** Права выдаются ролями пространства («Администратор», «Участник», «Наблюдатель» и свои). В общих пространствах роли подставляются в схему прав, поэтому одна роль может значить разное в разных пространствах.

**Процесс.** Статусы трёх категорий: «К выполнению», «В работе», «Готово». Переходы связывают статусы. У перехода три вида правил:
- **ограничить** — кто и когда может выполнить переход: исполнитель, автор, роль, группа, значение поля, пройденный статус, подзадачи. Если ограничение не выполнено, кнопки перехода не видно;
- **проверить** — поля и данные перед переходом. Если проверка не прошла, переход не выполняется и показывается ошибка;
- **выполнить действия** — после перехода: назначить, заполнить поле, создать связанную задачу, отправить событие.

**Согласования.** Ограничение «нужно согласование» есть в старших тарифах. В Jira Service Management согласование — отдельный шаг процесса, согласующие берутся из поля. Распространённая вариация — запрет согласовывать собственную задачу (разделение обязанностей).

**Автоматизация.** Правило: триггер → условия → действия, переменные вида `{{issue.key}}`, ветвления, журнал аудита. Правило с невыполненным условием останавливается молча. Главная ловушка — триггер «задача изменена»: правило меняет задачу, этим снова запускает себя, и получается цикл.

**Остальное.** Доски (Scrum, Kanban) с лимитами колонок, язык запросов JQL, сохранённые фильтры, схемы полей, экранов и уведомлений, типы работ, связи между задачами, подзадачи.

## Предложение

### Принципы

1. **Одна система прав.** Участие в проекте — это назначение роли из «Пользователей и ролей» с областью «проект» (область `project` уже есть в каталоге). Роли в проекте — обычные роли организации, своих ролей у проекта нет. Одна роль значит одно и то же во всех проектах. В этом отличие от схем прав Jira.
2. **Наследование.** Роль, выданная в фирме или регионе, действует в проектах этой области по уровню доступа проекта. В списке участников видно, откуда у человека доступ. Унаследованный доступ меняется только в «Пользователях и ролях».
3. **Причины вместо исчезающих кнопок.** Jira скрывает недоступный переход. У нас переход остаётся видимым и объясняет, почему закрыт: нет права, вы автор, нужна согласованная заявка. Для руководителя есть проверка «может ли сотрудник X сделать Y».
4. **Версии.** Процесс и правила автоматизации версионируются, как формы. Сначала черновик, потом публикация. При публикации задачи не переходят в другие статусы, новые правила действуют со следующего перехода. Запуски и согласования запоминают номер версии.
5. **Функции защищают данные.** Ограничения функций (например, «Водитель» не видит финансовые поля) действуют и в задачах, даже если роль даёт доступ к проекту.

### Макеты

| ID | Экран | Главное |
|---|---|---|
| 1a | Проекты и мастер создания | Шаблон → основное и доступ → процесс. Ключ, область (фирма, регион, организация), три уровня доступа. Процесс: «из шаблона», «копия проекта», «общая схема» |
| 1b | Участники | Роль в проекте — наша роль с областью «проект». Колонка «Откуда доступ» (назначен, группа, наследуется). Матрица ролей проекта, проверка «может ли и почему нет» |
| 1c | Процесс | Статусы по категориям, список переходов. У перехода: кто может, согласование, проверки, действия. Черновик v5 при действующей v4, «Проверить на задаче», «Опубликовать» |
| 1d | Доска и карточка | Быстрые фильтры вместо JQL («Ждут моего согласия»), лимит колонки. Карточка: блок согласования, доступные переходы, причина недоступного, связи с машиной и ответом формы, история с действиями автоматизации |
| 1e | Автоматизация | «Когда — если — тогда» с событиями модулей (рейс завершён, ответ формы принят). Выполняется от имени автора с проверкой прав. Журнал запусков с остановками по условию, предупреждениями и повтором ошибок |

### Согласование

- Задаётся в переходе. Согласующие — по роли в области задачи (например, «руководитель фирмы задачи»), конкретные люди или поле-сотрудник.
- Режимы: «достаточно одного», «все по очереди», «все сразу».
- Автор задачи не согласует свою, если это включено в переходе.
- Срок, напоминание и эскалация. Отказ возвращает задачу в выбранный статус, комментарий обязателен.
- Дополнительного согласующего может добавить автоматизация: например, при сумме больше 30 000 ₽ (1d).

### Автоматизация

- События модулей CRM как триггеры: рейс завершён, ответ формы принят, этап объекта сдан. Плюс изменения задач и расписание.
- Правило выполняется от имени автора. При каждом запуске проверяются его права, как у действий форм (D-26). Если право отозвали, запуск завершается ошибкой с кнопкой «Повторить».
- Правило не запускается от изменений, которые сделало само. Так исключены циклы.
- В журнале видно «остановлено условием»: в Jira такие запуски не отражаются. Предупреждения тоже видны, например «нет сотрудника с ролью, назначено руководителю».

### Новые права для `11-permissions.yaml`

```yaml
tasks.approve:          { level: review,   label: Согласовывать,             scopes: [tenant, unit, project] }
tasks.members.manage:   { level: settings, label: Управлять участниками,     scopes: [tenant, unit, project], sensitivity: sensitive, note: "делегирует только то, что имеет сам" }
tasks.workflow.manage:  { level: settings, label: Настраивать процесс,       scopes: [tenant, unit] }
tasks.automation.manage:{ level: settings, label: Настраивать автоматизацию, scopes: [tenant, unit, project], sensitivity: sensitive }
```

Шаблоны ролей проекта: «Руководитель проекта» (всё, кроме создания ролей), «Согласующий» (читать, согласовывать), «Исполнитель» (читать, создавать, менять статус своих), «Наблюдатель» (читать).

### Набросок данных

```text
project    { id, key, name, unit, access: open|limited|closed, workflow: { id, mode: copy|shared, version } }
workflow   { id, versions[{ v, statuses[{ id, name, cat: todo|progress|done }],
             transitions[{ id, from[], to, name, who: { roles[], groups[], fields[], notAuthor },
                           approval?: { mode: any|seq|all, approvers[{ kind: role_in_scope|member|field, ref }], due, escalateTo },
                           checks[], actions[] }] }] }
assignment { member, role, scope: { type: project, id } }          — существующая таблица назначений
task       { …, workflowVersion, approvals[{ transition, mode, steps[{ member, decision, at, comment }] }] }
automation { id, project, trigger, conds, actions, by, byId, version, on }
run        { at, rule, rv, result: ok|stopped|warn|error, text, refs[] }
```

### Что не берём сейчас

- **Язык запросов JQL.** Вместо него быстрые фильтры и сохранённые представления.
- **Схемы полей и экранов.** Поля задаются в проекте; шаблоном полей может служить форма.
- **Спринты, оценки, интеграции с разработкой.** Для логистики, ремонта и салонов они не нужны.
- **Отдельные схемы уведомлений.** Уведомления настраиваются по ролям в настройках проекта.

## Открытые вопросы

- **TP-01.** Нужно ли делегировать согласование на время отсутствия, и кто его назначает?
- **TP-02.** Руководитель проекта только назначает существующие роли или может предлагать новые? Создание ролей сейчас — `roles.manage`, область `tenant`.
- **TP-03.** Должны ли руководители вышестоящей области по умолчанию видеть закрытые проекты как наблюдатели?
- **TP-04.** Кто меняет общую схему процесса, если её проекты в разных фирмах?
- **TP-05.** Поля задач: фиксированный набор плюс свои поля проекта или поля из формы-шаблона?
- **TP-06.** Как переносить существующие задачи (LOG, ЗАЯ, SPA) в процесс с версиями: одна версия v1 на проект по текущим статусам?
