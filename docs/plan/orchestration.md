# Оркестрация: параллельные агенты, сборка, проверка

Как выполнять план `docs/plan/00-master-plan.md` силами нескольких агентов одновременно, не ломая друг другу код, и как результаты собираются и проверяются.

## 1. Единица работы — WS

Рабочий поток (WS) — самодостаточный бриф в `docs/plan/ws/WS-NN-*.md` с полями: цель, входы (ссылки на `docs/plan/analysis/*`), границы файлов (какие каталоги WS имеет право менять), контракты с другими WS (интерфейсы, типы, операции OpenAPI, компоненты), список тестов, которые пишутся первыми, чек-лист приёмки, команда проверки, размер.

Правила, которые делают WS параллельными:

- **Непересекающиеся каталоги.** Два активных WS не пишут в один каталог. Общие точки (`packages/ui`, `api/openapi/ortus.yaml`, `packages/domain`) принадлежат одному WS на волну; остальные используют их только через опубликованный контракт.
- **Контракт раньше реализации.** Волна 0 выпускает контракты: OpenAPI, `permissions.yaml`, токены, список компонентов `@ortus/ui` с пропсами, типы домена, сид. Все последующие WS пишут тесты против этих контрактов и MSW-моков, не ожидая реализацию соседей.
- **Собственная ветка и worktree.** Каждый агент работает в `git worktree` на ветке `ws/NN-<slug>` от `main`. Коммиты по Conventional Commits (скил `git-commit`).
- **Ничего «на потом».** WS закрывается только с полным DoD (`tdd-protocol.md` §4, `verification-protocol.md`), иначе интегратор возвращает его.

## 2. Волны

Волна — набор WS, которые можно выполнять одновременно, потому что их входы уже есть в `main`. Состав волн — в `00-master-plan.md` §6 (DAG). Общий принцип:

| Волна | Содержание | Параллельность |
|---|---|---|
| 0 | Скелет репозитория, CI, compose, контракт, токены, домен, сид, e2e-харнесс, превью эталона | 5–7 агентов |
| 1 | Оболочка приложения и `@ortus/ui`; просмотрщик документации; backend-платформа (сессии, tenant resolver, authz) | 3–5 агентов |
| 2 | Страницы на mock-адаптере по модулям (компания, платформа, логистика, главная/формы/задачи, календарь/БЗ/данные/файлы, SPA/касса/ремонт) | 6–10 агентов |
| 3 | Backend-модули S1–S2 (структура, роли, модули, файлы, логистика), подключение http-адаптера | 4–6 агентов |
| 4 | Остальные backend-модули (S3+), PWA/офлайн, нагрузочные и restore-проверки | по готовности |

Внутри волны нет барьера между WS: как только WS закрыт и влит, зависящие от него WS следующей волны стартуют (pipeline, не parallel).

## 3. Роли агентов

- **Исполнитель WS** — реализует по `tdd-protocol.md`, проверяет по `verification-protocol.md`, возвращает отчёт (§5).
- **Проверяющий страницы** — отдельный агент на каждую закрытую страницу: заново запускает e2e, делает проходку через Playwright MCP, сверяет с эталоном, пишет вердикт. Не тот же агент, что исполнитель.
- **Ревьюер** — по скилу `requesting-code-review`; 1 ревьюер на WS, 2 — для authz/миграций/финансов.
- **Интегратор** — один на волну: ребейз веток на `main` в порядке DAG, разрешение конфликтов (только механических; смысловые возвращаются исполнителю), прогон полного CI, слияние, запуск следующей волны.
- **Критик полноты** — после каждой волны сверяет сделанное с инвентарём экранов и реестром требований (`analysis/00-coverage-critique.md`, `08-requirements.md`), выдаёт список пропусков → новые WS.

## 4. Скрипт Workflow (шаблон)

Инструмент Workflow (Claude Code) запускает агентов по волнам. Шаблон — `docs/plan/workflow.template.js`. Схема:

```text
phase('Волна N')
pipeline(WS_WAVE_N,
  ws => agent(briefPrompt(ws), {isolation: 'worktree', label: `ws:${ws.id}`}),      // исполнитель
  (report, ws) => parallel(ws.pages.map(p => () => agent(verifyPagePrompt(p, report), {label: `verify:${p}`}))),  // проверяющие страниц
  (verdicts, ws) => agent(reviewPrompt(ws, verdicts), {label: `review:${ws.id}`}),  // ревьюер
)
→ agent(integratePrompt(wave), {label: 'integrate'})                                   // интегратор (барьер по волне)
→ agent(criticPrompt(wave), {label: 'critic'})                                         // критик полноты
```

Проверяющие страницы и ревьюер получают **только** отчёт исполнителя и бриф, но не его рассуждения — чтобы проверка была независимой. Если проверяющий находит расхождение, WS возвращается исполнителю (тот же агент продолжает через SendMessage), счётчик итераций ≤ 3, затем эскалация интегратору.

## 5. Отчёт исполнителя (обязательный формат)

```markdown
# Отчёт WS-NN <название>
## Сделано
- файлы/каталоги, коммиты (hash — subject)
## Тесты (red → green)
| Тест | Слой | Коммит red | Коммит green |
## Прогоны
<вывод npm run test / go test ./... / npm run e2e — дословно, последние 40 строк>
## Проверка MCP
- страницы: … ; снимки: docs/plan/evidence/<page-key>/
- расхождения с эталоном и что сделано
## Осталось fixme / открытые вопросы
- … (ссылка на decisions.md)
## Контракты, которые я изменил
- … (должны быть согласованы с интегратором до слияния)
```

## 6. Сборка и проверка волны (интегратор)

1. `git fetch`; для каждого WS волны в порядке DAG: `git rebase main`, разрешить механические конфликты, прогнать `npm run lint && npm run typecheck && npm run test && go -C backend test ./...`.
2. Слить (squash) в `main`; тег `wave-N-wsNN`.
3. После всех WS волны: полный CI, `npm run e2e` на всех проектах, визуальная сверка всех страниц волны, `npm run e2e:full` (фаза 2).
4. Обновить `docs/plan/status.md`: таблица WS → состояние (готово / возвращён / блокирован), ссылки на отчёты и evidence.
5. Запустить критика полноты; его пропуски становятся WS следующей волны.

## 7. Границы автономии агентов

- Можно: создавать файлы в границах WS, добавлять тесты и моки, добавлять devDependencies с пином версии, править `docs/plan/status.md` в своей строке.
- Нельзя без интегратора: менять контракт (OpenAPI, permissions, токены, пропсы общих компонентов), менять CI, добавлять внешние сервисы в compose, менять `design/` (эталон неприкосновенен), менять чужие каталоги.
- Любой вопрос, который меняет поведение относительно прототипа, записывается в `docs/plan/decisions.md` и решается владельцем продукта; до решения реализуется поведение прототипа.
