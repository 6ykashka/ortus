## Сделано

- **`backend/internal/platform/tenantctx`** (resolver без запасной БД, S1-02):
  - `CheckDatabaseName(name, reserved...)`. Пустое имя (путь DSN «/» — база по умолчанию роли), `postgres`, `template0`/`template1`, `ortus_control` и имена вне формы `^[a-z_][a-z0-9_]{0,62}$` отклоняются;
  - `Pools.For` отклоняет `uuid.Nil`, не обращаясь к `tenant_routing`. Маршрут в служебную БД (и в `Pools.Reserved`, например control DB) отклоняется до соединения. Sentinel-проверка W0.09 сохранена;
  - `mehttp/me.go` не трогал: заглушки переносят W1.03 и W1.10 (Q-W0.18-2).
- **`backend/internal/control/tenants`** — реестр и контроллер (S1-03):
  - `Ref`, `List`, `Lookup`, `Tenant`, `GetTenant`, `ListTenants` + непрозрачный `Cursor` (`(created_at, id)`, base64url);
  - `PlanPhases`. Canary — названные slug, иначе первая организация, которой нужна миграция. Дальше партии по `BatchSize` (0 → 10). Организации на цели — `Skipped`, впереди цели — `Failed ErrVersionAhead` без изменений. Неизвестный canary — ошибка до действий;
  - `Controller.Rollout`, `Migrate`, `Rollback`, `Status`. Каждая организация обрабатывается под session advisory-lock в control DB, маршрут перечитывается под замком. Затем сверяется фактическая версия с `tenant_routing` (`ErrSchemaDrift`), sentinel и `tenant_id` (`ErrSentinelMismatch`; в мигрированной базе без строки identity она пишется из маршрута). Дальше `UpTo`, `ensureIdentity` после 0001, условный `update tenant_routing … where schema_version = $from` (`ErrRoutingRace`) и `platform_audit` `tenant.schema.migrate|rollback` (`actor_kind=system`, `request_id = RunID`). Если упал canary, партии не стартуют (`ErrCanaryFailed` оборачивает причину). Если упала партия, следующие не стартуют без `ContinueOnFailure` (`ErrBatchFailed`). Dry-run не открывает ни одного соединения. При частичном отказе goose routing получает фактическую версию, чтобы не оставить дрейфа. `Rollback` выполняется только для перечисленных slug;
  - `DSNConnector` (учётка `MIGRATOR_DB_URL`, путь — имя БД маршрута, служебные БД отклоняются), `OpenDB` (ошибка называет переменную, хост и базу, DSN не содержит), `Controller.Redact` для текста ошибок в аудите.
- **`backend/internal/control/tenants/platformhttp`** — strict server тега `Platform`:
  - `listPlatformTenants`: limit 1…200, по умолчанию 50; при испорченном курсоре или limit — 400 `malformed_request`;
  - `getPlatformTenant`: `ETag "<revision>"`, неизвестная организация — 404;
  - `createPlatformTenant`: 201 `provisioning`, `ownerUserIds: []`, `Idempotency-Replayed`. Повтор ключа с другим телом — 409 `idempotency_key_reused`, неверное тело — 422 `validation_failed` (поля перечислены в `detail`);
  - `updatePlatformTenant` (W1.11), подписки (W1.08) и `listPlatformUsers` отвечают 501;
  - `SQLStore` работает поверх control DB с ролью `ortus_api`.
- **`backend/internal/control/provisioning`** (S1-01):
  - `Request.Validate` по `TenantCreate` и `Idempotency-Key`; `Slug` (транслитерация + `-` + 6 hex id), `DatabaseName` (`t_<slug>`); `TenantID` (UUID v5 от оператора и ключа), `RootUnitID`, `OwnerPersonID`;
  - `Registrar.Register` (только DML) пишет `tenants` (`provisioning`, `industry_pack=custom`), `tenant_routing` (`env:TENANT_DB_URL`, случайный sentinel, версия 0) и `platform_audit tenant.create`. В details записаны параметры заявки и `requestHash`; повтор ключа отдаёт ту же организацию. Если два запроса с одним ключом гонятся за вставку, проигравший получает ответ повтора;
  - `Provisioner` выполняет сагу `database → grants → migrate → bootstrap → activate`:
    - `CREATE DATABASE … OWNER ortus_migrator TEMPLATE template0` ролью `ortus_provisioner`; существующую базу чужого владельца не берёт (`ErrForeignDatabase`);
    - `REVOKE CONNECT, TEMPORARY … FROM PUBLIC` и `FROM ortus_provisioner`, `GRANT CONNECT` роли `pg_monitor` (только существующим; **возврат 1:** провиженер CONNECT к базам организаций не получает);
    - миграции через `Controller.Migrate`, sentinel берётся из маршрута;
    - корневое подразделение (`company`, имя и часовой пояс заявки), профиль владельца (e-mail), `access.policy_state`;
    - `provisioning → trial`, `revision + 1`, аудит `tenant.provision ok`.

    Упавший шаг пишется в `platform_audit` как `failed` с `step`, организация остаётся в `provisioning`, следующий `RunOnce` доводит её. Есть также `Pending` и `RunOnce`;
  - `EnsureRoleGrants`: `GRANT ortus_migrator TO ortus_provisioner WITH INHERIT FALSE, SET TRUE` (PostgreSQL 16+), повтор при гонке каталога. **Возврат 1:** с этим членством учётка `ortus_provisioner` равносильна учётке мигратора (`SET ROLE ortus_migrator`), см. раздел «Возврат 1», п. 2.

### Принятый риск: `ortus_provisioner` ≡ `ortus_migrator` (вопрос владельцу security)

Проверено тестом (`checkProvisionerHasNoTenantAccess`): прямой вход провиженера в базу организации отклоняется (42501), но в служебной базе `SET ROLE ortus_migrator` проходит. Дальше как владелец он может выдать себе CONNECT на любую базу организации или удалить её. Убрать это в пределах W1.02 нельзя: `CREATE DATABASE … OWNER ortus_migrator` (как и `ALTER DATABASE … OWNER TO`) в PostgreSQL 16+ требует права `SET ROLE` на нового владельца, а `ALTER DATABASE … OWNER` ещё и `CREATEDB` у текущей роли. База, оставленная во владении провиженера, тоже не годится: владелец базы управляет схемой `public` (там `goose_db_version`) и `ALTER DATABASE … SET search_path` — путь к выполнению кода под `ortus_api`. Кроме того, `migrations.Grant` (W0.06) отзывает CONNECT у PUBLIC как владелец.

Сейчас процесс провиженера и так держит `MIGRATOR_DB_URL`, поэтому новых возможностей процессу это не даёт. Учётку `PROVISIONER_DB_URL` нужно хранить как `MIGRATOR_DB_URL`. Варианты для решения — в `decisionsNeeded`. Тест зафиксирует изменение, если схему ролей поменяют.
