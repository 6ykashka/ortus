# Нагрузочный профиль пилота

Шаг 0.11 плана 27 · история S0-09 · решение D-08 · WS W0.16. Версия профиля 0.1.0 от 15.10.2026, статус **черновик: D-08 не отвечен**.

Профиль задаёт, какую нагрузку подаёт k6 на стенде stage в шаге 3.1 (W3.01) и против каких целей её проверяют. Числа, которые должен дать владелец продукта по D-08 («Пилотная компания: машины, сотрудники, одновременные пользователи», `design/docs/16-raid-glossary.md`), пока **заглушки**. У каждой заглушки есть номер допущения `A-NN`; где есть источник в комплекте, взят он. Сначала идёт пример планирования PLAT-09 (`01-technical-spec.md`): «100 машин × 20 смен × 12 фото × 1,2 МБ ≈ 28,8 ГБ новых фото в месяц».

Единственный источник чисел — `backend/test/load/profile.json`. Таблицы ниже проверяются тестом `backend/test/load/test/doc.test.mjs`: правка числа делается в `profile.json` и в этом документе одним коммитом, иначе тест падает.

## 1. Цели

Источники: NFR-03 (`01-technical-spec.md`), `15-quality-security.md` (уровень Load, k6, перед stage-релизом), `02-architecture.md` §14, план 27, шаг 3.1.

| Цель | Значение | Порог k6 |
|---|---|---|
| p95 обычного чтения (список 50 строк, карточка) | ≤ 500 мс | `http_req_duration{tenant:pilot,kind:read}`: `p(95)<500` |
| p95 короткой записи (команда без передачи файла) | ≤ 800 мс | `http_req_duration{tenant:pilot,kind:write}`: `p(95)<800` |
| Доля ошибок пилота (допущение A-19) | < 1 % | `http_req_failed{tenant:pilot}`: `rate<0.01` |
| Доля пройденных проверок пилота (допущение A-20) | > 99 % | `checks{tenant:pilot}`: `rate>0.99` |

- Передача файла по presigned URL (`kind:transfer`) и вход (`kind:auth`) в пороги не входят: NFR-03 считает задержку «без transfer файла».
- `queryDataset` — POST только для чтения, его порог — порог чтения.
- Запросы «шумного» тенанта под пороги не попадают. Проверяется, что пилот держит цели, пока соседний тенант шумит.
- Числа — **цели приёмки**, а не измеренная производительность (`02-architecture.md` §14). Результат прогона сохраняется вместе с конфигурацией окружения: CPU, RAM, версии PG/Go, размер пулов, число тенантов. Это делает W3.01.

### Пороги объёма

Пороги целей ничего не говорят, если генератор подал только часть нагрузки. Поэтому каждая итерация сценария заканчивается одной из двух метрик-счётчиков:

- `flow_completed{flow:<сценарий>}` — итерация дошла до конца;
- `flow_aborted{flow:<сценарий>,reason:<причина>}` — прервана: нет сессии (`login`, `context`), нет свободной машины (`no_vehicle`), гонка за машину (`vehicle_conflict`, ответ 409), отказ шага (`departure_inspection`, `expense`, `lists`, `review`, `page`, `upload` и т. п.).

Прогон проходит, только если завершённых итераций каждого сценария не меньше порога. В `smoke` порог — все итерации. В `pilot` и `stress` — плановый объём × `minVolumeShare` = 0,9 с округлением вниз (допущение A-24). Плановый объём: смен — `смен в час × длительность`; итераций менеджера — `VU × длительность / (managerThinkSeconds + 4 × 0,2 с)`; выгрузок и фото шумного тенанта — частота × длительность. `flow_aborted` порога не имеет: его причины — для разбора прогона.

| Порог | smoke | pilot | stress |
|---|---|---|---|
| `flow_completed{flow:driverShift}` | 2 | 13 | 70 |
| `flow_completed{flow:managerShift}` | 2 | 622 | 3114 |
| `flow_completed{flow:noisyExport}` | 2 | 162 | 162 |
| `flow_completed{flow:noisyUploads}` | 2 | 3240 | 3240 |

Начатые в конце прогона смены доигрываются: `gracefulStop` сценария `driverShift` — две расчётные длительности смены.

### Вопросы владельцу продукта (D-08)

Ответы заменяют заглушки:

1. Сколько машин, водителей, логистов, владельцев и руководителей у пилотной компании?
2. Сколько смен в день в обычный и в пиковый день? Когда выезды и возвраты, какая доля выездов приходится на окно?
3. Сколько фото на осмотр (выезд, сдача) и на чек? Каков реальный размер фото после сжатия на телефоне?
4. Сколько расходов на смену?
5. Сколько логистов работают одновременно?
6. Сколько истории переносится при старте и какой объём накопится за пилот?
7. Сколько организаций будет на одном стенде в пилоте? Кто из них «тяжёлый»: экспорт, фото?

## 3. Производные величины

Значения считает `deriveRates()` из `backend/test/load/lib/model.js`; округление — до трёх знаков.

| Ключ | pilot | stress | Что это |
|---|---|---|---|
| `shiftsPeakDay` | 90 | 90 | смен в пиковый день = `vehicles × peakDayUtilization` |
| `shiftsPerMinutePeak` | 0.525 | 2.625 | смен в минуту в окне пика × масштаб |
| `photosPerShift` | 12 | 12 | фото на смену = выезд + сдача + чеки (совпадает с PLAT-09) |
| `photoGBPerMonth` | 28.8 | 28.8 | ГБ новых фото в месяц (PLAT-09), без резервных копий |
| `concurrentUsersPeak` | 16 | 80 | одновременных пользователей в пике = водители в приложении + `managerVus` (менеджеры и владельцы × масштаб) |
| `managerVus` | 8 | 40 | VU сценария менеджера |
| `driverApiRps` | 0.376 | 1.881 | запросов API в секунду от водителей (без передачи файлов) |
| `managerApiRps` | 1.6 | 8 | запросов API в секунду от менеджеров (без приёмки) |
| `historyTrips` | 24000 | 24000 | рейсов в истории тенанта |
| `historyInspections` | 48000 | 48000 | осмотров (выезд и сдача) |
| `historyExpenses` | 48000 | 48000 | расходов |
| `historyFiles` | 288000 | 288000 | файлов (около 345,6 ГБ при 1,2 МБ) |
| `noisyExportRowsPerMinute` | 24000 | 24000 | строк в минуту, которые выгружает шумный тенант |
| `noisyUploadMBPerMinute` | 144 | 144 | МБ фото в минуту от шумного тенанта |

Вывод: по API пилот маленький — около 2 запросов в секунду в пике, около 10 на stress. Основная нагрузка на хранилище и сеть — фото: 12 на смену. Шумный тенант нагружает пулы БД постраничным чтением и поток загрузок. Поэтому смысл теста не в RPS пилота, а в проверке справедливости: пулы DB-per-tenant, rate limit и очередь сканирования файлов не должны давать соседу ухудшить p95 пилота.

Состав одной смены водителя (`requestsPerShift()`):

| Ключ | Запросов | Операции |
|---|---|---|
| `shift.read` | 12 | `getMyContext` 1, `listReservations` 1, `listVehicles` 1, `getInspectionChecklist` 2, `getTrip` 7 |
| `shift.write` | 31 | `reserveVehicle` 1, `initiateUpload` 12, `completeUpload` 12, `submitInspection` 2, `startTrip` 1, `createTripExpense` 2, `returnTrip` 1 |
| `shift.transfer` | 12 | PUT по presigned URL, вне порогов |

Итерация менеджера: 4 списка (`listTrips`, `listVehicles`, `listReservations`, `listInspections`, по 50 строк). Если есть рейс в статусе `returned_pending_review`, добавляется приёмка: `getTrip` 2, `listTripExpenses` 1, `getTripExpense` и `reviewTripExpense` по числу расходов, `reviewTrip` 1 (с `If-Match`).

## 4. Сценарии k6

Каталог `backend/test/load/` (подробности — `README.md` там же).

| Сценарий | Тег | Модель k6 | Что делает |
|---|---|---|---|
| `driverShift` | `tenant:pilot` | `constant-arrival-rate`, смен в час = `shiftsPerMinutePeak × 60` | Вход водителя → `/me/context` → своя бронь или самостоятельная бронь случайной машины из списка свободных на смену (`availableFrom`/`availableUntil`; допущение A-22: бронирует сам водитель, контракт это разрешает; 409 при гонке — ожидаемый ответ, смена прерывается с `vehicle_conflict`) → чек-лист → 5 фото (initiate → PUT → complete) → осмотр выезда → старт рейса → опросы рейса → 2 расхода с чеком → чек-лист и 5 фото сдачи → осмотр сдачи → `returnTrip` с `If-Match` |
| `managerShift` | `tenant:pilot` | `constant-vus` = `(managers + owners) × масштаб` | Списки по 50 строк. При наличии рейса на приёмке — расходы, решения по ним и решение по рейсу (`If-Match`) |
| `noisyExport` | `tenant:noisy` | `constant-arrival-rate`, `noisyExportsPerMinute` | Каталог наборов → выгрузка `noisyExportPages` страниц `queryDataset` по 200 строк. Асинхронной выгрузки в контракте 0.1 нет. Когда она появится (W4.50), сценарий переходит на задание выгрузки |
| `noisyUploads` | `tenant:noisy` | `constant-arrival-rate`, `noisyUploadsPerMinute` | Поток фото по 1,2 МБ (initiate → PUT → complete) |

Стадии: `smoke` — по `iterations` = 2 итерации каждого сценария на 1 VU, фото по 2 КБ, без пауз; это проверка синтаксиса, сквозного пути и того, что сессия переживает итерацию (`options.noCookiesReset`: менеджер и шумный тенант входят один раз на VU, а k6 по умолчанию чистит cookie перед каждой итерацией). `pilot` — 30 мин профиля. `stress` — 30 мин ×5.

Каждый запрос получает теги `op` (operationId OpenAPI 0.1), `kind` (`read` | `write` | `transfer` | `auth`) и `tenant`. Изменяющие запросы несут `Idempotency-Key` (уникален по прогону, сценарию, VU, итерации и шагу), `X-CSRF-Token` и `Origin`. Для `returnTrip`, `reviewTrip` и `reviewTripExpense` ставится `If-Match` из последнего `ETag`.

### Вход

**Local и compose.** Вход через dev-провайдер (допущение A-23): `POST /api/v1/dev/login` с `{ "persona": "<id>" }`, после него cookie сессии и cookie `ortus_csrf`. Точный механизм определит W0.09 / W1.03; переменные `DEV_LOGIN_PATH` и `CSRF_COOKIE` позволяют подстроиться без правки сценариев. Менеджер и шумный тенант входят один раз на VU и держат сессию между итерациями (`options.noCookiesReset`); водитель входит заново в каждой смене.

**Stage — не через dev-провайдер.** По PD-18 (вердикт «противоречит», `docs/plan/decisions.md`), Q-102 (`docs/plan/v2/questions-for-po.md`) и ADR-0004 dev-провайдер остаётся только для local и e2e: на stage он дал бы вход без аутентификации. Как сценарии входят на stage, решает интегратор или техлид до W3.01. Варианты: OIDC Code + PKCE через BFF с тестовыми учётками в realm stage (сессии готовятся до прогона) или отдельный тестовый механизм, который на stage включается явно и только на время прогона. До решения:

- `lib/client.js` в init падает, если `BASE_URL` не local/compose (`devLoginAllowed()` в `lib/model.js`: loopback, `localhost`, `host.docker.internal`, имя сервиса compose без точки);
- прогон W3.01 на stage заблокирован этим вопросом (§7, п. 6). Профиль, сценарии и пороги от него не зависят: меняется только `Session.login()`.

Персонажи, которых создаёт сид нагрузки (W3.01):

- водители `load-pilot-driver-001…110`;
- менеджеры `load-pilot-manager-01…08`;
- шумный владелец `load-noisy-owner-01`.

VU менеджеров переиспользуют 8 персонажей по кругу (на stress 40 VU на 8 персонажей).

Образ k6: `grafana/k6:2.3.0@sha256:9c2dee7f8ed74d317e4027c06a10f169b625638189de8d4555d0b3486a5aeb34` (релиз 21.09.2026).

## 5. Данные стенда для W3.01

- Тенант пилота: структура как в фикстурах `15-quality-security.md` (Москва-1/2, Самара), `vehicles` машин в статусе `available` с `odometerKm`, `drivers` водителей и `managers + owners` менеджеров с ролями логистики. История — `historyTrips` рейсов с осмотрами, расходами и файлами (метаданные; объём хранилища — по `historyFiles`).
- Шумный тенант: минимум один рейс (владелец загрузок) и набор данных рейсов с ≥ `noisyExportPages × noisyExportPageSize` строк.
- Ещё `tenantsOnStand − 2` фоновых тенанта с сидом по умолчанию.
- Генератор данных — Go-сид по `profile.json` поверх скелета сида W0.06. Это делает W3.01.

## 6. Как запускать

Проверка без стенда (Docker): `node backend/test/load/check-k6.mjs` выполняет:

- `k6 inspect` для стадий `smoke`, `pilot`, `stress`;
- smoke всех четырёх сценариев (по 2 итерации) против API-двойника `backend/test/load/test/fake-api.mjs` на `:8108` (слот 8, план §8; API исполнителя `8100 + слот`);
- сверку числа запросов по операциям с `requestsPerShift()` и `requestsPerManagerIteration()`, `flow_completed` по каждому сценарию и `http_req_failed` = 0 по обоим тенантам;
- отказ init при dev-входе на адрес не local/compose (`BASE_URL=https://stage.example`).

Прогон против локального или compose-стенда (dev-провайдер разрешён), например API на `127.0.0.1:8108`:

```powershell
docker run --rm --add-host=host.docker.internal:host-gateway -v "${PWD}/backend/test/load:/scripts" `
  grafana/k6:2.3.0@sha256:9c2dee7f8ed74d317e4027c06a10f169b625638189de8d4555d0b3486a5aeb34 `
  run -e LOAD_STAGE=smoke -e BASE_URL=http://host.docker.internal:8108 `
  --summary-export /scripts/results/smoke-summary.json /scripts/main.js
```

Внутри сети compose `BASE_URL` — имя сервиса (`http://api:8080`). Прогон `pilot` и `stress` на stage — W3.01 после решения о входе на stage (§4 «Вход», §7 п. 6). Команда та же, меняются `LOAD_STAGE`, `BASE_URL` и способ входа.

Переменные передаются флагом k6 `-e`, а не `docker -e`: `k6 inspect` не видит окружение контейнера.
