## 1. Цель

Карточка плана §4 «Этап 4» (W4.01 ★) и «Общие выводы для W4.01» (`v2/analysis/dor/README.md`):

1. **Виды областей** (ADR-0014 п. 3): оценщик регистрирует `space`, `page`, `folder`, `doc`, `account`, `chat`, `repair_project` (объектные, PD-53) и `relation` (вычисляемая связь с записью, без объекта — Q-W4.02-1). `FutureKinds` пуст: все виды каталога и `Scope.kind` контракта есть в реестре. Миграция `scope_kind` уже сделана W4.02 (tenant 0020) — новых миграций нет.
2. **RS-08**: `project` — только проект «Задач» (`tasks.projects`; Q-W4.00-tasks-1); объект ремонта — отдельный вид `repair_project` (Q-W4.00-repair-2); направление «Обращений» — сервисный проект задач, тот же `project`. Грант одного вида не покрывает объект другого вида с тем же id.
3. **Иерархия объектов** (ADR-0014 п. 4): грант на объект засчитывается и для объектов внутри него — страница внутри пространства, подстраница внутри страницы, документ в папке и её подпапках, эквайринг в кассе. Хук `ObjectResolver` (вид → место объекта: подразделение, содержащие объекты, предки своего вида, уровень доступа контейнера, ветка узлов со списками доступа); резолверы регистрируют модули-владельцы таблиц (W4.31, W7.23, W5.x).
4. **Уровень доступа контейнера** («открытый / ограниченный / закрытый») — `projAccess` W4.10 и `kbAccess` W4.30 в оценщике: территориальные гранты (`tenant`, `unit`) в открытом контейнере дают всё, в ограниченном — только чтение (действия чтения регистрирует модуль контейнера, `Evaluator.ContainerReads`), в закрытом — ничего; роль на самом объекте — всё. В проекте своя роль заменяет унаследованную (`projAccess`: при роли в проекте роль фирмы или региона в нём не добавляется); в пространстве роли складываются (`kbAccess`). TP-03 (Q-W4.10-4): закрытый проект закрыт и владельцу, кроме его роли в проекте; KB-04 (Q-W4.30-9): закрытое пространство владелец видит. То же в `ScopeQuery` (колонка уровня).
5. **ACL на узлах** — одна модель для БЗ и Документов: режим узла `inherit` / `edit` («читают все, правят выбранные») / `listed` («только выбранные»), записи `all`, `member`, `group`, `role` (+ подразделение), `relation`; проверка по ветке от верхнего узла к объекту; «только выбранные» без записи — объект невидим (404); правка — по ближайшему узлу со своим режимом; запись «правит» даёт правку видящим; руководитель (действие `Manage` из роли на объекте — пространство или узел; территориальная роль с тем же действием — нет, как `r-kb-lead` в `kbAccess`) проходит списки; автор с правом создания правит свой узел.
6. **`relation`**: грант покрывает запись, если субъект в людях связи записи (`Resource.Related`: прораб объекта, водитель рейса, исполнитель задачи); в SQL — колонки людей связи.
7. **Объяснение с объектом**: `explainAccess` принимает пары `x-explain-objects` (`knowledge/space → space`, `knowledge/node → page`), грант на содержащий объект засчитывается (по резолверу), ошибки зависимостей в `Explain` пробрасываются (Q-W1.04-21).
8. **Сопутствующее** (обязательные пункты брифа по отчёту W4.02): `kit.ScopeFromAPI`/`ScopeToAPI` знают новые виды (назначение 201, `Scope.kind` не пустой; `relation` — без `resourceIds`); `/me/context` отдаёт возможности новых видов; «Главная» org — «без роли» только по областям организации, подразделения, `self`, склада и ресурса (объектная роль этапов 4–7 модулей не даёт, PD-53); строки `scope_kinds_gate.yaml` перепроверены.

| # | Вопрос | По умолчанию |
|---|---|---|
| 1 | Какие виды регистрирует W4.01 | Все восемь карточки (+ `repair_project`): виды без модуля не дают ничего лишнего — объекта нет ни в одном ресурсе, `x-scope` операций их не допускает |

| 13 | Кто руководитель для списков узлов (возврат 1) | Только роль объектного вида с `NodeRule.Manage` (как `r-kb-lead`); территориальная роль с тем же действием списки не проходит |
| 14 | Чтения ограниченного контейнера (возврат 1) | Регистрирует модуль (`Evaluator.ContainerReads`); без регистрации — ничего (fail-closed) |
