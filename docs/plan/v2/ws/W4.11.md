## 1. Цель

Тег Tasks на сервере вместо ответа 501 — 30 операций контракта `0.10.0-stage4` с поведением сценарного сервера W4.03 (`msw/tasks/{state,engine,index}.ts`, conformance `cases/tasks.ts`) и описаний контракта:

1. **Проекты:** `listTaskProjects`, `getTaskProject`, `createTaskProject` (шаблоны «Простой», «С согласованием», «Копия проекта» — правила копируются выключенными; создатель — руководитель проекта назначением с областью `project`), `updateTaskProject` (название — `tasks.projects.manage`, уровень доступа — `tasks.members.manage`, воронка — 409 `funnel_fixed`), `initTaskProjectWorkflow` (TP-06: v1 из текущих статусов 1:1, переходы «все во все»; 409 `workflow_exists` / `funnel_fixed`).
2. **Доступ к проекту** (`projAccess` с TP-03): роль проекта (прямо или через группу) заменяет роли области; роль области — по уровню (открытый — все действия, ограниченный — только чтение, закрытый — ничего); владелец организации — системная роль, кроме закрытого проекта; воронка «Заявки» — как открытый. `myAccess`, «Людей», «Открыто».
3. **Участники:** `listTaskProjectMembers` (только активные; «Откуда доступ», «Что может», «финансы скрыты» у функции «Водитель», роли проекта организации), `setTaskProjectMemberRole` (прямое назначение `access.role_assignments` с областью `project`; 422 «Выберите сотрудника», «{имя} заблокирован — назначить роль нельзя», «В проекте назначаются роли проекта»; 409 `delegation_exceeds_grant`), `removeTaskProjectMember` (себя — 409, групповой/унаследованный/системный доступ — 409, нет роли — 404), `checkTaskProjectAccess` (`tasks.members.manage` в проекте или `members.read` в области проекта; причины `projCan` дословно). Смена роли поднимает `policy_version` (PD-58).
4. **Процесс с версиями:** `getTaskWorkflow` (черновик — только с `tasks.workflow.manage`; воронка — фиксированные этапы `fixed: true`), `saveTaskWorkflowDraft` (структурные проверки редактора), `discardTaskWorkflowDraft`, `publishTaskWorkflow` (6 проверок публикации эталона + правило на удалённый статус, задачи остаются в своих статусах и переходят на новую версию). If-Match — ревизия процесса.
5. **Задачи:** `listTasks` (фильтры `projectId`, `assignee=me`, `awaitingMyApproval`, `parentTaskId`; задачи видимых проектов и свои вне них — область `self`; строки — через `ScopeQuery` оценщика), `getTask` (переходы с причиной `trCheck`, согласование, чек-лист, вложения, родитель visible/hidden/deleted, подзадачи с hidden), `createTask` (номер `{KEY}-{N}` с 101, первый статус категории «К выполнению», исполнитель должен видеть проект, правила «Задача создана»), `updateTask`, `updateTaskChecklistItem`.
6. **Переходы и согласование:** `transitionTask` (403 «нет права» / 409 `invalid_transition` + `reason`: `not_in_status`, `checklist_open`, `children_open` — только видимые подзадачи, `author_forbidden`, `already_voted`, `doc_route`; 422 комментарий и удалённый переход; голос «достаточно одного / нужны все», раунд фиксирует состав и версию процесса; «на автора»; правила «перешла в статус»), `rejectTaskApproval` (только право, «не автор», текущий статус — PD-60; комментарий обязателен).
7. **Подзадачи:** `setTaskParent` (один родитель, три уровня, без циклов, родитель видим и не завершён; невидимый — 404; история обеих задач).
8. **Вложения:** `attachTaskFiles` (своя завершённая загрузка `task_attachment` с владельцем `tasks/task/<эта задача>`, 20 МБ, 30 файлов, типы эталона), `removeTaskFile` (свой файл — `tasks.update`, чужой — руководитель проекта). Родитель `tasks/task` регистрируется в модуле файлов (`files.Parents`, purpose `task_attachment`), чтение файла — как задачи (резолвер места проекта в оценщике, закрытые проекты скрыты из `listFiles`).
9. **История и комментарии:** `listTaskHistory` (от новых к старым), `commentTask` (append-only, без If-Match).
10. **Автоматизация:** `listTaskAutomations`, `createTaskAutomation`, `updateTaskAutomation` (смена содержания — версия + 1 и новый автор; `enabled` — без версии), `deleteTaskAutomation` (журнал переживает правило), `listTaskAutomationRuns` (30, от новых; задача — только видимая). Запуск от имени автора правила (`tasks.transition` автора в проекте), глубина 1, ошибка — событие владельцам.
11. **События и уведомления:** события `tasks.*.v1` в outbox; владельцам — тексты эталона (`api.js`: создан проект, роль в проекте, исключён из проекта, опубликован процесс, правило не выполнено).

## 10. Риски и решения по умолчанию

- Доступ к проекту для описаний («Откуда доступ», «Что может», согласующие, «Проверить доступ», автор правила) считает модуль по грантам участников и владению из control DB; совпадение с оценщиком держит тест паритета на фикстурах (Q-W4.01-14). Несколько ролей в одном проекте складываются, имя — первой (Q-W4.01-10).
- Участники — только активные члены организации (W4.03 возврат 1); владелец организации — «Системная роль, вся организация», в «Людей» не считается.
- Уведомления владельцам — системные (без права), тексты эталона; адресат-актор тоже получает (как `owners()` эталона).
- Дефект → задача: проект задач, чья область — фирма машины или ближайший её предок (иначе проект всей организации, старейший); нет проекта — задачи нет, очередь S2-17 остаётся. Исполнитель — назначенный дефекту, иначе владелец проекта. Решение по дефекту завершает задачу первым статусом категории «Готово». Очередь S2-17 не отключается (W4.24).
- Вложения: типы эталона (`FILE_OK`) — фото, PDF, текст, Office и ZIP; лимиты 20 МБ и 30 файлов.
- `listFiles`: задачи проектов, недоступных участнику по уровню (TP-03), скрыты через `files.Hider`.
- «Лотос»: проект «Салон · Тверская» получает v1 по TP-06 сидом (Q-W4.00-tasks-3), как MSW.
