# 0014. Расширяемые области оценщика прав

Статус: предложено
Дата: 2026-10-15 · W0.08 (стюард контракта этапа 1) · Участники: W1.04 (оценщик), W1.00, стюарды этапов 4–7, владелец продукта (PD-53)

Решение плана: F8 (план v2 §1), PD-53 (§7). Вход шага 1.4 (S1-11).

## Контекст

Оценщик `permit()` + `scopeQuery()` (шаг 1.4) стоит на критическом пути, а его модель областей уже сейчас не согласована между источниками (C п.3–5, факты 7–9):

| Источник | Виды областей |
|---|---|
| SQL `access.role_assignments.scope_kind` (tenant 0001) | `tenant`, `unit`, `project`, `warehouse`, `resource`, `self` — 6, `check` |
| Каталог `api/permissions.yaml` (11, 14.10) | те же 6 + `chat`, `relation` — 8 (`SCOPE_KINDS` в `tools/gen/lib/permissions.mjs`) |
| OpenAPI 0.1 `Scope.kind` | `tenant`, `org_unit`, `project`, `self`, `resource_pool` — 5, `enum` |
| Прототип 14.10 (`models.js` `scopeLabel`) | `tenant`, `region`, `firm`, `self`, `project`, `space`, `page`, `folder`, `chat`, `doc`, `account` — 11 |
| Документы 20–26 | `space`, `page` (23), `folder`, `doc` (24), `chat`, `relation` (25), `account` (26) |

Ещё три требования к оценщику шире S1-11 (C п.5):

- списки доступа на объектах: узлы базы знаний (`access.list`, 23), `share` документов (24), источники состава чата (`chat_source`, 25); права страницы могут сузить доступ пространства (KNOW-02);
- параметры гранта и правила: `limit: amount` (касса, 26), «не автор», «не тот, кто закрывал смену» (26), `owner_only`, `blocked_by_function: [driver]` (11);
- область `project` указывает на три разные сущности: проект «Задач» (21), объект ремонта (19, роль прораба «с областью объект»), направление обращений (22). `scope_ref` у одного вида ссылается на разные таблицы (C факт 8).

PD-53 (по умолчанию, B-4): роль с объектной областью (проект, пространство, чат, касса, объект) не даёт права без объекта. В эталоне это не так (B факт 6: Котова получает `tasks.settings` во всей организации через роль на проект) — расхождение идёт в allowlist.

Если оценщик этапа 1 знает только 6 видов SQL, этапы 4–7 будут переделывать ядро на каждом модуле, а `Scope.kind` в контракте будет меняться неаддитивно.

## Варианты

1. **Закрытый перечень.** Новый вид — правка `check` в SQL, `enum` в OpenAPI и кода оценщика. Плюсы: просто, всё видно в одном месте. Минусы: каждая область модуля — правка ядра и горячей точки (план v2 §3.5), оценщик знает о всех модулях, неаддитивные правки контракта, конфликты PR этапов 4–7.
2. **Реестр видов областей.** Модуль регистрирует вид: ключ, «объектный» ли он, резолвер «объект → область и её предки» и SQL-предикат для `scopeQuery`. `scope_kind` проверяется по справочнику реестра (FK), `scope_ref` — id объекта своего вида. Списки доступа на объектах, параметры гранта и правила — хуки с интерфейсами в ядре. Плюсы: области добавляются аддитивно контрактным PR модуля, PD-53 реализуется в одном месте, ядро не знает о модулях. Минусы: контракт резолвера, тест паритета с прототипом, миграция `check` → FK.
3. **Только списки доступа на объектах (ACL)** вместо областей. Плюсы: гибко для узлов базы знаний и документов. Минусы: не покрывает «весь бизнес», регион и фирму (AUTH-01, AUTH-04), дорогой `scopeQuery` для списков и отчётов, ломает модель назначений «кто + роль + где + когда».

## Решение

**Рекомендация: вариант 2** — реестр видов областей с хуками объектного доступа из варианта 3.

1. **Реестр** — явный (без `init()`, отступление CLAUDE.md): `ScopeKind{Key, Module, ObjectBound, Resolve(ctx, ref) → (unitID, ancestors), Covers(grant, object) bool, Predicate(alias) → SQL}`. В SQL — справочник `access.scope_kinds(key, module_key, object_bound)`; `role_assignments.scope_kind` ссылается на него вместо `check`. Миграция — W1.04 из резерва tenant 0007–0009 (номер выдаёт стюард, PD-59).
2. **Виды этапа 1:** `tenant`, `unit` (регион, фирма, подразделение — один вид, поддерево через `org.unit_closure`), `self`, `project` (только проект «Задач»), `resource`, `warehouse`.
3. **Виды модулей** добавляет контрактный PR этапа вместе с модулем: `space`, `page` (W4.01, база знаний), `account` (W5.00, касса), `repair_object` (W6.00 — объект ремонта не переиспользует `project`), `folder`, `doc`, `chat`, `relation`, `service_direction` (W7.00). Один вид — одна таблица `scope_ref`.
4. **PD-53:** объектный вид засчитывается, только если в запросе есть объект того же вида и id или его потомок по резолверу (страница внутри пространства). Без объекта грант не даёт права; гейт раздела меню считает отдельно (`permitAny`), операции его не используют.
5. **Хуки** (интерфейсы — W1.04, реализации — модули): `ObjectACL` (список доступа узла: участник, группа, роль в области, отношение; страница может сузить доступ пространства), `GrantParams` (`limit: amount`), `Rules` (`not_author`, `not_shift_closer`), `owner_only` (OwnerBinding в control DB), `blocked_by_function` (SoD, 409 `separation_of_duties_conflict`).
6. **`scopeQuery()`** собирает предикат из `Predicate` каждого вида гранта: фильтр до пагинации и агрегации (03 «Пагинация»).
7. **Контракт.** `Scope.kind` в OpenAPI остаётся `enum` и расширяется аддитивно стюардом этапа вместе с видом. Клиенты (W0.13, W1.20, W1.23) показывают неизвестный вид как «Особая область» и не падают. Соответствие имён каталога и API ведёт реестр: `unit` ↔ `org_unit`, `resource` ↔ `resource_pool` (отчёт W0.07). `explainAccess` (W0.08) уже отдаёт причину несовпадения гранта: `other_object`, `object_scope_without_object`, `out_of_scope`.

## Последствия

- Проще: модули этапов 4–7 добавляют области без правки ядра оценщика; PD-53 закреплён в одной функции `Covers` — если владелец продукта решит иначе (B-4), меняется только она.
- Сложнее: резолвер и предикат на каждый вид; тест паритета с `models.js` (`scopeCovers`, `scopeLabel`) и W0.11 (`access/can`); миграция `check` → FK.
- Сделать: W1.04 — реестр, интерфейсы хуков, виды этапа 1, миграция справочника; W4.01, W5.00, W6.00, W7.00 — свои виды в контрактных PR (SQL, `Scope.kind`, `SCOPE_KINDS` в `tools/gen/lib/permissions.mjs`, каталог прав).
- Проверим: строки матрицы изоляции W1.04 — грант на проект без объекта → отказ, на тот же проект → доступ, на другой проект → 404; тест «каждая область каталога и `Scope.kind` есть в реестре»; тест паритета с прототипом.
