# W2.60 · Шлюз модулей при draining: начатая смена сдаётся на экране (Q-W2.32-3)

Этап 2 · вид: backend · AC-12 (S1-18, D-23), дефект журни W2.32 Q-W2.32-3 · размер S.
Зависит от: W1.08 (шлюз модулей `modulesreg/gate.go`), W2.04 (осмотры), W2.05 («Завершить рейс»), W2.32 (строка `@known-defect`) — влиты в `main`.
Блокирует: строку AC-12 «рейс в пути сдаётся на экране после отключения» (`module-draining.spec.ts`).
Слот исполнителя: 6 (`ortus-s6`, API 8106, Vite 5206, свой эталон 4106). Контракт, миграции, страницы — без изменений.

## 1. Цель

Пока «Логистика» в `draining` (отключена при начатой смене), водитель завершает начатый рейс на экране: «Завершить рейс» (`finishTripRoute`) → «Осмотр при сдаче» (`submitInspection`, `kind=return`) → «Сдать машину» (`returnTrip`) → менеджер принимает смену → модуль «только чтение». Новые процессы остаются закрытыми: план рейса, бронь, старт рейса и осмотр перед выездом — 403 `module_read_only` «Модуль «Логистика» отключается: можно только завершить начатую работу.».

Эталон: design/docs/v0.1/02-architecture.md «Module draining — новые процессы модуля не создаются, идущие процессы безопасно завершаются», «draining + allowlisted finish operations»; `modulesreg.FleetTrips`: начатые рейсы — `on_route`, `returning`, `submitted`, `rework` (эффект `finish_allowed`), не начатые — `assigned`, `inspection`, `defect_review` (`closed`).

## 2. Границы файлов

Владеет (санкция задачи): `backend/internal/modules/modulesreg/gate.go` и тесты шлюза; обработчик осмотра `backend/internal/modules/fleet/inspections/submit.go` и его тесты; тесты `backend/cmd/api/*_test.go`; `frontend/apps/web/e2e/journeys/stage2/module-draining.spec.ts`; свои бриф и отчёт.

Не трогать: `api/**`, миграции, `cmd/api` вне тестов, MSW (`adapter/src/msw/modules`, W2.62), баннер draining оболочки (Q-W2.32-4), `design/**`, `docs/plan/decisions.md`, `docs/plan/v2/status.md`, `docs/demo/**`, стенд слота 0.

## 3. Решение

1. Шлюз (`finishOnly`): добавить `finishTripRoute` и `submitInspection`. Шлюз видит только операцию, не тело: вид осмотра (`departure` | `return`) он не различает.
2. Обработчик осмотра: осмотр перед выездом (`kind=departure`) при `draining` — 403 `module_read_only` с текстом шлюза, до проверки тела и данных (как шлюз: модуль — первым). Состояние модуля — `modules.installations` тенанта (строка ключа контракта `fleet` важнее синонима `logistics`, как `reservations.ttl` и `modulesreg.PGStore`); пакет модулей не импортирует `modulesreg` (depguard), `cmd/api` не меняется. Осмотр при сдаче (`kind=return`) относится к рейсу `returning`/`rework` — начатому; его допускает существующая проверка состояния рейса (`invalid_transition` для не начатого).
3. `read_only` и `disabled` по-прежнему закрывает шлюз.

## 4. Тесты первыми

1. unit `modulesreg/gate_test.go` (`TestGate`): `finishTripRoute` и `submitInspection` в `draining` — проходят; в `read_only` — `module_read_only`; `startTrip`, `reserveVehicle`, `createTripPlan` в `draining` — `module_read_only`.
2. integration `fleet/inspections` (`TestSubmitWhileDraining`, не параллельный — меняет модуль тенанта A): в `draining` осмотр перед выездом — 403 `module_read_only`, ничего не записано; осмотр при сдаче рейса `returning` — 201; при `enabled` выезд проходит.
3. integration `cmd/api` (`TestStackModuleDraining` → `checkDraining`): водитель при `draining` — `finishTripRoute` 200 (рейс `returning`), `submitInspection` `return` проходит шлюз (тело без фото — 422 `validation_failed` обработчика), `submitInspection` `departure` — 403 `module_read_only`.
4. e2e `@stand`: строка `@known-defect` «рейс в пути → отключение → «Завершить рейс», осмотр при сдаче, «Сдать машину» → приёмка → только чтение» — снять `test.fixme`, тег `@stand`.
