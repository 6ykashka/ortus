# 19. Ремонт и стройка: расширения — версия 0.4

Модель от 2 октября 2026 года. Ориентир — платформа «Створка», облачная CRM для строителей. Решения владельца продукта: все расширения входят в модуль «Ремонт и стройка» без отдельной оплаты; кабинет заказчика открывается по ссылке без входа.

Макеты:

- `Ортус CRM.dc.html` → «Ремонт и стройка» → «Объекты»: карточка объекта в приложении (см. «Модуль «Объекты»»).
- `Ремонт и стройка.dc.html` — разделы объекта (замер, смета, график, документы, снабжение, финансы, оплата бригады, подрядчики, кабинет заказчика) и воронка заявок. В CRM эти разделы открываются во вкладках карточки.
- `Объекты - варианты.dc.html` — разбор аналогов и три варианта карточки. В работу взят 1a «Сводка».

## Что взято у «Створки»

Цепочка «замер → смета → график → акты → прогресс → деньги»: обмерный план на объекте с переносом в смету, график по этапам сметы, акты и счета из сметы, прогресс по закрытым актам, подпись по SMS, чеки по QR, финансовый учёт объекта, зарплата сотрудникам и самозанятым по выполненным работам, фотоотчёты в кабинете заказчика. Видеонаблюдение и проверку цен поставщиков откладываем: это внешние интеграции.

## Заявки = проект модуля «Задачи»

Отдельного модуля заявок нет. Заявка — задача в проекте с процессом `leads` (`ortus/models.js → WORKFLOWS`):

| | Задачи | Заявки |
|---|---|---|
| Этапы | Новая → В работе → На проверке → Готово | Новая → Замер → Смета → Договор → Объект; из любого — «Отказ» |
| Общее | Исполнитель, срок, приоритет, чек-лист, комментарии, связи, уведомления, права `tasks.*` | То же |
| Своё | — | Поля клиента: имя, источник, сумма; этап «Замер» создаёт объект-черновик в «Ремонт и стройка» (замер и смета живут на нём), этап «Объект» переводит его в работу после договора |

Почему так: один движок вместо двух (меньше кода, одинаковые права и уведомления), а бизнесу не нужно учиться второму канбану. Владелец может переименовать пункт меню «Задачи» в «Заявки» в «Оформлении», если задачами почти не пользуется.

Модель: `projects.flow` (`tasks` | `leads`), переходы проверяет сервер по процессу проекта. Поля заявки — `tasks.lead jsonb` до появления пользовательских полей (S3). Персональные данные клиента — только при праве `tasks.read` в области проекта.

В прототипе: «Задачи» → вкладка проекта «Заявки · Ремонт» у владельца «Альты». В карточке объекта пункта «Заявки» нет: заявка живёт в «Задачах» до подписания договора. С этапа «Замер» у неё есть объект-черновик: в списке объектов он в фильтре «До договора», у него только вкладки «Обзор», «Замер» и «Смета», прораб его не видит.

## Модуль «Объекты»

Добавлено 2 октября 2026 года.

### Меню

У «Ремонта и стройки» своя группа в боковом меню, как у «Логистики». Группа видна владельцу, только пока модуль подключён. После отключения группа уходит из меню, а в группе «Отключены · только чтение» остаётся один пункт «Ремонт и стройка»: объекты открываются для чтения с баннером, новые операции закрыты. Если модуль ни разу не подключали, пункта нет. Первый пункт — «Объекты» (`page: repair`, иконка `home_work`), далее «Снабжение» (`page: repairSupply`) и «Шаблоны и расценки» (`page: repairCatalog`, иконка `library_books`, с правом `repairs.catalog.manage`). Остальные пункты группы пока не выбраны (RS-05).

| Персонаж | Группы меню |
|---|---|
| Владелец | … Логистика → **Ремонт и стройка: Объекты, Снабжение, Шаблоны и расценки** → Отрасли: Салон и SPA → Общие модули → Отключены · только чтение (если есть). Каждая отраслевая группа — только при подключённом модуле |
| Прораб | **Ремонт и стройка: Объекты** → Общие модули: Задачи, База знаний. Раньше пункт назывался «Мой объект» |

В «Оформлении» пункт можно переименовать. Если задан термин «Объект», пункт называется его множественным числом, например «Квартиры».

**Счётчик у пункта «Объекты»** — только у владельца: отметки на приёмке, активные объекты без прораба и допработы, которые ждут оценки, по всем объектам организации. Пока модуль не подключён, счётчика нет. Это те же пункты, что попадают в «Требует решения» на «Главной»; карточка модуля там показывает объектов в работе, на приёмке и ближайшую сдачу.

### Список объектов

Добавлено 3 октября 2026 года. «Объекты» в меню открывают список, строка или карточка открывает объект.

| | Владелец | Прораб |
|---|---|---|
| Какие объекты | Все объекты организации | Только те, где он назначен прорабом (фильтрует сервер) |
| Вид | Таблица; на экране уже ~880 px контента — карточки | Карточки с кнопкой «Отметить работу» |
| Колонки / поля | Объект и адрес · этап и готовность (принято + на приёмке) · сдача: дата и «через N дней» или прогноз, если срок сдвигается · прораб · первый пункт «Требует решения» и «ещё N вопросов» | То же без колонки «Прораб»; вопросы — «Мои вопросы по объекту» |
| Фильтры | Активные · Требуют решения · До договора · Сданы; поиск по адресу, заказчику, прорабу | Активные · Сданы |

Порядок: сначала объекты с вопросами (по самому срочному), затем по дате сдачи. «Требует решения» в строке считается той же функцией, что и в карточке, поэтому цифры совпадают. Если у участника один объект, список пропускается.

**Объект без прораба.** Пункт «Не назначен прораб» в «Требует решения» объекта и на «Главной», кнопка «Назначить» открывает подтверждение с последствиями. После назначения объект появляется в списке прораба. В демо один прораб; при нескольких нужен выбор из списка.

**Сданный объект** — в фильтре «Сданы»: дата сдачи и срок гарантии, новые отметки закрыты.

### Карточка объекта

**Шапка.** Этап, срок сдачи, число отметок на приёмке; название, адрес, площадь, вид ремонта, договор. Полоса «Готовность по объёмам» из двух частей: принято и на приёмке. Действия: «Отметить работу» (только прораб) и «Кабинет заказчика» (только с правом финансов).

**Вкладки и права.**

| Вкладка | Что внутри | Кому видна |
|---|---|---|
| Обзор | См. ниже | Всем с `repairs.projects.read` |
| Работы | Объёмы план / факт, форма отметки прораба, список отметок с приёмкой | Всем; форма — с `repairs.work_logs.submit`, приёмка — с `repairs.work_logs.review` |
| Замер, График, Документы, Снабжение | Разделы из «Расширений» | Всем |
| Смета, Финансы, Оплата бригады, Подрядчики, Кабинет заказчика | Цены заказчика, суммы договоров и оплат | Только с `repairs.finance.read`. Прораб этих вкладок не видит |

**Обзор.**

1. **«Требует решения»** (у прораба — «Мои вопросы по объекту»). Сначала идёт то, что держит работу:
   - отметки на приёмке — у владельца кнопка «Принять объём», у прораба статус «ждёт приёмки»;
   - у прораба — «Отметка за сегодня не отправлена»;
   - документы на подписи у заказчика, акты готовые к отправке (только с правом финансов);
   - заявки на материалы;
   - смета на согласовании.

   Кнопка ведёт в нужную вкладку. Пустое состояние — «Решений не требуется».
2. **Объёмы работ** — по каждой работе: принято из плана и сколько ещё на приёмке.
3. **Фотоотчёт** — фото из отметок со статусом. В кабинет заказчика попадают только фото принятых отметок.
4. **Как попасть на объект** — адрес, подъезд, этаж, домофон, лифт, ключи, время шумных работ. Кнопка «Маршрут» в макете отключена.
5. **Люди на объекте** — заказчик, прораб, бригада (карточки без входа), подрядчик со сроком доступа.
6. **Деньги** — договор, получено, расходы, маржа план. Только с `repairs.finance.read`.
7. **Лента** — отправка и приёмка отметок.

На ширине меньше примерно 840 px колонки обзора идут одна под другой, вкладки прокручиваются вбок.

### Правила карточки

- **Две готовности.** В шапке для команды — готовность по принятым объёмам. Для заказчика — готовность по закрытым актам (правило ниже не меняется). Объём на приёмке в факт не входит.
- **Вес работ.** В макете объёмы складываются напрямую: все работы измеряются в м². В продукте доля работы считается по её стоимости в согласованной смете (RS-07).
- **Приёмка одна.** «Принять объём» в обзоре, на «Главной» и во вкладке «Работы» вызывает одну команду. Повтор отклоняется с `conflict`. При приёмке списываются материалы из отметки.
- **Скрытое не показывается.** Без права финансов нет ни вкладок, ни карточки «Деньги», ни пунктов очереди с суммами. Сервер не отдаёт эти поля.
- «Объекты» в меню открывают список. Пункт с «Главной» открывает нужный объект на вкладке «Обзор».

### Данные и API карточки

Новые поля `objects`: `area_m2`, `rooms`, `kind`, `contract_no`, `due_on`, `client_name`, `foreman_id`, `access jsonb` (список `{icon, text}`: подъезд, лифт, ключи, время работ). Подрядчик — не поле объекта, а назначение с областью «объект» и сроком. В прототипе данные лежат в `ortus/extra-data.js → repair.objects` (пять объектов); у работ, отметок и материалов есть поле `obj`. Разделы «Замер», «Смета», «График» и остальные заполнены только у объекта с `sections: true` (кв. 42), у прочих объектов сводка разделов задана полем `st`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/repairs/projects` | Список объектов (есть в OpenAPI 0.1). PROPOSED: сводка для списка — этап, готовность, сдача и прогноз, прораб, число вопросов. Прораб получает только свои объекты |
| POST | `/repairs/objects/{id}/foreman` | PROPOSED. Назначить прораба; `conflict`, если уже назначен |
| GET | `/repairs/projects/{id}/overview` | PROPOSED. Шапка, очередь решений, объёмы, лента. Суммы только при `repairs.finance.read` |
| POST | `/repairs/work-logs` | Отметка прораба (есть в OpenAPI 0.1 как `submitWorkLog`) |
| POST | `/repairs/work-logs/{id}/accept`, `…/return` | PROPOSED. Принять объём или вернуть с причиной; `If-Match`, идемпотентность |

В OpenAPI 0.1 объект называется `RepairProject`. В интерфейсе — «Объект», в таблицах черновика ниже — `objects`. Перед S3 нужно выбрать одно имя (RS-08).

## Смета: кто правит, версии, допработы, шаблоны

Решено 3 октября 2026 года. Макет: `Ремонт и стройка.dc.html` → «Смета» и «Шаблоны и расценки»; в CRM — вкладка «Смета» карточки объекта, пункт меню «Шаблоны и расценки» и блок «Допработы» во вкладке «Работы».

### Кто что делает

| Роль | Смета | Шаблоны и расценки |
|---|---|---|
| Владелец | Правит сметы всех объектов | Ведёт |
| Сметчик (новая роль) | Правит сметы всех объектов | Ведёт |
| Менеджер заявок | Правит сметы своих заявок | — |
| Замерщик | Правит сметы объектов, где делал замер | — |
| Прораб | Не видит. Предлагает допработы без цен | — |
| Заказчик | Согласует версию и подписывает допсоглашение в кабинете | — |

Права: `repairs.estimates.edit` (составить, править, отправить заказчику, допсоглашения; вместе с `repairs.finance.read`), `repairs.catalog.manage` (справочник и шаблоны), `repairs.changes.submit` (прораб предлагает допработу). Скидка свободная: её даёт любой, у кого есть право правки, отдельного согласования нет.

### Версии

1. Заявка переходит на этап «Замер» → создаётся объект-черновик, замер вносится в него.
2. Черновик сметы собирается по шаблону: объёмы считаются из замера по формулам, цены берутся из справочника на дату сборки. По умолчанию выбран шаблон с тем же видом ремонта, что у объекта.
3. В черновике можно добавить строку из справочника, раздел, поменять объём и цену, удалить строку, задать скидку в процентах. Объёмы «из замера» пересчитываются при изменении замера; если объём поправили вручную, строка больше не пересчитывается, пока не нажать «вернуть из замера».
4. «Отправить заказчику» фиксирует объёмы. Пока заказчик не согласовал, отправку можно отозвать и править дальше.
5. Согласованная версия не меняется, предыдущая получает статус «заменена». До договора правка — новая версия, после договора — только допсоглашение. Договор и акты ссылаются на номер версии.

**Сравнение версий.** Версию сравнивают с предыдущей, черновик — с версией, от которой он сделан. Строки помечены «добавлено», «убрано», «изменено: объём / цена»; для каждой — было, стало и разница, внизу итоги. Строки без изменений скрыты и показываются по ссылке. Строки сопоставляются по идентификатору строки: замена позиции справочника показывается как «убрано» плюс «добавлено».

### Допработы после договора

1. Прораб во вкладке «Работы» описывает работу, указывает объём и единицу, пишет комментарий и прикладывает фото (хотя бы одно). Цен он не видит.
2. У офиса появляется пункт «Требует решения» в карточке и на «Главной», счётчик на вкладке «Смета» и у пункта меню.
3. «Оценить в черновике» создаёт черновик следующей версии: строки действующей версии плюс раздел «Допработы · ДР-N». Несколько допработ можно собрать в одно допсоглашение.
4. «Отправить допсоглашение № K на подпись»: документ появляется в «Документах» и в кабинете заказчика с суммой разницы, заказчик подписывает кодом из SMS.
5. После подписи версия начинает действовать, сумма договора в «Финансах» меняется, работа добавляется прорабу в объёмы, прораб получает уведомление.
6. Офис может отклонить допработу с причиной из списка («Работа уже есть в смете», «Заказчик отказался», «Сделаем по гарантии», «Не согласовано с заказчиком»). Прораб видит причину.

Статусы допработы: `proposed` → `priced` (в черновике) → `sent` (допсоглашение у заказчика) → `signed`, либо `rejected`. Удалённый черновик возвращает допработу в `proposed`, отозванное допсоглашение — в `priced`. Пока допсоглашение у заказчика, новую допработу в него добавить нельзя.

### Шаблоны объекта и справочник расценок

Шаблон привязан к виду ремонта и состоит из шести частей:

| Часть | Что внутри |
|---|---|
| Разделы и работы сметы | Строки со ссылкой на позицию справочника; цена в шаблоне не хранится |
| Формулы объёмов | Из замера: площадь пола, пол без санузлов, площадь стен, стены без санузлов, санузлы (пол и стены), периметр, периметр без санузлов — с коэффициентом (запас, расход на м²). Либо фиксированное количество. Штуки, мешки, рейсы, комплекты и литры округляются вверх |
| Технология графика | Этапы по порядку, выработка, паузы на сушку и опережение (см. «График работ») |
| Комплект документов | Договор, акты по разделам, акт сдачи, гарантийный паспорт со сроком |
| Чек-лист приёмки | Пункты, которые прораб и заказчик проверяют при сдаче |
| Материалы для снабжения | Позиции справочника с расчётом из замера; из них собираются заявки в «Снабжении» |

Откуда берутся шаблоны: стартовые шаблоны Ортуса копируются в организацию при подключении модуля, и организация правит свою копию; «Сохранить объект как шаблон» берёт строки действующей версии сметы с формулами и остальные части исходного шаблона; «Сделать копию» — из любого шаблона. Импорт из Excel не делаем. Правка шаблона не меняет уже созданные объекты и сметы.

Справочник расценок: работы и материалы с разделом, единицей и ценой; видно, в скольких шаблонах используется позиция. Новая цена попадает в черновики, собранные после изменения, и в строки, добавленные из справочника; отправленные и согласованные версии не меняются.

**В прототипе.** Четыре шаблона: «Капитальный ремонт квартиры», «Косметический ремонт», «Коммерческое помещение» (копии Ортуса) и «Ремонт под ключ · дом» (сохранён из объекта «Дом на Лесной»); 23 позиции справочника. Объект-черновик «Дом 120 м², Истра» — сборка сметы по шаблону. «ЖК Речной · кв. 42» — версии 1 и 2, допработа ДР-1 от прораба, допсоглашение и сравнение. Сметы, шаблоны и справочник живут в модуле до перезагрузки страницы; допработы — в API прототипа (`proposeChange`, `setChange`, `ortus/extra-data.js → repair.changes`).

## Снабжение по всем объектам и склады

Решено 3 октября 2026 года. Пункт меню «Снабжение» в группе «Ремонт и стройка» (`page: repairSupply`, счётчик — заявки, которые ждут решения). Макет: `Ремонт и стройка.dc.html` → «Снабжение и склады». Вкладка «Снабжение» в карточке объекта показывает заявки этого объекта и ведёт сюда.

**Основа — общий модуль «Склад»** (OpenAPI 0.1: номенклатура, склады с доступом по области, неизменяемые движения, без ухода в минус). Номенклатура склада — материалы справочника расценок: одна позиция и в смете, и на складе. Складов несколько, по фирмам или регионам; объект тоже держит остаток.

| Роль | Что делает |
|---|---|
| Владелец, снабженец (новая роль) | Решают по заявке: выдать со склада или купить; собирают закупку на несколько объектов; перемещают остатки между объектами |
| Кладовщик (новая роль, область — склад) | Выдаёт зарезервированное по заявке, принимает возвраты и приход |
| Прораб | Пишет заявку, забирает со склада по заявке, сдаёт излишки; цен не видит |

**Заявка прораба.** Ждёт решения → либо «Выдать со склада» (резерв → кладовщик выдал, прораб забрал → на объекте), либо «В закупку» (заказано → получено по чеку QR → на объекте) → списано в работу. Решает офис, система подсказывает: свободный остаток по каждому складу и остатки на других объектах. Статусы: `request` → `reserved` → `issued` или `request` → `ordered` → `bought`, далее `used`.

**Одна закупка на несколько объектов.** Отмеченные заявки группируются по материалу, снабженец выбирает поставщика и цену закупки (по умолчанию — средняя цена склада). Строки закупки хранят объект и заявку, поэтому после получения сумма разносится по объектам.

**Стоимость.** Учёт в количестве и деньгах: закупка — по цене поставщика, выдача со склада — по средней цене склада. Сумма идёт в расходы объекта («Финансы»). Возврат на склад уменьшает расходы объекта и пересчитывает среднюю цену склада; перемещение переносит стоимость на другой объект и, если там есть заявка на тот же материал, уменьшает или закрывает её.

**Движения.** Приход на склад, закупка на объект, выдача со склада, возврат на склад, перемещение между объектами, списание в работу. Не редактируются, ошибка исправляется обратным движением.

Данные (сверх таблиц модуля «Склад»): `supply_requests` — object_id, price_item_id, qty, need_by, state, warehouse_id, purchase_id, cost_minor; `purchases` / `purchase_lines` — supplier, state (ordered/received), receipt_qr; line: request_id, object_id, qty, price_minor. Остаток на объекте — склад типа `object` в модуле «Склад».

API (PROPOSED): `GET /repairs/supply-requests?state=` (все объекты в области), `POST /repairs/supply-requests/{id}/reserve` (склад), `POST /repairs/supply-requests/{id}/issue`, `POST /repairs/purchases` (список заявок, поставщик, цены), `POST /repairs/purchases/{id}/receive` (чек QR), `POST /repairs/objects/{id}/stock/return`, `POST /repairs/objects/{id}/stock/transfer`. Движения пишутся через `POST /inventory/movements` в одной транзакции с сменой статуса.

**В прототипе.** Два склада («Москва · Отрадное», «Мытищи»), 9 заявок с четырёх объектов: плинтус и ламинат 32 класса есть на складе, керамогранит для кв. 42 и кофейни — одной закупкой, остатки сданного «Дома на Лесной» — на возврат. Данные живут в модуле до перезагрузки страницы. Открыто: частичная выдача (часть со склада, остальное купить) и закупка на склад для пополнения — RS-14.

## График работ (диаграмма Ганта)

Добавлено 2 октября 2026 года. Вкладка «График» карточки объекта; макет — `Ремонт и стройка.dc.html` → «График». График отвечает на вопрос «что должно произойти на объекте, чтобы сдать его в обещанный день»: связывает объёмы сметы со сроками, порядком работ и исполнителями.

### Как сделано у других

| Продукт | Что есть | Что берём |
|---|---|---|
| Створка | Этапы сметы переносятся в периоды графика, сроки двигаются на диаграмме, прогресс считается по закрытым актам. Как считается длительность и сдвигаются ли связанные этапы, публично не описано | Черновик из сметы, прогресс по актам |
| Gectaro | График строится из сметы автоматически, работы связываются, при сдвиге одной сдвигаются связанные. В отзывах — привязка только к окончаниям, без смещения в начало | Связи со сдвигом; добавляем опережение |
| Buildertrend | Предшественники с паузой и опережением, базовый план, причина переноса, уведомления исполнителям при сдвиге, критический путь, рабочие дни | Базовый план, причины, уведомления, критический путь |
| JobTread | Группы задач с прогрессом, связи с паузой, сдвиг всего графика; задачи заказчика и подрядчика видны в их кабинетах | Фазы с общей полосой; этапы подрядчика в его доступе |
| Procore | Окно на 1–6 недель для площадки: детальный план без риска сдвинуть основной график | Вид «Ближайшие 3 недели» |

### Решения

1. **Черновик из сметы.** Разделы сметы превращаются в этапы по шаблону технологии («Капитальный ремонт квартиры»). Порядок — технологический; раздел можно разбить на части (электрика черновая и чистовая). Длительность = объём ÷ выработка, паузы — из шаблона. Прораб проверяет черновик, владелец утверждает его вместе с договором.
2. **Связи «окончание → начало» с паузой.** Пауза считается в календарных днях (сушка идёт и в выходные). Отрицательная пауза — опережение: штукатурка начинается за 3 дня до конца электрики в комнатах, где проводка готова. Сдвиг этапа сдвигает последующие.
3. **Базовый план и прогноз.** Базовый план фиксируется при утверждении и меняется только допсоглашением. Прогноз сдачи считается от текущих сроков. Обе даты видны в графике, шапке объекта, очереди «Требует решения» и кабинете заказчика.
4. **Изменение = предпросмотр + причина + уведомление.** Перетаскивание полосы (начало), её края (длительность) или кнопки в карточке этапа создают предпросмотр: что сдвинется и как изменится дата сдачи. Сохранение требует причины. Уведомления получают исполнители затронутых этапов и заказчик, если меняется дата сдачи. На касание полоса только выбирается.
5. **Критический путь и запас.** У каждого этапа считается запас в рабочих днях; этапы без запаса образуют критический путь. Сводка предлагает, какие этапы сократить, чтобы вернуть дату по договору.
6. **Полоса этапа — по факту.** Закрыто актом, принято, на приёмке, запланировано — те же цвета, что у готовности объекта.
7. **Исполнители и материалы.** Этап без исполнителя, исполнитель на двух этапах одновременно и незакупленный материал к началу этапа показываются у этапа и в сводке. Материал связан с заявкой снабжения, срок «нужно к» = начало этапа.
8. **«Ближайшие 3 недели».** Список для прораба по неделям: что идёт, что начинается, готовы ли исполнитель и материалы, что подготовить заранее. На экране уже 640 px — вид по умолчанию.
9. **Рабочий календарь.** Пн–пт и праздники производственного календаря; в макете — 4 ноября.

### Правила графика

- Начавшийся этап не сдвигается: меняется только длительность, окончание — не раньше следующего рабочего дня. Выполненный этап не меняется.
- Этап не начинается раньше, чем позволяют связи. Чтобы начать раньше, уменьшают паузу или длительность предыдущего этапа.
- Дата сдачи — веха, она считается от этапов. Дата по договору меняется только допсоглашением (новый базовый план).
- Перенос без причины не сохраняется; история переносов хранится у объекта. Смена исполнителя сроков не меняет и применяется сразу.
- Прораб переносит этапы своего объекта; подрядчик видит только свои этапы; цен в графике нет.

| Раздел | Что делает | Опирается на |

| Замер | Помещения: длина, ширина, высота, проёмы; площади пола и стен | Формы, файлы |
| Смета | Разделы, работы и материалы; объёмы «из замера» пересчитываются; версии, согласование заказчиком | Справочник расценок (новый) |
| График | Этапы из разделов сметы, диаграмма Ганта, план и факт по отметкам прораба, зависимости | Календарь, задачи |
| Документы | Договор, счета, акты из сметы по шаблонам; подпись заказчика кодом из SMS | Файлы |
| Снабжение | Заявка прораба → закупка → чек по QR → списание на объект | Склад, касса |

| Подрядчики | Временный доступ к одному объекту: отметки, фото, акты | Временные назначения (как пул водителей) |
| Кабинет заказчика | По личной ссылке: этапы, фото, документы на подпись, оплаты | Публичные ссылки (как у форм) |

## Правила

- **Смета.** Согласованная версия неизменяема: до договора правки — новая версия, после — допсоглашение. Отправка заказчику фиксирует объёмы. Договор и акты ссылаются на версию сметы.
- **Готовность объекта** считается по закрытым (подписанным) актам, а не по отметкам прораба.
- **Начисления бригаде** открываются только после подписания акта заказчиком. Исполнитель видит только свои начисления.
- **Финансы объекта** — закрытое право `repairs.finance.read`: прораб, бригада и подрядчики не видят цены заказчика и маржу.
- **Подрядчик** получает назначение с областью «объект» и сроком; цены заказчика ему не видны.
- **Кабинет заказчика** — одноразово выданная ссылка с токеном (хранится только хеш), срок до сдачи объекта, отзыв в один клик; места в тарифе не занимает. Подпись — код из SMS на номер из договора.
- **Простая электронная подпись** по SMS требует соглашения сторон в договоре; формулировку проверяет юрист.
