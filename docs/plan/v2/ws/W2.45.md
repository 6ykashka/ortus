Этап 2 · вид: backend · работа после показа (резерв W2.41…W2.50, `decisions.md` «Ответы владельца 17.10», строка W2.45; D-30 комплекта) · размер S.

## 1. Цель

Ответ владельца 17.10 по D-30: «checklist_versions.definition хранить в формате FormDefinition из OpenAPI: тогда на 4.2 чек-лист и есть форма». Миграция данных и колонка — W2.52; здесь — модуль осмотров:

1. **Чтение.** `getInspectionChecklist` читает `definition` версии и отдаёт его в `InspectionChecklist.definition`; `items` и `requiredPhotoRoles` ответа выводятся из определения (пункты — поля `single_choice`, обязательные ракурсы — обязательные поля `file` `photo_<роль>`), так что определение — источник истины версии.
2. **Публикация.** Встроенная версия 1 пишется с `definition`, собранным в Go тем же правилом, что `fleet.checklist_definition` (сверка двух писателей — integration).
3. **Проверка осмотра по определению** (`submitInspection`): пункт с ключом вне определения — 422 «Неверный пункт чек-листа.»; результат вне вариантов поля — 422; обязательные поля — «N пунктов чек-листа» / «N фото» (409 `inspection_incomplete`, как прежде); ответ из `blockingValues` поля перед выездом блокирует выезд — дефект `blocking` пункта в очередь S2-17 (как критический дефект водителя).
4. **Обратная совместимость.** Версии до 0017 (перенесены миграцией) и версии, вставленные писателями без `definition` (триггер), читаются по определению; версия, определение которой не является формой чек-листа (не проходит сверку со схемой `FormDefinition` и правилами чек-листа), читается по старым `items` и `required_photo_roles`, а `definition` в ответе не отдаётся (поле необязательно). Q-W2.52-21 — сверка определений со схемой — в unit- и integration-тестах.

## 6. Тесты первыми

1. `definition_test.go` (unit): определение встроенной версии (заголовок, поля, варианты, ракурсы, `blockingValues`), вывод версии из определения (круговой проход), отказ для определений, не являющихся формой чек-листа (пусто, ключ не по шаблону, дубль, чужой тип, вариант вне pass/fail/not_applicable, `blockingValues` вне вариантов, `visibility`, файл не `photo_<роль>` или без ограничений), проверка ответов по определению, блокирующие ответы, чтение старой версии по `items`.
2. `checklist_integration_test.go` (testcontainers, тенант B — версии чек-листа тенанта общие, остальные тесты пакета работают в A): встроенная версия = `fleet.checklist_definition`; версия без `definition` (триггер) с `interior` и `failureBlocksRelease`; версия, где определение расходится с `items` (источник — определение) — 422 чужого пункта и варианта, 409 обязательного пункта, 201 по определению; блокирующий ответ — дефект в очереди, рейс в `defect_review`; версия с определением не формы — по `items`, без `definition`; все определения тенанта проходят сверку.

## 10. Риски и решения по умолчанию

- `allowedMimeTypes` и `maxFileBytes` полей фото в этапе 2 не применяются к файлу (HEIC без декодера уходит как HEIC — W2.44; размер и тип проверяет модуль files) — описательные до шага 4.2.
- Поля, кроме `single_choice` (варианты pass/fail/not_applicable) и `file` `photo_<роль>`, и непустая `visibility` осмотру некуда записать — такое определение не форма чек-листа, версия читается по `items` (шаг 4.2, W4.24, расширит).
- Блокирующий ответ — только перед выездом (критичность выбирается до выезда, как у дефекта); при сдаче не действует. Дефект пункта: зона — подпись пункта, описание — комментарий пункта или «{вариант}: {пункт}»; не создаётся, если водитель уже отметил критический дефект той же зоны.
