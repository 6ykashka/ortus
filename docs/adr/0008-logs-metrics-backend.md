# 0008. D-07 · Бэкенд логов и метрик

Статус: принято
Дата: 2026-10-15 · Автор: агент W0.01 · Участники: SRE, DevOps, backend lead
Решение комплекта: D-07 (`design/docs/16-raid-glossary.md`, «Решения, нужные для старта»)
Кто решает: SRE
Блокирует: S0-02 (шаг 0.5) по 16; в плане v2 — W0.04 (CI), W0.06 (OTel collector в стенде), W3.00 (prod-pilot)
Принято: 2026-10-17 — ответ владельца продукта (`docs/plan/v2/po-answers-2026-10-17.md`, D-07); перенёс W2.40. До ответа агенты работали по рекомендации (план v2 §2, B-2).

## Контекст

- `14-engineering.md`, «Стек»: OpenTelemetry (traces, metrics), `log/slog` в JSON; «бэкенд хранения — D-07».
- S0-03: стенд содержит OTel collector. DoD истории (13): «логи без секретов и restricted-полей; метрики и трасса есть».
- Логи содержат ПДн (идентификаторы, иногда телефоны в ошибках) — размещение логов подчиняется D-05.
- Нагрузочные цели шага 3.1: p95 чтения ≤ 500 мс, записи ≤ 800 мс, «шумный» тенант — нужны метрики по тенанту.

## Варианты

1. **Тот стек, что команда уже эксплуатирует** (через OTel collector) — плюсы: нет нового сервиса, есть дежурства и алерты; минусы: если стек вне РФ — конфликт с D-05. Цена: настройка экспортера collector'а.
2. **Grafana-стек (Prometheus или Mimir, Loki, Tempo) в контуре D-05** — плюсы: открытый, работает с OTel; минусы: эксплуатация на команде. Цена: развёртывание и хранение.
3. **Мониторинг облачного провайдера D-05** — плюсы: без эксплуатации; минусы: зависимость от провайдера, ограничения запросов к логам. Цена: подписка.

## Решение

**Принято 17.10.2026** (ответ владельца продукта, `docs/plan/v2/po-answers-2026-10-17.md`, D-07): В коде с первого дня OpenTelemetry; бэкенд в МВП — **мониторинг облака** (D-05); свой стек (Prometheus + Grafana + Loki) — когда появится SRE.

Отличие от рекомендации: рекомендация — «тот стек, что уже эксплуатирует команда; без своего — Grafana-стек в контуре D-05». Своего стека нет, и владелец выбрал не Grafana-стек, а мониторинг облака. Код не меняется (OTel и `slog` JSON уже так и пишутся); меняется только экспортер collector’а — W3.00.

Рекомендация до ответа (история):

Рекомендация: «Тот, что уже эксплуатирует команда» (вариант 1). Приложение пишет только в OTel (traces, metrics) и `slog` JSON в stdout; выбор хранилища меняет только экспортер collector'а. Если своего стека нет — вариант 2 в контуре D-05.

## Последствия

- Проще: код не зависит от бэкенда наблюдаемости; на стенде collector пишет в отладочный экспортер.
- Сложнее: фильтр секретов и restricted-полей — в приложении (до сериализации лога), а не в бэкенде.
- Сделать: W0.06 — collector в compose; W0.09 — `slog` JSON и OTel в `cmd/api`; W3.01 — метрики по тенанту для нагрузки.
- Как проверим: тест логгера — restricted-поля не попадают в вывод; трасса запроса `GET /me/context` видна в collector'е стенда.
