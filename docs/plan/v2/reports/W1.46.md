## Причины

| Флейк | Причина (проверено) |
|---|---|
| `get provider: rootless Docker is not supported on Windows` (`cmd/seed`, `importer`, `org`, `authz`, `cmd/worker`) | testcontainers v0.44 без `DOCKER_HOST` находит Docker на Windows стратегией `dockerSocketPath`, то есть через `os.Stat("//./pipe/docker_engine")`. `Stat` открывает именованный канал. При параллельном старте пакетов он получает `All pipe instances are busy`, а стратегия считает это «сокета нет». Следующая стратегия, `rootless`, на Windows отвечает той ошибкой, которую видно в логе. Результат кешируется `sync.Once` на процесс, поэтому три попытки `tcpostgres.Run` в `accesstest.Start` не помогали. Воспроизведение в scratchpad: 200 параллельных `os.Stat` канала дали 181 ошибку «All pipe instances are busy». Второй прогон: 100 `os.Stat` — 88 ошибок, а 100 параллельных `winio.DialPipeContext` (так клиент Docker подключается при заданном `DOCKER_HOST`) — 0 ошибок |
| `TestCreateAssignmentRacesExtendWorkProfile`, `TestUpdateRoleRacesCreateWorkProfile` | `race` считал, что «моя» команда ждёт политику, раз она не закончилась за `Pause` (400 мс). Детерминированное воспроизведение: «моя» команда стартует с задержкой 2×`Pause`. Тогда W1.05 первой запирает человека и пишет функцию, и «моя» получает 409 вместо неё (T-3 на `50cba22`) |
| `53300 too many clients` (`authhttp`, Q-W1.03-19) | На 22 CPU у `pgxpool` по умолчанию `MaxConns = 22`, у мира две такие пулы. К ним добавляются два `sql.DB` суперпользователя (`NewDatabase`) и два `sql.DB` мигратора, все живут до конца теста; параллельно идут до 22 тестов. Воспроизведение: 16 миров разом — 50 строк `53300` (T-4 на `5d8d0f3`) |

### Новый класс флейков вне объёма WS: loopback-соединения на перегруженной машине

В прогоне 1 `notify/mail` и тесты писем `assignments` упали на `dial tcp 127.0.0.1:<порт>: i/o timeout` к SMTP-серверу `mailtest`, который слушает в том же процессе. `TestSMTPTimeout` с таймаутом 300 мс вернулся через 19,6 с (в прогоне 4 — через 27,3 с). Значит, сам `connect` к loopback висел десятки секунд. Зонд (`listen 127.0.0.1:0` → `dial` раз в 0,5 с, `accept` сразу) во время прогона 3 намерил задержки 11,4 с, 25,9 с, 11,7 с, 14,5 с, 28,2 с, 9,4 с. `TIME_WAIT` при этом 230–970 из 16 384 динамических портов: порты не исчерпаны. На машине Kaspersky (5 продуктов в `SecurityCenter2`), AmneziaVPN и локальный прокси `127.0.0.1:12334`, а CPU занят тестами других агентов на 100 %. Задержки дают сетевые фильтры среды под нагрузкой. В коде WS это не исправить. Предложение — в decisionsNeeded.

## Осталось fixme / открытые вопросы

- `migratetest.Start` (W0.06) при прямом `go test` без `DOCKER_HOST` всё ещё может упасть на канале. Через `ci:local`/`ci:job` путь закрыт env конвейера. Предложение владельцу: задать `DOCKER_HOST` так же, как `accesstest.Start` (`defaultDockerHost`), или вынести хелпер в общий тестовый пакет.
- `access/roles`, `access/groups` по-прежнему ждут `Running(Pause)`. Там одна команда, и после фиксации она видит тот же результат, так что флейка нет, но тест может пройти впустую. Предложение владельцам — перейти на `accesstest.Waiter`.
- Loopback `i/o timeout` в `notify/mail` и тестах писем (см. «Новый класс флейков»). Таймауты тестов `mail` — у W1.41, среда — у человека. 16.10 в прогонах 1 и 2 не повторился.
- `RYUK_RECONNECTION_TIMEOUT` задаёт только конвейер. При прямом `go -C backend test -tags integration ./...` на Windows гонка ryuk остаётся. Обойти её можно, задав env вручную: `$env:RYUK_RECONNECTION_TIMEOUT='5m'`.

### Флейк 4: ryuk сессии умирает между пакетами (исправлен)

Хвост прогона 1:

```
2026/10/16 10:55:02 🐳 Creating container for image postgres:17.11@sha256:2d2b8998…
2026/10/16 10:55:03 ⏳ Waiting for Reaper "530e8052" to be ready
migratetest: Docker недоступен или образ postgres:17.11@sha256:… не запустился — запустите Docker Desktop: run postgres: generic container: create container: reaper: from container "530e8052": wait for reaper 530e8052: context deadline exceeded
FAIL	github.com/ortus/ortus-crm/backend/internal/control/tenants/operators	65.608s
```

**Причина (проверено).** В testcontainers v0.44 у всех пакетов одного `go test` одна сессия: `bootstrap.go` хеширует PID родителя и время его старта. Значит, и ryuk у них один. Ryuk завершается через `RYUK_RECONNECTION_TIMEOUT` (по умолчанию 10 с) после того, как отключилось последнее соединение. При `-p 2` (или `-p 4`) на нагруженной машине следующий пакет собирается и линкуется дольше 10 с. Тогда он находит контейнер ryuk, который ещё в списке, но уже гасится (`reaper.go`: `lookupContainer` → `fromContainer`). Дальше `wait.ForLog("Started")` получает ошибку `Logs()` и повторяет запрос до таймаута стратегии в 60 с. Повтор `reaperSpawner` ограничен 20 с и к этому моменту исчерпан.

**Воспроизведение** (`reaprepro` в scratchpad оркестратора: тестовый бинарь запускается несколько раз подряд из одного процесса PowerShell, у всех запусков одна сессия, пауза между запусками задаётся `REPRO_SLEEP`):

- По умолчанию (10 с), паузы 9,0–11,5 с, 30 запусков. 3 падения: `wait for reaper c49025ff: context deadline exceeded` через 1m1s (ровно ошибка прогона 1), `port endpoint: invalid port`, `detect internal port: … unexpected container status "removing"`. Ещё в 10 запусках `Reaper handshake failed: read ack: EOF`: пакет прошёл, но его контейнеры остались без защиты ryuk.
- С `RYUK_RECONNECTION_TIMEOUT=5m`, 12 запусков с паузами 9,0–11,5 с (плюс первый запуск, который создаёт ryuk). 0 падений и 0 `handshake failed`, каждый раз `🔥 Reaper obtained from Docker for this test session 44d2cc2c` — один и тот же ryuk.

**Исправление.** `tools/ci/pipeline.mjs` (`dockerEnv`): шаги `go-integration`, `go-isolation`, `go-concurrency` на win32 получают `RYUK_RECONNECTION_TIMEOUT=5m`, если таймаут не задан ни под одним из двух имён (`RYUK_…`, `TESTCONTAINERS_RYUK_…`). На linux без env поведение прежнее. После прогона ryuk живёт ещё до 5 минут без соединений и завершается сам; тестовые контейнеры тесты гасят сами.
