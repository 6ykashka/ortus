# Обзор технологий Ортус

Версия 0.1. Проверка источников 30 сентября — 1 октября 2026 года.

## Что известно о текущем проекте

Пользователь выбрал Go для backend. Прежние правила модулей проекта описывают Go-пакеты `apps/api/modules/{id}` и интерфейс `apps/web/src/modules/{id}`; упоминаются маршруты Next.js, общий контекст, PostgreSQL и отдельные базы тенантов. Это сведения из проектных документов. Репозиторий, `go.mod`, lockfile фронтенда, миграции и инфраструктура не проверялись, поэтому наличие конкретной библиотеки или рабочей функции не считается установленным.

Перед реализацией составить фактическую ведомость: компонент → версия → лицензия → владелец обновлений → известные ограничения → где используется. Если существующий код уже решает задачу, сохранить совместимость или оформить обоснованную миграцию. Переход с упомянутого в старом обсуждении NestJS на Go нельзя считать выполненным без чтения репозитория.

## Что известно о конкурентах

Публично подтверждены функции и интеграционные поверхности YCLIENTS, Stworka, Jira, Confluence и сервисов маршрутизации. Полный актуальный backend stack этих продуктов по изученным источникам не установлен. Веб-интерфейс и наличие REST API не позволяют определить язык сервера, способ разделения клиентов и внутреннюю СУБД.

В конкурентном обзоре зафиксированы только опубликованные возможности. Ни Go, ни PostgreSQL, ни выбранная нами модель модулей не приписываются конкурентам. Их пользовательские сценарии полезны как ориентиры, а технический стек Ортус выбирается по нашим ограничениям.

## Рекомендуемый стек первой версии

Таблица содержит предложения, а не установленный стек проекта. Точные поддерживаемые версии закрепляются при создании репозитория и проверяются CI.

| Слой | Предложение | Причина выбора | Что проверить перед фиксацией |
|---|---|---|---|
| Backend | Go, стандартный `net/http`, chi при необходимости | Явные зависимости, простой HTTP-контур и составные маршруты | Существующий router, версия Go, timeouts и graceful shutdown |
| Работа с БД | PostgreSQL + pgx + sqlc | Явные SQL-запросы, типизированный доступ, удобный контроль scope | Сложные запросы, миграции, транзакционные интерфейсы |
| Мультитенантность | Control DB + отдельная DB клиента | Простая граница tenant data, восстановление отдельного клиента | Пулы соединений, предел числа БД, миграции и стоимость эксплуатации |
| Frontend | TypeScript + React; сохранить Next.js, если он есть | Богатые таблицы, формы, интерактивный календарь и адаптивность | Не переносить бизнес-инварианты во второй backend Next.js |
| UI | Одна существующая библиотека и дизайн-токены | Повторное использование компонентов и единая доступность | Не смешивать HeroUI, shadcn и собственные копии одного компонента |
| Вход | OIDC, Keycloak как кандидат IdP | Вход, SSO, MFA и централизованный жизненный цикл identity | Эксплуатация, резервирование, корпоративные подключения |
| Прикладные права | Собственное ядро action + scope + conditions + fields | Организационные и отраслевые правила не равны ролям IdP | Единый evaluator и SQL-фильтрация без обходов |
| Файлы | Приватное S3-совместимое хранилище | Фото отдельно от OLTP, загрузки с ограниченными возможностями | Поведение конкретного провайдера, lifecycle, шифрование, резервные копии |
| Фоновые работы | Go worker, PostgreSQL outbox/inbox | Надёжные повторяемые операции без обязательного брокера | Lease, retries, дедупликация, dead-letter и ручной повтор |
| Кэш и лимиты | Сначала без обязательного кэша; Redis/Valkey после обоснования | Меньше эксплуатационных компонентов в пилоте | Invalidation прав, лимиты, лицензия выбранной версии |
| Поиск | PostgreSQL full-text для первой версии | Не нужен отдельный поисковый кластер для раннего пилота | Русская морфология, объём индекса и права в поисковой выдаче |
| Аналитика | Защищённые запросы и витрины PostgreSQL | Общие фильтры доступа и прослеживаемость данных | Не мешать тяжёлыми отчётами коротким транзакциям |
| API | OpenAPI 3.1, JSON, HTTP, типизированный TS-клиент | Согласованный контракт до параллельной разработки | Совместимость выбранных генераторов с используемыми конструкциями |
| Наблюдаемость | Метрики и трассировки OpenTelemetry, структурированные логи | Связь UI-запроса, API и фоновой операции | Не писать токены, содержимое форм и фото в логи |
| Доставка | Контейнеры, CI, staging, управляемые миграции | Повторяемое развертывание и откат приложения | Restore drill, секреты, миграции разных tenant versions |

Go определяет серверную часть. Для насыщенного конструктора форм, таблиц и календаря предлагается TypeScript на клиенте. Вариант Go templates + HTMX можно оценить для более простого интерфейса; он не считается выбранным для описанного сложного конструктора.

## Почему начать с модульного монолита

Бронирование специалиста и кабинета, завершение визита и списание материалов, возврат машины и изменение доступности требуют согласованности. В одном tenant DB такие операции можно выполнить одной транзакцией через явно объявленные интерфейсы модулей. Уведомления и аналитические проекции отправляются через outbox после успешной записи.

Модуль имеет собственные таблицы, миграции и контракт; другие модули не редактируют их напрямую. Критичная межмодульная транзакция использует общий transaction coordinator и интерфейсы сервисов, а не скрытое событие с обещанием «когда-нибудь догнать». Некритичные подписчики допускают eventual consistency и показывают время обновления.

Микросервис выделяется при измеренной необходимости: независимая нагрузка, иной цикл выпуска, отдельная команда или требование изоляции. Первые кандидаты — обработка медиа, тяжёлые экспорты и оптимизатор маршрутов. Сам факт наличия подключаемого модуля не требует отдельного сервиса и базы.

## База данных и расширяемость

Типизированные таблицы хранят деньги, движения склада, интервалы брони, состояние рейса и принадлежность ресурса. Пользовательские поля используют metadata schema и проверенные значения, например JSONB с типами и ограничениями. Системные поля не подменяются пользовательским полем с тем же названием.

Запросы используют явные индексы и ограничения целостности. PostgreSQL поддерживает исключающие ограничения для непересекающихся диапазонов [T4]; это подходящий механизм для ресурсов единичной вместимости. Для вместимости больше единицы требуется отдельный алгоритм проверки и блокировки. Проверка «сначала SELECT свободно, потом INSERT» без транзакционной защиты недостаточна.

RLS может служить дополнительным рубежом, но его нельзя объявлять автоматической защитой всего приложения: суперпользователи и роли BYPASSRLS обходят политики, а владельцы таблиц обычно тоже [T5]. Runtime и migration роли должны различаться. Connection pool сбрасывает контекст, а задача всегда несёт проверяемый tenant identity.

Система отдельных БД не даёт бесплатного масштабирования. Нужны ленивые ограниченные пулы, закрытие неактивных соединений, реестр версии схемы, canary-миграции, фоновые очереди с tenant fairness и лимит тяжёлых запросов. Возможность перенести крупного клиента на отдельный кластер сохраняется через реестр подключения.

## Вход и realms

Keycloak realm управляет набором identities и изолирован от других realms [T6]. Предлагается общий realm клиентов платформы, бизнес-членства в Ортус и отдельный административный контур. Это позволяет сотруднику использовать один вход для нескольких бизнесов, сохраняя разделённые прикладные данные.

Realm на каждый бизнес допустим при доказанном требовании независимой identity-политики. Он не заменяет scope-проверки модулей и не нужен автоматически из-за наличия tenant DB. Все рабочие роли, ограничения по регионам, начислениям и объектам проверяет приложение.

## Файлы и квоты

Подписанный URL предоставляет временное право на конкретную операцию [T7]. Выданный URL не следует считать обычной ссылкой, которую можно без последствий публиковать. На выдаче проверяются tenant, объект и разрешение; на завершении загрузки проверяются размер, checksum и допустимый источник.

Фотографии резервируют место до загрузки, затем переводятся в фактическое использование. Неподтверждённые загрузки и карантин имеют собственный срок очистки. Политика удаления исходного объекта, производных изображений и версий задаётся явно. Возможности Amazon S3 не приписываются без проверки любому S3-совместимому серверу.

## Маршрутизация

Первая версия хранит маршрут и проверяет ограничения: вес, объём, габариты, оборудование, временные окна и температурную совместимость. Вычисление дорог и времени — адаптер картографического провайдера. Квоты запросов, коммерческие условия и территория покрытия уточняются при выборе поставщика.

Полноценная оптимизация маршрутов — отдельный этап. OR-Tools документирует задачи маршрутизации с ограничениями [T10]; это кандидат для отдельного сервиса, а не готовая функция, автоматически появляющаяся в Go. Требования к точности, времени расчёта, переназначению и невозможным заказам описываются до выбора solver. Система показывает неподходящие и нераспределённые заказы, а не скрывает их за красивым маршрутом.

## Варианты эксплуатации

Пилот может работать на контейнерной инфраструктуре с отдельно управляемыми PostgreSQL, хранилищем и резервным копированием. Если у команды уже есть устойчивый Kubernetes-контур, допустимо использовать его. Создание нового сложного кластера само по себе не является условием выпуска первой версии.

Минимальный набор процессов: web, Go API, worker, provisioner для создания/миграции tenants, IdP, PostgreSQL и объектное хранилище. Provisioner имеет административные права БД, которых нет у обычного API. Операторы не получают доступ к содержимому бизнеса автоматически через экран управления подпиской.

Резервные копии проверяются восстановлением конкретного клиента вместе с версиями файлов. Целевые RPO/RTO и задержки из ТЗ — цели испытаний. Числа пользователей на одной машине и себестоимость сервиса нельзя корректно обещать без нагрузочного профиля и выбранного размещения.

## Какие инструменты пока не вводить

Kafka, Elasticsearch, ClickHouse, Redis, service mesh и Kubernetes не должны появляться только ради списка технологий. Для каждого нового компонента нужен конкретный предел текущей реализации и ожидаемый измеримый эффект. ClickHouse может стать аналитическим контуром при подтверждённом объёме данных, но не источником истины для брони и денег.

Ни внешний движок workflow, ни графовая авторизация не исключены навсегда. На старте достаточно ограниченного движка переходов и вычислимого action/scope доступа. При расширении важна миграция существующих правил и объяснение итогового разрешения.
