## Сделано

Ответ владельца 17.10 по D-30: «checklist_versions.definition хранить в формате FormDefinition из OpenAPI: тогда на 4.2 чек-лист и есть форма». Колонку, функцию `fleet.checklist_definition`, триггер и перенос данных сделал W2.52 (tenant 0017). W2.45 перевёл модуль осмотров на определение: теперь оно источник данных версии.

- **`backend/internal/modules/fleet/inspections/definition.go`** (новый):
  - `checklistDefinition` — `FormDefinition` версии по правилу 0017. Заголовок «Осмотр перед выездом» или «Осмотр при сдаче». Пункты — поля `single_choice` с вариантами pass/fail/not_applicable («Исправно», «Неисправно», «Не применимо» — временные подписи до Q-W2.52-8, как в 0017 и MSW); у блокирующих пунктов есть `blockingValues`. Ракурсы — обязательные поля `file` `photo_<роль>` («Спереди»…«Одометр», «Груз», «Повреждение»): один JPEG до 20 МБ.
  - `parseDefinition`, `readForm` — строгое чтение. Сверяется со схемой `FormDefinition` (без лишних свойств, длины, 1–200 полей, ключ `^[a-z][a-z0-9_]{0,63}$`, уникальность) и с правилами чек-листа:
    - есть хотя бы один пункт;
    - у `single_choice` варианты только из pass/fail/not_applicable, без повторов; `blockingValues` — среди вариантов;
    - `file` — только `photo_<роль контракта>` с `maxFiles`, `allowedMimeTypes`, `maxFileBytes`, без вариантов;
    - других типов нет, `visibility` пустая.
    Необязательный пункт и необязательное фото допустимы. Необязательное фото разрешено, но в `requiredPhotoRoles` не входит.
  - `readVersion` — обратная совместимость. Если определение — форма чек-листа, версия читается по нему. Иначе — по старым `items` и `required_photo_roles` (tenant 0002: `back` → `rear`, `interior` пропускается), и `definition` в ответе не отдаётся (поле необязательно).
  - `checkAnswers` — ответы осмотра сверяются с версией. Пункта нет в версии → 422 «Неверный пункт чек-листа.». Результата нет среди вариантов пункта → 422 «Для пункта «{подпись}» такого результата нет.».
  - `blockingDefects` — ответ из `blockingValues` перед выездом создаёт критический дефект пункта. Зона — подпись пункта (до 100 символов), описание — комментарий пункта или «{вариант}: {пункт}». Дефект не создаётся, если водитель уже отметил критический дефект той же зоны. При сдаче ответ не блокирует: критичность выбирается только перед выездом.
- **`checklist.go`**:
  - `getInspectionChecklist` читает `definition` и отдаёт `InspectionChecklist.definition`;
  - `items` и `requiredPhotoRoles` ответа берутся из определения (по контракту они по-прежнему источник экранов этапа 2);
  - встроенная версия 1 пишется с `definition`, собранным в Go. Он совпадает с `fleet.checklist_definition` до jsonb — это проверяет integration-тест. Триггер остаётся для писателей без `definition`.
- **`submit.go`**:
  - `checkEvidence` возвращает версию и проверяет ответы по определению: после проверки версии, до «Осмотр не завершён: …»;
  - обязательность пунктов и ракурсов берётся из определения;
  - `withBlockingAnswers` добавляет дефекты блокирующих ответов к отмеченным водителем. Дальше путь тот же, что у критического дефекта W2.04: осмотр `requires_review`, дефект `in_review` в очереди, рейс `defect_review`, машина недоступна, бронь сохраняется, менеджеры получают уведомление.
- **`rules.go`** — у `checkItem` появились `Options` и `Blocking` (`json:"-"`: формат `items` в базе не меняется), у `checklist` — `Definition`. **`doc.go`** — абзац о версии как форме.
- **Фронтенд не менялся.** Экран водителя (W2.22, `driver/api.ts`, `model.ts`) читает `items` и `requiredPhotoRoles`, а их значения у встроенной версии остались прежними. Определение экрану этапа 2 не нужно; на шаге 4.2 по нему будет строиться форма (W4.24).

## Осталось fixme / открытые вопросы

`fixme` нет. Вопросы ниже, значения по умолчанию — как сделано; внести в `docs/plan/decisions.md` (файл интегратора):

1. **Q-W2.45-1 · определение — источник версии (технический).** `items` и `requiredPhotoRoles` ответа выводятся из `definition`; колонки `items` и `required_photo_roles` читаются, только если определение не форма чек-листа. Писатели без `definition` по-прежнему получают его от триггера 0017. Расхождение `items` и `definition` в одной строке разрешается в пользу определения.
2. **Q-W2.45-2 · ответ вне определения (продукт, отличие от MSW).** Пункт с ключом вне версии — 422 «Неверный пункт чек-листа.» (раньше пропускался молча). Результат вне вариантов пункта — 422 «Для пункта «{подпись}» такого результата нет.» (текст временный, в эталоне нет). Клиенты этапа 2 шлют только ключи `items`, поведение экранов не меняется. MSW (`fleet/inspections.ts`) чужие ключи не отклоняет — для паритета нужна правка стюарда.
3. **Q-W2.45-3 · блокирующий ответ (продукт).** Ответ из `blockingValues` перед выездом не выпускает машину: создаётся критический дефект пункта (зона — подпись пункта, описание — комментарий или «Неисправно: {пункт}»), дальше путь S2-17. Если водитель уже отметил критический дефект с той же зоной, второй дефект не создаётся; некритичный дефект зоны блокирующий ответ не заменяет. При сдаче ответ не блокирует. Во встроенной версии `blockingValues` нет (`failureBlocksRelease = false`, W2.04 п. 8), поэтому поведение показа не меняется. Альтернатива — 422 «опишите неисправность», чтобы водитель сам отметил дефект.
4. **Q-W2.45-4 · что не считается формой чек-листа (технический, к шагу 4.2).** Типы, кроме `single_choice` и `file` `photo_<роль>`, и непустую `visibility` осмотр записать не может (в `InspectionCreate` для них нет полей). Такая версия читается по `items`, без `definition`. Расширение — W4.24 вместе с ответом формы.
5. **Q-W2.45-5 · ограничения файла поля фото (технический).** `allowedMimeTypes [image/jpeg]` и `maxFileBytes` к файлу в этапе 2 не применяются. HEIC без декодера уходит как HEIC (W2.44), тип и размер проверяет модуль files (до 20 МБ). Применять ограничения из определения — на шаге 4.2 или после решения Q-W2.52-8.
