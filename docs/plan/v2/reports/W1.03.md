## Сделано

- **`backend/internal/platform/session/oidc/`** — OIDC-клиент BFF на stdlib (новых зависимостей нет):
  - `Provider`: discovery (кеш 1 ч, issuer сверяется), URL авторизации (`response_type=code`, PKCE S256, state, nonce, `scope=openid email profile`), обмен кода (`client_secret_basic`, `code_verifier`), проверка ID token (JWS RS256/ES256 по JWKS, `alg=none`/HMAC отвергаются, ключ типа = alg; `iss`, `aud`/`azp`, `exp`, `iat`, `nonce`, `sub`; неизвестный `kid` перечитывает JWKS, тот же неизвестный `kid` — не чаще раза в 30 с), `EndSessionURL` (`client_id`, `post_logout_redirect_uri`);
  - `ErrUnavailable` → 503, `ErrRejected` → 401; `NewPKCE`, `RandomToken`, `Hash`;
  - durable-хранилища control DB: `PGSessionStore` (`session.Store` + `Revoke`/`Revoked`; в БД SHA-256 идентификатора; отозванная, истёкшая сессия и сессия заблокированного аккаунта не аутентифицируют; уборка истёкших), `PGLoginStore` (одноразовая запись входа, `delete … returning`, срок 10 мин), `PGAccounts.Upsert` (аккаунт `iss`+`sub` при первом входе без членств; активный следует почте IdP, имя не трогает; `locked`/`deleted` не обновляется); `MemLoginStore`, `MemSessionStore` для тестов;
  - `oidctest` — фейковый IdP (discovery, token, JWKS, logout, RS256/ES256, ротация ключа, `Authorize` играет браузер и пользователя).
- **`backend/internal/platform/session/oidc/authhttp/`** — strict server тега `Auth`:
  - `startLogin`: `returnTo` по шаблону контракта (≤ 512, CWE-601), realm операторов для `/platform…` (D-03, ADR-0001/0004), запись входа, pre-auth cookie `ortus_login` (`__Secure-ortus_login` в prod; HttpOnly, SameSite=Lax, `Path=/api/v1/auth`, `Max-Age=600`) с непрозрачным дескриптором, 302;
  - `completeLogin`: гасит pre-auth cookie, потребляет запись, state за постоянное время, `error=access_denied` → 403, `server_error`/`temporarily_unavailable` → 503, без `code` → 400, неподтверждённая почта → 403, `locked` → 403, старая сессия удаляется (фиксация), `IssueFor` с issuer и `auth_time`, 302 на `returnTo`; причины отказа — в лог без токенов;
  - `getCsrfToken` (синхронизирующий токен сессии и срок), `logout` (`Revoke` с `Idempotency-Key`, `endSessionUrl` провайдера сессии или `null` для dev), `ReplayLogout` (повтор после отзыва: тот же ключ, CSRF-токен той сессии и разрешённый Origin → тот же 200 с `Idempotency-Replayed: true`; иначе 401 шлюза — Q-W1.01-10);
  - `inspectInvitation` (Origin, если прислан, — из `ALLOWED_ORIGINS`; токен 32…256 → иначе 422), `acceptInvitation` (сессия, токен);
  - `createRealtimeTicket` (появился в 0.4.0-stage1) — 501, пока W1.07 не задаст `Server.Realtime`;
  - `WithExchange` — запрос и writer вызова в контексте (strict server не даёт поставить несколько cookie).
- **`backend/internal/modules/access/invitations/`** — `Issue` (токен 32 байта base64url, в БД SHA-256, срок 7 дней, автор — членство или приглашение владельца), `MaskEmail` (`o•••••@alta.example`), `Service.Inspect` (статус `pending/accepted/revoked/expired`, скрытая организация → 404), `Service.Accept` (порядок возврата 2): `tenant_id` приглашения без блокировки → `FOR UPDATE` строки `tenants` (принятия в одном бизнесе по очереди) → `FOR UPDATE` приглашения вместе с состоянием бизнеса → почта аккаунта = почта приглашения (403) → `invalid_transition`/`public_token_expired` → состояние организации (403 `tenant_suspended`/`tenant_read_only`, 404) → профиль уже `active`/`suspended`-участник → 409 → своё членство (`active`/`suspended` → 409; `invited`/`ended` — активируется), иначе `invited`-членство профиля (сид, раньше выданное) переходит к вошедшему аккаунту, иначе новое; `ended` и новое членство проверяют место (`tenant_seat_usage` против `entitlements.seats` → 409 `seats_exhausted`) → транзакция tenant DB (профиль ↔ членство, имя вместо почты-заглушки, `dormant` → `active` только для назначений из `invitations.role_assignment_ids` с непросроченным `valid`, `policy_version + 1`, `audit.events` `access.invitation.accept`) → control (членство, `owner_bindings` для `grants_owner`, `accepted_*`, `last_tenant_id`/`last_tenant_at`).

6. **(продукт) Принятие приглашения:** членство создаётся при принятии (у приглашённого может не быть аккаунта); `invited`-членство профиля (сид или W1.06) переходит к вошедшему аккаунту; активный и приостановленный участник второе приглашение в тот же бизнес не принимает (409); место проверяется для нового и для `ended`-членства (`invited` уже занимает место); без записи `seats` — без лимита.
