Подготовил аналитик DoR для W4.00, часть 1, 19.10.2026. Этап плана — 6 (W6.00…W6.24, W6.90). Этот разбор заменяет `docs/plan/analysis/06b-repair-child-layout.md` (снимок 03.10, 906 строк).

**Источники.** Все файлы взяты из экспорта `Downloads/Ортус CRM_ первая итерация/export/ortus-crm-design/` и только читались:

- `ortus/api.js`, `ortus/extra-data.js`, `ortus/models.js`, `ortus/mock-data.js`, `docs/19-construction.md` (версия 0.4), `docs/12-errors-and-events.md`, `docs/16-raid-glossary.md`, `README.md` («Итерация 7»).

**Сверка экспорта с `design/` (`main`).** Почти все файлы совпадают побайтно: `Ортус CRM.dc.html`, `Объекты - варианты.dc.html`, `ortus/*.js`, `docs/16`, `docs/19`. Отличается только `Ремонт и стройка.dc.html`: в `design/` лежит версия на 905 строк, в экспорте — на 1707. Новые части модуля:

## 0. Сводка

1. Модуль собран из двух файлов. Карточка, список, обзор и вкладка «Работы» лежат в основном файле (`CRM:1901–2123`, логика `CRM:4261–4434`) и работают через `ortus/api.js`. Остальные вкладки объекта и две страницы группы — это дочерний DC-компонент `<dc-import name="Ремонт и стройка">` (`CRM:2121`). Его состояние хранится локально в `window.__ortusRepairStore` до перезагрузки страницы (`:842–843`, `:1050`). Права дочерний компонент не проверяет. В API он ходит только через `onChange`, то есть через `api.setChange`, а других вызовов у него нет.
2. Обмен с CRM: CRM передаёт `tab`, `obj`, `changes`, `can-edit` (`= repairs.edit && finance.read`, `CRM:4270`); дочерний компонент возвращает сводку `onStatus`. Состав сводки (`:1667–1671`): `sched`, `req`, `draft`, `sms`, `est`, `estLabel`, `fin`, `objEst`, `reqBy`, `hub`. Из неё CRM строит шапку, бейджи, «Требует решения», «Деньги» и счётчик «Снабжения» в меню.
3. Полные данные есть у двух объектов: `obj-42` (действующий) и `obj-50` (черновик; у него только «Замер» и «Смета»). У остальных четырёх вкладки заменены заглушкой (`CRM:2067–2075`). Документы, финансы, оплата бригады, подрядчики и кабинет всегда считаются от `obj-42`, даже если передан другой `obj` (`:1648–1650`, `:1656`, `:1683`).
4. Сейчас в контракте 4 операции Repairs: `listRepairProjects`, `createRepairProject`, `listWorkLogs`, `submitWorkLog`. По экранам и `docs/19` нужно около 60 операций (§2.2). План указывает «~35» (W6.00), и эту оценку стоит пересмотреть.
5. Права. В `permissions.yaml` уже есть 15 ключей `repairs.*`, 10 из них PROPOSED. Ошибки ремонта уже заведены в `errors.yaml`: `estimate_version_locked`, `estimate_draft_exists`, `change_order_closed`, `agreement_pending`, `public_token_expired`. В прототипе (`models.js:56–57`) ключи называются по-другому (`repairs.worklogs.create` и т. п.), а финансы проверяются общим флагом `role.finance.read`.
6. Домена ремонта в репозитории нет. Есть только манифест меню W1.20 и запись `out-of-stage` для «Главной». Backend-модуля и миграций тоже нет; под них зарезервирован блок 0050–0059.
7. Самые дорогие части:
   - «График» — CPM, Гант и drag: шаблон `:279–511`, логика `:936–997` и `:1063–1311`;
   - «Смета» — шаблон `:103–277`, логика `:1313–1488`;
   - «Снабжение и склады» — шаблон `:724–829`, логика `:1544–1642`.

### 1.5 Пустые состояния, ошибки, загрузка

- **Пустые состояния.** Список — 3 варианта (§1.2). «Решений не требуется». «Фото появятся с первой отметкой прораба». «Допработ по объекту пока нет.». «Сметы ещё нет. …». «В разделе пока нет строк …». «Новых допработ нет.». «Строки не менялись.». «Работ по графику нет». «Все заявки разобраны.». «Закупок пока нет.». «Остатков на объектах нет.». «Ничего не найдено.» (2 места). Заглушка вкладки.
- **Ошибки (`role="alert"`).** Форма отметки — тексты `api.js:899–907`: «Выберите работу этого объекта», «Отметку по объекту отправляет его прораб», «Объект сдан: новые отметки не принимаются», «Объём должен быть больше нуля», «Объём превышает план более чем на 10%: осталось …», «Отметьте работников», «Добавьте хотя бы одно фото». В графике «Сохранить и уведомить» неактивна без причины.
- **Загрузка.** Скелетонов нет. ### 3.3 Области (W4.01)

- **Объект.** У `repairs.*` в каталоге область `project`, но `tasks.*` тоже используют `project` (проект задач). `scope_kind = 'project'` с одним `scope_ref` не различает «проект задач» и «объект ремонта». Решение RS-08 в W4.01 должно назвать вид области. По умолчанию: отдельный вид `repair_project` (Q-W4.00-repair-2).
- **Связь (relation).** Нужна для двух ролей: менеджер заявок правит сметы «своих заявок» (связь «исполнитель задачи-заявки») и замерщик — «объектов, где делал замер» (связь «автор замера»). В W4.01 relation перечислена, нужно добавить две разновидности.
- **Склад (warehouse).** Кладовщику, для `inventory.*`. Есть в `scope_kind`, но не входит в список расширений W4.01.
- **Временное назначение.** Подрядчику: область — объект, плюс `until`. Как у пула водителей: assignment со сроком, фаза 1.
- **Касса (account).** Выплаты бригаде через кассу (W5.31, область «касса»).
- **Публичный контур.** Заказчик не участник организации: кабинет открывается по токену, места не занимает.

### 3.4 Ограничения функций

- `repairs.finance.read` и `repairs.estimates.edit` — restricted: их нет в шаблонах по умолчанию, функция driver запрещена.
- `estimates.edit` действует только вместе с `finance.read`. Это проверка сочетания при сохранении роли, по аналогии с `separation_of_duties_conflict`.
- Прорабу, бригаде и подрядчику суммы не отдаются на сервере. Сейчас `view()` удаляет только `o.st.fin` (`api.js:221`), а дочерний компонент отдаёт всё.

## 5. Расхождения

**Прототип и документ:**

1. «Шаблоны и расценки» в меню. По документу — только с `repairs.catalog.manage`. В прототипе пункт виден владельцу без проверки (`CRM:2984`), а правка зависит от права на смету (`:1680`). Манифест W1.20 следует документу.
2. «Принять объём» на «Главной». По документу это та же команда. В прототипе кнопка «Принять» только открывает обзор (`CRM:4064`).
3. Режим только чтения. По документу при отключённом модуле «новые операции закрыты». А `acceptWorkLog` не вызывает `assertActive` (`api.js:914`), и приёмка проходит в режиме только чтения.
4. Списание материалов. По документу оно происходит при приёмке: материалы из отметки, номенклатура = справочник. В прототипе два несвязанных списания:
   - CRM уменьшает `repair.materials` (`mt1…`, «Грунтовка», «Шпаклёвка»);
   - дочерний компонент списывает заявку кнопкой «Списать на объект» (`useUp`, `:1559`).

   Материалы формы отметки не совпадают с позициями справочника `m-*`.
5. Скрытие сумм. По документу «сервер не отдаёт эти поля». В прототипе:
   - `view()` удаляет только `st.fin`;
   - дочерний компонент держит сметы и деньги локально и скрывает их только вкладками;
   - в контракте `RepairProject.budget` обязателен и не закрыт правом финансов.
6. Заявка на материал прораба. В документе есть, в прототипе формы нет нигде, заявки только в сиде.
7. Объект-черновик. По документу он создаётся на этапе «Замер» заявки. В прототипе он есть только в сиде: переход заявки в `api.js` ничего не создаёт (`api.js:24`).
8. Права графика. По документу прораб переносит этапы, а подрядчик видит только свои. В прототипе проверок прав в графике нет, а уведомления — только текст `notice` (`:1088`), событий нет.
9. Рабочий календарь. По документу — производственный календарь. В прототипе праздник один, 04.11 (`HOL = [30]`).
10. Цена закупки по умолчанию. По документу — средняя цена склада. В прототипе `buyPrice` берёт цену любого склада, а если её нет — 85 % цены справочника (`:1547`). Подсказка на экране говорит «или последняя закупка».
11. Устаревшие места в самом документе:
    - RS-05 перечисляет «Снабжение» как кандидата, хотя пункт уже добавлен;
    - `supply_requests` описан дважды с разными полями (стр. 207 и 309);
    - `stages` дублирует `schedule_stages`;
    - `/repairs/supply-requests/{id}/receipt` дублирует `/repairs/purchases/{id}/receive`.
12. Готовность. По документу — две готовности, причём в продукте по стоимости (RS-07). В прототипе:
    - CRM суммирует м² работ `w1–w3`;
    - дочерний компонент считает готовность для заказчика как «доля демонтажа + 8» (`:1650`);
    - 1a показывает третью величину, «выполнено 40%».

**Внутри прототипа:**

13. Две модели работ. Работы карточки CRM у кв. 42 — «Подготовка стен, Грунтование, Монтаж перегородок» (м²). Смета и график — «Демонтаж, Электрика 38 точек, Стены, Полы». Связь «работа ↔ строка сметы ↔ этап графика» не задана.

**Прототип и контракт:**

26. `WorkLogLine` устроен как строка на работника (`workerId`, `quantity`, `presenceMinutes`). В прототипе отметка — это одна работа, один объём, список бригады, материалы и счётчик фото. Единицы контракта hour/m2/m3/m/piece. В прототипе встречаются шт, м, м², рейс, меш, л, компл.

## 7. Вопросы владельцу продукта

Формат: вопрос → значение по умолчанию. Это значение действует до решения.

- **Q-W4.00-repair-1.** Как называется сущность в API: `project` или `object` (RS-08, Q-81)?
  По умолчанию: `RepairProject` и пути `/repairs/projects/{projectId}`; `/repairs/objects/*` из `docs/19` переименовываются. В интерфейсе — «Объекты».
- **Q-W4.00-repair-2.** Вид области для объекта ремонта: общий `project` с проектами задач или отдельный?
  По умолчанию: отдельный `scope_kind = repair_project` (миграция W4.01). `project` остаётся за задачами.
- **Q-W4.00-repair-3.** Возврат отметки с причиной (RS-09): кнопка «Вернуть» есть только в 1a.
  По умолчанию: операция `returnWorkLog` с обязательной причиной есть в контракте, бригада причину не видит. Кнопку UI добавляют после дорисовки, до неё — как в основном файле, без кнопки.
- **Q-W4.00-repair-4.** Как считать готовность (RS-07, Q-78)?
  По умолчанию: как в прототипе. Готовность для команды = сумма принятых объёмов к плану (+ на приёмке), для заказчика — по подписанным актам. Взвешивание по стоимости — после связи «работа ↔ строка сметы» (Q-…-5).
- **Q-W4.00-repair-5.** Работы карточки и строки сметы или этапы графика — разные сущности (§5 п. 13). Связывать ли их?
  По умолчанию: у работы есть необязательная ссылка `estimate_line_id`. При подписи допсоглашения работа создаётся из допработы (как `setChange`). В сиде сохраняются значения прототипа (`w1–w3`) ради паритета.
- **Q-W4.00-repair-6.** Где прораб пишет заявку на материал (в эталоне формы нет)?
  По умолчанию: операция `createSupplyRequest` в контракте и дорисовка формы во вкладке «Снабжение» объекта. До дорисовки заявки создаются только сидом и MSW.
- **Q-W4.00-repair-7.** Списание материалов: при приёмке отметки (документ) или кнопкой «Списать на объект» (дочерний компонент)?
  По умолчанию: оба пути через одно движение `use` модуля «Склад». Приёмка списывает материалы из отметки, кнопка остаётся для заявки без отметки. Номенклатура формы отметки — позиции справочника (`m-*`), а не `mt1…`.
