# Архитектурное описание CRM-конструктора — версия 0.1

Исследование источников: 30.09.2026. Сводная редакция: 01.10.2026. Статус: проект архитектуры для реализации, согласованный с техническим заданием пакета. Репозиторий и развёрнутый backend не предоставлены; реализации, нагрузочные испытания и аудит существующего кода не подтверждены. Предыдущие материалы о ролях и правилах модулей учтены как исходные проектные решения.

## 1. Решение и границы

Предлагается модульный монолит на Go, единый адаптивный web/PWA-клиент, отдельная БД управления платформой и отдельная PostgreSQL DB для каждого тенанта. Модуль — доверенный компонент платформы с собственными таблицами, API, событиями и интерфейсами, а не отдельный микросервис. Конструктор настраивает поля, формы, представления, статусы, роли и ограниченные автоматизации; бизнес-инварианты — бронь, складской остаток, начисление, принадлежность записи — остаются в проверяемом серверном коде.

Один холдинг из Москвы, Самары и Санкт-Петербурга, имеющий по четыре фирмы в каждом регионе, — **один тенант**, если владелец сознательно выбрал совместное управление и единую границу данных. Внутри — 3 региона и 12 рабочих подразделений. Юрлицо и подразделение — разные сущности: юрлицо содержит реквизиты, подразделение определяет организационную область работы. Их связь может быть m:n. Нельзя автоматически делать отдельный тенант на каждое юрлицо: межфирменное бронирование тогда становится внешней интеграцией вместо внутреннего процесса.

Независимые клиенты SaaS — разные тенанты. Один Account может состоять в нескольких тенантах; один владелец может владеть несколькими. Общая учётная запись не даёт общей видимости данных.

Термины интерфейса следует закрепить:

| Термин | Значение |
|---|---|
| Администратор платформы | Создаёт и обслуживает тенанты, тарифы, доступность модулей, технические лимиты |
| Владелец бизнеса | Управляет одним своим тенантом и видит его данные; переключается только между своими бизнесами |
| Организация в панели платформы | Тенант — независимая граница данных |
| Компания / юрлицо внутри бизнеса | Организационные и юридические сведения внутри выбранного тенанта |
| Подразделение | Регион, филиал, салон, рабочая единица; иерархия необязательна для маленькой компании |

Фраза пользователя «владелец организации видит все организации, выключает и продлевает» трактуется как **роль администратора платформы**. Владелец клиентского бизнеса не управляет чужими тенантами.

## 2. Контуры и развёртывание

| Компонент | Ответственность | Ограничения |
|---|---|---|
| Web/PWA | Общая оболочка; рабочий стол водителя, мастера, прораба, менеджера; конструкторы | Скрытие кнопок не заменяет серверную авторизацию |
| Go API | Tenant resolver, авторизация, бизнес-команды, запросы, подписки realtime | Не выбирает БД по DSN или произвольному заголовку клиента |
| Go worker | Outbox, импорты, экспорт, уведомления, миниатюры, пересчёты | Работа всегда содержит tenant context и ограниченный actor/service principal |
| Provisioner | Создание БД, миграции, назначение служебных ролей, резервное восстановление | Отдельные полномочия и процесс; DDL-учётных данных нет у API |
| Control PostgreSQL DB | Реестр тенантов, routing, Account, Membership, OwnerBinding, подписки, лимиты, метаданные состояния | Не содержит рейсов, клиентской базы салонов, смет и фотографий |
| Tenant PostgreSQL DB | Core access, структура, профили, бизнес-модули, outbox, metadata, billing usage projection | Отдельная БД и runtime identity на тенант; схемы по модулям |
| Identity Provider | OIDC, вход, MFA, восстановление аккаунта, корпоративный SSO в будущем | Не является хранилищем всех прикладных прав |
| Объектное хранилище | Фото, документы, вложения, результаты экспортов | Закрытые объекты, серверная проверка доступа перед выдачей |
| Observability | Метрики, трассировки, технические логи, алерты | Секреты, фото, полные ответы форм и начисления в технические логи не попадают |
| Redis — по необходимости | Краткоживущий кеш, rate limits, realtime coordination | Не источник истины брони, остатка или прав |

Минимальная производственная установка имеет web, API, worker, IdP, PostgreSQL и объектное хранилище; provisioner запускается отдельно по событию. API и worker собираются из общей Go-кодовой базы, но могут масштабироваться независимо. Kubernetes не является обязательной предпосылкой продукта; выбор между управляемой инфраструктурой, контейнерами на VM и Kubernetes определяется операционной командой. Учитывая DevOps-компетенции заказчика Kubernetes допустим, но не должен становиться отдельным проектом до первого пилота.

Первоначально не нужны Kafka, Elasticsearch/OpenSearch, отдельный policy server и десятки микросервисов. Текстовый поиск и очереди небольшого пилота могут начинаться в PostgreSQL; переносить их следует по измеренной нагрузке и требованиям, а не по количеству функций в презентации.

Не обещается изоляция от произвольного кода внутри Go-процесса: trusted modules не являются sandbox для стороннего плагина. Сторонний исполняемый код и публичный marketplace расширений — отдельная архитектура с процессной изоляцией и моделью доверия.

## 3. Изоляция тенантов и жизненный цикл данных

Сервер проверяет сессию, Account, активный TenantMembership и состояние тенанта; только после этого создаёт immutable TenantContext с tenant_id, membership_id, actor_id, policy_version и capability-based доступом к БД/хранилищу. Клиентский tenant_id выбирает желаемый контекст, но не предоставляет доступ. Отсутствие или неизвестный tenant_id не переводит запрос в «главную БД».

Routing хранится в control DB: tenant_id → shard/database/secret reference/schema version. Runtime credentials ограничены своей tenant DB; права CONNECT PUBLIC пересматриваются при provisioning. Пул соединений создаётся лениво, имеет idle TTL и общий бюджет на процесс/шард. Создание постоянного максимального пула для каждой из тысячи пустых организаций не допускается.

В tenant DB сохраняется tenant identity sentinel. При открытии нового пула выполняется проверка, что полученная DB соответствует ожидаемому tenant_id. Это защищает от ошибки registry и перепутанного секрета, но не заменяет права БД.

Отдельная DB упрощает перенос тенанта и логический экспорт, однако не даёт физически независимые CPU, WAL или диски, когда БД находятся на одном PostgreSQL-кластере. Крупного клиента можно перенести на выделенный шард/кластер через controlled migration, не меняя пользовательскую модель.

Database-per-tenant имеет цену: миграции по множеству БД, контроль drift версий, лимиты подключений, инвентаризация backup и частичные ошибки rollout. Нужен migration controller: canary tenants → небольшие партии → остальная группа; tenant DB version фиксируется отдельно. API в переходном окне поддерживает согласованный диапазон схем. Expand/contract предпочтительнее одновременной несовместимой замены всех БД.

Изоляция обязательна также для object keys, cache keys, notification topics, idempotency keys, очередей, индексов и export jobs. Внешний идентификатор объекта никогда не считается доказательством права. Публичные формы используют отдельно выданный publish token, который открывает только конкретную опубликованную форму; он не является tenant session.

PITR физического PostgreSQL-кластера восстанавливает кластер, а не произвольно одну tenant DB в общей инсталляции. Для точечного восстановления одного тенанта требуется восстановление в изолированное временное окружение и затем логический перенос нужной DB либо другой заранее проверенный механизм. Restore-план обязан охватывать версии файлов и manifest, control mapping и outbox; «backup успешен» не равнозначно «тенант восстановлен».

## 4. Идентичность: realm, аккаунт, участие и сотрудник

По умолчанию — один общий realm IdP для клиентских аккаунтов и отдельный административный контур/клиент входа платформенных операторов. Приложение использует глобальный Account и TenantMembership. Keycloak документирует SSO, OIDC и Organizations внутри realm; это подтверждает доступность механизмов, но выбор общей модели realm здесь является нашей архитектурной рекомендацией, а не обещанием полной SaaS-авторизации от Keycloak [S1].

Realm на каждый бизнес не нужен по умолчанию: человеку, состоящему в нескольких бизнесах, сложнее управлять несколькими identity; растёт количество конфигураций входа, клиентов, ключей и миграций. Отдельный realm или отдельный IdP deployment допускается позже для конкретного enterprise-требования к независимым настройкам и изоляции идентичности. Это отдельная опция; прикладные роли всё равно остаются в платформе.

| Сущность | Где | Назначение |
|---|---|---|
| Account | Control DB, привязка к issuer + subject IdP | Глобальная идентичность и состояние входа |
| TenantMembership | Control DB | Приглашён / активен / приостановлен / завершён в конкретном тенанте |
| OwnerBinding | Control DB | Неконструируемое обычной ролью право владения тенантом |
| PersonProfile | Tenant DB | Карточка человека, может не иметь аккаунта |
| ProfessionalAssignment | Tenant DB | Функция: водитель, мастер, прораб; квалификация и период работы отдельно |
| RoleAssignment | Tenant DB | Прикладные действия в конкретной области, условия и срок |
| GroupMembership | Tenant DB | Принадлежность к группе для назначения ролей |

Рабочие стройки без входа представлены PersonProfile и назначениями на объект; приглашение необязательно. Роль не создаёт второго человека. Отображаемое имя роли можно переименовать; профессиональный смысл хранится стабильным идентификатором функции, а не сравнением строки «Водитель».

Приглашение связывает существующий Account с tenant-local PersonProfile после подтверждения одноразового ограниченного по времени токена и ожидаемой идентичности. Автоматическое объединение людей только по одинаковому имени запрещено. Администратор клиентского бизнеса управляет **участием в своём бизнесе**, но не блокирует глобальный аккаунт сотрудника во всех его других бизнесах и не меняет ему пароль.

Вход — OIDC Authorization Code с PKCE; для браузера предпочтителен backend session/BFF с HttpOnly Secure cookie, CSRF-защитой и проверкой Origin для state-changing requests. OIDC tokens не должны бесконтрольно лежать в localStorage. Полные mutable business permissions в долгоживущий JWT не помещаются. RFC 9700 рекомендует PKCE и для веб-клиентов; конкретная реализация и threat model оформляются отдельной security спецификацией [S2].

В интерфейсе статус «активен/приглашён/заблокирован» отделён от присутствия «был в сети» и рабочего состояния «на маршруте/на смене». Нельзя трактовать отсутствие heartbeat как увольнение, а открытую вкладку как работу.

**Последний владелец.** Назначение и снятие OwnerBinding, приостановка Membership владельца и передача владения блокируют одну tenant control row и проверяют, что после изменения остаётся хотя бы один активный подтверждённый владелец. Обычная роль «Администратор» не может снять владельца или скопировать владение. Передача владения требует повышенного подтверждения и аудита. Удаление самого бизнеса и аварийное восстановление владельца — отдельные процессы, а не обход last-owner invariant.

## 5. Модель доступа с действиями, областями и полями

Основная запись: `principal + role_version + scope + conditions + valid_from + valid_until`. Роль содержит конкретные action keys. Scope задаёт «где». Условия только сужают право. Вложенные группы и произвольные пользовательские выражения политик в MVP не поддерживаются.

Поддерживаемые scopes: tenant; org_unit с флагом include_descendants; workspace/project/warehouse/fleet; конкретный resource. `scopeQuery(action)` строит предикат только из целых разрешающих назначений.

Для контекста `c`, действия `a`, ресурса `r`, поля `f`, текущего времени `t`:

```text
permit(c,a,r,f,t) =
  trusted_tenant(c,r)
  AND active_account_and_membership(c)
  AND feature_access_mode_allows(a,t)
  AND module_installation_and_state_allow(a,t)
  AND mandatory_platform_and_tenant_boundaries(c,a,r,f)
  AND EXISTS grant g:
      action_in_grant(a,g)
      AND scope_contains(g.scope,r)
      AND conditions_match(g,c,r)
      AND g.valid_from <= t < g.valid_until
  AND object_policy_admits(c,a,r)
  AND field_policy_allows(c,a,r,f)
```

`feature_access_mode_allows` вычисляет допустимую операцию по подписке и правилам сохранённого доступа. Историческое чтение после окончания оплаты не требует активной платной лицензии, если оно разрешено режимом `read_only`. Установка модуля, его операционное состояние и коммерческое право проверяются раздельно.

Чтение и изменение поля — разные разрешения. Условия и область проверяются совместно с действием для **каждого** grant. «Редактировать Москва-1» плюс «читать Самара-2» не превращается в «редактировать Москва-1 и Самара-2». Отсутствие разрешения в одной роли не отменяет разрешение в другой.

Обычные роли только добавляют разрешения. Свободного конструктора deny rules с правилом «самый локальный запрет побеждает» не вводим. Небольшой перечень обязательных границ контролирует платформа/владелец: чужой tenant, disabled membership, недоступная функция, конфиденциальные поля, предел делегирования и согласованные бизнес-ограничения. Это не разрастающаяся ACL-матрица пользовательских исключений.

### Локальное ограничение, которое можно реализовать

У существующего проекта/склада/рабочей области есть `visibility_mode`:

1. `inherited`: достаточно подходящего grant в области подразделения/проекта и остальных проверок.
2. `restricted`: дополнительно требуется admission — запись пользователя/группы в участниках контейнера, согласованный resource-specific grant либо явное разрешённое надзорное полномочие. Владелец сохраняет доступ ко всему своему tenant с соблюдением обязательных ограничений, включая несовместимость функции `driver` и начислений; это указано в UI.

Членство в restricted-контейнере **не добавляет действие**. Например, участник без `tasks.update` может читать при наличии `tasks.read`, но не менять задачу. Удаление локального action grant не отменяет независимый региональный grant; UI показывает источник оставшегося доступа. Смена режима inherited → restricted показывает список затронутых пользователей и фоновых процессов.

Владелец управляет ограниченными проектами, однако не обходит границу чужого tenant, недоступность тарифа для новых операций и серверные инварианты бронирования. «Владелец видит всё» не означает «владелец может повредить ledger прямым редактированием».

### Делегирование

Назначающий должен иметь `roles.assign` и право делегировать весь набор действий, полей, областей, типов получателей и сроков выбранной роли. `can_perform` не равно `can_delegate`. При clone/edit роли, добавлении человека в привилегированную группу и переносе org unit выполняется такая же проверка. Удаление чужих ограничений и создание полномочий самому себе не являются исключениями.

На каждом module manifest есть: action keys, чувствительность, поддерживаемые scopes, relationships для «назначено мне», datasets, field sensitivity, dependencies и role templates. Новые actions после обновления не добавляются автоматически в старые роли. Wildcard `module.*` не используется в пользовательских ролях; built-in Owner обрабатывается явно.

### Начисления водителям

Текущее требование заказчика имеет приоритет: **водители не видят начисления вообще, включая собственные**. Нет `fleet.earnings.read_own`, экрана зарплаты, суммы в профиле, уведомления с суммой и скрытой колонки, которую всё-таки возвращает API. Менеджер с отдельным `fleet.earnings.read` / `fleet.earnings.manage` видит начисления только в своей рабочей области; владелец — по тенанту. Начисление принадлежит области работы/заказа, а не текущему филиалу водителя, чтобы передача водителя не переносила историю зарплат.

В MVP действующее профессиональное назначение `driver` блокирует доступ к начислениям независимо от названия, числа ролей, групп и выбранного рабочего экрана. Наличие квалификации или водительского удостоверения без действующего назначения `driver` само по себе не является запретом. Конфликтующие назначения финансовых прав и функции `driver` отклоняются; проверка обязательна также во время исполнения запроса, чтобы неверная старая конфигурация не открыла данные. Ограничение действует и для владельца: совмещение владельца/менеджера с рабочей функцией водителя требует отдельного продуктового решения вне MVP. Это ограниченное правило разделения обязанностей, а не универсальный пользовательский deny-конструктор.

Расход рейса и вознаграждение водителя — разные сущности. Водитель может видеть отправленный им расход на бензин/мойку и состояние проверки, но не сумму заработка, маржу, внутренние ставки и расчёт менеджера.

## 6. Пример холдинга и матрица решений

| Участник / назначение | Что разрешено | Что закрыто |
|---|---|---|
| Владелец холдинга | Все 3 региона и 12 фирм; начисления; структура; лимиты в рамках тарифа | Чужие tenants; бесконтрольный обход инвариантов |
| Руководитель Москвы | Разрешённые модули четырёх московских фирм по назначению на регион | Самара и Санкт-Петербург без отдельного назначения; деньги без чувствительного permission |
| Менеджер Москва-1 | Свои машины, склады, рейсы, рабочие профили; начисления своей фирмы при выданном праве | Полные карточки Москва-2, её склад, начисления и клиенты |
| Менеджер Москва-1 в каталоге обмена | Опубликованные свободные интервалы и профессиональные признаки Москва-2 | Кадровое досье, заработок, история перемещений и все телефоны Москва-2 |
| Водитель Москва-1 | Допущенные свободные машины; бронь; свои осмотры, рейсы и заявленные расходы | Любые начисления; маршрут другого водителя; весь парк по одному знанию ID |
| Водитель Москва-2, работающий временно на Москва-1 | Согласованный автомобиль/рейс/интервал; ограниченный комплект рабочих сведений | Все другие записи принимающей фирмы и прошлые рейсы автомобиля |
| Мастер SPA | Назначенное расписание, необходимые сведения о своих визитах, факт выполнения | Клиентская выгрузка, чужая выручка и все визиты клиента без отдельного права |
| Прораб | Разрешённые объекты; задачи; фото; отметка работ и людей без аккаунтов | Чужие объекты; себестоимость, если право не выдано |
| Платформенный оператор | Статус tenant, тариф, объём, health, технические операции | Бизнес-данные без отдельного временного допуска |

Scope записи задаётся при создании явным выбором или единственной допустимой областью. Сервер проверяет и область, и все связанные ID. Смена `owner_unit_id` через общий PATCH запрещена; отдельная команда transfer проверяет обе стороны и воздействие на роли, связи, брони и вложения.

Смена названия подразделения не меняет доступ. Перенос подразделения под другой регион меняет наследуемые scopes: нужен impact preview, особое право и аудит. Неопределённая принадлежность при импорте отправляется в закрытую очередь разбора, а не становится общедоступной.

## 7. Межфилиальный обмен, бронь и временный доступ

У каждого ресурса отдельно хранятся: home_unit, текущая физическая локация, профессиональная/техническая пригодность, рабочие назначения, календарь reservations и фактическая занятость. Передача на смену не меняет владельца машины или профиль человека.

`AvailabilityPublication` публикует специально сформированную карточку: случайный catalog resource id, тип ресурса, квалификации/характеристики, район подачи, свободные интервалы. Имя/контакт и точная локация по умолчанию не раскрываются до согласования. Каталог имеет отдельное право `fleet.driver_transfers.request`, действует только внутри tenant и разрешённых владельцем направлений обмена. Не используется обычный `users.list` чужого филиала.

Протокол:

1. Получатель создаёт `ResourceRequest` с целевой работой, интервалом, набором ресурсов, требованиями и принимающей unit.
2. Источник рассматривает запрос; при нескольких владельцах ресурсов нужны все обязательные approvals. Черновое согласие не предоставляет доступ.
3. При финальном approve сервер заново проверяет actor, policy version, принадлежность, квалификацию, доступность и состояние каждого ресурса.
4. В одной tenant transaction фиксируются подтверждённая бронь на весь комплект, статус заявки, временные grants и событие outbox. Если любой ресурс недоступен — весь комплект не подтверждается.
5. Принимающий менеджер и водитель получают только необходимые действия/записи. Грант не открывает исторические рейсы, начисления и все вложения resource.
6. Отмена/отзыв завершает бронь и grants согласно реальному состоянию работы; событие инвалидирует кеши/подписки. Повтор одной команды с тем же idempotency key не создаёт новую бронь.

Единый сервис scheduling владеет Reservation, Approval и TemporaryAssignment, необходимыми для атомарного подтверждения. Это общая функциональность логистики, SPA и стройки; правила пригодности приходят из отраслевого модуля через типизированный контракт, а не SQL-доступ к его приватным таблицам.

Интервалы полуоткрытые `[from, until)`, время хранится как абсолютные timestamps, UI использует timezone места работы. Для подготовки, мойки, дороги и уборки у ресурса есть отдельные buffer intervals. Не путать плановую бронь с фактической занятостью: затянувшийся рейс остаётся занят даже после окончания планового времени.

Конкурентные брони защищаются на уровне PostgreSQL: транзакционные блокировки и exclusion constraint для ресурса/пересекающегося временного диапазона. PostgreSQL документирует range types и exclusion constraints для запрета пересечений [S3]. Нельзя обеспечивать уникальность только проверкой «свободен ли?» перед INSERT или Redis-lock без проверки БД. Ресурсы блокируются в стабильном порядке, retry ограничен, конфликт возвращается как бизнес-ошибка 409.

Краткая hold-бронь имеет expires_at. Её срок проверяется сервером; истёкший hold не обязан ждать cron. Реализация expiry согласуется с ограничением БД: нельзя использовать `now()` в условии partial index как постоянно меняющийся фильтр. Для v1 можно держать строки states и под локом переводить истёкшие holds перед повторной попыткой; confirmed interval проверяется исключающим ограничением. Удалённый worker cleanup лишь убирает старые служебные записи.

По истечении временного доступа запрещены новые рейсы и изменения чужих ресурсов. Для уже начатого рейса заранее существует отдельное узкое continuation capability: отправить возврат/последние фото для этого рейса. Оно не открывает полный ресурс, не продлевает право брать машину и закрывается завершением работы. Если аккаунт заблокирован по безопасности, продолжение делает уполномоченный менеджер: блокировка Membership выше continuation. Задержка возврата создаёт incident и препятствует новой выдаче той же машины.

## 8. Общие сервисы без универсальной «таблицы всего»

| Ядро | Что переиспользуют отрасли | Что остаётся отраслевым |
|---|---|---|
| Scheduling | Ресурсы, интервалы, reservations, buffers, conflicts, reminders | Грузоподъёмность/температура; кабинет+мастер; строительная смена |
| Tasks/workflows | Задачи, исполнители, статусы, комментарии, уведомления | Правила выпуска авто, завершения процедуры и приёмки этапа |
| Files/forms | Поля, версии форм, обязательные фото, публикации, заполнения | Шаблон кругового осмотра, отчёт прораба, клиентская анкета |
| Inventory | Номенклатура, единицы, партии, приход/расход/перемещение | Норма масла на массаж; детали/шины; материалы по смете |
| Operational finance | Денежные счета, операции, категории, возвраты, сверка | Начисления водителям, оплата услуги, платежи по стройке |
| Knowledge | Страницы, разделы, версии, вложения, ссылки на задачи | Инструкции по авто; протоколы процедур; документация проекта |
| Data Hub | Каталог datasets, безопасные представления, фильтры, графики, drill-down | Смысл показателя, агрегация и write-команды принадлежат модулю |

Доменная запись имеет одного владельца. Календарь показывает проекцию рейса или визита, а не создаёт второй независимый рейс/визит. Изменение проекции отправляет команду владельцу записи. Задача, связанная со сметой, не раскрывает смету только из-за наличия ссылки.

Custom fields подходят для дополнительных атрибутов; обязательные связи, остатки, суммы, timestamps и ключевые состояния имеют типизированную схему. Метаданные форм и представлений версионируются; заполненный осмотр ссылается на опубликованную версию шаблона, чтобы изменение вопроса не меняло смысл старого ответа.

Складские операции — журнал движений с исходным документом и idempotency key. Списание крема/масла идёт по норме услуги с возможностью корректировки уполномоченным лицом; повтор события о завершении визита не списывает второй раз. Отрицательный остаток запрещён по умолчанию и не должен появляться при гонке двух процедур. Для точных количеств и денег используются decimal/numeric или integer minor units, не float.

Финансовая операция после подтверждения не редактируется без следа; исправление — сторно/корректировка с причиной. Внутренняя «касса» означает управленческий учёт денег в приложении. Её нельзя называть заменой фискального оборудования или юридически значимой бухгалтерии без отдельного предметного и правового проектирования.

Модули не пишут напрямую в чужие схемы. Для событий используется transactional outbox с at-least-once delivery и идемпотентными consumers; не обещается магическое exactly-once через сеть. Только действительно неделимые операции помещаются под общий trusted transaction coordinator и явно перечисленные capabilities. Если разные модули сохраняют независимые транзакции, процесс имеет промежуточный статус и компенсацию; пользователь не видит «всё выполнено» до подтверждения обязательных частей. Например, при асинхронном списании материалов визит может находиться в `completion_pending_inventory` до подтверждения склада.

Полная изоляция SQL-ролей по модулям из прежних правил и произвольная общая транзакция между модулями несовместимы без явного orchestration capability. Для первой версии атомарное ядро scheduling ко-лоцируется; другие cross-module операции либо проходят через отдельно ограниченный coordinator, либо оформляются процессом. Не давать всем модулям административную роль БД ради удобства.

## 9. Data Hub, поиск, отчёты: как не обойти права

«Хранилище данных» — пользовательский каталог типизированных наборов из подключённых модулей и единое представление информации. Это не прямой SQL-клиент, не копия всех таблиц и не отдельный набор прав «видеть вообще всё».

Модуль публикует DatasetManifest: стабильный id, label, schema version, поля/типы, разрешённые операции/фильтры/агрегации, row scope, field capabilities, source entity link, read adapter, refresh semantics. Data Hub запрашивает данные от имени пользователя и с той же политикой, что обычный API. Редактирование разрешённого поля из таблицы вызывает доменную команду модуля, не generic SQL UPDATE.

| Канал утечки | Обязательное правило |
|---|---|
| Счётчики и пагинация | Row permissions применяются до count, facets и limit; totals отражают доступные записи |
| Поиск и автодополнение | Возвращают только разрешённые строки/поля; индексы учитывают tenant, scope и текущие политики |
| Сортировка и фильтр | Нельзя фильтровать, сортировать или группировать по запрещённым начислениям и восстанавливать их бинарным поиском |
| Формулы | Производное поле наследует чувствительность входных полей; сумма/разница не превращается в общедоступное число |
| Join / lookup | Каждая сторона проверяется отдельно; отсутствующая доступная ссылка не раскрывает имя, контакты и скрытые идентификаторы |
| Dashboard | Открытие сохранённого дашборда проверяет права зрителя; сохранение владельцем не раздаёт его privileged query |
| Отчёт по расписанию | Запуск и доставка под актуальными полномочиями получателя/сервисного principal; запрет отправки отключённому участнику |
| Экспорт | Отдельное export permission + row/field checks; recheck перед выдачей результата; job принадлежит tenant и actor |
| Вложения | Проверяется доступ к конкретному файлу и родительскому объекту; связь с доступной задачей не снимает classification |
| Audit/history | События с начислениями редактируются по field policy; драйвер не читает сумму из diff |
| Уведомления/realtime | На enqueue и на доставке проверяется audience; при отзыве закрываются подписки, payload не содержит лишние поля |
| Кеш | Ключ включает tenant, actor/membership или безопасный scope fingerprint, policy version, поля и параметры |

Read-only доступ в Data Hub не даёт экспорт автоматически. Owner dashboard нельзя публиковать по «открытой ссылке» без отдельного publishing policy; публичные dashboard в MVP лучше не предоставлять. Поле, которое пользователь не вправе читать, отсутствует в response body, экспорте и поисковом документе его представления. Ограничение поля должно срабатывать до DTO serialization, а не только при рисовании таблицы.

Отдельный аналитический storage позже допускается как защищённая read projection с tenant/scope/classification lineage и политикой свежести. До появления корректной авторизации по всем каналам он повышает риск, а не только скорость.

## 10. Файлы, фото и офлайн

Upload flow: проверка доступа к действию/объекту → quota reservation → upload session → загрузка в quarantine → проверка фактического типа/размера/целостности → malware/content validation по выбранному формату → finalize → привязка к объекту и usage ledger. Прямой object key клиент не выбирает. PUT upload URL привязан к уникальному ключу; нельзя выдать перезапись уже принятого файла.

Фотографии хранят original и необходимые превью по явной политике; удаление EXIF/GPS из доступной копии не должно молча уничтожать original, если он нужен как доказательство осмотра. Серверные timestamps upload/submit отделены от заявленного capture_at устройства. Приложение не обещает, что обычная браузерная фотография гарантирует место, время съёмки или отсутствие подделки.

Скачивание: endpoint авторизует действие и возвращает короткую ссылку либо проксирует выдачу. AWS S3 документирует presigned URL как bearer access; ссылку можно использовать повторно до expiry, а начатое скачивание может продолжиться после истечения срока [S6]. Следовательно, нельзя обещать мгновенный отзыв уже выданной ссылки или скачанного файла. Для чувствительных документов лучше контролируемая выдача; короткий URL ограничивает окно, но не делает файл отзывным. Реальная совместимость и правила конкретного S3-compatible провайдера проверяются отдельно.

Один PWA-клиент показывает водителю «Сегодня / Машины / Осмотр / Расходы / Завершить». Для мастера — «Мои записи / Клиент / Процедура / Материалы». Для прораба — «Объекты / Работы / Люди / Фотоотчёт». Разные рабочие пространства и route bundles не требуют разных пользовательских баз.

Офлайн разрешены: локальный черновик осмотра, подготовка фото, черновик расхода, чтение заранее разрешённого минимального набора своей активной работы. Подтверждение брони, согласование передачи и выпуск на маршрут требуют серверного ответа. Offline UI явно пишет «Не отправлено»; отсутствие сети не превращает локальное нажатие в состоявшийся выезд в учёте.

Sync идемпотентен и проверяет текущую сессию, scope, срок доступа, version и quotas. Отклонённые операции показываются человеку, а не теряются. При logout удаляются локальные кэши и очередь по правилам продукта; пользователь получает предупреждение о неотправленных черновиках. Отозвать уже закешированные данные на отключённом устройстве немедленно невозможно; offline retention минимален, чувствительные финансовые данные не кешируются. Сам браузер не гарантирует долговечное хранение черновика: перед важной сдачей нужно получить серверное подтверждение.

## 11. Подписки, trial, квоты и отключение модулей

Нужно разделить три слоя: `subscription` (коммерческий договор/период), `entitlement` (разрешённая функция и предел), `module_installation` (состояние установленного модуля и его версия). Пользовательская роль — четвёртый независимый слой. Покупка модуля не открывает его всем сотрудникам.

`Entitlement` содержит feature/module, source_type/source_ref (тариф, add-on, trial, админская компенсация), effective_from, effective_until, limit и mode. Увеличение ресурсов/продление — версионированная операция с reason и audit. Обработчики платежей и ручные продления идемпотентны. Изменение лимита считается эффективным после применения подтверждённой версии в tenant meter; промежуточное состояние видно оператору.

Предлагаемые стартовые настройки для проверки: trial 14 дней, до 10 пользователей с входом и 5 ГиБ учитываемых файлов; предупреждения за 3 и 1 день. После окончания оплаченного или пробного периода — 7 дней `grace`, затем `read_only` с чтением и экспортом для владельца. Рабочие без входа не занимают пользовательские места. Это настраиваемые продуктовые гипотезы, а не согласованный коммерческий тариф. **Неуспешный платёж и уменьшение квоты не запускают автоматическое удаление данных.** Длительное хранение после расторжения, закрытие бизнеса и сроки резервных копий определяются опубликованной политикой отдельно от неоплаты. `suspended` предназначен для отдельной административной или защитной блокировки; он не наступает автоматически через выдуманный срок неоплаты.

| Состояние | Новая работа | Данные | Действие владельца |
|---|---|---|---|
| Trial / active / grace | В пределах текущего режима и лимитов | Доступны по ролям | Покупка, продление, изменение лимитов |
| Read-only после 7 дней grace | Новые рейсы/визиты/записи запрещены | Чтение и ограниченный экспорт по retained access | Продлить или выгрузить |
| Over quota | Новые увеличивающие объём загрузки ограничены | Существующие записи и файлы сохраняются | Увеличить лимит, удалить своё, отменить уменьшение |
| Module draining | Новые процессы модуля не создаются | Идущие процессы безопасно завершаются | Дождаться завершения или управляемо отменить |
| Module read-only | Новые процессы запрещены | Исторические данные доступны по прежним правам | Выгрузить или возобновить |
| Module disabled | Обычные actions, Data Hub и автоматика модуля заблокированы | Данные и настройки сохранены; отдельный owner export | Включить обратно, выгрузить, удалить явно |
| Tenant suspended | Прикладные операции закрыты | Хранение согласно политике; billing/export/support channel отдельно | Возобновить или запросить удаление |

Уменьшение объёма планируется на следующую границу расчётного периода. Перед подтверждением показываются использованный объём, новый лимит, дата и последствия. Применение возможно только при использовании не выше нового лимита; при превышении уменьшение отклоняется или переносится, а прежний лимит сохраняется. Проверка выполняется повторно в момент применения. Принятые фото не удаляются, принудительное применение слишком маленькой квоты в MVP не предусмотрено.

Пользовательский «объём памяти» следует назвать «Хранилище». Измеритель v1: байты принятых оригиналов + выбранных пользовательских версий + корзины; показывать раздельно. Производные превью и технические резервные копии можно включить в сервисную цену, не выдавая их за пользовательскую загрузку. Размер таблиц БД, индексов и WAL показывается оператору отдельно: физический объём PostgreSQL не является стабильной мерой пользовательских файлов. Если планируется тариф по записям/сотрудникам/рейсам, это отдельные счетчики.

Проверка квоты атомарна: `used + reserved + new_bytes <= limit`; reservation имеет TTL, finalize сверяет реальный размер и release неизрасходованное. Два одновременных upload не могут оба пройти по одному последнему гигабайту. Незавершённые orphan uploads очищаются как технический мусор; это не удаление уже принятых пользовательских данных. До начала осмотра резервируется необходимый бюджет фото; политика может иметь небольшой заранее оплаченный резерв для завершения активного рейса. Такой резерв не даёт бесконечную загрузку после блокировки.

Отключение сначала запрещает новые процессы и завершает активные в `draining`; затем допускает предусмотренное чтение истории. Полное состояние `disabled` сохраняет роли и grants в dormant-состоянии с версией; обычный effective access равен нулю, отдельный канал owner export остаётся регулируемым платформой. Повторное включение показывает, какие сохранённые назначения возобновятся, и учитывает истёкшие сроки/удалённые actions. Новые чувствительные actions автоматически не добавляются. Hard dependencies нельзя выключить без зависимых модулей; soft integrations прекращаются с явным warning и сохранением ссылок.

Удаление tenant/модуля/файла — отдельная команда с явным объектом, review последствий, правом и аудитом. Перед hard deletion нужны согласованный срок восстановления и учёт backup retention; нельзя обещать моментальное удаление каждой физической резервной копии. Автоматические lifecycle rules допускаются для известных временных/export/quarantine объектов, но не для неявного уничтожения бизнес-истории по окончании оплаты.

## 12. Контракты и инварианты Go-модулей

Документация Go рекомендует `internal` для непубличных частей сервера и `cmd` для команд [S7]. Это механизм видимости пакетов, а не защита данных сам по себе. Предлагаемая структура должна адаптироваться к реальному репозиторию после его появления, а не выдавать черновой layout за уже существующий.

Платформенные capabilities: `Authz`, `ScopedDB`, `Storage`, `Directory`, `Scheduling`, `Events`, `Workflow`, `DataSets`, `Audit`, `Clock`, `Usage`. Модуль получает только нужные capabilities через context/constructor. Raw control DB, глобальный storage client и произвольный tenant selector ему не передаются.

Авторизация предоставляет:

- `authorize(action, resource)` — решение над конкретной записью.
- `scopeQuery(action, dataset)` — проверенный предикат/план до пагинации и агрегации.
- `readFields/writeFields(action, resource)` — разрешённые поля; write body не принимается по принципу «игнорируем неизвестное» для защищённых полей.
- `explainAccess(actor, action, resource)` — объяснение без раскрытия сверх полномочий проверяющего.
- `previewPolicyChange(change)` — затронутые люди/области/процессы, без автоматического применения.

Права на роуте — первый guard. Object checks, field checks, transition preconditions и источник scope обязательны и не могут быть запрещены стилевым правилом «authz в обработчике только два раза». Их можно вынести в единый service/repository слой, но нельзя заменить проверкой имени endpoint.

Idempotency key scoped по tenant + actor + operation; хранится request hash и результат. Повтор с другим payload возвращает конфликт. Для изменяемых объектов используются version/ETag и optimistic concurrency. Удалённая запись и запись без права обычно дают одинаковое 404 там, где различие раскрывало бы существование; информационные ошибки собственных объектов остаются полезными пользователю.

Версии политик и объекта повторно проверяются в локальной согласованной транзакции. Изменения tenant-local policy увеличивают policy_version, инвалидируют кеш и realtime. Между control DB и tenant DB нет неявной атомарной транзакции: блокировка membership/tenant проверяется authoritative gate; уже принятый короткий запрос может завершиться. Security-контракт должен честно определить точку проверки и максимальное время запроса. Для новых финансовых/доступных операций после suspension используется свежая control-проверка; при неизвестном состоянии control plane sensitive writes fail closed. Отзыв не зависит только от TTL долгого JWT.

RLS может быть дополнительным барьером строк внутри tenant DB, если команда реализует единую понятную политику, tests и корректный transaction-local context. PostgreSQL явно описывает обход RLS superuser, BYPASSRLS и обычно table owner [S4]; поэтому RLS нельзя объявить достаточной защитой, одновременно выполняя всё владельцем таблиц. Для v1 надёжнее одна полностью проверенная модель серверных scopes, чем две противоречащие друг другу policy-системы. Database-per-tenant остаётся главным межклиентским барьером.

## 13. Поддержка, break-glass и безопасность

Обычный platform admin не получает tenant membership автоматически и не читает бизнес-таблицы. Панель показывает эксплуатационные метаданные: владельцев/контакты для договора в разрешённом объёме, статус, тариф, лимиты, usage, health, версии, срок trial. Не нужно копировать в неё всех клиентов SPA или работников стройки.

Нормальная поддержка: запрос цели → одобрение уполномоченного владельца → временный support grant на конкретный tenant, scopes/actions и срок → заметный баннер → аудит → отзыв. Default: read-only, до 60 минут, без начислений и массового экспорта. Это предлагаемые ограничения продукта; расширение только отдельным явным допуском. Actor поддержки сохраняется; скрытое impersonation под владельцем не используется.

Emergency break-glass нужен для восстановления сервиса, когда обычный approval недоступен: выделенная защищённая operator identity, MFA, ticket/reason, ограниченное время, отдельное подтверждение вторым оператором при наличии такого операционного режима, внешняя неизменяемая запись события и последующее уведомление клиента. Он не должен превращаться в штатную кнопку «войти за пользователя». Степень гарантий зависит от эксплуатации: администратор инфраструктуры с доступом к ключам и backups технически сильнее ролей приложения; это учитывается организационными мерами, а не скрывается обещанием «никто никогда не увидит».

Нельзя делегировать business owner роли Keycloak `realm-admin`: это совершенно иной уровень доступа. Структуру CRM и группы клиентов не следует давать редактировать напрямую в общей IdP-консоли.

OWASP рекомендует least privilege, deny by default и проверку разрешений на каждом запросе [S5]. В этой архитектуре deny by default означает отсутствие подходящего полного grant, а не необходимость строить пользовательскую сетку deny-исключений.

## 14. Нефункциональные цели и проверка

Все числа ниже — **предлагаемые критерии приёмки**, не результаты benchmark и не обещанная вместимость неизвестного сервера. Перед фиксацией договора нужен нагрузочный профиль пилота: число активных пользователей, запросов/с, строк, фото и пиковых одновременных загрузок. Результаты теста сохраняются с конфигурацией окружения.

| Область | Предлагаемая цель / метод |
|---|---|
| Изоляция | 0 раскрытых чужих tenant/unit records в negative suite по всем API, search, files, counts, export, reports, websocket |
| API latency | p95 ≤ 500 мс для обычного списка 50 строк и карточки; p95 ≤ 800 мс для обычной команды при согласованной нагрузке, без transfer файла и внешнего геокодера |
| Устойчивость | SLO устанавливается после выбора инфраструктуры и измерений пилота; заранее не заявляется достигнутая доступность |
| Revocation | Новые запросы после применения ревокации блокируются; кеш и realtime отражают изменение ≤ 5 с; незавершённые обычные запросы ограничены timeout, по умолчанию ≤ 10 с |
| Booking correctness | 100 конкурентных попыток на один интервал дают ровно 1 подтверждение; связанный комплект не остаётся частично подтверждённым |
| Idempotency | 100 повторов одной команды не создают второе начисление, движение, бронь или форму |
| Файловые квоты | Конкурентные upload reservations не превышают effective limit; finalize сверяет фактический размер |
| Backup | Цели RPO ≤ 15 минут и RTO ≤ 4 часа для согласованного максимального pilot tenant; проверяется отдельным restore drill, а не существованием backup job |
| Async operations | Видимая очередь/статус, ограниченные retries, dead-letter и возможность безопасного повторного запуска |
| Security audit | 100% изменений доступа, владельцев, подписок, sensitive export, support grants, finance transitions имеют actor/time/target/reason/result |
| Accessibility | Основные сценарии с клавиатурой, focus return, понятные labels/errors, контраст; формальное соответствие стандарту заявлять после отдельной проверки |
| Offline | Потеря сети не превращает draft в confirmed; повторная синхронизация не дублирует операции; пользователь видит неотправленные данные |

Нагрузочный тест обязан включать одного «шумного» tenant с экспортом и фото, чтобы проверить fairness очередей и лимиты подключений. Бизнес-авторизацию тестируют парами с одинаковыми role names, но разными scopes, и пользователем с несколькими ролями; иначе трудно обнаружить ошибочное перемножение областей и действий.

Наблюдаемость: correlation/request id, tenant technical id, latency/error metrics, outbox lag, failed jobs, quota reservations, booking conflicts, authz deny classes, DB pool pressure, upload finalize failures. Слишком высокая кардинальность tenant_id в метриках требует отдельного решения; все полные пользовательские IDs не становятся labels. OpenTelemetry имеет Go API/SDK для traces, metrics и logs; зрелость отдельных сигналов проверяется при выборе библиотек, точные версии этот документ не фиксирует [S8].

## 15. Архитектурные решения и уточнение прежних подходов

| ADR | Решение | Причина / цена |
|---|---|---|
| A-01 | Модульный Go-монолит, отдельно API/worker/provisioner | Простые транзакции и deployment; внутренние границы нужны до выделения сервисов |
| A-02 | Control DB + DB-per-tenant | Явная граница клиентских данных; повышенная цена migrations/pools/backups |
| A-03 | Shared customer realm, global Account, tenant memberships | Общий вход и несколько бизнесов у одного человека; роли CRM не равны realm roles |
| A-04 | Один tenant холдинга, legal entities внутри | Внутренний обмен 12 фирм; отдельные tenants только для настоящей независимой границы |
| A-05 | Additive action+scope grants + curated hard boundaries + optional restricted admission | Предсказуемые права без свободного deny precedence; единый evaluator |
| A-06 | Единое scheduling ядро для атомарных комплектов | Один источник occupancy для логистики, SPA и смен; отраслевые constraints отдельно |
| A-07 | Data Hub — защищённые datasets и команды владельцев | Нет обхода scopes через отчёты и generic SQL; сложнее агрегации |
| A-08 | One adaptive PWA with workspaces | Меньше дублирования frontend/auth; offline approval исключён |
| A-09 | Dormant permissions при disable, сохранение данных | Возобновление понятно и обратимо; требуется preview reactivation |
| A-10 | Файловый ledger quota reservations, downgrade без удаления | Предсказуемые лимиты при параллельных фото; нужны metering/reconciliation |
| A-11 | Outbox + idempotency, явные transaction boundaries | Повторы безопасны; async процессы имеют pending/failed состояния |
| A-12 | Начисления недоступны водительскому доступу | Приоритет текущего запроса; старый `read_own` не переносится |

Конкретные расхождения, которые нужно утвердить до реализации:

| Прежнее положение | Предложение v1 |
|---|---|
| «Права вычищаются из ролей при выключении» в прежних правилах модулей | Effective permissions обнуляются, исходная конфигурация сохраняется как dormant; реактивация с preview |
| `read_own` начислений и отдельный маршрут водителя | Исключить для начислений по текущему требованию; `own` остаётся допустимым отношением для задач/осмотров |
| «Без запретов» в прежних правилах модулей, локальные обязательные ограничения в прежней модели доступа | Роли остаются additive; платформенные/tenant hard boundaries и restricted admission формально отделены от role denies |
| Идентификаторы только text | Сохранить на существующем проекте до миграционного ADR; для greenfield предпочтителен native UUID там, где это UUID. Пользовательский номер — отдельное поле |
| Номер `max + 1` в той же транзакции | Нужен atomic counter с lock/UPDATE RETURNING либо sequence и UNIQUE constraint; одна транзакция без блокировки не устраняет гонку |
| Все ссылки на core без FK, потому что модуль не может писать core | Отсутствие права записи не запрещает FK. Внутри одной tenant DB stable core refs могут иметь FK, создаваемые privileged migration role; cross-DB refs валидируются через контракт. PostgreSQL имеет отдельное REFERENCES permission [S9] |
| «Время — организации» | Сохраняем tenant timezone по умолчанию, но событие/салон/регион имеет timezone места; UTC instants + IANA zone, date-only даты отдельно |
| Scope только org→region→unit | Дополнить стабильным scope ref проекта/контейнера и local admission для задач/знаний/строительства |
| Небольшое фиксированное число вызовов authz в handler | Не число, а полнота guards и единый service/query layer; object/field checks обязательны для всех каналов |
| Клиент вообще ничего не считает | Авторитетные деньги, availability и права — сервер; UI может делать preview/форматирование без выдачи результата за подтверждённую бизнес-операцию |
| Только размеры desktop 1280/1024 | Добавить реальные сценарии телефона: камера, одна рука, плохая сеть, PWA safe areas; desktop thresholds остаются внутренним выбором дизайна |

## 16. Основные failure modes

| Сбой | Как обнаружить / предотвратить |
|---|---|
| Tenant registry направил запрос не в ту DB | Sentinel и scoped credentials; cross-tenant negative tests; без fallback |
| Привилегии складываются как action-set × scope-set | Evaluator проверяет каждый grant целиком; тест edit-A/read-B |
| Менеджер создал privileged group и добавил себя | Delegation closure для роли и group membership; audit impact |
| Водитель восстановил начисление через отчёт | Нет поля, фильтра, формулы, audit diff и export по earnings для driver access |
| Две брони после одновременного GET availability | DB constraint и транзакционный complete bundle |
| Водителя считают свободным после expiry, хотя рейс не завершён | Actual occupancy отдельно от planned window; overdue incident |
| Отключение модуля бросило активный рейс | draining + allowlisted finish operations, owner intervention |
| 20 параллельных фото превысили лимит | Atomic reservation ledger + bounded finalization |
| Повтор события дважды списал крем / начислил деньги | Consumer dedupe unique source event/operation id |
| Старый JWT или export открыл данные после отзыва | Fresh membership gate, policy version, recheck before delivery |
| Offline draft принят как подтверждённый маршрут | Только сервер переводит confirmed/started; UI pending state |
| Выгрузка менеджера опубликована всем по ссылке | Actor-owned job, download authorization, short TTL, no public dashboards v1 |
| Generic form workflow исполняет код/SQL | Allowlisted typed actions, validation и limits; без произвольного кода |
| Все tenant DB обновлены несовместимой миграцией | Canary/batches, backward-compatible deploy, schema version routing |
| Backup есть, но восстановленные фото не совпадают с DB | Restore drill + manifests/hashes/versioned object recovery |
| DB-per-tenant объявлен защитой от оператора инфраструктуры | Явная trust boundary, separate roles, KMS/backup access controls, external audit |
