## 1. Цель

1. **Provisioner (S1-01).** Оператор создаёт организацию (`createPlatformTenant`: имя, e-mail владельца, часовой пояс, пакет). API только регистрирует её в control DB: `tenants` в состоянии `provisioning`, `tenant_routing` (имя БД, `secret_ref`, случайный sentinel, `schema_version = 0`), запись `platform_audit` `tenant.create` с параметрами запроса. DDL-учётки у API нет. Отдельный процесс `cmd/provisioner` выполняет сагу: `CREATE DATABASE` ролью `ortus_provisioner` → явные гранты CONNECT (Q-W0.06-2) → миграции через контроллер → sentinel `core.tenant_identity` → начальные данные (корневое подразделение, профиль владельца) → `provisioning → trial`. Каждый шаг идемпотентен, упавшая сага продолжается следующим запуском.
2. **Resolver без запасной «главной БД» (S1-02).** `tenantctx`: пул открывается только для `tenant_routing` с допустимым именем БД; пустое имя, `postgres`, `template0/1`, control DB и `uuid.Nil` отклоняются до соединения. Нет `TenantContext` — нет пула. Сессия тенанта A с `tenantId` B → 404, пул B не открывается (AC-02).
3. **Migration controller (S1-03).** `migrate tenants up` идёт фазами canary → партии по `--batch`. Отказ canary останавливает партии. Версия схемы фиксируется в `tenant_routing` условным `update`. Перед миграцией сверяются sentinel и фактическая версия (дрейф). Параллельные запуски сериализуются advisory-lock в control DB. Каждый тенант пишет `platform_audit`.
4. **Down-guard по allowlist.** `down` (control, tenant, tenants) разрешён только при `APP_ENV ∈ {dev, test, e2e}`. Пустое или любое другое значение — отказ (fail-closed вместо запрета `prod|production`). `tenants down` выполняется только на явно перечисленных slug (`--canary`), массового отката нет.
5. **Гранты provisioner и мониторинга (Q-W0.06-2).** CONNECT у PUBLIC остаётся отозванным. Новая БД получает CONNECT для `ortus_provisioner` и ролей мониторинга (`PROVISIONER_CONNECT_ROLES`, по умолчанию `pg_monitor`). `migrate roles ensure` выдаёт `ortus_provisioner` членство в `ortus_migrator` с `INHERIT FALSE, SET TRUE` (PostgreSQL 16+). Это нужно для `CREATE DATABASE … OWNER ortus_migrator`, и прав мигратора провиженер не наследует.

## 10. Риски и решения по умолчанию

1. **Параметры заявки на создание** (`ownerEmail`, `timeZone`, `planKey`) хранятся в `platform_audit.details` записи `tenant.create`. Таблицы заданий provisioning в control DB нет, номер миграции выдаёт стюард. Предложение стюарду: control-миграция `provisioning_requests` (decisionsNeeded).
2. **`slug` и `industry_pack`** в `TenantCreate` отсутствуют. `slug` = транслитерация имени + `-` + 6 hex id (уникален без повторов), БД `t_<slug с _>`. `industry_pack = custom`.
3. **Идемпотентность `createPlatformTenant`** без хранилища W1.01: id организации = UUID v5 от (оператор, `Idempotency-Key`), `requestHash` в аудите.
4. **Владелец.** Приглашение владельца (control `invitations`) требует `created_by` = членство, а у оператора членства нет. Провиженер создаёт в tenant DB профиль владельца (`OwnerPersonID`, имя = e-mail до принятия), приглашение и `owner_bindings` — W1.03 (decisionsNeeded).
5. **Подписка и trial.** Провиженер переводит `provisioning → trial`, строку `subscriptions` и срок trial не пишет — это W1.08.
6. **Роли оператора.** Шлюз пускает любого активного оператора; карта роль оператора → `platform.*` не задана (decisionsNeeded).
7. **Код выхода canary = 6**, а не 2 из WS-41: код 2 у W0.06 уже означает ошибку аргументов.
8. **Down-guard:** allowlist `dev, test, e2e`; на `stage` откат тоже запрещён (forward-fix, Q-W0.06-4).
9. **Членство `ortus_provisioner` в `ortus_migrator`** (`SET TRUE, INHERIT FALSE`) — PostgreSQL 16+; стенд 17.11, CI 16.4.
10. **Мониторинг:** CONNECT для `pg_monitor`; отдельные роли бэкапа — W3.02.
