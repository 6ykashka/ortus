## 0. Коротко

1. **Последовательность берётся из плана 27:** этап 0 → платформа → логистика (вертикальный пилот) → пилот → общие модули → SPA, склад, касса → ремонт → чаты, документы, обращения. Принцип старого плана «сначала весь UI на моках» (бывший D-15, теперь PD-15) отменён.
2. **Единица параллельности — шаг плана 27.** Шаг идёт конвейером из четырёх ступеней:
   - контрактный PR (OpenAPI, `permissions.yaml`, миграция, примеры);
   - MSW-моки из примеров;
   - backend ‖ frontend ‖ строки матрицы изоляции;
   - проверка и интеграция.

   Шаги без общих файлов внутри этапа идут одновременно.
3. **Опережающая дорожка.** Пока агенты строят этап N, отдельные агенты готовят этап N+1: сверку DoR с прототипом, перенос домена и черновики контрактных PR. Так выполняется правило 5 плана 27 («дизайн опережает разработку на этап»), и у стюарда контракта не бывает простоя.
4. **Лимиты одновременной работы:** не больше 10 исполнителей и 6 проверяющих страниц. Стюард контракта и интегратор — по одному на этап.
5. **Блокеры, которые снимает только человек (§2):**
   - полный эталон: 7 модульных `.dc.html` отсутствуют;
   - решения D-01…D-12, прежде всего D-05 и D-08;
   - перенумерация решений плана (`D-` → `PD-`);
   - решение PD-53 об объектных ролях.

   Этапы 0–2 стартуют без них на значениях по умолчанию.

## 3. Модель выполнения

### 3.1 Дорожки

| Дорожка | Код | Что делает | Пишет в |
|---|---|---|---|
| Контракт | К | Контрактный PR шага: OpenAPI (файл на тег), `permissions.yaml`, `errors.yaml`, миграция с номером, примеры, `make gen`. Один стюард на этап, PR в порядке шагов | `api/**`, `backend/migrations/**`, `backend/internal/api/<tag>/` (генерация), `frontend/packages/api-client/` (генерация) |
| Домен и моки | Д | Перенос `models.js` и модулей `ortus/*.js` в `packages/domain` (TDD, тесты паритета с эталоном), MSW-хендлеры шага поверх сида | `frontend/packages/domain/src/modules/<m>/`, `frontend/packages/adapter/src/msw/<m>/` |
| Backend | Б | Модуль Go по контракту: сервис, запросы, хендлеры, интеграционные тесты (testcontainers), строки изоляции и конкурентности | `backend/internal/modules/<m>/`, `backend/internal/platform/<x>/`, `backend/test/isolation/<m>_test.go` |
| Frontend | Ф | Страницы на MSW (режим `mock`), затем против стенда (режим `stand`). Четыре проверки страницы | `frontend/apps/web/src/routes/<area>/`, `e2e/<key>.*`, `packages/texts/src/<domain>.ts` |
| QA | Т | Сквозные сценарии, конкурентность, AC, стенд-e2e. Пишут не авторы экранов | `frontend/apps/web/e2e/journeys/`, `backend/test/{concurrency,load}/` |
| Инфраструктура | И | Репозиторий, CI, стенд, харнесс, процесс | корень, `.github/`, `deploy/`, `tools/` |
| Люди | Ч | Решения, юрист, пентест, полевой тест, обучение. Агент готовит материалы | `docs/adr/`, `docs/plan/decisions.md` |

### 3.2 Конвейер шага

```text
             ┌──────── стюард (К): контрактный PR шага X.Y ────────┐
             │ OpenAPI paths/<tag>.yaml · permissions · errors ·    │
             │ миграция NNNN · examples/<op>/*.json · make gen      │
             └──────────────┬──────────────────────────────────────┘
                            ▼ merge в main (контракт аддитивный)
        ┌───────────────────┼─────────────────────┬──────────────────────┐
        ▼                   ▼                     ▼                      ▼
  Д: домен + MSW      Б: модуль Go         Т: строки изоляции     Ф: экран на MSW
  (если ещё нет)      red → green          (красные до хендлера)  e2e-скелет → green
        └───────────────────┴──────────┬──────────┴──────────────────────┘
                                       ▼
            проверяющие страниц (mock + stand) · ревьюеры (2 для authz/миграций/финансов)
                                       ▼
                   интегратор: rebase по DAG, CI, squash, status.md
```

- Frontend не ждёт backend: после контрактного PR и MSW-хендлеров экран строится в режиме `mock`. Перед закрытием шага тот же spec проходит в режиме `stand`.
- Backend не ждёт frontend. Строки матрицы изоляции пишутся красными до хендлера (правило 3 плана 27).
- Шаг закрыт, когда зелёные режимы `mock` и `stand`, все страницы шага прошли четыре проверки, а ревью принято.

### 3.3 Опережающая дорожка

Во время этапа N работают ещё два-три агента, которые готовят этап N+1:

1. **DoR-сверщик** (`W<N+1>.00`):
   - замораживает снимок эталона этапа: тег `design-stage-<N+1>`;
   - сверяет экраны прототипа с историями;
   - обновляет анализ экранов (`analysis/` — файл на модуль);
   - собирает открытые вопросы в `decisions.md` и составляет список экранов, которые надо дорисовать.
2. **Перенос домена модулей этапа N+1** (Д): потоки P1x из `analysis/B` §5.3.
3. **Стюард** готовит черновики контрактных PR этапа N+1 в `api/drafts/` и вливает их по очереди на старте этапа.

Истории этапов 4–8 пишутся в этой же дорожке: план 27 требует написать их до конца этапа 2. Агент делает черновик, владелец продукта утверждает.

### 3.4 Роли агентов

Роли — по `orchestration.md` §3: исполнитель, проверяющий страницы, ревьюер, интегратор, критик полноты. Новые роли:

- **Стюард контракта** — один на этап. Единственный, кто пишет в `api/**` и выдаёт номера миграций. Ведёт очередь контрактных PR и `api/openapi/screens.yaml` (экран → операции).
- **DoR-сверщик** — см. §3.3.

Критик полноты сверяет результат с историями и инвентарём экранов **этапа**, а не со всем прототипом.

### 3.5 Горячие точки и сериализация

| Файл | Правило |
|---|---|

| `api/permissions.yaml`, `api/errors.yaml` | Раздел на модуль, только добавление. Входят в контрактный PR. Два ревьюера (CODEOWNERS) |

| Словарь текстов | Файл на домен. `screen-labels.ts` и `errors.ts` — только добавление, владелец — стюард |

### 3.7 Режимы проверки

- `mock` — приложение на MSW-сценарном сервере поверх сида прототипа. Персонаж выбирается через dev-вход `?persona=` только в e2e-сборке: демо-панель не переносится (шаг 0.9 плана 27, R-08).
- `stand` — compose, миграции, Go-сид, dev-провайдер. Доступен с этапа 1. Для страниц пилота обязателен при закрытии шага.
- Пиксельная и структурная сверка — против снимка `design-stage-N` (эталон: главный файл или модульный `.dc.html`, фикстура `reference(file)`).
- Новые виды allowlist:
  - `out-of-stage` — пункт меню, источник «Главной» или шаг «Пути проверки» из будущего этапа, со сроком снятия;
  - `no-reference` — экрана нет в прототипе.
