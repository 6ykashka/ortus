# Протокол верификации страницы

Применяется каждый раз, когда в приложение добавляется или меняется страница, вкладка, диалог или состояние экрана. Протокол состоит из четырёх обязательных проверок: **E2E-тесты Playwright**, **визуальная сверка с эталоном**, **проверка через Playwright MCP** и **ревью кода**. Страница считается добавленной только после всех четырёх.

Редакция v2 от 14.10.2026 (W0.00, план `docs/plan/v2/00-parallel-plan.md` §3.7 и §6):

- режимы `mock` и `stand`;
- эталон замораживается на этап;
- `reference(file)` для модульных `.dc.html`;
- персонаж выбирается через dev-вход;
- новые виды allowlist: `out-of-stage` и `no-reference`.

Эталон — прототип из проекта Claude Design, байт-в-байт лежащий в `design/`. На время этапа N он **заморожен**: проверяющие этапа сравнивают со снимком с git-тегом `design-stage-N` (PD-57). `design/` обновляет только DoR-сверщик на границе этапа. Запуск локально:

```bash
node tools/design-preview.js design 4173      # снимок текущего этапа
node tools/design-preview.js design 4174      # снимок предыдущего этапа (worktree на теге design-stage-<N-1>), если нужен
# http://127.0.0.1:4173/Ортус%20CRM.dc.html            — главный файл: оболочка, компания, платформа, логистика
# http://127.0.0.1:4173/Задачи%20и%20проекты.dc.html   — модульные файлы этапов 4–7 (Документы, Чаты, Касса, Ремонт и стройка…)
# http://127.0.0.1:4173/Документация.dc.html           — просмотрщик документации
```

Файл эталона задаётся параметром фикстуры `reference(file)` из `e2e-kit`. По умолчанию это `Ортус CRM.dc.html`, а страницы модулей сверяются со своим модульным `.dc.html`.

Прототип сам подгружает React UMD с CDN (см. `design/support.js`), поэтому нужен доступ в интернет или локальная копия React (см. `docs/plan/analysis/11-design-system-and-docs-site.md`).

## 1. E2E-тесты Playwright

1. Spec `frontend/apps/web/e2e/<page-key>.spec.ts` уже существует с шага 1 TDD-протокола (`docs/plan/tdd-protocol.md`) и содержит по одному тесту на пункт чек-листа приёмки из `docs/plan/analysis/0N-*.md`.
2. Перед закрытием WS все `test.fixme` сняты. Прогон:

```bash
pnpm e2e -- --project=mobile-390 --project=desktop-1440 --grep "<page-key>"            # режим mock
pnpm e2e:full -- --project=mobile-390 --project=desktop-1440 --grep "<page-key>"       # режим stand, с этапа 1
```

3. Обязательные пункты для любой страницы (добавляются в spec, даже если чек-листа из анализа нет):
   - страница открывается из навигации по дословной подписи пункта меню и по прямому URL;
   - заголовок страницы и хлебные крошки/контекст (организация, область) соответствуют прототипу;
   - состояния: пусто, загрузка (скелетон), ошибка, «нет права» / «модуль не подключён» / «только чтение» (AccessGate), офлайн — каждое воспроизводится MSW-сценарием (`X-Test-Scenario`), `context.setOffline` или персонажем dev-входа и имеет дословный текст (демо-панели в реализации нет, PD-54);
   - клавиатура: Tab обходит все интерактивные элементы, Escape закрывает диалог/лист, фокус виден;
   - axe: нет нарушений уровня serious/critical (`@axe-core/playwright`);
   - раскладка на 390 px: нет горизонтальной прокрутки, нижняя навигация, цели нажатия ≥ 44 px; на 1440 px — боковая панель.
4. Отчёт Playwright (`playwright-report/`) прикладывается к отчёту агента; падения не «гасятся» ретраями.

## 2. Как запускать приложение для E2E

Режимы (план v2 §3.7):

- **`mock`** — с этапа 0. `pnpm e2e` (`E2E_MODE=mock`): приложение в e2e-сборке работает на MSW-сценарном сервере поверх сида прототипа. Playwright `webServer` стартует его сам на порту слота (`5200 + slot` у исполнителя, `6100 + полоса проверки` у проверяющего — порт задаёт шаблон Workflow, `orchestration.md` §4, `E2E_FRESH_SERVER=1`). Персонаж задаётся dev-входом `?persona=<id>`. Он есть только в e2e-сборке, демо-панель не переносится (PD-54, шаг 0.9 плана 27, R-08).
- **`stand`** — с этапа 1. `pnpm e2e:full` (`E2E_MODE=stand`): compose (PostgreSQL, MinIO, Mailpit), миграции, Go-сид, вход через dev-провайдер BFF. Общий стенд принадлежит интегратору. Исполнитель поднимает свой стенд только с `COMPOSE_PROJECT_NAME=ortus-s<slot>` и сдвигом портов, а API — на `HTTP_ADDR=127.0.0.1:(8100 + slot)`. OIDC и Keycloak проверяет отдельный smoke у интегратора (шаг 1.3).
- Один и тот же spec должен проходить в обоих режимах. Для страниц пилота `stand` обязателен при закрытии шага. Расхождение режимов — дефект MSW-хендлера или backend либо запись allowlist с решением.
- Экран, которого ещё нет на стенде (шаг будущего этапа), помечается `test.fixme(E2E_MODE === 'stand', 'этап N')` со ссылкой на шаг.

## 3. Визуальная сверка с эталоном

Цель — «точно так же, как нарисовано». Сверка выполняется Playwright-тестом `e2e/visual/<page-key>.visual.spec.ts`:

1. Открыть эталон — снимок этапа (`design-stage-N`) на `127.0.0.1:4173` — через фикстуру `reference(file)`: главный файл или модульный `.dc.html` страницы. На **эталоне** персонаж, ширина и флаги по-прежнему выставляются панелью «Демо-режим». Перейти на экран (`#` маршрута нет — через меню по дословной подписи или через `window.__dcSetProps`/`go()`, см. `01-shell.md`), скрыть панель демо-режима (`[aria-label="Панель демонстрации"]`) и сделать снимок области приложения.
2. Открыть **реализацию** на том же маршруте, с тем же персонажем и данными. Персонаж задаётся dev-входом `?persona=`, данные — MSW-сценарий на том же сиде. Сделать снимок той же области. Пиксельная сверка выполняется в режиме `mock`. В режиме `stand` достаточно структурной сверки (п. 4), её расхождения разбираются по §2.
3. Сравнить `expect(page).toHaveScreenshot()` с порогом `maxDiffPixelRatio: 0.01` на 390 и 1440 px. Шрифты (Golos Text, IBM Plex Mono, Material Symbols Rounded) должны быть загружены в обоих случаях — в CI используются локальные копии шрифтов.
4. Дополнительно к пикселям — структурная сверка: список текстов всех `button`, `a`, `h1–h3`, `label`, `[aria-label]` в эталоне и в реализации должен совпадать (порядок и дословность). Тест `e2e/visual/<page-key>.labels.spec.ts` извлекает обе выборки и сравнивает как массивы.
5. Допустимые отличия записываются в файл ключа `e2e/visual/allowlist/<key>.md`. В записи обязательны ID решения (`PD-NN`, `D-NN` или `Q-NN`) и причина, формат проверяет `allowlist-lint` (PD-50). Любое другое отличие — дефект. Виды записей:
   - `pixel` и `state` — как раньше (например, системный скроллбар; исправленная ошибка эталона — PD-27, PD-60);
   - `out-of-stage` — пункт меню, источник «Главной», кнопка или шаг «Пути проверки», который относится к будущему этапу. Нужен срок снятия `expires: stage-N`. После этого этапа запись ошибочна, и `allowlist-lint` её отклоняет;
   - `no-reference` — экрана нет в эталоне (вход OIDC, принятие приглашения, переключатель бизнеса, входящие, «Хранилище», импорт CSV, очередь S2-17 — B-6 плана v2). Пиксельной и структурной сверки нет; e2e и MCP-проходка обязательны. Нужна ссылка на решение и на задачу «дорисовать в прототипе».

Если эталонный экран требует состояния, которого нельзя добиться через демо-панель, агент документирует шаги в `docs/plan/analysis/*.md` («Как воспроизвести») и использует их в тесте. Если экран в снимке этапа отличается от анализа, правится анализ (DoR-сверщик), а не эталон.

## 4. Проверка через Playwright MCP

Это ручная проходка живого приложения агентом через MCP-сервер `@playwright/mcp` (конфигурация `.mcp.json`, см. `docs/plan/analysis/12-prior-project-and-skills.md` — наследуется из проекта 2.0: пиновая версия, свой браузер, `npm run mcp:install`). Делается после зелёных E2E, перед ревью.

Сценарий проходки для страницы (агент выполняет и прикладывает к отчёту снимки и выдержки accessibility-дерева):

1. `browser_navigate` на страницу; `browser_snapshot` — дерево доступности. Сверить с инвентарём элементов из анализа: все регионы (`aria-label`), заголовки, кнопки, пустые состояния присутствуют и подписаны дословно.
2. Пройти основной сценарий страницы кликами по ролям и подписям (не по координатам): каждое действие → ожидаемый тост/диалог/переход, тексты дословно.
3. Пройти негативные проверки из «Пути проверки» прототипа, относящиеся к странице и этапу (нет права, модуль не подключён, только чтение, конфликт, офлайн, сбой загрузки). В режиме `mock` — через персонажа dev-входа и MSW-сценарии (`X-Test-Scenario`), в режиме `stand` — через сид стенда и `X-Test-Scenario` при `APP_ENV=e2e` (PD-31). Шаги «Пути проверки» из будущих этапов не проходятся и отмечаются как `out-of-stage`.
4. Переключить размер окна `browser_resize` на 390×844 и 768×1024, повторить п. 1 — проверить раскладку (нижняя навигация, карточки вместо таблиц, закреплённая панель главного действия).
5. `browser_console_messages` — нет ошибок и предупреждений React; `browser_network_requests` — нет запросов к неожиданным хостам; в режиме `stand` — все ответы в рамках OpenAPI.
6. Сделать `browser_take_screenshot` на трёх ширинах и положить в `docs/plan/evidence/<page-key>/` (в режиме `stand` — в `…/stand/`), эталонный снимок с 4173 — рядом. MCP-сервер у каждого агента свой: `--isolated --output-dir .playwright-mcp/<порт>`.
7. Записать результат в отчёт WS в разделе «Проверка MCP»: что пройдено, где расхождение с эталоном, что исправлено.

Если MCP-сервер недоступен (нет браузера, не поднят `.mcp.json`), WS **не** закрывается; агент сообщает об этом интегратору как о блокере, а не подменяет проверку.

## 5. Ревью кода

- Запрос ревью по скилу `requesting-code-review`: в описании — ссылки на чек-лист приёмки, отчёт E2E, снимки MCP, список коммитов.
- Ревьюер проверяет по чек-листу: тесты написаны до кода (порядок коммитов `test:` → `feat:`), дословность подписей, отсутствие запрещённых данных в логах (`14-engineering.md`), соответствие скилам Go/React, отсутствие прямых вызовов `api-client` из компонентов.
- Изменения в `authz`, миграциях, финансах и `permissions.yaml` требуют второго ревьюера (CODEOWNERS).

## 6. Автоматизация в репозитории

- `husky` pre-commit: `lint-staged` (prettier, eslint, gofmt). pre-push: `pnpm test` и e2e-smoke (`--grep @smoke`) для изменённых страниц.
- CI (`.github/workflows/ci.yml` или `.gitlab-ci.yml` — решение D-02): конвейер из `14-engineering.md`: lint → contract → unit → integration → isolation + concurrency → build → e2e (Playwright на эфемерном compose) → визуальная сверка. Артефакты: `playwright-report`, снимки, отчёт axe.
- Claude Code: хук `Stop` в `.claude/settings.json` запускает `node tools/verify-pages.js`, который по `git diff --name-only` находит затронутые `routes/**` и выводит напоминание со списком страниц, для которых нужно выполнить §1–§4, если в текущей ветке нет свежего отчёта в `docs/plan/evidence/<page-key>/`. Хук не заменяет проходку, а не даёт её пропустить.

## 7. Что считается расхождением с эталоном

Любое из: другой текст (включая регистр, «ё», знаки препинания), другая иконка, другой порядок элементов, иное состояние по умолчанию (выбранный таб, фильтр), другой цвет/радиус/отступ, другие точки перелома, отсутствие состояния (пусто, ошибка, нет права), отсутствие подтверждающего диалога, другой текст тоста. Дизайн-«улучшения» без решения в `decisions.md` не принимаются.
