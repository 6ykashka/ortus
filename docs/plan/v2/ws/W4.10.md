## 10. Риски и решения по умолчанию

| # | Вопрос | По умолчанию |
|---|---|---|
| 1 | TP-03 «закрытый значит закрытый»: владелец бизнеса в эталоне видит закрытый проект через системную роль | Закрытый проект доступен только по роли в самом проекте, владельцу тоже; владелец видит его через «Проверить доступ» и аудит, при нужде назначает себя наблюдателем (TP-03). Расхождение с эталоном — в тесте паритета |
| 2 | Старые команды (`moveTask`, `toggleTaskCheck`, `commentTask`, `createTask`) проверяли `can(tasks, verb)` без объекта | Сначала право модуля где-либо (`canAny` — `assertCan` эталона без области), до поиска задачи: ответ не выдаёт существование задачи. Затем объект: в проекте с процессом — доступ проекта `projCan` (TP-03, PD-60: закрытый — только по роли в проекте, унаследованный доступ в ограниченном — только чтение; чек-лист и `moveTask` — «Менять статус», комментарий — «Читать», `createTask` — «Создавать»); в воронке «Заявки» без процесса — по PD-53 `can` с объектом-проектом и подразделением проекта (возврат 1) |
| 3 | `createProject` проверяет `can(tasks, settings)` без объекта | По PD-53: роль проекта не даёт создавать проекты (Котова — нет) |
| 4 | Проекция `projects` в эталоне (`projVisible`) показывает закрытый проект унаследовавшим роль, хотя `projAccess` даёт им `null` | Видимость проекта = `projAccess ≠ null` (PD-60) |
| 5 | `checkFiles`/`checkParent`/`autoFire` в эталоне — замыкания адаптера | Чистые функции с явными `db`, актором, часами и `emit` |
| 6 | Время в комментариях и журнале — `new Date()` эталона | Часы домена `Clock` (Europe/Moscow) |
| 7 | Проект «на всю организацию» в эталоне — `unit: null` | `unit` отсутствует (тип ядра `ProjectRef.unit?: string`) |
