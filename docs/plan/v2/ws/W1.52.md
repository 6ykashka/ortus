## 1. Цель

Сейчас `inviteMember` (W1.06) создаёт карточку `people.person_profiles` без `membership_id` и приглашение в control DB; членство появляется только при принятии (`invitations.Accept`). DTO `Member` строится по членству, и карточку приглашённого `listMembers`/`getMember` отдают как `active` без `userId` — как карточку без аккаунта. На стенде: строки «Приглашён» нет, клиент считает «9 из 10», а сервер на следующем приглашении отвечает 409 «Свободных мест нет» (`freeSeats` считает действующее приглашение местом). В mock (MSW W0.13) и в Go-сиде (Петрова, Ильин — членство `invited`) приглашённый — `invited`.

1. **`Member.status` из приглашения.** `listMembers` и `getMember` (модуль `people`, всё, что строит `Member` из `people.person_profiles`) отдают `status: invited` для карточки с **действующим** приглашением — не принятым, не отозванным, не истёкшим (`expires_at > now()` control DB, тот же предикат, что у `freeSeats` и `checkProfile`).
2. **Порядок правил статуса:**
   - членство `active` → `active`, `suspended` → `suspended` (как раньше, приглашение не влияет: `Issue` не выдаёт приглашение профилю с живым членством);
   - членство `invited` (сид) → `invited`;
   - нет членства или членство `ended` и есть действующее приглашение → `invited`;
   - членство `ended` без приглашения → `suspended` (как раньше);
   - нет членства и нет действующего приглашения (карточка без аккаунта, отозванное или истёкшее приглашение) → `active` без `userId` — карточка без аккаунта (Q-W1.00-5).
3. **После принятия** — `active` с `userId` аккаунта (членство `active`, приглашение `accepted_at`).
4. **`userId`** — только из членства: до принятия аккаунта у приглашения нет (в MSW есть — расхождение, §10 п. 3).
5. **Места согласованы:** сервер считает местом членства `active`+`invited` и действующие приглашения без членства `invited` того же профиля (`freeSeats`, `tenant_seat_usage`). После W1.52 каждый такой человек виден в `listMembers` как `invited` или `active` с `userId`; карточка без аккаунта (`active` без `userId`) и `suspended` места не занимают — то же правило, что `seatsUsed` MSW, кроме `userId` у приглашённого (§10 п. 3).
6. **Видимость не меняется:** приглашения читаются только для людей, уже отобранных областью `members.read` (scopeddb), одним запросом на страницу.

## 4. Контракты

Контракт API не меняется (`Member.status` — прежний enum). Внутренние интерфейсы:

```go
package invitations
// Reader — control DB (pool или транзакция) для чтения.
type Reader interface {
	Query(ctx context.Context, sql string, args ...any) (pgx.Rows, error)
}
// Pending — действующие приглашения профилей бизнеса: профиль → срок приглашения (последнего, если их несколько).
func Pending(ctx context.Context, db Reader, tenantID uuid.UUID, persons []uuid.UUID) (map[uuid.UUID]time.Time, error)
```

```go
package people
// Invitations читает действующие приглашения людей в control DB (W1.52).
type Invitations interface {
	Pending(ctx context.Context, tenantID uuid.UUID, persons []uuid.UUID) (map[uuid.UUID]time.Time, error)
}
// ControlInvitations — Invitations над control DB (invitations.Pending).
type ControlInvitations struct{ DB invitations.Reader }
type Server struct { /* … */ Invitations Invitations // nil: control DB kit.ControlDirectory, иначе нет приглашений }
```
