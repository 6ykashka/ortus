# Ортус CRM — прототип (итерации 1–5)

**Старт разработки:** комплект v0.2 в `docs/` (модель данных и SQL, каталог прав, ошибки и события, бэклог S0–S2, инженерный регламент, качество и безопасность, решения и глоссарий) и справочник `Дизайн-система.dc.html`. Начните с `docs/README.md`, план по шагам — `docs/27-implementation-plan.md`. Все документы с навигацией и поиском: `Документация.dc.html`.

Интерактивный прототип: `Ортус CRM.dc.html`. Откройте файл в браузере. Сборка не нужна, но файл должен открываться с веб-сервера, а не через `file://`, иначе браузер не загрузит модули из `ortus/`. Подойдёт, например, `npx serve .`.

## Ключевые UX-решения

1. **Одно приложение и рабочие места по обязанностям.** Навигация собирается из вычисленных прав (`navFor`). Оператор платформы работает в отдельной оболочке с тёмной шапкой и не видит бизнес-данные клиентов.
2. **Контекст всегда виден.** В шапке показаны организация и область. Владелец сужает область через селектор «Все подразделения / регион / фирма». У остальных ролей область задана назначением.
3. **Три отдельных действия:** подключить модуль → разрешить его роли → выбрать область при назначении. Состояния «модуль не подключён», «нет права» и «нет доступа к объекту» показываются отдельно: на экране-заглушке и в «Проверке доступа».
4. **Мобильный приоритет у сотрудника.** Ширина меньше 640 px: нижняя навигация (3 пункта и «Ещё»), карточки вместо таблиц, кнопки высотой 48–54 px, закреплённая панель главного действия со списком недостающего.
5. **Локальное и серверное разделены.** У каждого фото, расхода и сдачи есть статус: «На устройстве · ждёт связи», «Загрузка N%», «Ошибка — повторить» или «Принято сервером». Бронь, выезд и приёмка без связи не выполняются.
6. **Значимые изменения подтверждаются диалогом с последствиями:** подключение и отключение модуля, уменьшение квоты ниже занятого места, окончание trial, приёмка смены, действия оператора.

Порядок экранов основного пути: Модули и место → Пользователи и роли → (водитель) Сегодня: машина → осмотр → рейс и расходы → сдача → (логист) Приёмка смен.

## Как проверить

В панели «Демо-режим» есть кнопка **«Путь проверки»**. Шаги в ней отмечаются автоматически, у каждого есть кнопка «Перейти». Там же перечислены негативные проверки. Флажки «Нет связи», «Конфликт брони» и «Сбой загрузки фото» включают соответствующие состояния. «Ширина» показывает раскладки 390, 768 и 1440 px.

## Структура

| Файл | Слой |
|---|---|
| `Ортус CRM.dc.html` | UI: оболочка, страницы, диалоги, view-model'и (`*VM`) |
| `ortus/models.js` | Доменные правила: права и области (`can`, `canEarnings`), совместимость машины (`compat`), загрузка по участкам (`legs`), валидация осмотра и расходов, справочники статусов |
| `ortus/mock-data.js` | Демо-данные: 3 региона × 4 фирмы, участники, роли, машины, рейсы, пул |
| `ortus/api.js` | Сервисный слой. `createMockAdapter()` — локальный «сервер»: задержки, 409, офлайн, ответы для конкретного участника без запрещённых полей. `createHttpAdapter()` — заготовка под Go API по `ortus-openapi-v0.1.yaml` |
| `ortus/roadmap.js` | Карта экранов следующих итераций |

UI работает только через методы адаптера. Чтобы подключить Go API, замените `createMockAdapter()` на `createHttpAdapter({ tenantId, getToken })` в `boot()`.

**Почему не React + TypeScript-проект.** Среда прототипирования собирает экраны в Design Component (React-класс и шаблон с инлайн-стилями) без шага сборки. Слои разделены так же, как в будущем TS-проекте, а JSDoc-типы в `models.js` переносятся в `types.ts` один к одному. Дизайн-токены записаны ниже и в среде применяются инлайн.

- Текст: основной `#1C2A26`, вторичный `#5C6964`.
- Акцент: `#1F6B52`, мягкий акцент `#E3EFE7`.

### Компоненты и состояния

- **Шапка**: организация, область, индикатор «Нет связи», уведомления (только адресованные участнику), профиль с назначениями.
- **Навигация**: боковая панель от 1080 px, иконочный рейл от 640 px, нижняя панель и лист «Ещё» на телефоне. Будущие модули помечены «план». У владельца отраслевая группа («Логистика», «Ремонт и стройка», «Салон и SPA») есть только у подключённого модуля; отключённый с историей — один пункт в группе «Отключены · только чтение» внизу меню (страница для чтения с баннером); не подключавшийся модуль в меню не показывается.
- **Баннеры**: окончание trial, отключённый модуль (только чтение), нет связи, отправка очереди, переполнено место.
- **AccessGate**: модуль не подключён / нет права.
- **Карточка модуля**: подключён / не подключён / отключён · только чтение, зависимости, сколько сотрудников имеют доступ через роли.
- **Редактор роли**: переключатель модуля и действия из манифеста; отдельный финансовый блок, заблокированный для функции «Водитель»; предпросмотр ключей прав; черновик, «Отменить», «Сохранить».
- **Назначение роли**: роль, область (организация / регион / фирма), срок, итог прав и предупреждение о конфликте.
- **Подбор машины**: проверки доступности, массы, объёма, длины и температуры; загрузка по участкам (объём и масса раздельно); оговорка, что это не 3D-укладка.
- **Слот фото**: пусто, загрузка с прогрессом, ошибка с кнопкой «Повторить», на устройстве, загружено. Камера через `capture`.
- **Форма расхода**: категория, сумма, дата, литры, комментарий, чек; ошибки валидации у полей.
- **Приёмка**: фото до и после, пробег, дефекты, расходы, начисление (только при праве), замечания, возврат по разделам.
- **Пустые состояния**: нет смен на проверке, нет подходящих машин, нет рейсов в области.
- **Загрузка**: скелетон.

## Итерация 2: Формы и опросы

Раздел «Формы и опросы» в навигации владельца и логиста — отдельный модуль `Формы и опросы.dc.html`, встроенный в CRM. Функциональность повторяет Яндекс Формы в оформлении Ортуса; что взяли и чего нет — `docs/20-forms.md` (D-25).

- **Список**: плитки «Создание формы» и «Все шаблоны» с поиском (15 шаблонов: основные, опросы CSAT/NPS/CES, сотрудники, тест с баллами, отраслевые — только при подключённом модуле); поиск, «Мои формы», статус, «По группам», «Создать группу», меню «…» у формы.
- **Конструктор**: «Содержание» слева, страницы (переименовать, переставить, перемешать вопросы, удалить с «Восстановить»), выбор вопроса — частые типы и «Показать все вопросы» (21 тип), карточка вопроса с пояснением, значением по умолчанию, вариантами, сортировкой, ограничениями, идентификатором и условиями «И / ИЛИ»; «…» → дублировать, скрыть, удалить. Черновик сохраняется автоматически.
- **Предпросмотр** на телефоне и компьютере, **Настройки** (доступ, область, сроки, лимит, тест с баллами, вид), **Действия после ответа** (задача, уведомление, письмо, HTTP-запрос, сохранение в Базу знаний — строкой в таблицу или записью на страницу, D-26), **Поделиться** (ссылка, код для сайта).
- **Публикация**: создаёт новую неизменяемую версию. Смена типа поля даёт новый ID поля, смена подписи ID сохраняет. Новое обязательное поле не требуется от старых ответов.
- **Версии**: структура каждой версии, отличия от предыдущей, удалённые поля.
- **Ответы**: показываются по структуре своей версии; различаются «Не показывался по условию» и «Не ответил». Журнал автоматизации: «ответ → задача менеджеру».
- **Связь с логистикой**: каждый отправленный осмотр водителя (выезд и сдача) создаёт ответ формы «Осмотр машины» по действующей версии и одну задачу менеджеру. Повтор дубль не создаёт.
- **Права**: логист видит форму только для чтения — у роли нет действия «Настраивать» (`forms.publish`).

## Итерация 3: Задачи

- Проект LOG · Логистика · Север: канбан (Новая → В работе → На проверке → Готово) и список, фильтр «Мои задачи».
- Карточка задачи: исполнитель, приоритет, срок, чек-лист, связанные объекты (ответ формы, рейс, машина, форма — переход в исходный раздел), история статусов и комментарии.
- Статус меняется только кнопками разрешённых переходов (`TASK_FLOW` в `models.js`); сервер отклоняет остальные. «Готово» недоступно, пока чек-лист не закрыт.
- Задачи из автоматизации «осмотр → задача» помечены «⚡ из ответа формы», критический дефект даёт приоритет «Срочно». У логиста в меню счётчик новых задач.
- Перетаскивание в канбане сознательно не сделано: кнопки переходов — основной способ (WCAG 2.2, 2.5.7).
- С итерации 9 этот вид остался только для воронки «Заявки»; проекты с процессом работают в новом модуле.

## Итерация 4: остальные модули раздела 5

Все модули из раздела 5 промта теперь работают в приложении, а не только на карте экранов:

- **Календарь ресурсов**: машины, сотрудники, помещения, оборудование; фильтр по типу; шкала дня 08–20 с подготовкой и уборкой. Перенос визита проверяет все ресурсы брони сразу; при конфликте сервер объясняет причину и предлагает свободные слоты. Рейсы и ТО переносятся только в исходном модуле, у каждой записи есть переход к источнику.
- **База знаний**: дерево пространств, поиск только по доступным страницам (приватная «Политика начислений» видна лишь владельцу), просмотр и редактирование с публикацией новой версии, история версий, конфликт при устаревшей базовой версии.
- **Данные**: наборы «Автомобили, Поездки, Расходы, Ответы на осмотр, Задачи» строятся из тех же записей и с теми же правами. Есть фильтр, сортировка, сохранённые виды и выгрузка (если у роли есть право выгрузки); строка открывает исходную карточку. Колонка «Начисление» есть только у тех, кому она разрешена.
- **Файлы**: фото осмотров, чеки и документы с привязкой к объекту и состояниями «готов / проверяется / отклонён»; открытие проверяет доступ к родительскому объекту.
- **Салон и SPA**: «Мой день» массажиста: визиты, кабинет, оборудование, буферы, технологическая карта в мл/г. Завершение списывает материалы один раз. Если материала не хватает, услуга фиксируется как выполненная, а учёт ждёт решения владельца.
- **Внутренняя касса**: счета и балансы, приход / расход / возврат с основанием, исправление сторно (без удаления). Принятые расходы смен приходят как предложения кассовых операций. Банка и фискализации нет.
- **Ремонт и стройка**: объект, плановые и фактические объёмы, бригада из учётных карточек без аккаунтов, отметка прораба с материалами и фото. Факт меняется только после приёмки владельцем. Модуль по умолчанию не подключён: подключите его в «Модули и место».

Роли из шаблонов получили чтение базы знаний; у массажиста есть право «Изменять» в календаре, у логиста — выгрузка данных.

## Главная (стартовая страница)

Владелец и логист после входа попадают на «Главную». На ней нет декоративных показателей — только то, с чем нужно работать сегодня.

1. **Приветствие и контекст**: дата, текущая область (организация, регион или фирма) и одна строка о том, сколько вопросов ждёт решения.
2. **Начало работы** (только у владельца, пока не пройдено): подключить модуль → назначить роли с областью → пригласить сотрудников. Текущий шаг выделен, пройденные отмечены. Блок исчезает, когда все шаги выполнены.
3. **Требует решения** — единая очередь из всех модулей, отсортированная по срочности: сначала то, что блокирует работу.
   - критический дефект (выезд заблокирован);
   - смена на приёмке (машина не вернётся в пул);
   - рейс без водителя (или ожидание ответа из пула);
   - незавершённый учёт материалов в SPA;
   - отметка прораба на приёмке (с названием объекта, кнопка открывает этот объект);
   - объект без прораба (кнопка «Назначить»);
   - допработа прораба ждёт оценки (кнопка открывает смету объекта); смета объекта-черновика не собрана;
   - окончание пробного периода и заполненность места;
   - сотрудники без роли;
   - свои новые задачи и задачи на проверке.

   Карточка дублирует статус иконкой и подписью, а не только цветом. Кнопка ведёт прямо к нужной записи. Пустое состояние — «Решений не требуется».
4. **Сегодня в работе**: по одной карточке на каждый подключённый модуль (логистика, SPA, ремонт, задачи) с короткими счётчиками и переходом в раздел. Неподключённые модули показаны пунктиром с кнопкой «Подключить» (только у владельца).
5. **Сбоку**: рейсы на сегодня со статусами и последние события, адресованные этому пользователю.

Всё строится по правам: логист видит только свою область, без начислений, подписки и вопросов других модулей. Водитель, массажист и прораб стартуют со своего рабочего места («Сегодня», «Мой день», «Объекты») — для них главное действие важнее обзора.

## Итерация 5: платформа, места и тарифы

Модель описана в `docs/17-users-and-billing.md`, SQL — `docs/db/control_0001_init.sql` и `control_0002_billing.sql`.

**Оператор платформы:**
- **Организации:** в карточке видны тариф, оплата, полоса «места с входом» и открытая заявка.
- **Использование:** сводка, сигналы «Требуют внимания» (места, хранилище, пробный период, неактивность), отраслевые модули, таблица по организациям с сортировкой. Только метаданные.
- **Заявки на тариф:** подтверждение меняет лимит мест сразу; отказ только с причиной.
- **Пользователи:** слева организации, как realm в Keycloak. Первой стоит системная «Ортус · Платформа», затем организации клиентов. Внутри организации видны её участники, при наведении на человека — все его организации. В «Ортус · Платформа» — операторы с ролями владелец / администратор / биллинг / поддержка, приглашение и отключение.
- **Тарифная сетка:** ступени по числу мест и сроки 1 / 4 / 8 / 12 мес со скидкой. В черновике новой версии тарифы задаются полностью: название, лимит, цена, добавление и удаление. Версия с будущей датой «запланирована» и отменяется до начала.

**Владелец:**
- **Подписка и места:** занято из лимита, выбор тарифа и срока с расчётом, заявка оператору; списки «Занимают место» и «Не занимают место».
- **Приглашение:** показывает свободные места; при нехватке приглашение закрыто, есть переход к подписке.

Как проверить: у владельца пригласите сотрудника (мест станет 10 из 10, следующее приглашение закроется) → «Подписка и места» → заявка → переключитесь на оператора → «Заявки на тариф» → подтвердить.

## Итерация 6: оформление организации

Владелец → «Компания» → «Оформление» (модель — `docs/18-branding.md`, SQL — `docs/db/control_0003_branding.sql`):
- название и короткое имя (заменяет «ортус» в шапке), логотип и знак;
- акцентный цвет: палитра из 8 или свой HEX; при контрасте ниже 4.5:1 цвет затемняется автоматически; статусы не меняются;
- термины в четырёх формах (смена, машина, рейс, визит, объект), иконки, порядок и скрытие пунктов меню;
- «Работает на Ортус» в формах и письмах;
- предпросмотр: приложение, публичная форма, письмо-приглашение.

После сохранения цвет, логотип и меню применяются ко всему интерфейсу. У оператора видны знаки организаций в фирменных цветах.

**Вторая организация для проверки изоляции.** В списке «Персонаж» три группы: «Платформа», «Альта Групп», SPA «Лотос». У «Лотоса» своя база в mock-адаптере: 23 сотрудника, салоны «Тверская» и «Арбат», роль «Администратор салона», свои задачи и касса, сливовое оформление. Анна Морозова — один аккаунт в обеих организациях. Сценарий проверки — `docs/18-branding.md`, раздел «Проверка изоляции оформления».

## Итерация 7: Ремонт и стройка → Объекты

В меню появилась группа «Ремонт и стройка», устроенная как «Логистика». Первый пункт — «Объекты». Варианты карточки и разбор аналогов: `Объекты - варианты.dc.html`, в работу взят вариант 1a «Сводка».

- **Список объектов**: «Объекты» в меню открывают список. У владельца на широком экране — таблица: объект и адрес, этап и готовность, сдача (прогноз, если срок сдвигается), прораб, главный вопрос из «Требует решения». Фильтры «Активные / Требуют решения / Сданы» и поиск по адресу, заказчику и прорабу. Сначала идут объекты, где ждут решения, затем по дате сдачи. На узком экране и у прораба — карточки; у прораба на карточке кнопка «Отметить работу».
- **Прораб видит только свои объекты**: сервер отдаёт объекты, где он назначен. Если объект один, карточка открывается сразу. «Объекты» в хлебных крошках карточки возвращают к списку.
- **Объект без прораба** попадает в «Требует решения» и на «Главную» с кнопкой «Назначить»; после назначения объект появляется в списке прораба.
- **Счётчик у пункта «Объекты»** (у владельца): отметки на приёмке, активные объекты без прораба и допработы, которые ждут оценки, по всем объектам. Пока модуль не подключён, счётчика нет. Карточка «Ремонт и стройка» на «Главной»: объектов в работе, на приёмке, ближайшая сдача.
- В демо шесть объектов: пять после договора и один объект-черновик. Разделы «Замер», «Смета», «График» и остальные заполнены только у «ЖК Речной · квартира 42» (у черновика — «Замер» и «Смета»), у других объектов во вкладках — заглушка со ссылкой на этот пример. Обзор и работы у каждого объекта свои.
- **Смета** (детали — `docs/19-construction.md`, «Смета: кто правит, версии, допработы, шаблоны»). Правят владелец, сметчик, менеджер заявки и замерщик; скидка свободная. Вкладка показывает версии (действует / заменена / черновик), редактор черновика (строки из справочника, объёмы из замера или вручную, цены, разделы, скидка) и сравнение с предыдущей версией. До договора правка — новая версия, после — допсоглашение с подписью по SMS.
- **Объект-черновик** создаётся на этапе заявки «Замер», в списке — фильтр «До договора». Во вкладке «Смета» — выбор шаблона и «Собрать черновик сметы»: объёмы из замера, цены из справочника.
- **Допработы**: прораб предлагает их во вкладке «Работы» (описание, объём, фото, без цен). Офис оценивает в черновике сметы или отклоняет с причиной, заказчик подписывает допсоглашение, после подписи работа попадает прорабу в объёмы. В демо у кв. 42 ждёт оценки ДР-1 «Перенос розеток на кухне».
- **Снабжение** — пункт группы «Ремонт и стройка» со счётчиком заявок. Вкладки: «Заявки» (все объекты; «Выдать со склада» или отметить и «Собрать закупку» на несколько объектов), «Закупки», «Остатки» (два склада и излишки на объектах: вернуть на склад или переместить), «Движения». Основа — общий модуль «Склад», цена закупки идёт в расходы объекта (детали — `docs/19-construction.md`).
- **Шаблоны и расценки** — пункт группы «Ремонт и стройка». Шаблон объекта: разделы и работы сметы, формулы объёмов из замера, технология графика, комплект документов, чек-лист приёмки, материалы для снабжения. Стартовые шаблоны Ортуса копируются в организацию, свои — «Сохранить объект как шаблон» или «Сделать копию». Справочник расценок: правка цен и новые позиции.

- **Шапка объекта**: этап, срок сдачи, число отметок на приёмке, адрес и договор. Готовность по объёмам считается так: принято + на приёмке. Для заказчика готовность по-прежнему считается по закрытым актам.
- **Вкладки**: Обзор, Работы, Замер, Смета, График, Документы, Снабжение, Финансы, Оплата бригады, Подрядчики, Кабинет заказчика. Прораб не видит вкладки с ценами и деньгами.
- **Обзор**: «Требует решения» (у прораба — «Мои вопросы по объекту»), объёмы работ, фотоотчёт, «Как попасть на объект», люди, деньги (только с правом финансов) и лента.
- Кнопка «Принять объём» в обзоре делает то же, что на «Главной». Отметка прораба отправляется на вкладке «Работы».
- Разделы из `Ремонт и стройка.dc.html` встроены во вкладки. Модуль передаёт в обзор заявки на материалы, документы на подписи и сводку денег (`onStatus`).

- **Защита процесса**: для проектов с процессом старая смена статуса (`moveTask`) отклоняется — согласование не обойти.
- **Как проверить** (владелец): «Задачи» → LOG → T-65 «Заменить шины» → «Согласовать»; T-66 «Подготовить парк к зиме» не завершится, пока не готовы T-65 и T-58; «Участники» → «Проверить доступ» для Ильи Васильева.

Решения из разбора:

- Направление заводит владелец («Массаж», «Отделка»). Это сервисный проект модуля «Задачи»: ключ, область, команда, страница для клиентов, типы обращений и сроки.
- Клиент не заводит аккаунт и не занимает место. Каналы: личная ссылка или QR, SMS или мессенджер после работы, кабинет заказчика, виджет, бот; звонок заводит сотрудник.
- Очередь со сроками первого ответа и решения в рабочем времени направления. Пауза только на «Ждёт клиента», эскалация, у претензий — срок по закону без пауз.
- Оценка после услуги: 1–3 с просьбой связаться становится жалобой. После решения клиент оценивает решение. Сотрудник не видит жалобу на себя до разбора.
- Отчёт по направлениям: сроки, оценки с числом ответов, причины низких оценок; оценки сотрудников — по отдельному праву.

## Допущения

- Пул водителей и одобрение фирмой-владельцем имитируются кнопками «Демо: одобрить / отклонить».
- При уменьшении квоты ниже занятого места фото уже начатых смен загружаются в пределах временного резерва. Размер резерва не определён.
- «Критический дефект → менеджер разрешает выезд или подтверждает неисправность» — предложенный сценарий; в OpenAPI для него нет эндпоинта (помечен `PROPOSED`).
- Оператор продлевает trial на 14 дней. Цены тарифов — пример для макета, налоги и онлайн-оплата не рассчитываются.
- «Сегодня» в демо — 1 октября 2026; активность на экране «Использование» считается от этой даты.
- Роли операторов в макете не ограничивают действия на экранах платформы: демо-оператор — владелец.
- Отключение модуля по умолчанию переводит его в режим чтения истории; группа модуля уходит из меню владельца, остаётся пункт в «Отключены · только чтение». В «Альте» по умолчанию подключён только SPA — «Ремонт и стройка» появится в меню после подключения в «Модули и место».
- Фото и чеки хранятся только в браузере (object URL) и никуда не отправляются.

## Расхождения с документами

- В HTML-ориентире роль «Менеджер» имела начисления по умолчанию. Здесь они вынесены в отдельный финансовый блок шаблона и действуют только в области назначения (AUTH-03).
- В ориентире меню владельца называлось «Хранилище данных». По 07-ux-and-data §3 разделы разведены: «Данные» и «Файлы».
- В ТЗ нет отдельного «Ресурсного пула» как экрана; он оформлен по AUTH-06/07 и 07 §5.

## Ограничения прототипа

- Состояние живёт в памяти страницы; после перезагрузки оно сбрасывается (кнопка «Сбросить» делает то же).
- Права и изоляция tenant'ов имитируются mock-адаптером. В промышленной версии их обеспечивает сервер.
- Реальных платежей, рассылок, навигатора и фискализации нет; соответствующие кнопки отключены и подписаны.
- Экспорт в один HTML-файл не приложен: модули `ortus/*.js` загружаются динамически. Отдельную сборку можно сделать по запросу.

## Следующая очередь

1. Перенести слои в репозиторий React + TS: `types.ts` из JSDoc, адаптер `http` с клиентом, сгенерированным по OpenAPI.
2. Формы: шаблоны, публичные ссылки, предпросмотр на телефоне, проверка ответов с возвратом.
3. Календарь: вид недели, повторения, перенос перетаскиванием как дополнение к кнопкам.
4. Данные: графики и сводки, общие виды, серверная выгрузка с журналом.
5. Склад как отдельный раздел (приход, перемещение, резерв) для SPA и ремонта.
6. Матрица устройств для камеры, офлайн-очереди и PWA.
