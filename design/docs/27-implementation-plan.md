# 27. План реализации по шагам — версия 0.1

Предложение от 14 октября 2026 года: как перейти от прототипа и комплекта v0.2 к работающему продукту. Основа — бэклог `13-backlog-s0-s2.md`, регламент `14-engineering.md`, качество `15-quality-security.md`, решения `16-raid-glossary.md` и последовательность выпуска P0–P2 (`08-domain-scenarios.md`, §11). Этапы 0–3 расписаны по историям, этапы 4–8 — по модулям: их истории пишутся до конца этапа 2.

## Исходное состояние

- **Прототип** — 17 итераций: `Ортус CRM.dc.html` и восемь встроенных модулей (Формы, Задачи, Обращения, База знаний, Документы, Чаты, Касса, Ремонт и стройка); правила и демо-данные — `ortus/*.js`. Это UX-референс и источник доменных функций, а не код продукта.
- **Комплект v0.2**: модель данных и SQL (control 0001–0003, tenant 0001–0002), каталог прав, ошибки и события, бэклог S0–S2, регламент, тесты и модель угроз, решения D-01…D-28, токены и контракт компонентов.
- **Контракт** OpenAPI 0.1: 118 операций. Что в нём не покрыто — `03-api-guide.md`, «Что требуется допроектировать».
- **Ещё нет**: репозитория, CI, стенда, ответов на D-01…D-12, бэклога после S2, календарной оценки.

«Следующая очередь» из README прототипа разложена по шагам 0.9, 2.10, S2-19, 4.2, 4.4, 4.5 и 5.1.

## Правила последовательности

1. Сначала один вертикальный пилот — логистика. SPA и ремонт проверяют универсальность ядра после него (R-05).
2. Шаг начинается с PR в контракт: OpenAPI, `permissions.yaml`, миграция. Затем моки из примеров, потом backend и frontend параллельно.
3. Изоляция раньше бизнес-логики: каждый эндпоинт добавляет строки в матрицу изоляции, набор блокирует merge.
4. Горизонтальный модуль строится тогда, когда он нужен вертикали.
5. Дизайн опережает разработку на этап: перед стартом этапа его экраны в прототипе сверяются с историями (DoR).
