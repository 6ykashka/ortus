До решения агенты работают по рекомендации (план v2 §2, B-2). Решение нужно **до этапа 3**; план 27, шаг 0.1, требует его до этапа 1 — агенты этапа 1 его не ждут, но провайдер влияет на W1.02 (provisioner) и W3.02 (восстановление).

## Контекст

- `15-quality-security.md`, «Персональные данные», п.2: требование 152-ФЗ о локализации баз данных с ПДн граждан РФ на территории РФ → выбор размещения. Ортус обрабатывает ФИО, телефоны, email, фото машин (люди и номера), рейсы, позже — клиентов SPA. R-07 — неясный правовой статус ПДн.
- Архитектура — отдельная БД на тенанта (R-02): provisioner создаёт БД (`CREATE DATABASE`, роль `provisioner`, `14-engineering.md:81`), controller гонит миграции партиями, восстановление одного тенанта с файлами (AC-15, шаг 3.2).
- `10-data-model.md:7`: нужно расширение `btree_gist` — у managed PostgreSQL проверить.
- Файлы: S3-совместимое хранилище, presigned PUT, сканирование, квоты (S1-20…S1-22); локально — MinIO.
- Секреты — во внешнем хранилище (`14-engineering.md:81`), ротация и MFA — шаг 3.3.

## Варианты

1. **Российское облако с managed PostgreSQL, S3 и хранилищем секретов (KMS / Secret Manager провайдера)** — плюсы: локализация ПДн, бэкапы и PITR от провайдера, меньше эксплуатации; минусы: ограничения managed PostgreSQL (число БД в кластере, `CREATE DATABASE` для роли приложения, расширения), зависимость от провайдера. Цена: подписка; проверка ограничений до W1.02.
2. **Свой ЦОД или colocation в РФ: PostgreSQL на ВМ (Patroni), MinIO, Vault** — плюсы: полный контроль над БД на тенанта и расширениями; минусы: эксплуатация кластера, бэкапов, обновлений на команде (R-02). Цена: SRE-время и железо.
3. **Зарубежное облако** — нарушает требование локализации (15, п.2). Не рассматривается для ПДн.

## Решение

Рекомендация: «Российское облако с managed PostgreSQL и S3 (локализация ПДн)» (вариант 1). Чтобы решить, от решающих нужно:

- провайдер и регион; где лежат бэкапы;
- подтверждение провайдера: PostgreSQL 17 или 16.4+ с `btree_gist`; создание БД ролью `provisioner` и предел числа БД; PITR; S3 с presigned PUT, шифрованием на стороне сервера и lifecycle; хранилище секретов;
- заключение юриста по ролям сторон и поручению на обработку (15, п.1, п.3; шаг 3.4).

## Последствия

- Проще: бэкапы, шифрование хранилища, TLS — средствами провайдера; restore drill (3.2) опирается на PITR.
- Сложнее: если провайдер не даёт `CREATE DATABASE` роли приложения — provisioner работает через API провайдера (W1.02 закладывает интерфейс сразу); квоты числа БД ограничивают число тенантов на кластер.
- Сделать: W1.02 — provisioner за интерфейсом (локально — `CREATE DATABASE`, в облаке — API провайдера); W3.00 — план окружения prod-pilot; D-31 (SMS) выбирается вместе с D-05.
- Как проверим: восстановление одного тенанта с файлами на окружении провайдера (AC-15) с измеренными RPO и RTO.
